# OURO 架构底层重构设计

> 文档性质：历史设计与验收记录。当前结构以
> [`docs/OURO_AGENT_开发架构.md`](OURO_AGENT_开发架构.md) 和 [`dev/specs`](../dev/specs/README.md) 为准。
> 状态：已实现并完成验收（2026-08-01）
> 日期：2026-07-31
> 实施计划：[`dev/plans/architecture-foundation-refactor.md`](../dev/plans/architecture-foundation-refactor.md)

## 1. 目标

本轮重构不增加新的产品能力。目标是让 OURO 已有能力建立在可执行的不变量上，使后续 TUI、Desktop、
长会话、插件和高级 Agent 编排能够沿稳定边界演进，而不是继续扩大中央编排器或增加兼容分支。

完成标准不是文件变短或测试继续通过，而是同时满足：

- 持久化版本在读取边界被严格执行，兼容只能通过显式迁移发生；
- Session-scoped 状态具有唯一所有者，branch、export、trash 的语义完整一致；
- Catalog 和子进程输出的成本有明确上界；
- Run/Session 状态转移只有一套可复用不变量，各 application 用例不再重复投影规则；
- 依赖方向由完整规则保护，共享基础设施不归属于任一业务 adapter；
- 插件扩展面由真实消费者证明，遗留兼容具有删除边界；
- Runtime 与 ToolCall 按事务和变化轴收敛，不增加空 façade、通用 manager 或回调层。

## 2. 当前问题的共同根因

审查发现的问题不是互不相关的小缺陷，而是四个底层缺口的不同表现。

### 2.1 声明存在，但没有成为不变量

核心持久记录声明 `schema_version`，但读取边界不要求字段存在，也不拒绝未知版本。`RunLifecycle` 被描述为
状态转换中心，但 Agent、恢复、continuation 和 session control 仍能各自拼装 Run/Session 投影。

根因是系统把“字段/类/文档存在”当作边界成立，没有让所有入口经过同一个可执行规则。

### 2.2 聚合所有权只覆盖了首批内置能力

Session 聚合覆盖消息、Run、事件、压缩、Delegation 和资源引用；Goal、Plan、Todo 后来使用插件私有目录保存
session-scoped 状态，却没有进入 branch、export、trash 生命周期。与此同时，插件 Context Provider 又可把状态
派生指令持久化为 canonical synthetic message，导致状态与消息可以被分别复制或删除。

根因不是缺少某个清理 hook，而是没有先定义“session-scoped 扩展状态是否属于 Session 聚合”。

### 2.3 有界公共接口背后仍执行全量工作

Session Catalog 对 Host 暴露有界 DTO，但构建 `search_text` 时拼接完整对话，本地和 SQLite 后端又通过完整
RuntimeSessionSnapshot 重建索引。Shell 对外声明输出上限，但 `communicate()` 已先将完整输出读入内存。

根因是上界只存在于最终投影，没有下沉到数据产生和读取边界。

### 2.4 抽象分布与变化轴不一致

RuntimeService、ToolCallCoordinator 承担越来越多流程；InnerAgentLoop 周围则增加大量单方法 Protocol。
插件的每一种 contribution 又默认复制 preparation、projection、SDK、worker、contract 层。抽象数量增加，
但中央认知负担和修改冲突没有下降。

根因是按调用点或类型数量抽象，而不是按独立事务、不变量和资源生命周期抽象。

## 3. 目标不变量

### 3.1 持久化版本边界

1. 每个独立持久化根记录必须显式携带版本；缺失、非整数、未知版本都在 adapter 解码边界失败。
2. 领域模型使用封闭版本类型，不能构造出带未知版本的当前记录。
3. Store 不猜测旧字段，不使用默认值把未知旧格式解释成当前格式。
4. 需要保留的旧版本必须通过独立 migrator 转换；迁移具有来源版本、目标版本、失败诊断和测试。
5. data layout、SQLite schema、插件 manifest/state 和核心记录遵循同一原则，但版本号可以独立演进。

最小目标结构：

```text
bytes / database payload
  -> versioned persistence decoder
  -> current typed record
  -> application / core
```

版本 decoder 是基础设施入口，不成为序列化框架，也不负责业务迁移编排。

### 3.2 Session-scoped 扩展状态所有权

采用以下唯一语义：

- 只要状态以 `session_id` 为 identity，并影响该 Session 后续模型行为，它就是 Session-owned extension state；
- plugin generation 拥有代码与执行资源，但不拥有 Session 状态的生命周期；
- Host 负责登记状态的稳定 `owner_id`、schema、branch policy、export representation 和 trash 行为；
- private 表示不进入普通消息/公开 DTO，不表示可以脱离 Session 生命周期；
- 持久化 synthetic context 是状态派生投影，不是状态本体；branch 不能只复制投影而不处理来源状态。

首版只服务已存在的 Goal、Plan、Todo，不设计任意插件数据库或通用远程 KV。需要的最小能力是：

- 枚举一个 Session 已登记的扩展状态；
- 在 branch 事务准备阶段按明确 policy 复制、重建或排除状态及其派生消息；
- 在 export 中生成类型化、版本化的私有扩展 section；
- 在 trash tree 发布时把扩展状态纳入同一可恢复封存边界。

不允许通过 `session_trashed` Observer 做事后清理，因为 Observer 是 fail-open 通知，不能承担 canonical 生命周期。

### 3.3 有界 Catalog

Session Catalog 只保存和查询有界投影：

- Session identity、lineage、title、状态、时间；
- workspace/model/tags 等筛选字段；
- canonical 计数；
- 有界的最后消息预览。

Catalog 不保存完整 transcript。全文搜索是独立、可重建、可关闭的索引能力；在真实需求和基准出现前，
搜索只覆盖有界 Catalog 字段。一次 Run 完成更新 Catalog 的 I/O 与内存成本不得随全部历史线性增长。

### 3.4 有界进程输出

Shell stdout/stderr 在 pipe 消费时实施上限。执行原语必须同时满足：

- 持续排空两个 pipe，避免子进程因反压死锁；
- 内存累计有硬上限，并分别报告截断；
- timeout/abort 终止完整进程树；
- 终止后有界等待 EOF，不因继承 pipe 的后代无限挂起；
- PowerShell CLIXML 解码不能重新制造无界副本。

输出截断属于进程执行边界，不由某个 builtin tool 在返回前补做。

### 3.5 Run/Session 状态转移内核

Run 状态是事实源，Session 的 active/status/last-run 字段是受约束投影。目标内核只负责纯规则：

- 校验允许的来源状态与目标状态；
- 生成新的 RunRecord；
- 从 Run 转移生成对应 SessionRecord 投影；
- 表达需要原子提交的记录集合。

application 用例继续负责锁、Store transaction、消息、事件、外部调用和资源释放。不同用例可以启动、恢复、
暂停、终止或排队 Run，但不能自行重复 `status + active_run_id + last_run_id` 规则。

该内核不是 Unit of Work、workflow engine 或第二套状态机。

### 3.6 编排收敛原则

Runtime/ToolCall 只按以下真实边界拆分：

- Run command：新建/恢复输入到 active Run；
- Run execution：持有 lock、abort、Run-local extension lease 并驱动 inner loop；
- interaction resume：审批、AskUser、child wait 的同 Run 恢复；
- terminal settlement：状态、continuation、Agent result 和 follow-up；
- Tool batch preflight、interaction、execution、commit 四个 durable phase。

Inner loop 依赖应收敛为少量内聚 collaborator，而不是继续增加单方法 callback。迁移以 characterization tests
保护行为，每一步删除旧入口后再进行下一步，禁止长期双轨。

### 3.7 依赖与扩展面治理

- 架构测试声明 package allowed-edge matrix，并递归检查全部 Python 模块；
- local atomic I/O、跨进程 mutation lock 属于共享 infrastructure，resources/config/billing/sessions 只依赖共享层；
- 新 contribution kind 必须有真实 builtin 或最小可运行 user plugin 证明；
- 没有消费者的 capability 不继续增加适配层，稳定性等级在 SDK 文档中显式说明；
- 内部 legacy 路径必须有迁移或删除里程碑；外部协议兼容与内部数据兼容分别治理。

## 4. 目标依赖关系

```text
hosts
  -> application use cases
       -> core transition rules and records
       -> ports
            <- file / SQLite / process / provider adapters

local_application
  -> composes runtime, plugins, MCP and session extension state owners

shared local infrastructure
  <- sessions
  <- resources
  <- config
  <- billing
```

插件只能通过 Host contract 注册 session extension state owner；它不能取得 SessionStore，也不能自行加入 Session
事务。LocalApplication 负责组合 owner，SessionService 只依赖最小生命周期端口。

## 5. 实施顺序

### 阶段 A：版本边界

先让未知/缺失版本可靠失败，再删除由默认字段掩盖的内部兼容。该阶段不改变当前版本号，也不自动迁移用户数据。

### 阶段 B：Session 扩展状态

先建立所有权与 contract tests，再迁移 Goal、Plan、Todo。最后修正 branch/export/trash 和 synthetic projection。
禁止先在三个插件里分别增加清理代码。

### 阶段 C：资源上界

Shell 有界读取与 Catalog 有界投影可以独立实施。前者先保证内存安全；后者先移除 transcript duplication，
再建立长历史基准。

### 阶段 D：状态内核与编排收敛

先列举所有直接 Run/Session 写入并建立 transition contract tests，再迁移 Agent、continuation、recovery、
session control 和 Runtime。迁移完成前不按文件长度拆 Runtime。

实施结果：Run status 已收敛到不含 Store/锁/事件的纯 transition plan；Session 只由 Run kind/status 投影。
terminal 不可复活、active/terminal 的 `ended_at` 约束、新 Run 初态和 compaction failure 的 idle 语义均由
contract tests 固化。应用层继续显式拥有事务与事件，没有引入通用 UoW 或 workflow engine。

编排收敛结果：Runtime 的进程内 lock/signal 所有权已移入单一 `RunExecutionOwnership`；InnerLoop 的微型 Protocol
按 context/run/turn 三个变化轴收敛；Tool batch suspension 成为纯规则并贯通 planning/checkpoint/completion/resume。
每个 Run 复用一个 ToolCallCoordinator，完整 Host 扩展通过一次性绑定代替三个分步 attach。interaction resume 与
terminal transaction 仍留在 RuntimeService，因为它们真实跨越 Store、模型循环、工具和 queued input；继续拆分只会
产生多回调转发 façade。

### 阶段 E：边界与清理

共享 local infrastructure、完整依赖矩阵、插件 capability 稳定性和 legacy 删除在前述不变量稳定后收口。

实施结果：共享原子 I/O/文件锁不再归属 Session adapter，完整 package allow-edge matrix 递归覆盖 `ouro/**`。
13 类插件 capability 均核对到真实 Host 语义消费者并冻结清单；没有 consumer 的新扩展不得复制 adapter 链。
内部 question alias、完整 tool-call event、旧工具 contract 与无效 Toolkit 参数已删除，非流式 Provider 也统一投影
delta。唯一保留的历史 ContextSnapshot schema-1 digest 分支明确随 schema 2 迁移删除；外部 MCP SSE 继续隔离在
transport adapter。UsageLedger 的公开对象与 append-only cache 已无可变别名。CI 新增约三秒的 architecture/core
先行门禁，三平台 full suite 继续作为最终证据。

### 阶段 F：完成审计

完成审计逐项核对了本设计的不变量与非目标。全量 1301 项通过、2 项按 Windows 平台能力跳过，branch coverage
为 83.89%；资源告警和不可回收析构告警已经升级为 pytest 失败。File/SQLite 共享同一 contract suite，当前
Windows 实跑与三平台 CI matrix 共同保护平台边界。Ruff、format、Mypy、compileall、distribution build 和 diff
检查均通过。审计未引入新产品能力或通用框架；发现的 stale Toolkit schema 与未闭合的 SSE/worker 资源所有权
已在根边界删除或修正。

## 6. 明确非目标

- 不引入 ORM、通用 UoW、事件溯源框架或 workflow engine；
- 不增加 plugin lifecycle hook 总线；
- 不为所有插件提供任意 KV/CAS；
- 不因为文件较长而创建转发 façade；
- 不在本轮增加 TUI、Desktop、Marketplace、OS sandbox 或跨进程调度；
- 不保留新旧内部 API 的长期兼容双轨。

## 7. 全局验收

每个阶段必须有针对自身不变量的测试；最终完成还需要：

```bash
uv run --frozen pytest
uv run --frozen pytest --cov=ouro --cov-report=term-missing
uv run --frozen ruff check ouro tests
uv run --frozen ruff format --check ouro tests
uv run --frozen mypy ouro
uv run --frozen python -m compileall -q ouro
uv build
git diff --check
```

另外必须通过：

- File/SQLite 同一持久化契约；
- 缺失和未知 record version 的失败测试；
- branch/export/trash 的扩展状态一致性测试；
- 大输出子进程内存上界测试；
- 长历史 Catalog 不加载完整 message/event history 的证据；
- 所有 Run/Session 状态转移入口清单审计；
- 完整 package dependency graph 测试；
- 权威规格、开发架构、路线图与代码一致性检查。

上述项目均已由实施计划 A8 的当前代码、测试与文档证据满足。
