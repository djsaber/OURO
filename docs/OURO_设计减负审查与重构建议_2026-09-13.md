# OURO 设计减负审查与重构建议

> 日期：2026-09-13\
> 审查基线：`a57b14a`；审查开始时工作区干净。\
> 文档性质：架构与实现评估、待实施建议，不是已完成的重构说明。\
> 本次交付仅修改文档，不修改源码、测试、配置、依赖或数据格式。

## 1. 核心判断

OURO 当前的主要负担不是“抽象太多”这一笼统问题，而是**同一操作的状态、解释权和生命周期分散在多处**：

- 同一事务重复读取已经取得的 Harness；worker 将同一返回值解析成对象后丢弃，再解析一次。
- 同一个 Run 的进程内资源分布在多个字典，清理依靠多处手动保持一致；部分框架执行信息又退回裸 metadata，产生反复解释和校验。
- 插件的固定贡献类型被组织成多套相互依赖的适配器，装配机制承担了超出实际扩展需求的复杂度。
- 插件命令的会话创建、输入接受和消费流程泄漏到 CLI/TUI，界面被迫理解执行协议。
- TUI 用功能继承链组织无关工作流；观察数据又在持久记录和 Host DTO 之间往返转换。

这些问题值得处理，因为它们增加修改一个行为时必须同时理解的位置，或带来可以直接证明的重复计算。相反，运行所有权、原子提交、插件代次隔离、历史代次、异步事件观察与增量渲染具有当前功能上的必要性，不能因为实现复杂就删去。

**建议采用局部收敛，不进行框架重写。** 优先完成 R1、R2、R3、R5，再处理 R4、R6；R7、R8 作为边界明确的后续整理。每项均可独立交付，没有必要等待一次全仓“大重构”。

本报告不承诺减多少行，也不预报吞吐提升百分比。功能不退化、性能不退化是后续实施的验收条件；分析和既有测试通过不能代替改后验证。

## 2. 方法、范围与证据强度

用户指定的 `docs/OURO_AGENT_编码准则_ZH.md` 在当前仓库不存在。实际依据是[中文编码准则](OURO_编码准则_ZH_2026-09-02.md)，特别是第一性原理、最小必要改良、行为不变、错误可见和性能须有证据的要求。

已有架构文档和规格用于了解承诺的行为，不作为现有设计正确性的证明。一个抽象即使被规格正式命名，只要没有独立变化原因或必要运行语义，仍应接受质疑；一个检查即使看起来重复，只要保护的时间点或信任边界不同，就不能直接删除。

本次执行了全量 Python 文件结构统计、依赖和引用搜索，并深入追踪以下路径：

|---|---|

| 插件链 | SDK、manifest、worker、贡献准备、Catalog 投影、代次租约、执行契约、Harness 调用与内置插件状态 |

### 2.2 必要性判定

一项建议只有同时满足以下条件才进入清单：

1. 能指明实际重复、职责泄漏或状态维护问题，而非仅仅不喜欢命名、长度或风格。
2. 能说明被维护的真实不变量，以及更简单实现如何继续维护它。
3. 能明确删除的责任、表示或计算，不以增加新的通用框架补偿旧复杂度。
4. 能列出行为与性能的验证方法；不能靠减少功能、扩大超时、放松持久性或降低刷新频率达标。

“高置信度”表示现状有源码或探针支持，不表示建议已经实现，也不表示所有边界用例已被证明等价。

## 3. 从本质重新确定边界

Agent 框架必须解决的是以下几件事，而不是维持当前目录中的每一个类：

| 必要事实或能力 | 最小所有者 | 不应混入的内容 |
|---|---|---|
| 当前对话与可撤销业务状态 | Session 的消息序列及 Harness 引用 | 实际已经发生的费用、外部工具副作用 |
| 一次执行的进展、挂起与结果 | Run 及原生工具批次记录 | UI 显示细节、插件私有存储实现 |
| 某次模型请求所依据的设置与控制绑定 | 请求边界固定的执行视图 | 随后发生的路由、权限、目标变更 |
| 一次提交是否已接受 | 原生提交回执与操作身份 | 第二套业务事件源或无限重放的业务执行器 |
| 进程中的任务、锁、租约与关闭 | 对应运行/插件/Host 的资源所有者 | 可序列化业务状态和历史恢复事实 |
| 插件输入输出是否合约有效 | 插件边界的一次解释和校验 | 下游重新猜测原始字典含义 |
| 用户当前看到与编辑什么 | TUI 的观察、草稿和渲染状态 | 运行接受、权限授权、持久事务规则 |

由此得到四个判断：

- **“只校验一次”应限定为同一不可变输入、同一边界。** 外部输入解码、锁内提交前置条件、跨 await 后状态检查、执行前权限重检各自有理由，不能合并成一次早期检查。
- **“单一事实来源”不意味着没有投影或快照。** Session 当前值、Run 当时的绑定、Host 只读投影解决不同问题；重复的是同一时点同一职责的多份独立可写表示。
- **异步没有消除资源所有权。** `to_thread`、任务取消、文件锁和数据库事务之间仍需明确完成边界；把等待与清理压成一行不等于简化正确。
- **扩展点应位于真实变化边界。** Provider、工具、插件调用、存储后端都是真实差异；为了装配固定的内部种类再造可扩展管线，不一定有价值。

## 5. 逐项审查与最小重构方案

### R1：同一次一致读取不应重复加载同一 Harness

**证据。** [文件后端](../ouro/sessions/file_commits.py#L45)和[SQLite 后端](../ouro/sessions/sqlite_commits.py#L27)的 `load_session` 均为补齐 `session.controls` 而加载 Harness。各自 `commit` 随后又对同一个 `current.harness_version` 调用 `load_harness`。[`capture_session_harness`](../ouro/application/harness.py#L21)也先取得已经补齐 controls 的 Session，再加载同一 Harness。

只使用临时目录、临时 Session 和方法调用计数的探针得到：

| 一次操作 | 文件后端 `load_harness` 调用 | SQLite 调用 | 不同 Harness 身份数量 |
|---|---:|---:|---:|
| 无新增效果的 `SessionCommit(before=session)` | 3 | 2 | 均为 1 |
| `capture_session_harness` | 2 | 2 | 均为 1 |

文件提交的第三次读取位于 `finish`，服务已持久化决定的执行/恢复验证。它与准备阶段的重复读取性质不同，不应为了使数字变成 1 直接删除。

**根因。** `load_session` 隐藏了“为了补齐投影，已经取得完整 Harness”这一成本，但事务编排只拿到 Session，后续不得不重新获取同一事实。

**最小改法。** 在现有存储读取边界提供一个明确的 Session/Harness 成对读取能力，内部加载一次并同时返回；Session-only 查询继续复用该实现。提交准备和调用快照直接使用成对结果。由后端在一个已有 mutation/transaction 中完成，不在应用层组合两次无锁读取，也不增加跨操作缓存。

**应保留。** Harness 身份校验、当前引用一致性、提交 CAS、文件恢复时的完整性验证及 SQLite 原生事务。不要合并 Session 当前 controls 与 Run 历史控制绑定，它们不是重复事实。

**验收。** 同一阶段同一版本的读取/解码下降；`capture_session_harness` 的两次读取收敛为一次。文件恢复流程继续单独验证持久化决定。两后端在并发状态变更、缺失/错误 Harness、undo、branch、转移和重复提交下行为一致。R1 不应增加新写入、fsync、索引、后台任务或缓存失效规则。

### R2：worker 的验证和解码实际在重复做同一件事

**证据。** [`WorkerPluginInstance._result`](../ouro/plugins/worker.py#L380)调用 [`_validate_worker_result`](../ouro/plugins/worker.py#L1321)。其中 `context.call` 对每个 fragment 调用 `_worker_context_fragment`，创建结果后丢弃；[`_context_handler`](../ouro/plugins/worker.py#L530)再调用一次同一解析器。`command.call` 对 session inputs、batches、control transitions 也存在验证阶段构造、handler 阶段重建的路径。continuation 的 action/mode 分支亦重复检查。

探针以假的 JSON-RPC 返回代替外部进程，调用真实 `_context_handler`：**一个 context fragment 触发两次 `_worker_context_fragment`，最终只保留一个 fragment**。这是调用和对象构造重复的证据，不是时延基准。

**根因。** “校验通过的原始字典”不是有明确类型的阶段结果，校验器已经具备解码能力，却没有把结果交给使用者。

**最小改法。** 每种现有 worker 方法由一个解码函数把外部响应变为对应 SDK 输出；验证和构造在此合为一步。handler 直接使用输出，不再重解码或以 `str(...)` 等转换重新解释字段。保留现有方法种类和 SDK 类型，不增加第二套 Wire DTO、schema 生成器或通用 RPC 框架。

响应中的 `session_state` 仍是独立的调用草稿提案：先完整验证方法输出和状态提案，再按原有 Harness 调用边界暂存；不能让无效输出留下部分状态变更。协议错误仍经现有 `report_invalid_result` 统计和隔离，不能因移动解析位置而绕开它。

**应保留。** 外部进程响应的类型检查、大小限制、timeout、方法身份、字段互斥、插件 owner 隔离、只读限制、未知结果和取消语义。SDK → core 的转换有层间独立性理由，不因消除 worker 双解码而一并删除。

**验收。** 单份片段/输入/transition 每次响应只解释一次；正常输出、默认值、错误类别及错误隔离行为不变。覆盖非法 role/tag、bool 冒充数值、混合工具结果与输入请求、越权状态替换、malformed batch、取消与 worker 崩溃。新增成本不得转化为另一层 DTO 往返。

### R3：Run 的资源生命周期不应由多个字典人工拼成

**证据。** [`RuntimeService.__init__`](../ouro/application/runtime.py#L319)为同一 run_id 保存七组信息：extension lease、controller IDs、Agent catalog、tool caps、tool refs、delegated constraints、tool coordinator。[`_finish_run_observers`](../ouro/application/runtime.py#L3969)和 [`_detach_extension_snapshot`](../ouro/application/runtime.py#L3993)分别重复清理它们。后者的名称只表达 extension，但实际上同时管理 Agent 和工具运行资源。

另一个相关负担是框架执行信息存入裸 metadata：[`_restore_run_tool_cap`](../ouro/application/runtime.py#L4003)手工解析工具名、工具引用和委派约束；[`_restore_session_control_snapshot`](../ouro/application/runtime.py#L4132)再解释 controller 字典；[`RunRecord.control_bindings`](../ouro/core/state.py#L259)每次访问又构造 `RunControlBinding`。新增一个绑定字段需追踪多处手工解释。

**根因。** 缺少表达“一次运行当前持有的执行资源”的局部对象，使用 run_id 作为联结键来模拟对象。持久记录的解释和运行期派生视图也未集中。

**最小改法。** 用一个 application 私有的运行资源记录承载现有七组成员，以一个 `run_id → resources` 容器管理；该对象负责幂等释放。原有 attach、detach、finish 路径使用同一释放实现。它不拥有 durable Run.status，不替代 RunLifecycle/RunExecutionOwnership，也不成为可序列化的第二套 Run。

queued input lease 的身份和寿命不同，继续按 queue_id 独立持有；只有输入被某个 Run 接受时才显式转移。不能为减少字典数量将二者混为一谈。

执行绑定先做局部收敛：在恢复/模型轮次绑定阶段统一解码，并将已得到的类型化值分发给该阶段调用者；工具名集合从同一批有效工具引用派生。当前磁盘 metadata 可以保持不变，不同时维护新的持久字段和旧 metadata 两个权威值。若未来要改持久结构，应另行评审，不作为本项前置条件。

**应保留。** 暂停期间租约、观察任务对旧代次的独立保留、恢复时精确执行契约匹配、请求边界重新绑定以及权限收紧。不能在每次模型轮次结束就释放整次 Run 的资源。

**验收。** 成功、失败、取消、暂停/恢复、启动中异常、热更新和 shutdown 都走唯一资源释放边界；不漏释放、不重复关闭。Run 的历史绑定、工具范围、审批结果及 usage 归属不变。资源字典和重复清理点减少，不新增长期快照缓存，不增加每个 delta 的对象分配。

`execute_batch` 的多个闭包也持有一组执行期状态，但它们至少被限制在一次调用内。本轮先解决跨方法、跨 Run 的分散所有权，不因为该函数有 598 行就同时重写批调度。

### R4：插件贡献装配不需要成为内部的“插件框架”

**证据。** [`ContributionTypeAdapter`](../ouro/plugins/contribution_types.py#L88)明确声明为 Host 拥有的封闭种类表，固定登记 13 类贡献；每类再关联 preparation、projection、SDK、worker、contract、resource 等面。以 commands 为例，维护者需经过类型表、SDK adapter、worker adapter、[`_CommandPreparationAdapter`](../ouro/plugins/contributions.py#L887)、coordinator 的静态方法、contract adapter 和 projection adapter。

其中部分层只是无状态转发。`_SnapshotProjectionAdapter` 用字符串属性名调 `replace_owner`；[`project_prepared_contributions`](../ouro/plugins/adapters.py#L157)再用对象 `id` 去重，因为 MCP 和工具共享同一投影 adapter。字段已经不可空，循环中仍检查 `adapter is None`；preparation 也有同类检查。

`contribution_types` 导入 api/contributions/contracts/worker，而这些模块的函数又局部导入 `contribution_types`。这使封闭清单成为一个相互回指的装配中心。包间依赖矩阵可以全部通过，但不代表包内拓扑清晰。

**根因。** 实际扩展需求是“插件提供某种能力”，当前内部机制却还在处理“固定能力种类如何分别接入每个阶段”。种类表、多个策略对象和反射属性形成了多份需要协同的描述。

**最小改法。** 首先压平 preparation/projection 的纯转发层：固定字段直接准备、直接投影，或由一份静态、类型明确的装配表引用普通函数。保留具体能力自己的校验、错误策略和生命周期；上层显式组合，下层不再反向导入装配表。不要同时引入新的注册 API、元类、动态发现或代码生成。

SDK 解耦、worker transport、执行合同计算、generation resource 生命周期仍是不同职责。不是把六个面合进一个超大文件，也不是把所有 registry 继承到一个万能基类。13 种能力全部保留；例如 MCP 工具先汇入准备后的工具集合，再只投影一次，替代按 adapter 对象身份去重。

`ContributionCoordinator` 所持有的基础 registries 当前被 `PluginRuntimeResource._capture_catalog_base` 使用，**不是死字段**。压平时应把这些基础资源直接交给拥有 Catalog 的 runtime；不能仅因 coordinator 内部没有读取就删掉注入。

**应保留。** 发布的 Catalog 不可变、原子切换、旧 Run 的 lease、背景服务单例约束、依赖拓扑、配置修订、执行契约和 namespace 冲突检测。当前没有证据支持用“统一一个 hash”替代不同范围的合同身份。

**验收。** 对 13 种贡献的 in-process/worker/声明式适用组合运行原有行为测试。新增一个已有种类的贡献不要求改主循环；修改一个种类的投影不再涉及多份转发描述。候选失败不污染当前 Catalog；热切换和恢复行为不变。静态清单完整性可用测试保护，外部 manifest 校验仍在运行时执行。

### R5：插件命令的业务协议应止于 application

**证据。** [应用层命令执行](../ouro/application/plugin_commands.py#L21)在有目标 Session 时原子接受 owner state、controllers 和输入，返回 `accepted_inputs`；无 Session 时返回待处理 `session_inputs/session_input_batches`。随后：

- [`TuiController.execute_plugin_command`](../ouro/tui/controller.py#L1838)自行判断是否创建 Session，并分别执行 receipts、batch、single 三种路径。
- [CLI interactive](../ouro/cli/interactive.py#L274)也判断同一组表示、创建 Session、管理消费 task 或逐条提交。
- TUI 该 async 方法的两处 `runtime.create_session` 为直接同步调用（1861、1885 行），会沿现有 Session 持久化路径运行；CLI 同样有对应调用。

问题不在 DTO 名字多，而在界面必须知道命令结果“已经接受还是尚待接受”，并承担完成业务协议的责任。

**根因。** application 暴露了执行中间产物，却没有封装“执行一个 Host 插件命令并安置其后续工作”的完整用例。

**最小改法。** 在现有 application 命令边界完成命令选择、必要时创建 Session、状态/输入接受与后续执行安排。CLI/TUI 传入目标 Session 或创建所需的草稿设置，只获得输出、最终会话身份及明确的接受/运行结果。应用层复用既有队列、Runtime 和适用的 Supervisor 能力，不新建命令总线或另一套调度器。

不能简单提前为所有命令创建空会话：无会话、无输入的查询命令应继续不产生会话；`requires_session`、创建失败、插件已经执行后接受失败等现有语义须分别保持。多个独立输入仍是独立 FIFO 单元，显式 batch 仍不可拆分。

同步创建/查询/提交以**完整应用操作**为单位使用既有 `run_blocking` 等有所有权的执行边界；不是到处散加 `to_thread`。取消后必须明确是尚未接受还是已持久接受，不能放弃仍持锁写入的线程。已有原生回执继续承担幂等，不增加第二份 command log。

**应保留。** UI 对展示时机、草稿和交互等待方式的控制；应用层对 provenance、history epoch、合同及状态提交的判断；已接受输入的取消/撤销语义。不能为统一提交 API 把插件输入伪装为直接用户输入。

**验收。** CLI/TUI 在已有/新建 Session、纯查询、单输入、多独立输入、batch、活动 Run、命令失败、取消和 undo 竞争下产生同样的 canonical 消息与回执。TUI 插件命令路径不得同步调用存储；并发额度、队列顺序及首个流式输出不退化。

补充发现：`TuiController._save_endpoint` 的 create/update 存在性预检也属于写操作的业务前置条件，当前位于最终配置写锁之外。应在日后触及该用例时把操作意图送到已有原子配置边界；不能只删除 TUI 检查，否则会把创建/编辑悄悄变成 upsert。本轮不据此重构全部配置系统。

### R6：功能继承链没有表达真实的 TUI 类型关系

**证据。** 实际继承关系为：

```text
OuroTuiApp
  → ConfigurationWorkflowsApp
  → TaskManagementWorkflows
  → PluginManagementWorkflows
  → ProviderConfigurationWorkflows
  → Textual App
```

对应代码见 [configuration](../ouro/tui/configuration_workflows.py#L122)、[tasks](../ouro/tui/task_workflows.py#L14)、[plugins](../ouro/tui/plugin_workflows.py#L21)、[providers](../ouro/tui/provider_workflows.py#L29)。任务管理并不是插件管理的一种，插件管理也不是 Provider 配置的一种。这条链只是为共用 `self`、controller、screen 操作和若干回调服务，拆文件后仍是一个横跨功能的 App 对象。

[`_choose_providers`](../ouro/tui/provider_workflows.py#L34)等方法还分别维护 `menu.push_page` 和 `push_screen_wait` 两种承载路径，重复选择、返回、刷新流程。两个入口可能都必要，但无需复制业务步骤。

**最小改法。** `OuroTuiApp` 直接拥有功能工作流，工作流接受小而具体的 UI 能力和 controller；可用普通异步函数或有真实流程状态的对象。共用一个菜单打开/推进方法，决定将同一页面放入现有菜单栈还是新 screen。继续使用现有 `ChoiceScreen`，不新造导航框架。

先选择 Provider 工作流作为局部试点，保持交互轨迹不变，再消除余下功能继承。不要把长继承链换成多重继承，也不要传入整个 App 作为万能 context 后声称已经解耦。

**应保留。** 返回、Esc、取消、独立弹窗和设置菜单内操作、主题、键盘焦点、刷新、错误提示、未完成草稿，以及当前 Textual worker 的 exclusive/group 生命周期。工作流不能额外接管流式渲染或运行状态。

**验收。** 通过相同键盘序列比较页面栈、选中项、焦点和操作结果；独立命令与设置菜单入口都可用。每个功能工作流不再继承另一个无关功能。不能通过移除独立入口、禁用热刷新或整段重绘降低实现难度。

### R7：观察模型应面向消费，避免事件记录往返转换

**证据。** Supervisor 将 `EventRecord` 投影为 [`RuntimeEventView`](../ouro/application/event_models.py#L25)，TUI 收到后又通过 [`_event_record`](../ouro/tui/app.py#L4638)构造 `EventRecord`，只是为了交给现有 reducer。另有 [`_publish_runtime_event`](../ouro/tui/app.py#L1363)处理 fallback sink，[`_consume_observation`](../ouro/tui/app.py#L1432)处理 subscription；前者需检查后者是否已经拥有某条流。

两条入口目前有实际职责：首次创建会话时的交接，以及受控父会话与可见子会话的不同通知。因此不能把 fallback 看成死代码直接删掉。

**最小改法。** 先让 TUI/reducer 只依赖它需要的只读事件字段，使用现有 Host 事件表示，不重建持久化记录。仍由边界负责脱敏与投影，不为了少一个对象把内部原始数据绕过 Host 边界传出。保留有独立消费者用途的 Host 分类、摘要字段，不全局删 DTO。

观察入口进一步收敛前，先明确“已确定目标会话 → 取得快照与 cursor → 建立可补读的观察”这一交接。优先复用当前 subscribe/replay 机制，使初始化也能走同一路径；Agent tree 通知继续承担树和子交互的职责。只有首次输入、并发子事件、父子切换、终态和断开/重接均验收后，才删除被替代的 fallback。若仍需独立入口，只保留其必要范围，不追求形式上的单通道。

**应保留。** 持久化先于实时发布、单调 sequence、history epoch、重复事件去重、慢消费者有界缓冲、lag 后重同步、关闭旧订阅、旧异步结果隔离。TUI reducer 与 Supervisor 复用同一纯活动规则是好的设计，不应各自维护一套新的业务状态机。

**验收。** 同一事件在 TUI 不发生 DTO→持久记录的往返构造；所有流片段、最终输出、工具状态和历史完整保留。事件 storm、undo、新建 Session、共享 LocalApplication、跨进程追加、只读子会话均正确。不能扩大缓冲区掩盖竞态，也不能增加每个 delta 的全量 history/activity 重建。

### R8：灵活回调只需在绑定边界解释一次

**证据。** [`Tool._handler_arguments`](../ouro/tools/base.py#L457)、[`_resume_handler_arguments`](../ouro/tools/base.py#L483)每次执行检查 Python signature；插件内部 [`callback_arguments`](../ouro/plugins/harness_calls.py#L134)再做一次参数选择。SDK 工具经过 adapter 时，框架生成的、签名已知的包装函数也进入这套通用解释路径。

**根因。** 回调的固定调用形式被当成每次 invocation 的动态状态。它增加分支和理解成本；其时延影响尚未做独立基准，不应夸大。

**最小改法。** 在 Tool 绑定或 plugin generation 准备时，把实际 handler 规范化为内部固定调用形式；已知的框架包装函数直接使用该形式。保留当前支持的单参数、context、signal、keyword 和 resume 调用语义，不以删除合法回调形式换取减负。热替换产生新的绑定，而不是加全局 signature 缓存。

**应保留。** `invoke_callback` 与 `invoke_owned_callback` 对同步回调取消的不同处理、异步支持、调用结束后的 state view 关闭、unknown outcome 以及 resume 的人工输入结果。

**验收。** 以现有回调形式矩阵对比行为；常规执行不再对同一个固定包装函数反复反射。取消、timeout、同步异常、异步异常、返回 awaitable、工具恢复均不退化。此项不要求改 SDK 公共契约，也不值得独立引入一个回调框架。

| 用户关注维度 | 本次结论 |
|---|---|
| 冗余验证、限定和分支 | R2 是已证明的同一响应重复解码；R4 有封闭内部装配表上的不可空检查。R8 是绑定信息被反复推断。跨 await/锁边界的检查不能按文本相似度删除。 |
| 重复模型、字段、函数、模块 | 优先处理 R3 的同寿命资源容器和绑定解释、R7 的事件往返、R2 的临时解码对象。SDK/core、请求/结果、当前状态/历史快照不是同一模型。 |
| 过度内部管线与不必要联动 | R4 的固定种类适配拓扑、R5 的命令协议跨界面流转、R7 的观察入口协调是实际目标；不替换 inner loop 或事件系统。 |
| 职责耦合与依赖不规范 | R5 将完整用例收回 application；R6 消除伪类型继承；R4 消除包内反向装配依赖。包间 import 测试通过只是最低保证。 |
| 拆分过细 | 有害拆分主要是一个流程跨纯转发层跳转、无关功能通过继承才能拼回，并非所有小文件。见 R4、R6。 |
| 其他健壮性/效率问题 | R1 消除重复 IO，R3 建立明确资源所有权，R5 修复完整用例的异步边界；不把这些问题扩大成持久层、调度层或全仓类型系统改造。 |

## 7. 明确保留或不纳入本轮的设计

以下结论来自实际职责差异和失败场景，不是“文档说了所以保留”。

| 看似可删的机制 | 为什么当前仍必要 | 本轮处理 |
|---|---|---|
| Session、Run、ToolBatch 多种状态 | 对话可持续多次执行；一次执行可暂停在多工具/人工交互之间；恢复必须知道哪一步已产生副作用 | 保留，避免改成一个万能 status |
| `history_epoch`、提交身份、Harness 引用 | 分别防止旧历史的迟到输入、重复提交、错误状态回退；不能相互替代 | 保留 |
| Session controls 与 Harness controls | 存储写入 Session 时排除 controls，读取时从 Harness 投影；不是两份独立落盘的业务事实 | 不做字段删除重构 |
| runtime snapshot、完整 snapshot、observation snapshot | 正常运行、导出/审计、快照/live 交接所需数据不同；合并会让热路径加载更多数据 | 保留不同读取形状 |
| 文件决定恢复与 SQLite 事务 | 相同的原子性要求，需要不同后端机制；核心 `prepare_session_commit` 已共享纯规则 | 保留两后端，按 R1 复用读取，不造 ORM/统一存储引擎 |
| 提交回执中保存结果、历史版本 | 幂等重试和撤销后身份不能复活依赖它们；仅因与 canonical 消息有重叠不足以删去 | 大回执成本可另测，不在本轮改保留策略或回收语义 |
| 运行锁与短 mutation lock | 前者约束执行 owner，后者保护读改写；一个长事务锁无法替代两者 | 保留分工，不扩大锁持有区间 |
| 请求前与工具执行前的权限检查 | 排队/审批期间权限和 Session 设置可变化，早期允许不等于此刻允许 | 保留执行时重检 |
| 提交前对模型再次验证 | 当前模型可变，且大量使用 `model_copy(update=...)`；“已经是 Pydantic 对象”不能证明更新后的完整约束仍成立 | 不直接删除提交验证，也不为此推行全仓 frozen 模型 |
| 插件 release/generation/config/contract 多种身份 | 包内容、进程实例、配置及可恢复执行合同寿命不同；同名工具不能代表同一执行能力 | 保留；只收敛编解码和装配 |
| SDK 与 core 相近的数据类型 | SDK 必须可独立使用，worker 需要序列化，core 不能反向绑定插件实现 | 保留必要适配，不追求全仓只有一种 DTO |
| Observer 与语义策略分开 | observer 观察失败不应替代业务决策；prompt/tool/turn/continuation 策略的作用时点和失败语义不同 | 不合成统一 Hook 管线 |
| Plan/Goal/Todo 状态解析 | owner JSON 由插件解释，框架不知道业务 schema；Goal 的 usage 是不可回滚事实 | 保留业务校验，不建立共享 GenericPluginRepository |
| Provider 独立 codec 与共享重试 | 请求/流格式有真实差异；已有重试约束避免输出之后自动重放 | 保留，不为相似构造函数增加公共 provider 父类 |
| MCP resource 包装与独立配置模块 | 它们拥有部署和资源生命周期，或明确的领域配置；短不意味着多余 | 不机械合并 |
| `message_roles.py`、`extensions.py`、`selection.py`、`message_journal.py` 等小模块 | 有多处消费者、明确的低依赖类型或真实共享算法；合并可能引入更重 import 或重复实现 | 不设文件最小行数，不搬进 utils |
| TUI 的流片段合并、增量 Markdown、可见 buffer、异步重绘 | 直接限制高频更新成本；简单全量重绘会损害交互和长会话性能 | 保留算法和运行节奏 |
| 任务 Scheduler、Supervisor、Runtime、Agent 关系记录 | 分别负责截止时间、进程调度、单会话执行、父子归属与交付；存在不同 scope | 不一律合并，也不强制所有直接交互套入同一种提交 API |

另外，不建议本轮开展：全仓不可变模型迁移、全部 metadata 类型化、统一所有 registry、无证据引入连接池/缓存、万条历史分页重写、换 TUI 框架、删除历史数据、重做插件权限体系。它们要么影响真实能力，要么需要独立需求和测量，不能借“减负”扩大范围。

## 8. 实施顺序与退出条件

| 阶段 | 范围 | 交付判断 |
|---|---|---|
| A：去除可证明的重复 | R1、R2；作为两个独立变更 | 同阶段读取/解析次数下降，原有错误与提交语义不变 |
| B：收敛所有权 | R3、R5；分别验证运行资源和 Host 命令 | 一个资源释放边界；CLI/TUI 不再各自实现输入接受协议 |
| C：压平拓扑 | R4、R6；先各选一个贡献种类/工作流试点 | 跳转和协调点减少，现有扩展能力及交互轨迹完全保留 |
| D：整理高频边界 | R7、R8 | 删除实际转换/反射；事件入口收敛有完整交接证据 |

每次只改变一个核心责任边界。新路径接管后删除被替代实现，不能长期同时运行两套生产管线以互相校验。必要的对照应放在测试或离线基准中。

任何阶段若发现需要新增通用 engine、通用 registry、长期缓存、第二份持久日志或数据迁移才能成立，应停止扩大该阶段，重新判断净收益。用户已要求功能与性能不降级，不能以“以后补回”作为完成理由。

本清单默认保持现有数据与合法外部调用可用。编码准则中“不编写历史兼容迁移”的约定不等于允许为了本次减负破坏用户数据。本轮建议不以改变持久格式为前提；若实施确实触及该边界，应单独提出设计与影响，不自行清理旧数据。

## 9. 功能与性能不退化的验收合同

### 9.1 行为等价

对改前改后使用相同输入和故障注入，对比 canonical 消息、Harness、Run/Tool 终态、usage、回执、输出及可见交互。只对运行时随机 ID 和时间做关联规范化，不忽略顺序、错误类型、资源身份或实际费用。

至少覆盖：

| 场景 | 必须保持的结果 |
|---|---|
| 普通流式与工具批次 | token/文本顺序、source index、并发读工具能力、写工具边界和最终结果不变 |
| 审批、修改参数、AskUser、Plan | 唯一交互身份、重复回答处理、暂停/恢复和无人值守策略不变 |
| 取消与进程中断 | 保留 unknown outcome，不重复执行已经产生副作用的工具，不遗留运行 owner |
| undo、分支、导出/导入、两后端转移 | 消息与 Harness 同一历史边界，迟到结果不能污染新代次，usage 不因撤销消失 |
| 排队输入、插件命令 | FIFO、批次不可分、幂等接受、来源与 role 区分不变 |
| 插件生命周期 | 旧代次在途调用可完成，失败候选不发布，缺失旧合同明确不可恢复 |
| 子 Agent 与自动任务 | 原并发额度、预算归属、父子关系、HITL、结果只交付一次和任务重启恢复不变 |
| TUI | 首次输入、切换会话/子会话、焦点、草稿、主题、resize、流式尾部、历史撤销和断开重接完整 |

测试应保护这些行为，不锁死 coordinator 类名、字段存在哪个字典或文件拆分方式。现有架构测试继续保护包边界；相关变更应补充跨调用边界的行为覆盖，不能只把 allowlist 放宽后宣布架构改善。

### 9.2 性能测量

复用现有离线基准，不在产品路径新增常驻测量框架：


## 11. 完成重构的判据

完成应能同时证明：

- 一个关键行为需要协调的状态与解释位置减少，重复 IO/解析消失。
- 被替代的实现确实删除，没有新增同等规模的通用抽象或平行事实源。
- 保留全部现有合法功能、插件能力、数据语义、异步能力和交互体验。
- 针对变更的行为测试与完整质量门禁通过；关键性能无可重复退化。

若某项只能减少文件数或代码行，却不能降低修改成本、错误面或运行成本，就不实施该项。OURO 的长期基础应是明确的事实所有者和必要的运行边界，而不是更多的抽象名称，也不是更少的安全与一致性保证。
