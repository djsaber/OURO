# OURO 插件观察器与语义扩展点设计

状态：目标设计（2026-07-29；待按 C1-C5 实施）

本文定义 OURO 插件生命周期扩展面的下一阶段结构。总体插件生命周期、不可变 Catalog、generation、授权和
durable execution contract 继续由[插件系统目标规格](../dev/specs/plugin-system.md)定义；实施顺序见
[插件观察器与提示策略计划](../dev/plans/plugin-observers-prompt-policy.md)。

## 1. 问题与结论

当前公开 `Hook` 只有 `after_run`、`after_context_build`、`before_tool_call`、`after_tool_call` 和 `on_event`。
它们只能观察，返回值只有 diagnostics，不能阻断或修改 Agent 行为；除 `on_event` 外，其余回调仍被 Agent 关键路径
同步等待。这个模型存在三个根本问题：

1. `before_*` 在主流 Agent 扩展语境中通常意味着可拒绝或改写，OURO 的命名没有暴露真实契约；
2. 观察者不改变语义，却能按回调数量线性增加模型、工具和 Run 完成延迟；
3. `HookOutput.diagnostics` 被 Registry 收集，但 application 调用点不消费成功结果，形成无效公共契约。

目标不是给 `HookOutput` 增加一个万能 patch，而是把两类职责彻底分开：

- **Observer**：消费不可变事实，不影响正在发生的操作，不进入语义关键路径；
- **Semantic contribution**：由具体类型定义输入、输出、组合、失败和授权规则，并由 application 解释结果。

因此下一阶段直接以 `observers` 替换 `hooks`，不保留旧字段或 alias；同时新增最小的 `prompt_policies`，填补当前
无法在用户提示持久化和 Run 创建前拒绝输入的真实缺口。

## 2. 第一性原理

### 2.1 事实、建议与决策不能使用同一种回调

一个扩展点必须先回答它拥有什么权力：

- 事实通知只能读取已经形成的不可变快照；
- enrichment 只能增加带 provenance 的数据；
- transform 必须返回受限、可重新校验的 typed patch；
- guard 只能做明确的 allow/deny 或更严格决策；
- lifecycle callback 只管理自己 owner 的资源。

把这些能力都表示为 `(data: dict) -> dict`，会让调用顺序、冲突、安全和恢复变成插件作者之间的隐式约定。OURO
不采用这种公共 middleware 模型。

### 2.2 观察不能成为业务事务的隐含参与者

Observer 超时、异常或积压不能改变以下结果：

- 用户提示是否被接受；
- 模型请求是否发出；
- 工具是否执行；
- Session/Run 是否提交；
- continuation 或 compaction 是否完成。

需要影响这些结果的插件必须使用对应的 Policy、Provider、Strategy 或 Controller。Observer 不能通过返回值获得
第二条隐蔽控制路径。

### 2.3 改写能力必须证明必要性

主流 Agent 的 Hook 常允许改写 prompt、模型请求、工具参数和工具结果，但这同时引入跨 owner 修改、顺序依赖、
schema 失效和安全策略绕过风险。OURO 当前已有：

- Context Provider：追加带 provenance 的模型上下文；
- Tool Policy：要求审批或拒绝工具；
- Turn Policy：拒绝候选完成并在同一 Run 继续；
- Continuation Policy：在终态 Run 后创建受控的后续行为；
- Compaction Strategy：替换明确选择的压缩实现；
- Session Controller：仲裁长期 Session 模式。

这些边界已经覆盖现有 Plan、Goal、Skills、MCP 和工具治理需求。因此本阶段不预建任意模型请求/响应、工具参数或
工具结果 transformer。未来只有在真实插件无法由现有类型表达时才新增具体类型。

## 3. 目标模型

```text
Plugin Generation
  |
  +-- snapshot-bound semantic contributions
  |     ContextProvider / PromptPolicy / ToolPolicy / TurnPolicy /
  |     ContinuationPolicy / CompactionStrategy / SessionController
  |
  +-- snapshot-bound observers
  |     immutable Observation -> bounded mailbox -> callback
  |
  +-- activation-singleton resources
        BackgroundService / owned process / MCP connection
```

Observer 与 semantic contribution 都进入不可变 `ExtensionCatalog`，共享 owner、generation gate、contract hash 和
`active_when` 过滤，但不共享调度器或失败语义。

## 4. Observer 契约

### 4.1 名称与事件

目标公开类型为：

```python
ObservationName = Literal[
    "runtime_event",
    "context_prepared",
    "tool_call_requested",
    "tool_call_finished",
    "run_finished",
]
```

旧名称直接替换：

| 当前 Hook | 目标 Observation | 精确含义 |
|---|---|---|
| `on_event` | `runtime_event` | canonical event 持久化成功后的脱敏事实 |
| `after_context_build` | `context_prepared` | 本轮模型上下文构建完成后的只读摘要 |
| `before_tool_call` | `tool_call_requested` | 模型工具请求已形成并已记录；不是执行许可点 |
| `after_tool_call` | `tool_call_finished` | 工具产生终态结果后形成的只读事实 |
| `after_run` | `run_finished` | Run 与 continuation settlement 完成后的只读 outcome |

名称不使用 `before` 或 `after` 表达控制力，而用已经形成的事实命名。

### 4.2 类型与输出

SDK 使用以 `event` 为判别字段的 frozen dataclass 联合，不再向插件暴露无约束的 `data: Mapping[str, object]`。
公共字段只包含稳定 identity、时间和有限上下文；各事件拥有自己的 payload：

- `RuntimeEventObservation`：稳定 `RuntimeEventView`，不暴露原始未脱敏扩展 payload；
- `ContextPreparedObservation`：message/tool 数量、model round 和安全的 context metadata，不包含完整消息正文；
- `ToolCallRequestedObservation`：call id、canonical tool identity、owner、effect 与已解析参数快照；
- `ToolCallFinishedObservation`：call id、tool identity、结果状态和有界模型可见结果；
- `RunFinishedObservation`：只读 `RunOutcome`。

Observer handler 返回 `None`。诊断通过 `PluginContext.diagnostics` 或 worker 的 `diagnostic.emit` 通道提交；Host
统一限长、脱敏、归因和持久化。不得保留一个 Host 不消费的 `ObserverOutput`。

### 4.3 投递与隔离

每个 Observer registration 拥有 generation-owned、有界、FIFO mailbox 和单一 consumer：

- application 只执行非阻塞 enqueue，不等待 handler；
- 每个 registration 独立积压，慢插件不能阻塞其他插件或 Agent；
- 投递是进程内 at-most-once，不宣称 durable exactly-once；需要可靠审计的事实来自 canonical event store；
- queue full、timeout 或异常只隔离该 observer，不回滚业务事实；
- 隔离 key 至少包含 owner、observer id 和当前公开 Observation 支持的 `run_id | session_id` scope；
- queue full 必须释放随 observation 保留的 Catalog/generation lease，并产生有界脱敏 diagnostic；
- generation retire 关闭 gate，待处理投递在 handler deadline 内结束并释放 lease；Host shutdown 按独立 deadline drain
  mailbox，超时后取消 consumer 并释放全部 lease。

`runtime_event` declaration 可以声明精确 `event_types` allowlist；为空表示全部稳定公开事件。Host 在入队前过滤，避免
把所有事件和敏感 payload 无条件发送给每个 worker。未知事件类型在 Manifest 校验时拒绝。

### 4.4 顺序

- 同一 registration 的成功入队项按 enqueue 顺序处理；
- 不提供不同 Observer 之间的先后关系；
- 不提供跨 registration 的共享可变状态或“后者看到前者修改”；
- priority 只用于稳定展示、诊断和同一生产点的 enqueue 顺序，不产生业务优先级。

依赖观察顺序才能正确工作的功能不属于 Observer，应建模为类型化 semantic contribution。

## 5. Prompt Policy

### 5.1 为什么是独立类型

当前插件可以在工具前拒绝动作，也可以在模型完成后要求继续，但不能在用户提示进入 canonical history 和创建 Run 前
执行安全检查。将这项能力放进 Observer 会把 fail-open 观察者变成隐藏 guard，因此新增独立
`prompt_policies` contribution。

### 5.2 调用边界

Application 在完成 Host 命令路由、确认输入是模型提示后：

1. 获取 prospective Run 将使用的同一 `ExtensionCatalogLease`；
2. 形成 `PromptPolicyCall`，包含 session、workspace、input source、原始提示文本、附件的安全 metadata 和
   catalog execution contract；
3. 按稳定 canonical identity 顺序评估 active policy；
4. 全部允许后才持久化 user message 并创建 Run；
5. 任一拒绝或策略失败时关闭 lease，不创建 message 或 Run。

插件命令、Host 管理命令、审批回答和 ToolInput resolution 不经过 Prompt Policy；它们各自由现有类型化用例校验。

### 5.3 决策与失败

```python
PromptPolicyDecision = allow | deny
```

- `deny` 必须包含有界、用户可见且可脱敏的 reason；
- `deny` 短路，Host 返回 attributed rejection；
- timeout、异常和非法返回按 fail-closed 处理，并产生不含提示正文的 diagnostic；
- Policy 不能重写用户文本、注入 system context、创建 Session/Run 或改变 input source；
- 被拒绝提示默认不持久化正文，避免把敏感输入写入 history；只允许记录无正文的拒绝审计摘要。

需要添加上下文时使用 Context Provider；需要规范化 Host 命令参数时在对应 command schema 内完成。

### 5.4 授权

User plugin 声明 Prompt Policy 时必须请求封闭 permission `sessions.prompt.inspect`。它表示 Host 会把用户提示和附件
metadata 交给插件回调，不表示 OS sandbox。capability fingerprint 和 exact-digest code trust 继续独立生效。

## 6. 组合与执行顺序

模型提示进入 Run 的关键顺序固定为：

```text
Host command routing
  -> acquire prospective ExtensionCatalogLease
  -> PromptPolicy (deny wins, fail-closed)
  -> persist canonical user input
  -> create Run bound to the same lease
  -> ContextProvider (typed enrich; omit/block)
  -> build model context
  -> enqueue context_prepared Observer
  -> provider request
  -> ToolPolicy / TurnPolicy / Continuation 等既有语义边界
  -> enqueue fact Observers after corresponding facts exist
```

如果未来增加 transformer，必须遵守：typed patch、字段级授权、原值不可变、修改后重新校验、restrictive policy 在
transform 后重新执行、变更带 provenance，并拥有至少一个无法由现有边界表达的真实插件用例。

## 7. Catalog、Contract 与恢复

- `observers` 和 `prompt_policies` 都是 snapshot-bound contribution；
- declaration、事件/filter、timeout、priority、`active_when` 和 permission 进入 contribution contract hash；
- Run 创建前的 Prompt Policy 使用并转交同一 Catalog lease，不能检查 current catalog 后再让 Run 获取另一版本；
- Observer 队列项保留精确 generation lease，直到处理、丢弃或取消；
- Observer 不参与 durable Run 恢复条件；其 registration contract 仍属于 Run Catalog contract，保证恢复后继续使用同一
  观察实现；
- Prompt Policy 在 Run 尚未创建前执行，不产生可恢复 pending state。

## 8. 迁移决策

OURO 尚无需要保护的公开插件生态，本次直接更新：

- Manifest schema；
- Plugin API major version；
- worker protocol major version；
- `hooks` contribution kind、Core/SDK 类型、worker method、示例、builtin 和测试；
- 旧 `hooks` 字段、旧事件名和 `HookOutput` 严格拒绝，不提供 alias、双读或 adapter。

迁移按“先类型与测试保护、再切换所有生产者/消费者、最后删除旧实现”完成，单个里程碑结束时不得保留双执行路径。

## 9. 明确不做

- 不实现万能 `before/after` middleware；
- 不允许 Observer 阻断、改写、要求重试或同步反压 Agent；
- 不实现任意模型 request/response mutation；
- 不实现跨 owner 工具参数或结果改写；
- 不为 Observer 建 durable delivery broker、重放 cursor 或分布式队列；
- 不让插件动态注册 ObservationName、Policy 类型或 `ContributionTypeAdapter`；
- 不把 permission 描述成对 full-trust runtime 的 OS 权限限制。

## 10. 完成判定

完成必须由代码与测试同时证明：

- 旧 Hook 名称和 schema 不再出现在运行路径、SDK、Manifest 或 worker 协议中；
- 所有 Observer 都不被 Agent 语义关键路径 await；
- 慢、失败、积压和取消的 Observer 不改变 Run/Tool/Session 结果，且无 lease/task 泄漏；
- diagnostics 只有一个有效通道，不存在被收集后丢弃的公共返回值；
- Prompt Policy 与 prospective Run 使用同一 Catalog lease，拒绝不创建 message/Run；
- `deny`、timeout、异常、插件 disable/revoke 和并发 catalog swap 均有集成测试；
- in-process 与 worker 行为等价，权限、contract hash、示例和文档同步更新；
- 全量 pytest、ruff、format、mypy、compileall、架构依赖和 `git diff --check` 通过。
