# OURO Goal 插件设计

> 文档性质：当前设计与实现契约。
>
> 日期：2026-08-16
>
> 适用范围：builtin Goal plugin、Plugin SDK、Application/Runtime 的最小通用输入能力。
>
> 被替代的旧实现及其历史理由见
> [2026-07-28 Goal Harness 调研与插件设计](OURO_目标模式Goal插件设计_2026-07-28.md)。

## 1. 结论

当前 Goal 复用 OURO 现有的 Session、Run、工具、排队输入、Session 控制权、扩展状态和恢复机制，
不增加 Goal 专用主循环、后台轮询器、目标队列或工作流引擎。

本次重构只做以下变化：

1. 每个主 Session 维护一个容量最多为 1 的“最新 Goal”槽位。
2. Goal 直接保存用户原始 objective，不再由模型编译六字段 Goal Contract。
3. `CreateGoal` 简化为 `objective` 和可选 `token_budget`。
4. `UpdateGoal` 简化为 `status` 和 `report`，模型只能设置 `complete` 或 `blocked`。
5. `UpdateGoal` 不再要求模型传入 `goal_id`；旧工作隔离改由内部 activation 与执行绑定完成。
6. `complete` Goal 不删除；最终 Token 结算后仍可通过 `/goal status` 查看，并在下一次创建时被覆盖。
7. 用户直接控制 pause、resume、replace、cancel 和预算；replace 不调用 `CreateGoal`。
8. Goal 的所有脚手架消息都是用户角色消息；脚手架语义由独立语义标签表达。
9. 创建 Goal 时，脚手架消息和用户原始 objective 作为一个不可拆分的有序输入批次进入同一次执行。
10. Token 预算在一个完整 Goal turn 结算后检查；可以有最后一轮 overshoot，但不会再启动新的 Goal turn。
11. “连续三次相同阻塞”是模型行为规则，不由插件解析错误文本或维护语义计数器。

## 2. 范围与非目标

### 2.1 本次范围

- Goal record、状态和权限边界；
- `/goal` 命令语义；
- `CreateGoal`、`GetGoal`、`UpdateGoal` 模型接口；
- 创建、控制和自动继续时的脚手架用户消息；
- Token budget、最终用量结算和恢复；
- 旧执行对新 Goal 的隔离；
- 为上述行为补充的最小通用 Host 能力。

### 2.2 非目标

- 多 Goal 并行、Goal 历史列表或归档库；
- 子目标树、DAG、重试工作流或定时调度；
- 由插件判断任务是否真的完成；
- 由插件理解错误文本、比较阻塞语义或强制验证“三次相同阻塞”；
- Goal 专用 Session API、Goal Manager 或第二套 Agent Loop；
- 精确阻止单次模型请求超过剩余 Token；
- 让 Goal 提高工具权限、跳过审批或改变安全策略。

## 3. 术语

### 3.1 Goal turn

一次由用户 Goal 输入或自动继续输入触发的有界 Agent 执行。它可以包含完整的模型响应、工具调用、工具结果和
必要的后续模型交互。Goal turn 必须在完整消息帧边界结束，不能留下孤立的工具请求或工具结果。

### 3.2 脚手架用户消息

由 Goal harness 生成、以 `role=user` 进入模型上下文的控制消息。`role` 只表示模型协议角色；消息实际由用户、
插件还是 Host 产生，继续由 provenance 表达。脚手架身份由 `semantic_tag` 表达，与 role 正交。

### 3.3 最新 Goal 槽位

每个主 Session 保存零个或一个 Goal record。完成后保留最新记录；创建新 Goal 时覆盖已完成记录；取消时槽位变空。
本设计不保存可查询的 Goal 历史列表，历史交付仍可从 canonical conversation 和 usage ledger 中审计。

## 4. Goal record

### 4.1 公开统一结构

`CreateGoal`、`GetGoal` 和 `UpdateGoal` 成功时都返回同一种 Goal 结构：

```json
{
  "objective": "用户要求推进的原始目标",
  "status": "active",
  "token_budget": 50000,
  "tokens_used": 12000,
  "tokens_remaining": 38000,
  "created_at": "2026-08-16T10:00:00+08:00",
  "updated_at": "2026-08-16T10:20:00+08:00",
  "report": null
}
```

字段语义：

| 字段 | 语义 |
|---|---|
| `objective` | 用户原始目标文本，不由模型扩写、缩写或编译成另一份目标 |
| `status` | 唯一 Goal 生命周期状态 |
| `token_budget` | Goal 累计总预算；`null` 表示无限制 |
| `tokens_used` | 已结算的 canonical Provider input + output Token |
| `tokens_remaining` | 计算字段；无限预算时为 `null`，否则为 `max(token_budget - tokens_used, 0)` |
| `created_at` | 当前 Goal 创建时间 |
| `updated_at` | objective、预算、状态、报告或用量最后变更时间 |
| `report` | complete、blocked 或 runtime 停止时的状态报告；active 时通常为空 |

所有时间和 Token 数由程序维护。模型不得猜测这些值并把猜测当作权威状态。

### 4.2 私有控制元数据

以下字段不进入模型工具参数，也不属于公开 Goal wrapper：

- `activation_id`：每次创建、替换或恢复时更新，用于使旧执行失效；
- 当前执行绑定：记录当前 Goal turn 的执行 identity 与 `activation_id`；
- `last_accounted_usage_id`：保证 Token usage 在恢复或重试时只结算一次；
- state schema version 与 owner attribution。

这些字段只解决并发、幂等和恢复，不构成第二套 Goal 状态。

## 5. 状态模型

```python
GoalStatus = Literal[
    "active",
    "paused",
    "blocked",
    "budget_exhausted",
    "complete",
]
```

| 状态 | 设置者 | 含义 | 是否自动继续 |
|---|---|---|---|
| `active` | 用户意图或创建流程 | Goal 可以继续推进 | 是 |
| `paused` | 用户 | 用户主动暂停 | 否 |
| `blocked` | 模型 | 同一阻碍经过足够尝试后仍需用户输入或外部变化 | 否 |
| `budget_exhausted` | Runtime | 累计 Token 已达到或超过总预算 | 否 |
| `complete` | 模型 | 目标已经完成，且没有剩余必需工作 | 否 |

取消不是状态。`/goal cancel` 删除当前 Goal record 并释放 Goal 对当前 Session 行为的控制。

### 5.1 状态转换

```text
empty ── CreateGoal ───────────────→ active

active ── UpdateGoal(complete) ────→ complete
active ── UpdateGoal(blocked) ─────→ blocked
active ── /goal pause ─────────────→ paused
active ── budget boundary ─────────→ budget_exhausted

paused ── /goal resume ────────────→ active
blocked ── /goal resume ───────────→ active
budget_exhausted ── budget+resume ─→ active

unfinished ── /goal replace ───────→ active
any Goal ── /goal cancel ──────────→ empty
complete ── new CreateGoal ────────→ active（覆盖旧记录）
```

所有自动调度只依据一个条件：

```python
should_continue = goal is not None and goal.status == "active"
```

Session control claim、activation 和执行 checkpoint 可以继续存在，但不能另存一份与 `Goal.status` 可能冲突的
Goal 生命周期枚举。

## 6. 用户命令

### 6.1 语法

```text
/goal [--token-budget N|unlimited] <objective>
/goal status
/goal pause
/goal resume [--token-budget N|unlimited]
/goal replace [--token-budget N|unlimited] <new-objective>
/goal cancel
```

`--token-budget` 是 Runtime 硬控制字段的唯一 slash-command 来源。objective 中出现的预算文字仍属于目标内容，
但不自动改变硬预算。这样可以避免参数和自然语言产生两个互相冲突的预算来源。

### 6.2 命令前置条件

| 命令 | 前置条件 |
|---|---|
| 创建 | 不存在 unfinished Goal；空槽位或 `complete` 均可 |
| status | 任意状态；空槽位返回无 Goal |
| pause | 当前状态必须为 `active` |
| resume | 当前状态必须为 `paused`、`blocked` 或 `budget_exhausted` |
| replace | 当前 Goal 必须存在且未完成 |
| cancel | 当前 Goal 必须存在 |

校验失败时不改变 Goal、不创建脚手架消息，也不启动模型执行。

### 6.3 创建

创建命令不直接伪造已创建状态，而是提交一个有序 `SessionInputBatch`：

```text
1. role=user, semantic_tag=goal-create
   告知模型：用户明确要求创建 Goal，并说明 CreateGoal 的调用要求和精确预算。

2. role=user, semantic_tag=None
   用户原始 objective，内容保持不变。
```

两条消息必须原子进入同一次 Goal turn，不能受全局逐条队列配置影响而拆成两次执行。模型只有在看到这次明确
授权后才可调用 `CreateGoal`。

若当前槽位保存的是 `complete` Goal，新 Goal 成功创建后覆盖旧记录，并重置 Token、时间和报告。

### 6.4 暂停

`/goal pause`：

- 立即把 `active` 改为 `paused`；
- 使当前 activation 失效，阻止旧工作随后改变 Goal；
- 在当前完整 turn 边界后追加一条 `role=user, semantic_tag=goal-paused` 的脚手架消息；
- 不要求模型调用 `UpdateGoal`；
- 不再自动开始新的 Goal turn。

### 6.5 恢复

`/goal resume`：

- 把 `paused` 或 `blocked` 改回 `active`；
- 生成新的 `activation_id`；
- 对曾经 blocked 的 Goal 开始一轮全新的阻塞审查；
- 追加 `role=user, semantic_tag=goal-resumed` 脚手架消息并继续推进。

从 `budget_exhausted` 恢复时，用户必须显式提供大于 `tokens_used` 的新总预算，或使用 `unlimited`。不允许只恢复
状态而保留一个已经耗尽的预算。

### 6.6 替换

replace 的语义是编辑当前 Goal，而不是创建另一个 Goal：

- 插件直接以用户原文更新 `objective`，不调用 `CreateGoal`；
- 保留 `created_at` 和 `tokens_used`；
- 清空旧 report，设置 `status=active`，更新 `updated_at`；
- 生成新的 `activation_id`，使旧执行无法完成或阻塞更新后的 Goal；
- 省略预算参数时保留原总预算；显式整数替换总预算；`unlimited` 清除预算；
- 新总预算必须大于 `tokens_used`，否则整条命令原子拒绝；
- 在 turn 边界追加 `role=user, semantic_tag=goal-updated` 脚手架消息，明确给出更新后的 objective 和预算。

如果用户希望重新计算 Token、创建时间和报告，应当取消后重新创建，或在已完成 Goal 上创建新 Goal。

### 6.7 取消

`/goal cancel` 删除当前 Goal，释放长期控制，并追加
`role=user, semantic_tag=goal-cancelled` 脚手架消息，通知模型当前不再有 Goal。取消后的普通用户输入恢复正常行为。

### 6.8 同一 turn 内的重复命令

状态变更按命令到达顺序立即校验和应用；尚未消费的生命周期脚手架按 Session、Goal owner 和当前 turn 使用稳定
coalesce key。后续命令原子替换先前未消费的脚手架，而不是继续追加。

因此：

- pause 后立即 resume，只留下最终 resume 脚手架；
- 连续 replace，只留下最终 objective 和预算；
- pause/replace 后 cancel，只留下 cancel 脚手架；
- 已经形成 canonical message 的旧命令不再被追溯删除。

coalescing 只用于同一 owner 在同一安全边界前生成的可替换控制投影，不扩展为通用优先级或依赖队列。

## 7. 模型工具

模型只看到下面三个简单工具。工具描述不得出现 Session Controller、Run binding、continuation policy、plugin state、
Host transaction 等模型不可见的实现概念。

### 7.1 CreateGoal

参数：

```json
{
  "objective": "string, required",
  "token_budget": "positive integer, optional"
}
```

建议工具描述：

```text
Create a goal only when the user or system/developer instructions explicitly ask for one.
Do not create goals for ordinary tasks, even when they are long or difficult.
Preserve the requested objective without expanding, narrowing, or inventing intent.
Set token_budget only when an explicit budget was provided, and use the exact requested value.
Fails when an unfinished goal already exists. A completed goal does not prevent creating a new one.
```

行为：

- 只接受当前明确创建授权；
- objective 必须与授权消息中的用户原文一致；
- 预算只复制明确参数或明确的 system/developer 要求，不能自主估算；
- 成功后创建 `active` Goal，返回统一 Goal wrapper；
- 空槽位或当前 `complete` 时可创建；unfinished Goal 存在时拒绝；
- 是否批准 state-changing tool 继续服从既有权限规则。

### 7.2 GetGoal

参数：无。

建议工具描述：

```text
Get the most recent goal for this conversation, including its objective, status, token budget,
token usage, remaining budget, timestamps, and latest report.
```

Goal 完成后仍可读取。只有空槽位时返回 `goal_not_found`。

### 7.3 UpdateGoal

参数：

```json
{
  "status": "complete | blocked",
  "report": "non-empty string"
}
```

建议工具描述：

```text
Update the current goal only to report that it is complete or genuinely blocked.

Set status to complete only when the objective has been achieved, the result has been checked,
and no required work remains. The report must summarize the delivered result and the evidence
that it is complete.

Set status to blocked only when the same obstacle has prevented meaningful progress in at least
three consecutive attempts, including the initial attempt and retries, and progress now requires
user input or an external change. The report must summarize completed progress, attempted
approaches, and the exact obstacle.

After the user asks to continue a blocked goal, begin a fresh assessment of repeated obstacles.
Do not use blocked because the work is difficult, slow, uncertain, incomplete, or merely easier
with clarification.

Do not use this tool to pause, resume, replace the objective, change the token budget, or report
that you are stopping. Usage and timestamps are tracked automatically; do not guess them.
```

`UpdateGoal` 不包含 `goal_id`。工具调用自身所属的执行由程序隐式绑定到当前 Goal activation。

## 8. 旧执行隔离

移除模型参数中的 `goal_id` 不等于移除内部身份校验。

最小规则：

1. Goal 创建、replace 或 resume 时生成新的 `activation_id`；
2. 每次 Goal turn 记录自己的 execution identity 和 `activation_id`；
3. `UpdateGoal` 根据工具调用所属执行查找绑定；
4. 绑定必须仍是当前 Goal 的 activation，且 Goal 必须为 `active`；
5. 真正提交状态时再次以 expected activation/revision 校验；
6. 任一检查失败都返回 stale update，不改变 Goal。

示例：

```text
旧 objective A：activation E1，旧执行绑定 E1
用户 replace 为 B：activation 旋转到 E2
旧执行随后 UpdateGoal(complete)：E1 != E2，拒绝
新执行 UpdateGoal(complete)：E2 == E2，接受
```

脚手架负责让模型在下一次请求中知道目标已更新；activation 校验负责处理极少数已经在途的旧工具调用。二者不能
互相替代。

## 9. 自动继续与输入控制

一个 Goal turn 完整结算后：

- Goal 不存在：结束；
- `status=active`：追加 `role=user, semantic_tag=goal-continue` 的脚手架消息，开始下一次有界推进；
- 其他状态：不再自动开始新 Goal turn。

继续脚手架包含当前 objective、预算、已使用 Token、剩余预算，以及以下通用要求：继续取得可验证进展；不要因为
一次回答结束而宣布 Goal 完成；只有满足工具规则时才调用 `UpdateGoal`。

当 Goal 处于 `paused`、`blocked` 或 `budget_exhausted` 时，普通用户输入不能静默把它恢复成 `active`。Goal 对主行为的
控制保持到 resume、replace、cancel 或 complete；不满足前置条件的输入应得到明确引导，而不是无限期排队。

## 10. Token budget

### 10.1 权限与语义

- budget 是 Goal 累计总预算，不是“从现在起再增加 N”；
- 只有用户显式命令或明确 system/developer 创建要求可以设置预算；
- 模型不能通过 `UpdateGoal` 修改预算；
- replace 和 resume 使用用户参数修改预算；
- `tokens_used` 不因 replace、pause 或 resume 清零；
- 新建 Goal 覆盖 complete Goal 时从零开始统计。

### 10.2 结算边界

插件只累计 Provider 返回的 canonical input/output usage，不用本地上下文估算替代缺失用量。每个完整 Goal turn 的
消息帧和工具结果结算后，按稳定 usage identity 幂等累加。

结算顺序：

```text
1. 完成当前 Goal turn 的模型响应和工具帧
2. 结算本 turn Token
3. 若 Goal 已 complete 或 blocked，保留该状态
4. 若 Goal 仍 active 且 tokens_used >= token_budget，设为 budget_exhausted
5. budget_exhausted 时不创建新的 Goal turn
```

预算是 turn 间软边界。单次请求的最终用量无法提前精确知道，因此 `tokens_used` 可以超过 `token_budget`；不得为追求
精确上限而截断流式响应、工具参数或工具结果。

### 10.3 budget_exhausted

进入该状态时：

- Runtime 生成包含预算、实际用量和停止原因的 report；
- 保留 Goal、Token 和最后一个完整消息帧；
- 不自动继续，也不允许普通输入启动新的模型执行；
- `/goal status`、带有效新预算的 resume/replace，以及 cancel 仍可用。

恢复必须满足：

```text
new_token_budget > tokens_used
```

或显式设为 `unlimited`。恢复后生成新 activation，并开始新的 Goal turn。

### 10.4 complete 后的最终用量

`UpdateGoal(complete)` 只改变状态并保存 report，不删除 Goal。当前 Goal turn 终结时继续结算最后一轮 Token，然后停止
自动继续。`last_accounted_usage_id` 防止恢复重放造成重复累加。

只有最后一轮结算完成后，新的 Goal 才可以覆盖该 complete record。这样不需要 pending-completion、tombstone 或 Goal
历史表，也不会丢失最后一轮用量。

## 11. blocked 的行为规则

“同一阻碍连续出现至少三次”由模型根据当前上下文中的错误、工具结果、已尝试方案和恢复消息自行判断。

插件不实现：

- 错误字符串归一化；
- 相似度比较；
- blocker hash；
- 连续阻塞计数器；
- 对模型 report 的语义裁决。

因此三次规则是模型行为约束，不是 Host 强一致性不变量。插件只检查：

- 当前 Goal 为 `active`；
- 调用来自当前 activation；
- status 为 `complete | blocked`；
- report 非空。

从 blocked 恢复时，`goal-resumed` 脚手架明确说明旧计数已经结束，应从新的初始尝试开始判断。Compaction 必须保留或
概括足以理解近期错误与尝试的信息，但不因此新增结构化 blocker 状态机。

## 12. 最小 Host 改良

Goal plugin 只要求三个通用改良。

### 12.1 SessionInputBatch

增加一个有序、不可拆分的输入单元：

```python
SessionInputBatch(
    inputs: tuple[SessionInput, ...],
    coalesce_key: str | None = None,
)
```

不变量：

- `inputs` 非空；
- 同一批次使用相同 delivery mode；
- 整批校验、整批入队或整批拒绝；
- 顺序持久化，消费时不能拆分或与其他消息交错；
- `one_by_one` 以一个 batch 为一个消费单位；
- `all_at_once` 可以消费多个完整兼容单位，但不能拆开 batch；
- 整批进入同一 Run 或同一安全 turn 边界；
- 进程恢复后仍保持批次 identity、顺序和 exact-once 消费；
- 单条 `SessionInput` 的现有行为不变。

队列内部只需稳定 `batch_id` 和组内顺序，不增加批次状态机、优先级、依赖关系或嵌套批次。

### 12.2 role、provenance 与 semantic tag 正交

`SessionInput` 增加可选 `semantic_tag`，并允许 `role=user` 消息携带合法标签。模型投影使用统一 semantic envelope renderer，
因此标签对模型可见，但不改变消息 role。

安全不变量：

- role 不证明消息由真人产生；
- producer/provenance 不因 role 改变；
- user-role 脚手架可以投影当前明确用户命令，也可以在已有 Goal 授权范围内表达自动继续；两者都保留插件来源；
- `role=user` 本身不构成创建 Goal、修改预算或扩大目标范围的授权；
- 标签只能描述语义，不能提升权限或伪造 system/developer role；
- 普通用户原文不因为和脚手架同批就自动获得脚手架标签。

### 12.3 未消费控制投影的最小 coalescing

批次可选携带 owner-scoped `coalesce_key`。同一 Session、owner、delivery boundary 下，新批次可以原子替换具有同 key 且
尚未消费的旧批次。已经成为 canonical message 的批次不可撤回。

该能力只解决“最终状态投影替换尚未消费的旧投影”，不增加任意消息搜索、重排、优先级或跨 owner 撤回。

## 13. 持久化与恢复不变量

- Goal record 和内部控制元数据仍使用 owner-bound Session extension state；
- branch/export/trash 不得把 Goal state 与其 canonical 脚手架投影分离；
- create、replace、resume 旋转 activation 后，旧工具调用永远不能命中新 activation；
- usage 结算按稳定 identity 幂等；
- complete record 在最后 usage 落盘前不可被新 Goal 覆盖；
- queued input batch 必须整批 durable 或整批不存在；
- coalescing 必须在同一 Session mutation 中选择旧批次并写入新批次；
- 恢复只依据 canonical Session、Run、queue、extension state 和 usage 事实，不依据内存定时器；
- Goal 插件关闭或状态损坏时 fail closed，不自动创建新 Goal 或继续未知工作。

## 14. 验收范围

### 14.1 Host

- 空闲 Session 提交两条输入的 batch，只启动一次执行并保持顺序；
- active Run 中提交 batch，只在合法边界整批消费；
- `one_by_one` 不拆 batch；
- 入队失败不留下半个 batch；
- crash/recovery 不重复或丢失组内消息；
- user-role semantic tag 进入模型可见 envelope，同时保留 plugin provenance；
- 相同 coalesce key 的未消费控制批次只保留最后一个；
- 不同 owner 或已经消费的批次不能互相覆盖。

### 14.2 Goal lifecycle

- 创建请求按 `goal-create` 脚手架、原始 objective 的顺序进入同一次执行；
- 三个工具共享统一 Goal wrapper；
- complete Goal 可读取且包含最后一轮 Token；
- complete 后创建新 Goal 会覆盖并重置统计；
- replace 直接编辑 Goal，不调用 `CreateGoal`，保留 `tokens_used`；
- replace 省略预算时保留预算，显式参数修改或清除预算；
- 无效预算使整个 replace/resume 失败且不产生脚手架；
- pause、resume、replace、cancel 严格执行状态前置条件；
- 同一 turn 的抵消命令只留下最终脚手架；
- 旧 activation 的 `UpdateGoal` 无法完成或阻塞新 objective；
- `UpdateGoal` 只能写 complete/blocked，且 report 必填；
- 插件不维护三次阻塞计数器；恢复 blocked 后脚手架声明重新审查；
- budget overshoot 只在完整 turn 后结算，不产生下一 Goal turn；
- budget_exhausted 拒绝普通执行，只允许 status、有效预算恢复/替换或 cancel；
- resume 旋转 activation，Token accounting 不重复。

### 14.3 模型可见文本

- 工具名称、参数、描述和错误只使用 objective、status、budget、usage、attempt、report 等通用概念；
- 不向模型解释 Session Controller、Run binding、activation revision、continuation policy、plugin generation、Host transaction；
- 脚手架可以说明“当前目标”“下一次尝试”“用户已暂停/恢复/更新”，但不泄漏框架实现；
- usage 与时间由工具结果提供，提示模型不得猜测。
