# 数据升级

> 文档类型：现行契约

## 目标和责任边界

`ouro-upgrade` 在指定的、已经停写的 home 内，将明确支持的历史核心数据升级为本机 OURO 的当前格式。
数据保留原位置，Session 与任务后端保持原选择。工具随 `ouro-agent` 发行，可用
`python -m ouro_upgrade` 调用；操作说明见[数据升级指南](../guides/data-upgrade.md)。

支持范围由实际数据契约和固定历史夹具确定，不能仅凭应用版本判断。工具不启动 Runtime、插件、模型、
认证刷新或任务调度；不修复损坏、不推测执行结果、不保证旧 Run 能恢复执行，也不处理插件私有数据升级。
正常 OURO reader 继续只接受当前格式，历史转换集中在独立的 `ouro_upgrade` 包。

升级成功表示所选后端已识别的历史格式完成转换，转换结果符合当前契约；当前格式记录保留原样。
升级不承担全库健康审计，不承诺发现既有数据损坏、缺失附件或历史引用错误。回收站、维护备份、未选后端、其他配置、凭据、
插件包及插件私有文件保留原样，并在结果的 `preserved_outside_scope` 中列出；它们不属于升级可用性保证。
尤其不能直接将旧回收站内容恢复到在线数据中并假定它已升级。归档但仍保存在在线 Session 存储中的会话
按普通 Session 处理。

## 支持矩阵

固定历史写入基线为 `96ebb7e`，包版本 `0.1.0`；ContextSnapshot 3 夹具由 `aa94cc5` 的模型序列化；
reasoning 配置夹具由 `v0.3.0`（`54757d7`）的配置 writer 生成。
夹具和来源说明位于
[tests/upgrade/fixtures](../../tests/upgrade/fixtures/README.md)。以下数据契约可组合升级，是否需要转换由实际记录版本确定：

| 容器 / 记录 | 接受的源格式 | 当前格式与处理 |
|---|---|---|
| 文件 Session 容器 | layout 9 | 保持布局；必要时重建 `sessions/index.json` |
| SQLite Session 容器 | schema 7 | 更新在线表中的 JSON payload，重建受影响 catalog；保留行身份与序列 |
| Session / Event / Harness / Compaction / Delegation / Resource | 2 / 2 / 1 / 1 / 1 / 2 | 识别当前版本并保留数据；新增迁移步骤后按相同管线处理 |
| Run | 2、5 | 目标 5；源 2 绑定 `ouro.default/1`，implementation 为 null、dependencies 为空、checkpoint 为 null |
| Message | 3、4 | 目标 4；源 3 的工具结果补 model producer |
| ContextSnapshot | 3、4 | 目标由当前模型定义；源 3 的 supports_vision 转为 supports_image_input，音频、视频输入能力设为 false；转换 source_messages，为缺失来源的 injected tool result 补 model producer |
| SessionCommitResult | 1 | 转换 messages、Session、Event 及 truncation 中的 Message |
| 文件任务 / SQLite 任务 | 1、3 | 目标 3；迁移 agent target、owner、result 与 cancel 字段，保留历史链与防重标记 |
| 用量 SQLite / 用量记录 / 审计 | 1、2 | 目标 2；增加 plugin 归属，保留原 Run 归属，更新表结构及审计内嵌记录 |
| `config/providers.json` | providers.items 下的具名端点配置；supports_vision、reasoning.default_effort / profile.variants 或当前字段 | 转换端点能力与 reasoning 配置，维护模板绑定指纹；使用当前配置 codec 校验 |

Run 2 的工具批次和 invocation 同样补 model producer。任务的 description 成为 agent target 的 prompt，
workspace、model、reasoning、approval_mode、session_mode 移入该 target；execution 的 Session / Run
身份移入 agent target。源任务没有插件所有者，owner_id 明确为 null；result 为 null、cancel_requested 为 false。

用量记录增加 `plugin_id=null`。用量主表允许独立插件归属所需的空 Session / Run 列，但升级不制造插件用量。
当前有效记录与完整审计分别转换，不通过重放审计重新累计用量，因此 reset 和 replace 的历史语义保持不变。

未列出的历史布局、记录版本或中间版本明确拒绝。SQLite Session schema 1 不在支持范围。
版本不受支持、重复 JSON 键、非有限数字和不可解析数据不会作为成功产物写回。
严格模式中止本次升级；TUI 隔离模式将错误归入相应单元，继续处理其他单元。
需要转换的记录还会拒绝未知原生字段和缺失的必要事实；已经是当前格式的记录不重复执行完整模型校验。
不通过当前模型的默认值补造 ID、时间、revision 或执行状态。

版本化记录按记录类型和源版本登记唯一转换步骤，每步声明目标版本，最终目标从当前模型的 schema_version 读取。
执行器只沿已登记的前向步骤推进；支持 Run 2→5、任务 1→3 等明确验证的跨版本转换，不因此接受中间版本。
缺失步骤、停留原版本、版本倒退或越过当前模型版本均拒绝。增加格式版本时保留已有步骤，追加转换与合成历史夹具。
外层记录完成升级后，已知嵌套记录按自己的版本独立转换，再验证完整目标结构；外层版本已是当前版本也不能跳过嵌套转换。
版本识别沿显式声明的嵌套边界进行，目标版本从对应模型读取；不按应用版本或“当前无迁移步骤”的类型名单跳过数据。
全部版本均为当前版本且无已知结构转换时，直接返回原记录。需要转换时，顶层记录复制一次，嵌套转换使用该副本中的子记录，
最后对整个目标结构执行一次递归模型与必要事实校验。增加迁移步骤不需要维护另一份优化版本表。
转换只修改规则指定字段。ContextSnapshot 保留快照内容、身份、时间、metrics、metadata 与原 context_digest。
文件和 SQLite 后端共用记录转换，不在存储层或 TUI 中实现记录版本兼容。

提供方配置没有 schema_version，使用有序的结构转换步骤，每步仅处理明确识别的端点字段结构，全部步骤完成后由当前 codec 校验。
不推测应用版本，不为无版本数据编造持久化版本号；无法识别的结构由校验拒绝。旧能力字段必须为布尔值；同一端点混用新旧能力字段、
未知根、提供方或端点字段及无效默认提供方引用均拒绝。转换保留提供方与端点身份、默认选择、连接设置、凭据引用、headers、
模板绑定及开放 metadata，不解析或刷新凭据，不递归修改开放内容中的同名字段。
`reasoning.capability.default_effort` 合入 `default.effort`。保留默认启停行为：旧 `default` 已显式选择 effort 且
mode 为 default 时转为 enabled；仅有 default_effort 时不改变原 mode。两处旧 effort 同时存在且不同，无法在单一默认值中
无损表达，明确拒绝转换。`profile.variants` 原样移到 `profile.effort`，补空 `supported_summaries` 与 `profile.summary`。
原生片段中的摘要参数及自定义内容保持原值，不从这些不透明片段推断独立摘要能力，不自动启用新的摘要请求。
同一 reasoning 对象混用历史字段与当前字段时拒绝转换；提供方配置 reader 识别旧字段后报告需要升级，不忽略旧字段。

提供方端点与保存的 v0.3.0 规范化指纹一致时，更新绑定指纹。原本已修改的内容保留旧基线，继续受用户修改保护。
不根据当前内置模板猜测旧基线，不修改模板 revision、来源、启用状态或其他覆盖信息。
配置与核心数据使用同一暂存、备份和恢复事务；当前格式不改写。其他配置文件仍在升级范围外。
`provider-templates.json` 由模板目录自身处理：加载旧结构时备份原文件并创建当前版本模板，不参与离线升级事务。

## 转换不变量

- 转换基于原始 JSON，只修改显式规则指定的字段。当前模型用于严格校验，不能通过模型重新序列化丢掉源字段。
- metadata、工具参数、提供方 opaque blocks、提交 output、插件 payload 等开放内容按 JSON 值保留；
  不递归搜索其中的 `schema_version`，不加载插件解释其内容。
- 保留 Session / Run / Message / Task / Execution 身份、历史时间、revision、顺序、状态、金额、token 和日程。
  `request_digest`、`context_digest` 等历史摘要保持原值，不重算旧请求。
- 不遍历附件内容、任务防重文件或执行历史链来审计已有数据，不重复校验整库消息顺序、引用和查询投影。
  转换保留这些关系所依赖的事实；SQLite 修改行仍检查 payload 与行身份一致，变更后的数据库检查完整性与外键。
- 未变化的文件不改写。仅在投影输入或单元可用性变化时重建 Session / Task catalog；Context、操作回执或审计记录的转换不触发无关目录重建。
  资源描述记录按自己的版本转换并保存，附件本体保持原位。Event journal 发生转换时移除其派生字节偏移索引，由正常 reader 重建；
  未变 journal 的索引保留原样。
- 已是当前格式时不建立备份或报告，不再次改写业务文件。检查工作区和工具锁不属于业务数据。

## 失败隔离与删除粒度

转换单元按数据所有权和版本解释边界划分，不依据应用版本或某份测试数据。TUI 使用隔离模式，
单元失败时丢弃该单元的暂存变更，保留原数据并继续处理；成功单元统一进入可恢复的发布过程。
命令行和 Python 接口默认使用严格模式，任一转换错误均在发布前终止。

| 数据 | 隔离与删除单元 | 边界依据 |
|---|---|---|
| 文件会话 | 单个会话目录 | Session、消息、运行、上下文、回执、委派及附件共同组成会话；不删除其中一条历史记录来拼凑可用状态 |
| SQLite 会话 | 单个会话及其所属行 | payload 有独立版本；私有副本中的 savepoint 撤销失败会话的转换，其他会话可继续升级 |
| 文件任务 | 单个任务目录 | 任务、执行历史与防重标记共同组成任务；各记录携带版本 |
| SQLite 任务 | 所选任务数据库及其 SQLite 辅助文件 | payload 没有独立版本，整库版本决定解释方式，不能混存未转换的旧任务与当前任务 |
| 提供方配置 | `config/providers.json` | 提供方、端点与默认选择组成同一配置注册表；凭据文件不属于该单元 |
| 用量 | `billing/usage.sqlite3` 及其 SQLite 辅助文件 | 有效投影与 reset / replace 审计共同维护账本语义，不按单条账单删除 |

SQLite 会话按归属键读取记录；源结构中缺少归属索引的 compactions 表只在私有副本上建立临时索引，发布前移除，避免逐会话反复全表扫描。
SQLite 会话清理显式删除该会话拥有的所有表行及目录投影；委派记录归 root Session 所有。
引用其他会话、任务或历史 Run 不转移这些数据的所有权，不做级联的跨会话、跨任务删除。
SQLite 会话独占的附件目录随会话删除；同目录存在文件后端 Session 记录时保留目录，避免删除未选后端。
文件会话目录保留失败会话的不可读提示；任务目录只发布可用任务，失败任务原始记录在确认前仍保留。

布局或数据库结构无法解释时，错误归属于整个所选存储域，其他域仍可处理。无法确定删除边界的共享结构错误，
以及未完成的源事务，不提供删除操作。权限、锁、磁盘 I/O、源数据变化和发布故障是维护失败，
不能作为用户数据损坏的证据，也不会触发删除兜底。

删除仅接受界面中已明确确认的失败单元集合。引擎在新一次独占维护中重新检查数据：仍失败且在确认集合内的
可删除单元才进入删除计划；已经修复的单元正常保留或升级，新发现的失败仍需确认。
删除与派生目录维护使用同一个发布清单；成功的原始数据和删除数据都保留在本次备份中。
删除没有全 home 兜底，不清理凭据、插件、其他配置、回收站或既有备份。

## 原地升级与故障恢复

```mermaid
flowchart LR
    A[识别需要转换的记录] --> B[转换校验并暂存]
    B --> C[同步产物与原文件]
    C --> D[持久化清单和升级中标记]
    D --> E[原文件移入备份并安装产物]
    E --> F[保存报告并解除标记]
```

1. `--home` 必须是已有的普通目录。用户负责停止所有写入者，包括旧 OURO 和外部脚本。
   当前标准 CLI/TUI 在访问 home 的完整生命周期内持有 `.upgrade/lock` 的 OS 共享锁，维护操作使用同文件的
   独占锁，禁止同时访问。嵌入式应用、直接调用 Store、旧版程序和外部脚本仍受停写前提约束。
2. 检查所选数据域。遇到 Session `commit.json`、任务 `transaction.json`、Session 创建 / 导入 / 回收发布
   中间态时拒绝处理相应边界，要求使用原版本完成正常恢复后再升级；home 级发布中间态阻止整次维护。
3. 在受限 `.upgrade/<id>/scratch` 中生成并验证产物，修改集合的产物保存在 `new/`。
   JSON 产物从序列化字节直接写入 `new/`，在同一次打开中写入并同步；JSONL 和数据库产物由工作区接管关闭后的暂存文件，
   在计算产物摘要的同一次打开中同步并移入 `new/`，不另行复制。
   JSONL 逐行处理，数据库按游标批次转换；
   `--check` 的暂存产物无需持久化。管线不复制整个 home 或附件，不构建版本路径搜索或任务工作流引擎。
4. 为修改集合生成 `before/` 与 `manifest.json`。清单记录相对路径、原来是否存在、前后 SHA-256 和文件模式。
   删除完整目录时还记录目录类型，摘要覆盖目录结构及所有文件内容；确认删除前才读取这些附件。
   清单以序号定位材料，产物已在暂存时完成同步。对待替换、删除的原文件复核读取时的摘要，并在同一打开的文件上同步内容。
   新增路径必须仍不存在。只复核修改集合，发生源变化则停止；`--check` 不进行发布准备、同步或再次读取源文件。
5. 清单、产物、原文件内容及相关目录持久化后写入 `.upgrade/in-progress.json`，此后才可修改业务路径。
   标准 CLI、TUI 入口和本地应用装配在初始化前检查该标记，存在时禁止 Runtime 使用此 home；
   TUI 进入独立恢复界面。入口保护不依赖升级包。
6. 每个原文件重命名到 `before/<序号>`，收紧备份权限并同步相关目录，再将暂存产物重命名到业务路径。
   删除操作只保留移入备份的原文件；新增操作直接安装产物。两次重命名之间业务路径可能暂时不存在，整个阶段受恢复标记和独占锁保护。
   重命名保留已同步文件的内容，无需再复制或读取产物作即时摘要验证。保存 `.upgrade/receipts/<id>.json` 后解除标记。
   工作区与待替换文件须位于同一文件系统；Windows 发布准备需要原文件的写访问权限以执行文件同步。
   成功保留备份和清单，删除本次暂存产物；是否清理备份由用户决定。

多个文件的替换不构成 home 级原子事务。标记前失败不改变业务数据；标记后失败保留标记和恢复材料，
该 home 必须先执行 `--restore`。写入清单格式 3，恢复同时接受格式 1、2。格式 2 支持文件替换，格式 3 还支持完整目录删除。后两者中，已移动的原文件位于 `before/`，尚未移动的原文件仍在业务路径；
恢复在任何业务写入前核对整个修改集合的原始摘要。备份存在时必须验证备份，不能用业务路径掩盖损坏；备份尚不存在时，
只有业务路径内容仍与原始摘要一致才可作为未移动的原文件保留。清单格式 1 要求所有原文件备份齐全，并使用同一恢复流程。
核对通过后恢复整个修改集合，删除原来不存在的
新增文件，复核后解除标记。恢复可以在中断后重复执行，不消耗原备份；不逐步骤续跑，也不从半升级数据重新规划。
恢复仅适用于尚有标记的未完成维护，不提供成功后又产生新写入的自动降级。
删除中断的恢复只还原该次操作，之前已发布的成功升级不回退。目录恢复使用保留的完整备份，复制中断后可再次执行。

SQLite 原数据库从不由升级器打开。主库及存在的 WAL / journal 先复制到工作区，由 SQLite 在副本上恢复；
SHM 在副本上重建。发生转换的目标库经过一次 integrity / foreign-key 检查、checkpoint、关闭连接后才写回，原 WAL、SHM、
journal 与主库作为同一个修改集合备份和恢复。自定义 trigger / view 不在支持范围，不执行其副作用。
私有 SQLite 副本使用 `synchronous=OFF`，其文件持久化由工作区接管产物时完成；不修改原数据库的连接设置。

`.upgrade` 在写入数据前收紧为当前用户权限，Windows 使用 ACL；待处理路径拒绝符号链接、reparse point
及文件硬链接。业务替换文件同样使用受限权限，POSIX 保留原模式。文件 fsync，POSIX 同步目录；
不承诺超出操作系统和文件系统能力的断电原子性。诊断只包含位置、契约和错误类别，不输出原始记录或模型验证输入。

## 处理成本与验证边界

识别成本由所选后端的记录数与数据量决定，转换成本由实际需要升级的记录决定。
必须读取版本化记录来发现混合版本和不受支持的版本，不能因当前迁移表没有某类记录的步骤而跳过整个类型。
大 JSONL 按行处理，识别期间同时计算摘要；未变化的行保留原始字节。正常转换不读取、不复制附件。
单个 JSON 记录的读取同时计算源摘要，避免为获取摘要重复打开文件。
独立记录文件由工作区持有的四个读取线程有界预取，按原遍历顺序交付；线程只读取文件，源摘要登记、转换、暂存及发布均由调用线程串行执行。
工作区退出时取消未开始的读取并等待运行中的读取结束，再清理暂存目录和释放 home 锁，不让后台读取越过本次升级的生命周期。
派生会话目录只需要 Session、最新 Run、末条消息及计数；历史消息按记录版本决定是否转换，不额外执行关系审计。
用于构建目录的少量头记录仍需模型解析和必要事实校验，防止由默认值补造身份、时间或状态后写入派生数据。

持久化成本与修改集合成正比：发布前同步产物和原文件，备份与安装使用同一文件系统上的重命名。
`--check` 和当前格式扫描不进入该持久化阶段。暂存区由当前升级独占，已写入并同步的产物不重复做摘要遍历；
跨执行保留的恢复材料仍必须在恢复前完整验证。停写要求与独占锁是并发前提，摘要复核不替代对旧程序和外部脚本的停写。

可用 `dev/benchmarks/data_upgrade.py` 测量合成历史记录或显式指定 home 的临时副本，记录分阶段时间、变更数与 Python 文件同步次数。
基准不包含复制输入与导入成本，不将固定耗时作为正确性测试；运行方式见[性能测量](../../dev/benchmarks/README.md)。

## 模块和接口

| 模块 | 职责 |
|---|---|
| `ouro_upgrade/cli.py` | 参数与结果输出；`--check` / `--restore` 互斥 |
| `engine.py` | 编排所选后端、报告、有限支持边界 |
| `records.py` | 无 I/O 的版本识别、显式历史转换、转换结果验证 |
| `steps.py` | 记录版本的前向迁移执行；检查明确目标、缺失步骤和非法推进 |
| `configuration.py` | 提供方的明确历史字段转换、绑定指纹维护、当前配置校验与暂存 |
| `files.py` | 文件记录与 JSONL 转换、受影响派生索引维护 |
| `databases.py` | 私有 SQLite 副本的 schema / payload 转换 |
| `workspace.py` | 工具锁、路径检查、暂存、备份、写回、未完成升级恢复 |
| `progress.py` | 与 UI 无关的阶段和计数通知 |
| `units.py` | 逻辑单元、数据失败收集、局部暂存 / savepoint 回滚与已确认删除 |
| `ouro/tui/recovery.py` | 离线恢复界面、进度展示和危险确认 |

`upgrade(home, check=False, restore=False, session_backend=None, task_backend=None, progress=None, isolate_failures=False, discard=frozenset())`
提供同等 Python 接口。可选 `progress` 回调同步接收 `UpgradeProgress(phase, completed, total)`；
计数只代表当前阶段，不推算整体百分比。会话及文件任务识别分别按会话数、任务数报告；产物准备、源数据复核和发布均按修改集合项数报告，完整目录删除计为一项。
产物写入与同步计入所属数据域的转换阶段；`prepare` 表示清单与目录准备，`verify_source` 表示原文件复核与同步，
`publish` 包含备份移动与产物安装，`finalize` 表示报告与清理；
恢复使用 `verify` 与 `restore`。引擎不依赖 Textual、Runtime 或具体调度器。
后端选择遵循 OURO 的命令行优先、环境变量次之、默认 files 的规则。
`--check` 对业务数据只读，但仍需要工作区写权限和暂存空间。结果状态为 `upgrade_required`、`current`、
`upgraded` 或 `restored`；严格模式失败返回非零。隔离模式用 `partial` 表示仍有失败单元，
`failures` 列出单元类型、身份、安全诊断与是否允许删除，`discarded` 列出本次实际删除单元。
`discard` 只接受 `UpgradeUnit` 集合，要求启用隔离模式且不能与 check / restore 混用。
报告列出修改项、所选后端、备份与清单位置及明确保留在范围外的内容。

## TUI 启动恢复

正常 reader 用 `UnsupportedDataVersionError` 区分版本不符与一般持久化失败。TUI 的启动和显式恢复会话过程中，
数据版本错误会结束当前 Host，待服务关闭、共享访问锁释放后，进入不创建 Runtime 的恢复 App。
恢复 App 在后台线程调用同一升级引擎，成功后启动新的 Host 并返回主页，保留原 home 和后端选择。
一次启动最多自动尝试一次升级；再次失败只显示恢复选项。读取器将已识别的旧提供方能力结构标记为
UnsupportedConfigVersionError，同时属于配置错误和数据版本错误，因此可进入相同升级流程。
普通配置错误不触发升级，正常启动不扫描全量历史数据。

恢复界面复用 `ChoiceScreen`、`ConfirmationScreen` 和共享菜单样式，采用同主题背景上的居中无边框布局，
不叠加遮罩。工作线程仅更新最新进度，UI 每 100 ms 合并读取，避免大量文件导致消息队列积压；
现有 loading 行直接使用当前主题的 `spinner_frames` 和 `spinner_interval_seconds`，不覆盖动画定义。
处理中禁止菜单退出，外部关闭时也等待线程结束后才释放生命周期。

部分失败时显示已保存成功升级的说明、失败范围和原因，提供重试、删除可安全归属的失败单元、退出。
默认选中退出；删除确认展示完整 home 与具体单元，默认选中取消。确认后只处理仍然失败且已确认的范围。
存在未完成发布时只允许恢复该次操作并重试，或退出；既有成功升级不回退。未知启动故障不会直接产生删除范围。
旧的全量 reset 中断标记继续阻止 Runtime 使用数据，界面提示人工恢复，不提供全量删除入口。

针对性验收覆盖历史 writer 夹具、当前 reader、TUI 启动、嵌套内容与摘要、幂等、未知输入拒绝、WAL、
混合成功 / 失败单元、局部回滚、确认前修复或新增失败、精确清理、删除和恢复中断、备份损坏、
进度响应、确认取消以及正常 Host 与维护互斥。
支持范围按该证据维护；未运行插件、外部执行环境与跨平台实机行为不在夹具保证内。
