# OURO TUI 架构与性能审查报告

- 审查日期：2026-08-29
- 审查范围：`ouro/tui` 的控制器边界、事件归约、会话恢复、历史渲染、流式渲染、命令补全、子智能体导航、配置持久化与内联编辑器
- 约束：不改变现有视觉、交互、命令和持久化语义；遵循 `docs/OURO_AGENT_编码准则_ZH.md`；只处理已确认的热路径

## 一、结论

TUI 的主体架构不需要重写。当前实现已经具备几项正确的基础设计：运行时事件是规范事实源；控制器隔离应用层；UI 事件缓冲有 1000 条硬上限并能在落后时回读持久化快照；会话投影可从事件恢复；历史区使用有界控件树和行缓冲；最近会话渲染缓存限制为 3 份。

本轮问题主要不是缺少新的架构层，而是若干高频边界仍在重复执行不变工作，以及部分 CPU/磁盘操作仍占用 Textual 事件循环。优化后保留原有分层，只收紧以下契约：

1. 相同状态不得重复触发 Rich 内容构造、Textual 更新或布局；
2. 长历史的纯计算和持久化 I/O 不得占用 UI 事件循环；
3. 冷加载按块发布尺寸，而不是按每个渲染片段发布；
4. 命令补全只计算当前正在编辑的命令参数；
5. 已有规范顺序的数据不再无条件排序；
6. 长文本视口计算必须保持线性复杂度。

## 二、架构审查

### 2.1 保留的正确边界

- `TuiController` 继续作为应用服务与 Textual 之间的适配边界，UI 不直接承担业务恢复逻辑。
- `TuiSessionProjection` 继续以规范事件重建运行中状态，没有引入第二套状态来源。
- `OuroTuiApp` 继续负责表面协调、帧级事件消费和导航排他性，没有把业务规则下沉到控件。
- `ConversationView` 负责会话呈现编排，`ConversationHistory` 负责有界控件树和 Rich 行缓冲，职责保持单一。
- 工具、思考、正文、运行摘要与压缩摘要的顺序仍由明确的消息边界决定，没有使用依赖当前 DOM 的隐式判别。

### 2.2 未采用的高风险改造

- 没有继续合并或丢弃规范事件。现有缓冲上限为 1000，落后时已有持久化重载路径；进一步做语义事件合并会扩大正确性风险，而直接归约 10000 条事件的诊断测量约为 52 ms，不足以证明需要改变事件契约。
- 没有在控件层伪造历史分页。真正分页需要存储查询、前插滚动补偿和内存窗口形成完整契约；只隐藏已经全量读取的数据不能解决底层成本。
- 没有引入通用缓存框架、观察者层或新的抽象基类。现有局部状态比较即可消除重复工作。

## 三、发现与改进

| 优先级 | 发现 | 原复杂度/影响 | 改进 |
|---|---|---|---|
| P1 | 每个运行时帧重复刷新活动栏、上下文、占位符和子智能体面板 | 状态不变仍构造 Rich 文本并触发布局；子智能体面板一帧可刷新两次 | 各呈现组件增加等值短路；根状态实际改变时才同步导航树 |
| P1 | 长历史投影、会话事件恢复和活动尾部恢复占用 UI 线程 | 数百条 Markdown 消息会形成可感知卡顿 | 会话投影在工作线程准备；历史达到 64 个结构项或 64 KiB 文本后在工作线程投影，小输入保留同步快路径 |
| P1 | 偏好设置原子写入和事件祖先 Session 查询在 UI/事件回调线程执行 | 慢磁盘会阻塞输入、动画或事件接收 | 通过明确的异步边界移入工作线程，错误语义保持不变 |
| P1 | 内联编辑器为每次候选窗口移动重复计算字符串切片宽度 | 长值最坏接近 O(n²) | 一次构建字符单元格前缀偏移，后续窗口宽度 O(1)，整体 O(n) |
| P2 | 冷历史加载为每个 Rich 片段更新 `virtual_size` | 一批 50 项产生多次尺寸通知和布局失效 | 每个加载块只发布一次尺寸，实时追加仍立即发布 |
| P2 | 思考/正文尾部每个分片都请求布局 | 同一视觉行内追加也使布局失效 | 内容仍立即刷新；只有宽度或可见行数变化时请求布局 |
| P2 | 命令目录每次按键都计算工作区、历史消息、模型、技能和队列参数 | 与当前命令无关的全量遍历；用户历史曾被扫描两次 | 只构造当前已进入参数阶段的内建命令选项；`/fork` 与 `/navigate` 共享一次用户消息投影 |
| P2 | 插件重名统计对每项再次扫描完整目录 | O(P²) | 使用一次 `Counter` 归约为 O(P) |
| P2 | MCP 与插件状态分别多次过滤、计数 | 多次 O(n) 遍历 | 单次遍历同时完成计数和名称收集 |
| P2 | 已按序事件仍无条件排序；历史条目先构造排序元组再排序 | O(E log E) 和额外中间列表 | 线性检测规范顺序，仅在发现逆序时排序；历史按消息边界直接分桶 |
| P2 | 相同工具、智能体、思考展开状态仍重复重绘 | 高频状态投影放大 Rich 渲染 | 不变模型直接返回，动画计时器仍独立维持既定帧率 |

## 四、关键行为不变量

本轮没有修改 CSS、颜色、间距、文案、快捷键、命令名称、参数匹配、滚动语义或消息排序。以下行为由现有测试和新增回归共同保护：

- 流式正文与思考内容完整，思考计时仍按 10 Hz 更新；
- 同一视觉行内追加不请求布局，跨行时仍立即请求；
- 历史顺序保持“消息内容 → 运行摘要 → 压缩摘要”；
- 子智能体导航选择、根节点状态和最近十个节点的呈现不变；
- 小型历史加载保持确定性，大型历史投影不阻塞事件循环；
- 偏好写入和事件祖先查询不阻塞事件循环；
- 中英文宽字符的编辑光标始终位于原有单行视口内；
- 无序恢复事件仍按 `(sequence, event_id)` 规范化。

## 五、诊断性性能测量

以下结果来自 Windows 本机、当前依赖环境下的隔离微基准，只用于验证复杂度方向，不作为跨机器 SLA。

| 场景 | 原路径 | 优化路径 | 结果 |
|---|---:|---:|---:|
| 4000 个中文字符，光标位于末尾，宽 60 单元格 | 1687.101 ms | 2.764 ms | 前缀宽度表消除重复切片扫描 |
| 1000 个插件命令的重名统计 | 50.968 ms | 0.083 ms | O(P²) 降为 O(P) |
| 3000 个插件命令的重名统计 | 446.281 ms | 0.240 ms | 规模增长保持近线性 |
| 10000 个已排序事件 | 2.904 ms | 2.155 ms | 避免无条件 TimSort 和结果复制 |
| 512 条、每条约 1 KiB 的历史投影 | UI 线程约 53.925 ms | 同等计算移入工作线程 | UI 不再承受超过一帧的连续 CPU 占用 |

帧级等值短路和分块尺寸发布使用调用次数回归测试验证：相同运行时快照不会再次触发活动栏、上下文、子智能体面板或占位符渲染；120 条冷历史只按加载块同步尺寸。

## 六、剩余边界

1. 会话快照仍从存储层一次读取完整消息集合。CPU 投影已移出 UI 线程，历史控件树也已保持有界，但读取时间和内存仍随会话总长度线性增长。若真实会话达到数千轮，应在 Session 查询层实施游标分页，而不是继续修改控件。
2. Rich Markdown 的最终解析成本仍与文本总量相关。当前通过完成块冻结、纯文本活动尾部和后台历史投影控制 UI 卡顿；只有真实遥测证明仍是主瓶颈时，才值得增加块级解析缓存。
3. 会话恢复仍需线性检查事件是否规范有序。这是避免错误信任外部顺序的必要 O(E) 校验；只有存储接口正式声明并验证顺序后才能安全移除。
4. 当前没有加入常驻性能日志，避免把诊断本身变成热路径。需要持续观测时，应只采样批次耗时、队列峰值、历史条目数和首屏时间，不记录用户内容。
