## 一、结论

OURO 1.0 的分层、状态恢复、事件顺序和 Host/Runtime 边界总体健康，不需要重写框架。近期 TUI 优化也确实有效：流式文本已经按原生显示帧批量消费，历史消息由单个 `RichLog`/strip 缓冲承载，问题重心已经从“终端每 token 重绘”转移到 Runtime 热路径。

原始审查确认的主要问题不是某个慢函数，而是四条违反比例原则的成本链。经过两个实施里程碑后，前两条主路径已
治理，第三、四条中的结构性扩展问题仍保留为后续项目：

1. **Provider 碎片放大（已治理）。** 普通 delta 已按固定 8 ms/16 KiB 语义边界合并，结构事件仍即时。
2. **同步持久化占用 asyncio 编排线程（已治理会话主链与工具/终态可达残留）。** 完整 mutation/投影操作已移入
   worker，取消期间先等待所拥有的同步操作 settle；没有引入跨 Session 的全局单线程串行器。
3. **Compaction 未缩短全部本地成本（部分治理）。** 摘要选块已由 Θ(N²) 线性化；covered history 的加载、lineage
   digest 与 tail-first 读取仍是长会话扩展项。
4. **派生投影和静态数据全量重写（部分治理）。** 草稿防抖、工具结果批提交已完成；文件 catalog、上下文 completion
   全量重写和静态 generation 重复序列化仍存在。

按“收益 ÷ 风险”排序，原建议及当前状态为：

1. 在 Provider/事件边界对相邻 text/reasoning delta 做有界时间与大小合并（已完成；Store 多事件批追加按收益后置）；
2. 把完整同步操作/事务闭包移到 worker，而不是零散地给事务内 store 调用套 `to_thread`（会话主链已完成）；
3. 把摘要分块改为线性算法（已完成），并让已验证 compaction 在一个 Run 内复用验证结果（待实施）；
4. 对输入草稿做 250–500 ms 尾随防抖（已按 300 ms 完成）；
5. 消除上下文快照的全量二次物化和完成态全量重写；
6. 降低 disposable catalog 的刷新频率，再依据实测决定是否改变文件表示。

## 二、第一性原理与性能不变量

性能改良应维护以下不变量，而不是在具体慢点上堆补丁：

| 原理 | OURO 中应有的含义 |
|---|---|
| 领域事实不等于传输碎片 | 文本拼接结果、reasoning 顺序和结构事件边界是语义；SSE 一次吐几个字符不是语义 |
| 事件循环只负责编排 | 会阻塞的文件锁、fsync、SQLite busy wait、全历史序列化和大文件 hash 不应运行在 loop 线程 |
| 持久化频率由恢复边界决定 | 需要区分“崩溃后必须恢复”的边界与“仅用于实时呈现”的增量，不能一律每碎片落盘或一律延迟 |
| 派生投影不应比规范事实更昂贵 | `sessions/index.json` 可重建，不应在每条消息后付出全量、强 fsync 的代价 |
| Compaction 必须降低所有后续历史成本 | 不仅减少模型 token，还应减少本地加载、校验、估算和物化成本 |
| 热路径工作量应与变化量成比例 | 一个 text delta 不应重复 dump 整个活动模型；一次上下文完成不应重写几 MB 不变内容 |
| 优化不能破坏恢复语义 | 两个 `save_run` 若代表不同 crash boundary，不能只为减少 I/O 机械合并 |

## 三、全生命周期链路

### 3.1 启动

`OuroTuiApp.on_mount()` 启动异步 worker；`TuiController.start()` 已把 `LocalApplication.build()` 放到工作线程（`ouro/tui/controller.py:456-476`）。MCP auto-start 是后台连接，Supervisor 启动不做全 Session 扫描，随后按顺序启动插件、Supervisor 和 Agent（`ouro/local_application.py:211-223`）。

总体评价：启动骨架正确。剩余首屏延迟主要来自被 await 的插件启动和 usage 汇总，而不是隐藏的 Session 全量恢复。usage 汇总虽在 `to_thread` 中执行，但输入面板仍要等待它完成（`ouro/tui/controller.py:486-495, 1776-1788`）。

### 3.2 Session 打开与观察

TUI 打开 Session 时把读取放入工作线程，但 `observation_snapshot()` 仍加载全部 messages、runs、compactions，再只读取 active Run 事件（`ouro/tui/controller.py:1940-1948, 2031-2046`；`ouro/sessions/local_files.py:526-545, 572-595`）。

总体评价：不会冻结 UI loop，但冷打开时间和内存仍为 O(历史总量)。需要注意，存储和 application 层已经有前向分页接口（`ouro/sessions/base.py:141-166`；`ouro/application/sessions.py:260-299`），因此问题不是“完全没有分页”，而是缺少适合首屏最近一页的反向/tail 契约，且 TUI 打开路径尚未使用分页。

### 3.3 Run 与模型轮次

每轮在上下文准备前通过 `_begin_model_round()` 保存控制器/续跑快照，上下文成功后由 `_commit_model_request()` 再保存一次请求计数。这两次写分别保护不同的恢复语义，不能机械合并。本次复审已让两个完整操作在 worker 上执行；全量 Run 中静态 extension generation 元数据的重复序列化仍未消除。

### 3.4 上下文准备

每轮会执行 context providers、加载 active compaction、投影消息、估算所有消息和工具、生成 digest，并保存完整 `ContextSnapshotRecord`。本次已把资源物化、上下文投影、digest/快照构造和保存作为完整操作移出 loop；Provider 发起请求时的再次 `provider_context()` 与完成时为少量字段全量重写快照仍存在，但已不再冻结 UI loop。

### 3.5 Provider 流与事件

Provider reader 保留 256 项有界 FIFO。原基线只合并“已经在队列中”的相邻 delta，慢于消费速度的分片仍逐个下行；
当前实现改为每段首分片即时、快速后续分片以最近发射时间为锚点在固定 8 ms 窗口/16 KiB 上限内合并，窗口不因新
分片续期，结构边界立即 flush。

每个分片随后被 InnerLoop await 持久化（`ouro/core/inner_loop.py:460-522, 611-680`），Recorder 在 per-Session `asyncio.Lock` 内 `to_thread(append_ordered_event)`，成功后才 fan-out（`ouro/application/events.py:262-298`）。顺序与“先持久化后发布”语义是正确的，粒度过细才是问题。

### 3.6 工具批次

工具执行有显式并发上限和错误隔离，设计正确。工具结果现已按 source order 一次 `append_messages()`、一次 Session 推进和一次 catalog refresh；阶段性 durable checkpoint 仍有多个，但每个完整 checkpoint 已移出 loop。剩余成本是恢复边界数量和文件 catalog 表示，不再是逐结果提交或 UI 事件循环冻结。

### 3.7 终态、观察与关闭

终态会保存 Run/Session、刷新 catalog、发送事件并结算观察者。完整 complete/fail/pause mutation 与 catalog refresh 已在 worker 上执行，事件仍在 durable transition 后按序发布。关闭顺序会先停止订阅和工作，再 drain 观察者、关闭插件/MCP，资源所有权清晰；无需重构生命周期。

## 四、实测结果

测试环境为当前 Windows 工作区和 `.venv` Python 3.14.6，使用临时本地目录；数据用于判断增长阶和相对放大，不应当作跨机器 SLA。

### 4.1 流式事件

相同总输出 1,000 字节，仅改变分片数：

| 后端 | 分片 | 每片字符 | 总耗时 | 事件吞吐 | 文件日志大小 |
|---|---:|---:|---:|---:|---:|
| files | 1,000 | 1 | 0.948 s | 约 1,056/s | 312,893 B |
| files | 100 | 10 | 0.096 s | 约 1,047/s | 32,092 B |
| files | 10 | 100 | 未单独计时 | — | 4,101 B |
| SQLite | 1,000 | 1 | 15.853 s | 约 63/s | — |
| SQLite | 100 | 10 | 1.317 s | 约 77/s | — |

结论：时间几乎由**事件数**而不是内容字节决定；1 字符事件的文件表示放大约 313 倍。SQLite 每 delta 新连接、`BEGIN IMMEDIATE`、`SELECT MAX(sequence)`、INSERT、COMMIT、close（`ouro/sessions/sqlite.py:510-520, 1301-1329`），在该环境下比 files 更敏感。

### 4.2 压缩分块

`LLMSummaryCompactionStrategy._next_chunk()` 在所有帧都能进入一个 chunk 时：

| 帧数 | 耗时 |
|---:|---:|
| 100 | 0.089 s |
| 200 | 0.348 s |
| 400 | 1.352 s |
| 800 | 5.341 s |

翻倍约四倍，确认 Θ(N²)。cProfile 下 400 帧产生约 3,080 万次函数调用、80,200 次 `model_visible_message()`，原因是每增加一帧都重新序列化整个 candidate（`ouro/application/compaction.py:404-449`）。

### 4.3 已压缩历史仍被全量校验

active compaction 将有效上下文压到 2 条消息时，单次 `project_compacted_messages()` 仍随原始历史线性增长：100/1,000/5,000 条分别约 0.7/5.0/23.8 ms。原因是每轮比较全部 covered IDs，并重新 dump/hash 全部 covered messages（`ouro/core/compaction.py:376-429`）。

### 4.4 文件 catalog

构造包含 N 个投影条目的 `index.json`，只刷新一个真实 Session：

| Session 数 | index 大小 | 单次刷新中位数 |
|---:|---:|---:|
| 10 | 9 KB | 69 ms |
| 1,000 | 916 KB | 73 ms |
| 5,000 | 4.58 MB | 133 ms |
| 10,000 | 9.17 MB | 238 ms |

固定成本中，`FileOwnerLock.acquire()` 单独中位约 21 ms，因为每次都写 owner 元数据并 fsync（`ouro/local_locks.py:21-56`）。`try_update()` 仍会 load、过滤、排序并重写整个 index（`ouro/sessions/local_index.py:82-100, 235-236`）。

### 4.5 上下文快照

不含工具 schema 的快照在 100/1,000/5,000 条、每条 200 字符时，files 单次保存约 5.2/11.8/40.1 ms；5,000 条文件约 4.56 MB。每轮准备与完成各写一次，意味着仅两次全量保存就约 80 ms，且当前直接运行在事件循环。

### 4.6 其他量化

- 10,000 个 text delta 的活动归约 + 全模型比较约 145 ms，但只有第一次产生语义活动变化；后续 9,999 次主要更新 sequence/time。
- 10,000 个无 observer 场景的 payload redaction/freeze 约 142 ms，尚未包含 Catalog lease fork。
- 输入草稿连续保存 20 次共约 103 ms，平均约 5.1 ms/次；当前一个击键只要上一次保存已经完成，就会再触发一次原子写/fsync。
- 相关语义测试共 116 项全部通过：events、runtime activity、compaction、files/SQLite stream persistence、catalog projection 和 input drafts。

## 五、问题清单与根因

### P0-1：Provider 分片被放大成全系统事务单位

**证据**

- 每个 delta 都 await `ports.emit()`（`ouro/core/inner_loop.py:611-680`）。
- files 每个 delta 获取跨进程锁、stat、打开、写、flush、关闭；仅省略 fsync（`ouro/sessions/local_files.py:396-433, 1407-1424`）。
- SQLite 每个 delta 是独立事务（`ouro/sessions/sqlite.py:510-520, 1317-1329`）。
- 每个事件还会进入 Supervisor 活动归约、TUI 投影、observer 路由，并追加到整 Run 的 `emitted` 列表（`ouro/application/events.py:135-155`；`ouro/core/results.py:11-16`）。

**本质**

SSE/provider chunk boundary 是 transport accident，不是 OURO 必须永久保存的领域边界。当前事件模型使响应耗时、日志体积、内存和观察成本全部与 chunk 数成正比。

**最小必要改良**

1. 在 `RuntimeAdapter` 的现有 FIFO 上增加**有界等待合并**：相邻同类型、同 turn/round 的 text/reasoning delta，在最多一个显示帧或 10–20 ms、最多 8–16 KiB 内合并；遇结构事件、类型切换、abort、done 立即 flush。
2. 明确事件契约只保证“连接后文本完全相等、顺序相等、结构边界相等”，不保证 Provider 原始 chunk 边界。
3. 为 `SessionStore` 增加 `append_ordered_events()`，让同一批剩余事件在一次锁/打开或一个 SQLite 事务中分配连续 sequence；发布顺序仍与持久化顺序一致。
4. `model_tool_call_delta` 先只做批量追加，除非能够证明按 index/字段合并的等价性；不要用文本规则贸然合并结构化参数。

### P0-2：同步持久化事务阻塞事件循环（工具/终态可达链已完成）

**证据**

- 每模型轮两次同步 `save_run`，并同步回读 Session（`ouro/application/runtime.py:3514-3559, 3685-3694`）。
- 上下文完整保存和完成态重写均同步（`ouro/application/compaction.py:792-813, 897-932`）。
- usage 记录、工具批次检查点、工具结果消息和终态转换均含同步 store 操作（`ouro/application/runs.py:295-336, 379-412, 449-668`；`ouro/application/tool_calls.py:800-863`）。
- `local_io` 的 Windows retry 使用同步 `sleep()`（`ouro/local_io.py:49-72`）。

**本质**

同步 store port 本身不是问题；在 async orchestration 线程调用它才是问题。简单地对每个方法分别 `to_thread` 也不正确，因为 nested transaction/lock ownership 使用 thread-local 状态，事务内调用必须留在同一线程。

**最小必要改良**

- 定义一个 application/core 层的 blocking-operation 边界，把**整个原子闭包**送到同一 worker 执行；闭包内部继续使用现有同步 store 和嵌套 mutation。这里的“同一 worker”只约束一个操作，不能误解为所有 Session 共用一个全局单线程 executor。
- 先迁移最重的模型轮、上下文保存、工具结果批次、complete/fail/pause；保留事件 Recorder 当前独立线程路径。
- 不机械合并 `_begin_model_round` 与 `_commit_model_request`。先写恢复测试，证明“上下文准备中崩溃”和“Provider 请求已提交后崩溃”仍可区分，再决定能否减少边界。
- 工具结果应先构造完整 message batch，在一次 `append_messages()` 中提交并只推进一次 Session/catalog。

### P1-1：摘要分块为 Θ(N²)（已完成）

`_next_chunk()` 每次把 current 与下一 frame 拼成新列表，并对整个 candidate 重新 `_summary_payload()` 和 token estimate（`ouro/application/compaction.py:404-449`）。这是确定性算法问题，不需要采样才能成立。

**改良**：每个 frame 只序列化/估算一次，维护 rolling total；固定 prompt 和 previous summary 只估算一次。若估算器对拼接有非加性误差，可保存保守边界并只在最终候选上做一次精确复核。目标是 O(N) 时间、O(N) 或更低额外空间。

### P1-2：Compaction 未降低本地历史成本

每轮 `_project_context()` 都重新验证 active compaction 的完整 covered prefix（`ouro/application/compaction.py:698-706`；`ouro/core/compaction.py:403-429`），Run 启动还加载所有 messages/runs/compactions（files：`ouro/sessions/local_files.py:572-595`；SQLite：`ouro/sessions/sqlite.py:625-643`）。

**改良分两步**：

1. Run 内按 `(compaction_id, history_boundary_message_id, last_message_id/message_count)` 缓存已验证 lineage，后续 round 只验证尾部未变条件；新 compaction 或历史变更时失效。
2. 后续为 compaction 记录 canonical message cursor/row boundary，让 Runtime 加载“summary + uncovered tail”；完整历史只供 TUI、export、branch 使用。

### P1-3：上下文每轮重复物化、digest、全量双写

`ContextView.provider_context()` 会重新转换所有消息和工具（`ouro/core/context.py:108-126`）；digest 再做 JSON sort/dump/hash（`ouro/core/context_snapshots.py:62-72`），Adapter 发请求时又转换一次。完成态只新增两个字段，却重写整份 ContextSnapshot。

**改良**：

- ContextBuilder 产出一次不可变的 `PreparedProviderRequest`，其中包含 provider-neutral request、digest、metrics 和 snapshot identity；Adapter 与快照共用它。
- 完整 prepared snapshot 只写一次；completion 使用小型 sidecar/独立列/完成事实，不重写 source messages 与 tool definitions。
- 缓存只覆盖明确静态部分：同 Run/Catalog/model route 下的 tool schema、基础 system/skill prompt 与 token estimate。动态 context provider 输出仍每轮求值。

### P1-4：文件 catalog 是 O(全部 Session) 的高频强写

默认后端是 files（`ouro/deployment.py:13-17`）。尽管 `try_update()` 只重新扫描一个 Session 的 canonical 文件，它仍读取、验证、过滤、排序并原子重写整个 `index.json`。此外工具结果逐条消息也会触发刷新。

**改良顺序**：

1. 先去重调用：一次逻辑 message batch 只刷新一次；工具内部 checkpoint 不刷新；终态与用户可见消息边界刷新。
2. 因为 catalog 可重建，允许短暂 stale：用 dirty set + 100–500 ms trailing flush，关闭/终态时强制 flush。
3. 只有当大量 Session 实测仍是瓶颈，再改表示为 per-Session projection shard 或 append-only update journal + 有界 compaction。单体 JSON 无法“像 SQLite 一样只更新一行”，不要伪装成局部写。
4. 不建议在修复 delta 事务前把 SQLite 直接设为默认；当前 SQLite 流式路径在本机反而显著更慢。

### P1-5：输入草稿每击键原子写并 fsync

`TextArea.Changed` 每次调用 `_remember_input_draft()`；只要上一保存任务已经结束，就立即再次 `write_model_atomic()`（`ouro/tui/app.py:1836-1846, 2256-2288`；`ouro/tui/input_drafts.py:102-116`）。该功能在被复核报告落盘后新增，因此属于后续回归。

**改良**：250–500 ms trailing debounce；submit、Session 切换、失焦/关闭时强制 flush。草稿要抗意外退出，但不需要每字符 durable。保留 revision loop 处理保存期间的新变化。

### P1-6：每个 delta 做无语义变化的投影与观察工作

Supervisor 对每个事件复制状态、执行 reducer，再通过两个完整 `model_dump()` 判断是否有语义变化（`ouro/application/supervisor.py:842-874`；`ouro/application/runtime_activity.py:383-388`）。TUI 又独立归约一次。0 observer 时仍构造 redacted/frozen observation，并 fork/scoped Catalog registry（`ouro/application/events.py:279-298, 429-446`；`ouro/application/runtime.py:388-405`）。

**改良**：

- RuntimeActivity 对连续同类 delta 走 fast path：只推进 sequence/time；仅在活动类别变化时构造完整 snapshot 和通知。
- 用显式字段 tuple/版本号比较，不对两个 Pydantic 模型做完整 dump。
- Extension Catalog 预计算 `runtime_event_type -> registrations` 索引和 `has_observers` 位；无匹配时在 redaction/freeze 和 generation lease 之前短路。
- delta 合并完成后再评估这一项收益，避免先优化被上游批处理自然消除的工作。

### P2-1：RunResult 留存整 Run 的全部事件（终态无界应用已修复）

Recorder 仍把每个事件追加到 `emitted`，终态 `RunResult.events` 也仍保留整份列表；但 TUI 已不再把结果事件直接无界
应用，而是先按当前 projection/pending sequence high-water 去重，再复用每帧最多 64 条的既有 consumer。由此消除了
终态绕过帧预算和重放 live prefix 的交互缺陷，剩余问题只是极长 Run 的事件列表内存与一次有界入队扫描。

优先由 delta 合并降低数量。若超长 Run 仍有内存压力，可让 Host 明确选择 `capture_events`：CLI JSON/print 保留，已有
可靠订阅的 TUI 只返回 terminal summary + event cursor。该改动只由现实内存证据触发，不能再作为当前 TUI 卡顿的默认
修复，也不能静默改变 CLI 输出契约。

### P2-2：资源附件每轮重复读、校验与 base64

每轮 context 投影会重新验证引用、读取 immutable blob、计算 sha256，并对最多 20 MiB 的图片重新 base64（`ouro/application/resources.py:210-307`；`ouro/resources/local.py:94-134`）。这些同步操作发生在 context prepare coroutine。

仅在使用附件时严重。建议先移入 I/O worker，再做 Run 内按 `(resource_id, digest, vision capability, role)` 的有界缓存；大图片缓存应受总字节上限约束。

### P2-3：AGENTS.md 每轮重复遍历，但不会阻塞 loop

被复核报告正确识别了每轮重复的路径查找/stat/resolve/read（`ouro/builtin_plugins/agent_context/instructions.py:47-99, 138-162`），但“同步 I/O 直接位于事件循环”不成立：同步 context provider 通过 `asyncio.to_thread` 调用（`ouro/core/callbacks.py:36-49, 64-73`）。

仍可用 `(canonical path, mtime_ns, size)` 做局部缓存，并在任何候选路径元数据变化时重载；它是减少线程与文件系统工作，不是修复 UI freeze。

### P2-4：长 Session 冷打开仍 O(H)，但不是全量 DOM

当前历史主体是一个 `ConversationHistory(RichLog)`（`ouro/tui/conversation_history.py:692`），不是“一条消息一个 DOM widget”。近期实现还对流式 Markdown、reasoning 行、历史 strip 和 Session state 做了增量/有界优化。因此不应重新设计整套 TUI。

真实剩余问题是：冷打开仍物化所有消息并生成所有历史 strip，内存和首次解析随 H 增长。等 Runtime 热路径治理后，用现有分页 API扩展 tail/before cursor，首屏加载最近一页、接近顶部再加载更早页。

### P2-5：Agent 树与根预算按树规模重复扫描

Agent tree snapshot 对每个 delegation 读取 child 状态、事件 sequence、全部 runs usage 和 activity（`ouro/application/agent_tree.py:68-163, 251-260`）。根预算每轮遍历所有 delegations 和每个 child 的全部 runs（`ouro/application/agents.py:1988-2015`）。当前首版深度限制为 1，通常可控；只有大量并行子 Agent/长 run history 时才值得做增量 usage 聚合。

### P2-6：锁、SQLite 索引与后台唤醒

- `FileMutationLock` 等待 live holder 时没有超时（`ouro/local_locks.py:95-111`）。应增加 deadline 和诊断；但进程崩溃后 OS 会释放文件锁，“崩溃残留导致永久持锁”不是准确原因。
- 读路径使用 mutation lock 是为了跨多个 canonical 文件获得一致快照。不能仅因原子 rename 就全部改成免锁/共享锁；应先把读移出 loop、缩短事务，并对单文件读逐项证明可放宽。
- SQLite `session_mutation(session_id)` 确实不使用 ID（`ouro/sessions/sqlite.py:958-960`），但 SQLite WAL 仍是单 writer，增加 per-Session Python 锁不会让多个写事务并行。真正的热问题是每 delta 一个连接/事务。
- `compactions` 缺少 `(session_id, row_id)` 索引（`ouro/sessions/sqlite.py:113-119, 720-728`），属于低风险补强，但 compaction 数通常很小。
- TUI 在配置了 MCP server 时以 0.25 秒周期同步状态（`ouro/tui/app.py:139, 1104-1108`）。可改为事件驱动或空闲时降低频率，优先级低。

| 缺少性能可观测性 | 正确 |

### 6.2 方向正确但需要修正

| 既有结论/建议 | 修正 |
|---|---|
| “每轮两次写合并成一次” | 不可直接执行；两次写代表不同恢复边界。先缩小载荷和移出 loop，再以 crash tests 证明可合并 |
| “统一用 `asyncio.to_thread` 包 store 调用” | 粒度应是完整原子事务闭包；逐调用切线程会破坏 thread-local nested transaction/lock 语义 |
| “AGENTS.md 同步阻塞事件循环” | 重复遍历属实，但 sync handler 已由 `invoke_bounded_callback` 放在线程中 |
| “SQLite catalog O(1)” | 相对全部 Session 有界，但仍扫描目标 Session 的 message/run/resource 计数，不是严格 O(1) |
| “文件 catalog 只更新一个条目” | 单体 JSON 无法原地更新一项；需要降频或改变投影表示 |
| “锁应有上界” | 建议成立；风险是 live/stuck holder 和事件 loop 尾延迟，不是崩溃后的 OS 锁残留 |
| “前端需要分页” | 方向成立；已有前向分页 API，只缺 tail/reverse 语义和 TUI 接入 |

### 6.3 事实或建议不成立

| 既有表述 | 复核结论 |
|---|---|
| TUI 使用固定 50 ms 帧缓冲 | 当前实现使用 `call_after_refresh()` 跟随 Textual 原生 compositor 帧，不是固定 50 ms（`ouro/tui/app.py:1252-1265`） |
| 持锁进程崩溃会留下永久文件锁 | 不准确；OS 文件锁随进程/descriptor 释放。无界等待仍应修复，但原因不同 |
| 订阅溢出时只丢最旧一条更好 | 错误。一旦丢任一规范事件，后续增量投影已经不可信；清空并发 lagged 诊断、从 durable cursor 重载是正确语义（`ouro/application/supervisor.py:118-143`） |
| SQLite 应按 Session 分区写锁 | 不能解决 SQLite 单 writer；应批量事务、减少事务数和连接 churn |
| 无依赖插件直接 `gather` 并行启动 | 当前 activate 受全局 mutation lock 和依赖/发布顺序约束，盲目 gather 没有收益且增加复杂度；先测启动剖析 |
| Session 层无游标分页 | 不准确；已有 message/event page，只是不支持 tail-first 且 TUI 未使用 |
| TUI 是全量 DOM | 不准确；历史是单个 RichLog/strip 数据结构。全量历史物化仍是问题，但不是 DOM 数爆炸 |
| “不要合并规范事件”与“合并 delta”同时成立 | 需重新定义边界：结构事件是规范事实；Provider 原始文本 chunk 不是。可合并 delta 而不丢失领域语义 |

### 6.4 既有报告遗漏的重要问题

1. SQLite 每 delta 独立连接/事务的数量级和 files/SQLite 对比分片基准；
2. 1 字符 delta 造成约 313 倍文件日志表示放大；
3. 摘要 `_next_chunk()` 的 Θ(N²)；
4. active compaction 每轮重算 covered history digest，且 Runtime 启动仍加载全历史；
5. ContextSnapshot prepared/completed 全量双写；
6. 输入草稿每击键 fsync（该功能晚于原报告）；
7. Supervisor 活动投影、TUI 投影和 observer work 对每 delta 重复；
8. `RunResult.events` 留存整 Run 事件并在 TUI 完成时再扫描；
9. 附件每轮重复读取、hash 和 base64；
10. 工具结果逐个 message/catalog 提交；
11. Agent tree/root budget 的 O(Agent × run history) 条件性风险。

## 八、验收指标与回归约束

不要只以单元测试通过作为性能完成标准。建议加入以下不含用户内容的采样指标：

| 指标 | 目标/用途 |
|---|---|
| `stream_delta_events / output_kib` | 不再由 Provider chunk 任意性决定；同一文本不同分片应接近 |
| event append batch size、p50/p95/p99 | files/SQLite 均应明显降低事务数 |
| event journal bytes / output bytes | 1 字符分片不应再出现数百倍放大 |
| event-loop lag p95/p99 | 模型轮、context save、tool commit 时不应出现磁盘级停顿 |
| context prepare 分阶段耗时 | provider、lineage、resource、token estimate、snapshot 分开统计 |
| catalog flush 次数 / logical message batch | 目标接近 1，工具 checkpoint 不触发 |
| cold Session open：100/1k/10k messages | 决定何时值得引入 tail pagination |
| compaction chunk selection 100/200/400/800 | 翻倍应接近 2 倍，不是 4 倍 |
| draft writes / typing burst | 一次连续输入通常 1 次，关闭/切换保证最终 flush |

必须保持的语义测试：

1. 持久化 sequence 与 live fan-out 顺序完全相同；
2. delta 合并前后 text/reasoning 精确拼接一致；
3. 结构事件、tool-call index、done、retry、abort 不跨边界重排；
4. 非 delta durable boundary 能提交之前的 delta prefix；
5. crash 分别发生在 context 前、Provider request commit 后、tool result commit 中时可恢复；
6. observer 无匹配时不 fork generation lease，有匹配时 lease 生命周期不缩短；
7. compaction 优化前后 chunk 选择与 token 安全边界一致；
8. TUI lagged 后从 durable cursor 重载，不尝试用有缺口的后续事件继续投影。

## 九、不建议的改动

- 不重写 TUI renderer，也不复制 Textual 私有 Markdown 实现；现有增量/strip 方向正确。
- 不移除事件日志、恢复检查点或“先持久化后发布”原则。
- 不把所有 store 方法各自随意包一层 `to_thread`；事务必须完整留在同一 worker。
- 不把所有文件读改成免锁或共享锁；多文件 observation 的一致性需要明确协议。
- 不在订阅缺一个事件后继续增量归约；应明确 lagged 并重载。
- 不因 files catalog 慢就立即切 SQLite 默认；先修复 SQLite 每 delta 事务。
- 不引入通用缓存框架；使用 Run/Catalog/compaction/resource identity 驱动的局部、有界缓存。
- 不为了并行而打乱插件 generation 的依赖与发布顺序。

## 十、最终判断

OURO 当前不是“架构太重”，而是**若干正确的可靠性机制被放在了错误的粒度上**：事件顺序、事务、恢复快照、catalog 投影和插件 lease 都有合理目的，但不应以每个 Provider 字符碎片或每个不变对象的全量副本为单位执行。

最优路线不是减少可靠性，也不是再加一层抽象，而是把工作单位校准到真正的语义边界：文本批次、模型请求、工具结果批次、Run 恢复点和可重建投影刷新点。这样既能保留 OURO 目前清晰的领域设计，又能从根因上消除 I/O、CPU、内存和事件循环延迟的共同放大源。

## 十二、2026-08-31 TUI 卡顿独立复审、纠错与实施结论

### 12.1 第一性原理因果模型

用户能感知的“键入和动画卡住”只有一个直接必要条件：Textual 事件循环在该时间段没有获得运行机会。一次工具进入或
终态更新即使总耗时较长，只要重工作在 worker 且 loop 可调度，输入和 spinner 仍能响应；反之，哪怕同步工作平均只有
数毫秒，只要多个 `fsync`、文件锁等待、全量序列化或 Rich 渲染连续落在 loop 上，就会形成肉眼可见的长帧。

当前拓扑中 TUI、Supervisor 和 Runtime coroutine 共用一个 asyncio loop，这本身不是缺陷；异步 Host 共享 loop 可以减少
跨线程状态同步并保持事件顺序。真正的框架缺陷是此前没有把同步 Store port 与异步编排之间的**执行边界**制度化，导致
正确的 durable/crash boundary 在错误的线程上执行。TUI 侧则存在两个放大器：定宽动画错误触发布局，以及稳定 history
strip 与可交互 live widget 之间在工具进入/退出时发生结构迁移。

由此得到三个不可混淆的成本层：

1. **loop starvation**：同步持久化、同步大对象物化、同步 durable abort 检查；这是键入与动画同时卡顿的充分解释；
2. **结构帧尖峰**：assistant 冻结、工具行 mount/remove、历史 strip 生成；它会在工具首次进入和终态精确出现；
3. **吞吐/扩展成本**：catalog 全量刷新、compaction covered history、ContextSnapshot 双写；它们不必然冻结 loop，但会增加
   worker 占用、磁盘争用和端到端完成时间。

### 12.2 对《OURO TUI 会话流式卡顿根因分析》的审查

该报告的主判断正确：共享 loop 上的同步 durable I/O 是四类症状的共同主因，TUI 层优化是必要的次级治理；保留两个
model-round crash boundary、不降低耐久性也正确。以下表述需修正或收窄：

| 报告观点 | 本次核查结论 |
|---|---|
| 新工具首次进入主要锚定于 `begin_model_round` | 不完整。直接链路还包括上下文完成/快照、assistant tool message、多个 batch checkpoint 与 catalog refresh；TUI 同时冻结 assistant 并 mount 工具行。不能把首工具尖峰归因于单个 `save_run` |
| “完整原子事务闭包送到单一 I/O worker” | 若“单一”指一次事务不换线程，正确；若指全局只有一个 worker，则错误，会制造跨 Session head-of-line blocking。当前实现使用默认 pool，每次完整操作由一个 worker 执行，既有 Session/SQLite 锁负责顺序 |
| 给 `_apply_runtime_event_batch`/`sync_tools` 套 `batch_update()` 可合并结构成本 | 只能合并可合并的刷新，不能消除 `AwaitMount`、`AwaitRemove`、Rich strip 生成或必需布局。实际治理采用 `mount_all`、`remove_children`、history batch 与后台渲染 |
| TUI 渲染是次因 | 正确，但应明确 live/history 双表示使工具边界必然有一次结构迁移；它是当前交互设计的局部成本，不足以证明 TUI 存在需要重写的本质缺陷 |
| 引用的阻塞点与行号代表当前代码 | 只代表 `ada7871` 分析基线。工作树中的 paint-only、批量结构操作和 worker 边界已使多处引用过时，不能继续据此声称 P0-2 未修复 |

该报告还遗漏了三个经本次动态探针确认的关键点：

1. pending Runtime event buffer 原先会在一个 handler 中全部耗尽；即使单事件很轻，积压后仍可形成无上界长帧；
2. `AbortSignal.is_aborted()` 的 checker 曾在 Provider/工具高频检查中同步 `load_run()`，一次 Run 可产生约 30 次 loop-thread
   读取，属于隐藏在“取消正确性”后的热路径 I/O；
3. Supervisor 第一次 event activity 投影会同步加载 Session/Run/context 状态，且 `RunResult.events` 在终态仍会被 TUI
   去重扫描。前者已移出 loop；后者经 delta 合并后显著减小，但仍是超长 Run 的剩余 O(E) 内存/终态扫描项。

### 12.3 TUI 是否有本质设计缺陷

结论是：**没有证据支持重写 TUI renderer 或把全部会话改成单一 surface。** 单个 `ConversationHistory` strip buffer 承载
稳定历史，少量 widget 承载需要 timer、hover、click 和子 Agent 导航的 live 状态，是清晰且可维护的职责分离。它避免了
长会话“一消息一 DOM”的更大问题。

但有两个关键设计锚点必须作为性能契约维护：

- 内容与几何必须分离。spinner、状态文案和定宽计时只刷新 paint；只有 cell width/显示结构改变才请求 layout；
- live→immutable promotion 是一次显式事务：先在 worker 生成昂贵 strips，再以批量 history append/mount/remove 提交到
  UI。它不能与每个 RuntimeEvent 的到达粒度绑定，也不能在一个 handler 中无界执行。

当前实现已把 Runtime event 应用限制为每原生 compositor frame 最多 64 条；剩余积压下一帧继续。这个常量是保护
响应性的简单预算，不是第二个固定帧率定时器。buffer 满仍按原契约发出 lagged 诊断并从 durable snapshot 重载。

### 12.4 OURO 框架层设计判断

OURO 的事实源、Session mutation、crash boundary、事件“先持久化后发布”和同步 Store port 均不需要推倒。缺陷位于
application/core 适配层：异步编排过去直接调用同步 port，且取消 checker 把 durable read 混入高频纯查询。此次最小
改良没有异步化整个 Store 接口，也没有建立新的 repository/cache 框架，而是加入一个窄的 blocking-operation primitive：

- operation 从锁取得到事务结束完整留在一个 worker；
- caller 被取消时先等待拥有的线程 settle，避免事务在“无人拥有”状态继续修改 durable 数据；
- 不同 Session 仍可由多个 worker 并行；既有 store lock/transaction 是唯一顺序权威；
- 本地 abort 在 durable transition 后立即更新内存 signal；signal 激活先执行一次 durable read 关闭启动竞态，跨进程
  abort 再由 50 ms 后台 poller 在线程中桥接；model-round mutation 始终从 latest Run 派生，避免旧快照覆盖请求；
- event emit 仍在 mutation 成功后回到 loop 顺序执行。

这一区分也解释了为何“把整个 Runtime 搬到专用线程”和“每个 Store 调用分别 `to_thread`”都不是优选：前者扩大线程
所有权和 Host 状态同步面，后者会拆散 thread-local nested transaction/lock 语义。当前边界只校正错误的同步工作位置。

### 12.5 已实施项目

本次结合工作树中已有 TUI 优化完成了以下收敛：

1. model round begin/commit、route/session refresh、context materialization/projection/snapshot、usage、tool checkpoint、
   Run start/complete/fail/pause、关键 queued input/approval/resume mutation 移出 loop；
2. tool batch 的 assistant message、状态 checkpoint、结果消息和 terminal batch 保存均以完整同步操作进入 worker；
3. abort signal 改为 O(1) 内存检查，durable poll/settlement 移出 loop，Run 结束拥有并清理 poller；
4. Supervisor 首次 activity snapshot 移出 loop；显式恢复多 worker FIFO provider-stream 启动顺序；shutdown 先取消 queued
   job 再等待 active abort，消除卸载 I/O 后暴露的启动竞态；
5. Windows 会话目录 publish 复用文件原子写已有的有界 sharing-race retry，解决并发 catalog/list 扫描暴露的
   `WinError 5`，重试在线程中进行；
6. TUI spinner/状态/reasoning label 使用 paint-only 或按 cell width 决定 layout；工具行批量 mount/remove，assistant 与
   terminal tool immutable 内容复用后台批量渲染；
7. TUI 每帧只应用 64 条 pending Runtime events，避免 backlog 在单帧全部耗尽。

为保持恢复和调度语义，第二里程碑额外增加了 blocking-operation cancellation ownership、durable abort bridge、FIFO
启动和 shutdown race 测试。这里没有删除任何 checkpoint，也没有降低 `fsync`、事件顺序或跨进程中止能力。

### 12.6 动态证据与解释边界

相同的单次 model→tool→model 场景，在含 `RuntimeSupervisor` 的 10 ms ticker 下：

| 后端 | 改动前最大 loop lag | 改动后最大 loop lag | 降幅 |
|---|---:|---:|---:|
| files | 93.2 ms | 15.6 ms | 约 83% |
| SQLite | 69.1 ms | 16.3 ms | 约 76% |

基准 wall time 分别出现 files 874→1397 ms、SQLite 1012→983 ms 的波动，说明本机临时目录、Windows 扫描和线程调度
噪声足以影响单样本吞吐；因此只把 loop lag 与线程探针用于本轮响应性结论，不宣称端到端吞吐按同一比例提升。

另一项确定性测试把 context snapshot、活动 tool checkpoint 和 terminal `save_run` 各人为延迟 60 ms：三者线程 ID
均不同于 loop 线程，且每段延迟内 1 ms ticker 至少推进两次。这直接验证“磁盘慢时 UI 仍可被调度”，比只比较总耗时
更接近本问题的验收条件。

TUI headless 诊断在 400 条历史、4 个工具下曾测得首次进入约 61.22 ms/4 次布局、终态约 78.59 ms/2 次布局，最大
loop lag 约 15 ms。该结果支持“结构迁移是残余放大器”，但 headless Textual 的 await wall time 不等于真实终端帧 SLA；
因此本次只采用后台渲染、批量结构操作和帧预算三项低风险改良，不据此重写历史/交互模型。

最终全量 collection 得到 1972 passed、2 skipped，另有 2 个 TUI 菜单键盘时序用例在 14 分钟运行中超时；两项隔离
复跑均通过。最后一轮 abort 竞态修正后的受影响边界又分别通过 application 136、core 15、TUI/history 23 项测试。
`ruff check ouro tests`、`mypy ouro`（265 个源文件）、`compileall -q ouro tests` 与 `git diff --check` 均通过。这里如实保留
全量时序波动，不把隔离复跑表述成一次全量零失败。

### 12.7 仍然存在但不应混入本轮的项目

1. active compaction 仍会加载/验证 covered history，Runtime 冷加载与 TUI 冷打开仍随完整历史增长；
2. ContextSnapshot completion 仍全量重写，Provider request 仍有第二次 provider-neutral→provider materialization；
3. files catalog 仍是 O(Session 总数) 的单体强写，静态 extension generation 仍随 Run 重复序列化；
4. `RunResult.events` 仍保留整 Run 事件，但 TUI 终态已复用有界 consumer；极长 Run 的剩余列表内存需要独立证据决定
   是否引入 `capture_events`；
5. manual compaction、维护/恢复扫描等工具边界不可达冷路径仍有同步 Store 调用；工具边界 Session control 已完成迁移。
   其余路径应以 loop-lag 采样而非静态“async 中出现 sync”计数决定是否迁移；
6. 尚缺生产级 event-loop lag/context phase/catalog flush 指标。本次测试能证明改动方向，但不能替代长期 p95/p99 数据。

这些项目已经写入后续性能地图，但没有为“看起来完整”而引入 completion sidecar、catalog journal、tail pagination、
通用缓存或专用 Runtime 线程。只有当对应增长阶和用户场景成为主导成本时，才应开启各自的独立里程碑。

### 12.8 最终核心洞察

这次卡顿不是单一 TUI 函数，也不是 OURO 可靠性架构过重，而是两种边界错位叠加：**同步可靠性工作越过了 async
执行边界，Runtime 事件粒度又越过了 UI 帧预算。** 根治方式不是删除可靠性、降低刷新率或叠加缓存，而是让每种工作
回到自己的自然单位：durable mutation 以完整事务为单位在线程中完成，取消检查以内存状态为单位，流式文本以有界
语义批次为单位，UI 以有限事件前缀和一次结构 promotion 为单位。

在这一模型下，TUI 与 Runtime 共用 loop 仍然成立，Store 仍然同步，恢复点仍然完整；但磁盘尾延迟不再等价于输入框和
ASCII 动画停顿。它是对 OURO 分层的校正，而不是在缺陷上堆补丁。

## 十三、2026-09-01 工具边界残留卡顿复核与第三里程碑结论

### 13.1 本轮确认的底层残留

第十二节的第一性原理模型继续成立：输入框键入与 ASCII 动画同时停顿，直接说明共享事件循环在该时段没有获得运行
机会；只延迟输入则还要检查 App message pump 是否被一个长 handler/await 链占有。第二里程碑消除了主链阻塞后，工具
首次进入、完成/下一轮和 Run 终态仍有两类能够直接违反这两个所有权边界的残留：

1. `shared_budget_reason`、approval/answer/child-wait 恢复、requested-abort/final boundary、continuation/terminal
   settlement、delegation/result delivery 和 Session control 持久化相位中，仍存在从 async 编排直接到同步 Store、
   文件锁或 SQLite I/O 的可达链；
2. TUI 的 live subscription 已经使用每帧最多 64 条的 consumer，但 `_apply_run_result()` 曾直接应用完整
   `RunResult.events`，在终态绕过帧预算；同一 event prefix 触发的 Session controls 查询虽已在线程读取 Store，App
   handler 仍会 await 查询完成，因而继续占有 pump。

二者都是调用所有权错误，不依赖短样本是否恰好超过某个毫秒阈值。前者的等待上界受文件锁、`fsync` 和 SQLite writer
控制；后者使已有背压/帧预算在 terminal path 失效。相比之下，projection/reducer/redaction 的对象复制只是候选 CPU
成本，必须先证明现实 payload 下形成主导不可让出片段，不能仅凭理论增长阶升级为重构。

### 13.2 最小必要实现

本轮没有增加新的事实源或调度框架，只校正既有边界：

- Inner Loop 的 shared budget port 改为 async application boundary，聚合预算 query 作为一个完整 `run_blocking()`
  operation settle；其余上述工具/终态 Store query/mutation 也以完整操作为单位进入默认 worker pool；
- Session control 保留原有“durable prepare → async plugin controller → durable commit/rollback”三相语义，只把两个同步
  持久化相位移入 worker；controller coroutine、Session lock、SQLite transaction 和 durable 后发布 event 的顺序不变；
- terminal `RunResult.events` 按 projection/pending high-water 去重并进入既有 64-event-per-frame consumer，不再重新
  应用 live subscription 已消费的前缀；
- controls refresh 使用一个 dirty flag 和单一后续任务合并连续请求，`RuntimeEventsReady` handler 不等待 Store 查询；
  查询完成后再次校验当前 Session/只读视图，过时结果不提交；
- Agent result delivery 的查重、Host 路由和 durable delivery commit 继续由同一 delegation lock 覆盖，线程迁移没有
  放宽 exact-once 并发边界。

### 13.3 为什么不做“同步调用与投影放大清零”

工具边界可达的 loop 同步 Store/锁操作必须迁移，因为这是线程所有权契约；但全仓库 async 函数中的同步调用数量不是
性能指标。manual compaction、显式维护和冷恢复扫描没有进入当前症状链，机械迁移只会扩大 cancellation、线程切换和
测试状态面。

投影也没有“清零”目标。本机每组 2,000 次分项基准中，1 KiB `tool_call_completed` payload 的
project/reduce/change/redact+freeze p99 约为 0.081/0.030/0.027/0.103 ms；100 KiB payload 的 project 与
redact+freeze p50 约 4.41/4.45 ms、p95 约 5.73/5.80 ms。p99 偶发约 8.56/8.37 ms，但没有稳定越过 8 ms，
也没有与当前超预算交互样本持续同相位。因此没有引入 projection cache、摘要 DTO、Host payload 分叉或 Observer
旁路。活动 TUI Session 本来就有订阅者，“无订阅者不构造 event view”也不能解释该场景。

同理，Context completion sidecar、tool checkpoint 拆分、时间 deadline、pump 外 prepare/commit、render generation
状态机和第二 renderer 均未通过本轮实施门禁。它们会增加恢复状态、并发协议或重复计算，不能作为“可能更快”的预防性
改造。

### 13.4 验证边界与当前状态

files/SQLite 的 model→tool→model 测试在 context snapshot、tool checkpoint 和 terminal `save_run` 各注入 60 ms
同步延迟，三个操作均在非 loop 线程执行，延迟期间 1 ms ticker 持续推进。shared budget、requested abort、
continuation terminal query、Session control persistence phase 和 Agent terminal settlement 另有线程所有权测试。TUI
测试确认 terminal prefix 不超过每帧上限、不会重放 live/pending sequence，controls handler 不等待查询、连续刷新会合并，
Session 切换后的旧结果会被丢弃。

受影响 application/core 集合 102 项、Runtime 69 项、conversation history 19 项通过；最终新增边界集合 13 项通过。
TUI 全文件在排除一个未修改基线同样失败的 2 秒 child-start 时序用例后为 229 passed、1 failed、1 deselected，唯一
失败是启动状态仍显示 `Loading session`，隔离复跑通过。项目 `.venv` 下 Ruff、Mypy（265 个源文件）、compileall 和
`git diff --check` 通过。

这些证据足以把 loop 所有权和 TUI dispatch 修复视为当前契约，但不能替代真实终端的最终体验验收。工具进入、完成、
下一轮和终态的 Key latency p95、event-loop lag 分布与 120 ms spinner cadence 仍需在真实终端场景测量；完成前不宣称
第三里程碑整体关闭，也不以降低动画频率、扩大流式窗口或减少 checkpoint 掩盖失败。
