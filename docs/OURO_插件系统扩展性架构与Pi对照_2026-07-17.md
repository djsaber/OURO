# OURO 插件系统架构审查与 Pi 对照

状态：当前实现审查与目标架构决策（2026-07-17）

本文以当前代码和可重复测试为事实来源，审查 OURO 插件系统是否符合“强扩展的个人智能体”定位，并给出
下一阶段的底层改良方向。规范性目标以[插件系统目标规格](../dev/specs/plugin-system.md)为准，实施顺序以
[连接与扩展计划](../dev/plans/connectivity-extensions.md)为准。

## 1. 产品边界与审查原则

本次审查采用以下已确认决策：

1. OURO 是强扩展的个人智能体，不是多租户平台或企业插件市场。安全只建立必要的代码信任、Host 能力授权、
   凭据隔离、路径校验和工具审批边界，不建设 OS 沙箱、发布者信任根或复杂策略中心。
2. 插件是 OURO 的系统级扩展模块，只有 `builtin` 与 `user` 两类。不存在项目级或 workspace 级插件；
   workspace 只是一次调用的执行上下文。Skills 与提示词仍可独立具有用户级和工作区级来源。
3. OURO 仍处于开发阶段。Manifest、Plugin API、worker protocol 和持久化模型可以直接修正；旧格式默认严格
   拒绝，不为尚未发布的历史契约保留兼容分支。
4. 社区项目用于校准插件形态和开发体验，不决定 OURO 的内部模型。采用一种社区模式前，必须先证明它符合
   OURO 的 Run、工具、资源和 Host 边界。

## 2. 当前架构理解

当前实现已经形成以下主链：

```text
Source
  -> static package validation
  -> immutable digest store
  -> configuration / capability authorization / code trust
  -> dependency order
  -> plugin generation
  -> prepared contributions
  -> owner-aware registry transaction
  -> Run extension snapshot
```

主要职责分布为：

- `ouro/plugins/manifest.py`：Manifest、runtime、contribution 和 permission 声明；
- `ouro/plugins/sources.py`、`package.py`、`store.py`：来源解析、静态校验、内容摘要和不可变存储；
- `ouro/plugins/authorization.py`：配置、能力授权和代码信任判断；
- `ouro/plugins/contributions.py`：贡献预校验、跨 registry 原子提交和 owner lease；
- `ouro/plugins/runtime.py`：Generation、资源所有权、启停和 Run snapshot；
- `ouro/plugins/worker.py`：stdio JSON-RPC worker；
- `ouro/sdk/plugins/v1.py`：独立于 core/application 的插件 SDK；
- `ouro/application/plugins.py`：Host-neutral 插件管理用例。

## 3. 已经合理的设计

以下设计应保留，而不是在后续重构中推翻：

- 安装阶段只做静态校验，不 import entrypoint、不启动 worker/MCP；
- 包内容按 digest 不可变保存，来源记录由 installer 生成，插件不能自报可信身份；
- executable code trust 与 capability authorization 分离；
- 插件工具继续经过 `ToolExecutor`、参数校验、审批、路径和取消边界；
- Contribution 先完整 prepare，再以 owner transaction 跨 registry 原子提交，失败恢复原快照；
- Plugin SDK 不暴露 `RuntimeService`、`SessionStore` 或具体 Host 对象；
- command、continuation 和 tool policy 使用类型化语义，而不是把所有行为塞进通用 Hook；
- 插件输入保留来源归因，不伪装为用户输入；
- worker 的 stdout、消息大小、超时、凭据和 stderr 已有明确协议边界；
- 插件失败不会阻止无关插件和 OURO 主运行时启动。

可重复基线：

```powershell
.venv\Scripts\python.exe -m pytest -q tests/plugins/test_plugin_system.py tests/application/test_plugin_extensibility.py
```

当前结果为 `34 passed`。这证明现有基础不是不可用，而是下一阶段需要修正若干结构性瓶颈。

## 4. 需要修正的架构问题

### 4.1 全局 Catalog barrier 阻塞所有插件生命周期

当前每个 Run snapshot 会租用全部 active generation；任意插件启停或重启又必须等待全部 snapshot 释放。
因此一个等待用户、等待审批或长时间运行的 Run，会阻止无关插件的启停和升级。Catalog 变更期间，新 Run 也
只能失败重试。

更关键的是，当前 activation 会先停止旧 generation，再构建候选 generation。候选失败时，旧代已经退出。
应用层对配置和选版做了补偿恢复，但普通 restart 仍可能造成不必要的插件下线。

目标修正：

- Run 持有不可变 `ExtensionCatalog`，而不是读取一组会变化的全局 registry；
- 受影响的候选 generation set 在旧代仍服务时完成 prepare、start 和健康检查；
- 成功后只原子提交 current catalog pointer 与 background service gate ownership；
- 新 Run 使用新 catalog，旧 Run 继续持有旧 catalog；
- 旧 generation set 在各自引用归零后异步停止；
- 撤权通过 generation gate 阻止后续调用，不依赖全局停顿。

后台服务不能简单跟随旧 catalog 保活，否则更新后两代轮询器或定时任务会同时产生外部副作用。它应作为每个
plugin id 的 activation-singleton resource：候选只能在关闭的 service gate 后准备，发布时把后台服务所有权从
旧代交给新代；旧代仍可为旧 Run 提供 snapshot-bound callback，但不再运行自主后台任务。

候选阶段也不能破坏性修改跨版本共享的 plugin data，否则“失败不改变旧版本”只是表面成立。目标 API 在发布前
只提供只读 data view；需要改变私有数据格式时，由插件在禁用状态下显式处理或由用户清空重建，不预建通用迁移框架。

Configuration 同样是执行契约的一部分，不能继续只是“每 digest 一个可覆盖值”。目标保存不可变 configuration
revision，active activation 和 durable Run 引用具体 revision；配置命令先创建候选 revision，只有候选 Catalog
发布成功才切换 active reference，失败或重启后仍能重建旧契约。

### 4.2 依赖只有拓扑顺序，没有 observed health 协调

当前 resolver 能检查 selected version、SemVer 和 cycle，但 Host 启动时某个依赖 activation 失败后，仍可能继续
尝试激活依赖者。`incompatible` 也只是一次返回值，后续状态投影可能重新显示 `ready`。

此外，Manifest 中的 `optional_feature` 没有任何解析语义，应直接删除，而不是继续保留无生产者字段。

目标修正：

- Dependency graph 只表达必需插件依赖，不预留 feature system；
- 依赖者只有在全部必需依赖 active 时才能 active；
- 依赖失败投影为稳定、可诊断的 `blocked`/`incompatible` observed status；
- 依赖恢复后由同一 reconciler 重新尝试依赖者；
- 依赖 digest 或 contract 改变时，候选单位是受影响的 generation closure；所有依赖者按拓扑重建后一次发布，
  不能把引用旧 dependency lock 的 generation 留在新 catalog；
- 当前阶段不引入插件服务导入/导出协议，出现真实组合需求后再定义类型化 contribution。

### 4.3 插件 scope 模型与产品定位冲突

当前状态模型出现 `user/workspace`，但实际上每个 plugin id 只有一份 activation、selection、configuration 和 data。
相同 digest 从另一个 scope 安装也会被直接去重，因此 workspace scope 既不能形成覆盖，也不能形成隔离。

这不应通过补齐多 scope overlay 修复，因为产品边界已经明确：插件是系统模块，不是项目资源。

目标修正：

- 删除 workspace、managed 和 development plugin activation scope；
- 插件分类只有 `builtin` 与 `user`；
- builtin 由 OURO 装配，不能被用户安装、替换或卸载；
- user plugin 安装到当前 `OURO_HOME`，每个 plugin id 只有一个 selected digest 和 activation；
- workspace 仅在 Tool/Hook/Command 调用时作为 request context 传入；
- Skills、提示词和项目配置继续独立支持 workspace 来源，不与插件模型合并。

### 4.4 扩展点仍是中心化硬编码集合

新增一种 contribution 当前需要同时修改 Manifest、SDK、worker feature、ContributionCoordinator、runtime 和
application registry。这说明插件能在既有表面上深度扩展，但 OURO 内部新增扩展点仍然昂贵且容易漏掉生命周期、
contract hash 或撤销路径。

目标不是让用户插件自行注册“新扩展点”，而是为 OURO 内部建立一个小而明确的 `ContributionTypeAdapter`：

```text
kind
  + declaration validation
  + SDK/worker adaptation
  + conflict and contract rules
  + catalog projection
  + owner cleanup
```

Host 仍显式决定支持哪些 contribution。该抽象只消除当前已经存在的重复，不发展成万能事件总线或动态类型系统。

### 4.5 observed status 与故障生命周期不完整

`starting`、`degraded`、`stopping` 已定义，但 worker 异常退出、background task 失败和 optional contribution 失败
通常只追加 diagnostic，active 状态和 registry projection 不一定同步变化。worker request 也只在 timeout 时发送
`cancel`，外层任务取消没有完整传播。

目标修正保持个人应用所需的最小闭环：

- worker 退出立即撤销其可调用 contribution，并将 generation 标记为 failed；
- request timeout 和 task cancellation 都发送 cancel；
- background task 失败使 generation degraded，并产生有界 diagnostic；
- 提供显式 `restart`，当前阶段不实现自动重启预算、熔断或复杂 backoff policy。

### 4.6 Plugin Skills 没有进入统一 Skill Catalog

当前插件 Skill 被转换为 `after_context_build` Hook，绕过了现有 Skill 的名称冲突、启停、发现诊断和按需加载
管理。这会形成两套 Skill 语义。

目标修正：插件 Skill 作为 `source=plugin` 进入同一 Skill Catalog；其 owner 和 package digest 由 catalog snapshot
固定。插件禁用后新 Run 不再看到它，旧 Run 仍可从不可变 package 读取对应内容。

### 4.7 `auto_start=false` 的插件 MCP 没有实际入口

当前 runtime 只创建和启动声明为 auto-start 的插件 MCP，又没有手动 start API，因此 `false` 实际表示永不生效。
对于系统级插件，最简单且一致的规则是：启用插件即启动其 MCP，禁用插件即关闭；不需要为每个 MCP 再建立一套
独立 activation 状态。

目标 Manifest 应移除 `auto_start`。MCP 可以声明 `optional`；必需 MCP 失败使插件 activation 失败，可选 MCP
失败使 generation degraded。

### 4.8 in-process 与 worker 的边界需要以正确性而非沙箱为目标

`python-inprocess` 是用户主动安装并授予代码信任的系统扩展，拥有当前 Python/OS 权限，这是设计事实而不是缺陷。
真正需要修正的是全局 `sys.path/sys.modules` 带来的依赖冲突和卸载不完整：

- in-process 插件必须使用 plugin-owned 顶层 namespace；
- 激活前检测已加载模块冲突；
- 任意独立依赖环境、多语言或进程崩溃隔离需求使用 worker；
- 当前不为每个插件建设 venv 管理器、wheel 仓库或 OS sandbox。

worker 也不需要立即获得万能反向 Host RPC。只有真实 worker 插件需要某项 Host 能力时，才增加一个类型化、可授权
的 protocol method。

### 4.9 durable identity 不应绑定不可重建的随机进程实例

当前恢复要求随机 `generation_id` 精确一致，进程重启后即使 package digest、配置和 contribution contract 完全相同，
也无法重建原 generation。这把进程实例身份误当成了执行契约身份。

目标使用稳定的 `execution_contract_hash` 判断能否恢复，至少覆盖 package digest、有效配置指纹、依赖锁、Plugin API
和 contribution contract。`generation_id` 只标识当前进程内的资源 owner，不作为跨进程兼容条件。

## 5. 必要安全基线

OURO 只保留以下核心安全框架：

1. 第三方 package 严格路径、类型、大小、schema 和 digest 校验；
2. 安装与执行分离，用户插件默认 disabled；
3. executable user plugin 的 code trust 绑定 exact digest；
4. capability/permission 变化使旧授权失效；
5. credential 只通过声明 slot 和引用解析，秘密不进入 manifest、状态、协议和日志；
6. 用户插件工具仍经过 ToolExecutor，`auto` 不由 manifest 单方面获得；
7. tool policy 只能收紧权限；
8. user plugin 不得覆盖 builtin identity；
9. 所有插件资源都有可关闭 owner 和超时/取消路径。

明确不建设：OS sandbox、managed policy、publisher/signature trust root、企业审计平台、细粒度系统调用权限、
多租户隔离。Permission 是 Host service 的授权和用户可见声明，不承诺限制 trusted code 直接调用 OS。

## 6. 与 Pi 的取舍

Pi 值得学习的是插件能参与真实 Agent 生命周期、工具拥有执行上下文、扩展开发反馈短，以及 package 能组合
extensions、Skills、prompts 和 themes。OURO 已通过 Tool、Command、Context、Compaction、Continuation 和
Tool Policy 获得相当一部分深层能力。

OURO 不复制以下模式：

| Pi 模式 | OURO 决策 |
|---|---|
| 直接暴露完整 session manager/runtime/TUI | 使用类型化 application command 和 request context |
| 依加载顺序变换共享可变对象 | 每个语义扩展点定义自己的组合和失败规则 |
| 动态覆盖 builtin tool | builtin identity 永久保留 |
| Run 中途任意改变工具集合 | 新 catalog 只影响新 Run |
| 项目目录自动加载可执行插件 | 插件只有 builtin/user；项目扩展使用 Skill、prompt 或显式工具配置 |

Pi 的同进程 full-trust 并不与 OURO 定位冲突。OURO 的差异主要是 canonical Run、工具审批和 Host 中立边界，
不是追求更重的企业安全模型。

## 7. 明确非目标

下一阶段不实施：

- 项目/workspace 插件和多 scope overlay；
- Marketplace、远程分发 registry、签名和 publisher policy；
- OS sandbox 或企业级权限引擎；
- 每插件虚拟环境和自动第三方依赖安装；
- 自动 worker 重启、熔断和复杂健康策略；
- 通用 UI widget/renderer/keybinding API；
- 万能 middleware、动态 contribution 类型或插件自定义 extension point；
- 对旧 Manifest、旧 state、旧 Plugin API 和旧 worker protocol 的兼容层。

## 8. 建设优先级

1. 统一 builtin/user 插件模型，删除错误 scope 和无语义 Manifest 字段。
2. 建立不可变 `ExtensionCatalog`，让 Run 使用 catalog-local contribution snapshot。
3. 改为候选 generation 先启动、catalog 原子切换、旧代独立 drain。
4. 建立 dependency/observed-state reconciler。
5. 抽取内部 `ContributionTypeAdapter`，统一现有贡献类型的生命周期。
6. 修正 worker cancel/exit、Plugin Skill 和插件 MCP 语义。
7. 以 `execution_contract_hash` 重建 durable recovery。
8. 最后再由真实插件需求增加 Agent、provider、resource、UI 或 worker Host service 扩展点。

这一顺序先修承载所有插件的底层，再增加能力面，符合“框架优化而非补丁修复”的原则。
