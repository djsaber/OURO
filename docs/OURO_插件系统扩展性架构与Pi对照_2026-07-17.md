# OURO 插件系统架构审查与 Pi 对照

状态：当前实现审查与目标架构决策（2026-07-17）

本文以当前代码和可重复测试为事实来源，审查 OURO 插件系统是否符合“强扩展的个人智能体”定位，并给出
下一阶段的底层改良方向。规范性目标以[插件系统目标规格](../dev/specs/plugin-system.md)为准，实施顺序以
[连接与扩展计划](../dev/plans/connectivity-extensions.md)为准。

## 1. 产品边界与审查原则

本次审查采用以下已确认决策：

1. OURO 是强扩展的个人智能体，不是多租户平台或企业插件市场。安全只建立必要的代码信任、Host 能力授权、
   凭据隔离、路径校验和工具审批边界，不建设 OS 沙箱、发布者信任根或复杂策略中心。
2. 插件是 OURO 的系统级扩展模块，只有 `builtin` 与 `user` 两类。不存在项目级或 workspace 级插件；
   workspace 只是一次调用的执行上下文。Skills 与提示词仍可独立具有用户级和工作区级来源。
3. OURO 仍处于开发阶段。Manifest、Plugin API、worker protocol 和持久化模型可以直接修正；旧格式默认严格
   拒绝，不为尚未发布的历史契约保留兼容分支。
4. 社区项目用于校准插件形态和开发体验，不决定 OURO 的内部模型。采用一种社区模式前，必须先证明它符合
   OURO 的 Run、工具、资源和 Host 边界。

## 2. 当前架构理解

当前实现已经形成以下主链：

```text
Source
  -> static package validation
  -> immutable digest store
  -> configuration / capability authorization / code trust
  -> dependency order
  -> plugin generation
  -> prepared contributions
  -> immutable candidate Extension Catalog
  -> atomic current pointer swap
  -> Run-local ExtensionCatalogLease
```

主要职责分布为：

- `ouro/plugins/manifest.py`：Manifest、runtime、contribution 和 permission 声明；
- `ouro/plugins/sources.py`、`package.py`、`store.py`：来源解析、静态校验、内容摘要和不可变存储；
- `ouro/plugins/authorization.py`：配置、能力授权和代码信任判断；
- `ouro/plugins/contribution_types.py`：封闭的 contribution 类型清单与各阶段 facet 组合；
- `ouro/plugins/contributions.py`、`contracts.py`：贡献声明校验、归一化、optional 与 contract hash；
- `ouro/plugins/generation_resources.py`：Skill/MCP generation-owned 资源准备、契约与清理；
- `ouro/plugins/catalog.py`：不可变 Catalog、结构冻结 registry、owner record、generation gate 与 lease；
- `ouro/plugins/runtime.py`：Generation、资源所有权、候选 Catalog 构建、pointer swap 和 retire；
- `ouro/plugins/worker.py`：stdio JSON-RPC worker；
- `ouro/sdk/plugins/v1.py`：独立于 core/application 的插件 SDK；
- `ouro/application/plugins.py`：Host-neutral 插件管理用例。

## 3. 已经合理的设计

以下设计应保留，而不是在后续重构中推翻：

- 安装阶段只做静态校验，不 import entrypoint、不启动 worker/MCP；
- 包内容按 digest 不可变保存，来源记录由 installer 生成，插件不能自报可信身份；
- executable code trust 与 capability authorization 分离；
- 插件工具继续经过 `ToolExecutor`、参数校验、审批、路径和取消边界；
- Contribution 先完整 prepare，再构建独立候选 Catalog；失败不改写 Host baseline 或 current Catalog；
- Plugin SDK 不暴露 `RuntimeService`、`SessionStore` 或具体 Host 对象；
- command、continuation 和 tool policy 使用类型化语义，而不是把所有行为塞进通用 Hook；
- 插件输入保留来源归因，不伪装为用户输入；
- worker 的 stdout、消息大小、超时、凭据和 stderr 已有明确协议边界；
- 插件失败不会阻止无关插件和 OURO 主运行时启动。

可重复基线：

```powershell
.venv\Scripts\python.exe -m pytest -q tests/plugins/test_plugin_system.py tests/application/test_plugin_extensibility.py tests/application/test_run_continuations.py tests/cli/test_plugin_commands.py
```

B3 实施后的阶段全量结果为 `672 passed, 2 skipped`；B5 后插件系统专项结果为 `45 passed`。候选失败、
传递依赖重建、后台服务交接、状态冲突、双 Run 新旧代际、adapter 清单和实际资源契约均已有行为测试保护。

## 4. 需要修正的架构问题

### 4.1 候选 activation 与 Background Service 转交已完成

B2 删除了全局 Catalog barrier；B3 又把 enable/restart/configure/select/revoke 收敛到同一个候选事务。
Runtime 在旧代继续服务时按拓扑构建受影响 generation closure 和候选 Catalog，随后用 expected-state
compare-and-commit 防止并发覆盖；state 提交、generation gate 打开和 current pointer 替换之间没有 `await`。
候选失败不会提交 selection、active configuration revision、Catalog 或 generation，因此 application facade 已删除
“先写 state、失败后恢复”的补偿路径。

依赖 digest/configuration 改变会重建所有传递 desired dependant；旧 generation 只等待引用自身 Catalog 的 lease。
disable/revoke 会关闭 gate、发布移除后的 Catalog，再异步 drain owner。候选 Host data 写入进入隔离 staging，发布
成功后才提交，失败时整体丢弃。该保证覆盖 Host API；full-trust in-process 代码直接绕过 API 的 OS 副作用不属于
框架可承诺的事务边界。

Background Service 保持 activation-singleton：候选期只准备声明，不启动自主服务；发布后先按逆拓扑停止旧代，
再按拓扑启动新代，因而新旧 Catalog 并存也不会运行两份声明式服务。服务启动失败记录为运行诊断；其 degraded/
failed observed-state 投影已由 B4 收敛，B6 已补齐 Worker 取消、严格协议与进程树清理。

为避免为个人应用引入 per-plugin 多锁图，当前候选 mutation 使用单一 runtime lock 串行化；插件代码、I/O、
prepare/start/stop 均不进入 catalog pointer lock。该取舍不阻塞已有 Run，只串行化低频插件生命周期命令。

### 4.2 依赖与 observed health 协调已完成

Resolver 现在把 composition root 提供的 builtin version/contract hash 与 selected user digest 放入同一个 lock graph，
并继续只表达必需插件依赖，不预留 feature system。enable 会先保存 desired intent，再按拓扑协调 generation；实际
失败记录在发生失败的 dependency owner，所有传递依赖者投影为 blocked，不能误显示 ready 或启动。

结构性的 cycle/missing/range conflict 统一投影 incompatible 与稳定诊断；依赖修复或用户 retry 会重新构建 desired
dependant closure。list/show/check/enable/start 读取同一 runtime observed projection。后台 task、optional contribution
和 service 启动失败投影 degraded；worker 退出关闭 gate、撤下受影响 closure并投影 failed。无关 root 不受影响，
shutdown 使用依赖图逆拓扑关闭。

### 4.3 插件 scope 模型与产品定位冲突

审查时状态模型出现 `user/workspace`，但实际上每个 plugin id 只有一份 activation、selection、configuration 和 data。
相同 digest 从另一个 scope 安装也会被直接去重，因此 workspace scope 既不能形成覆盖，也不能形成隔离。B1 已从
state、grant、provenance、CLI 和 DTO 删除该 scope。

这不应通过补齐多 scope overlay 修复，因为产品边界已经明确：插件是系统模块，不是项目资源。

目标修正：

- 删除 workspace、managed 和 development plugin activation scope；
- 插件分类只有 `builtin` 与 `user`；
- builtin 由 OURO 装配，不能被用户安装、替换或卸载；
- user plugin 安装到当前 `OURO_HOME`，每个 plugin id 只有一个 selected digest 和 activation；
- workspace 仅在 Tool/Hook/Command 调用时作为 request context 传入；
- Skills、提示词和项目配置继续独立支持 workspace 来源，不与插件模型合并。

### 4.4 扩展点接入边界已完成收敛

B5 已建立唯一 Host-owned `ContributionTypeAdapter` 清单：

```text
kind
  + declaration validation
  + SDK/worker adaptation
  + conflict and contract rules
  + catalog projection
  + owner cleanup
```

十种 Manifest capability 各有唯一记录，并组合 SDK、worker、prepare/optional、contract、resource 和 Catalog
projection facet。Coordinator、worker、Catalog 与 generation resource 主流程只遍历清单；新增 Host 支持的类型
不再向这些主流程添加条件分支。共享 Tool/Hook projection facet 只表达相同 Catalog 目标，各类型仍保留独立
声明、冲突与组合语义。

Host 仍显式决定支持哪些 contribution。清单是不可动态注册的内部常量，没有向用户插件开放类型注册 API，
也没有发展成万能事件总线、middleware 或动态类型系统。Background Service 唯一标记为
`activation-singleton`，其 projection 是显式 no-op；其余类型为 `snapshot-bound`。

### 4.5 observed status 与 worker 正确性边界已收敛

B4 已使 worker 异常退出关闭 gate 并撤下受影响 closure；background task 与 optional contribution 失败会投影
degraded。request timeout 与外层 task cancellation 均会发送 JSON-RPC cancel，显式 `restart` 继续复用候选发布。
这些行为形成个人应用所需的最小闭环：

- worker 退出立即撤销其可调用 contribution，并将 generation 标记为 failed；
- request timeout 和 task cancellation 都发送 cancel；
- background task 失败使 generation degraded，并产生有界 diagnostic；
- 提供显式 `restart`，当前阶段不实现自动重启预算、熔断或复杂 backoff policy。

B6 已补齐 stdout pollution、oversize、`result/error` 互斥、semantic invalid result、stderr 限流脱敏、无 pending
request 退出和进程树关闭。协议外 stdout 一律为 fatal，诊断消息和数量有界；timeout 与外层 task cancellation 都
发送 JSON-RPC `cancel`，退出使全部 pending future 失败。Windows 先终止仍存活父进程的完整子树，POSIX 使用独立
process group。显式 restart 继续复用候选发布，未增加自动健康策略。

### 4.6 Plugin Skills 已进入统一 Run-local Skill Catalog

Plugin Skill 已不再转换为 `after_context_build` Hook。基础 user/workspace Skill 与 `source=plugin` metadata 一起
进入不可变 Extension Catalog；名称冲突使候选整体失败，不按加载顺序覆盖。每个声明必须恰好解析一个同名
`SKILL.md`，并携带 plugin id、package digest、generation 与 contribution provenance。模型提示词在每轮从 Run lease
生成；插件禁用后新 Run 不再看到它，旧 lease 仍从不可变 package 读取对应内容。

### 4.7 Plugin MCP activation 与资源型接入已收敛

B1 已从 Manifest 删除 `auto_start`：启用 generation 时启动其全部 MCP，禁用时随 owner 关闭，不再维护第二套
MCP activation 状态。B2 将已发现 MCP Tool 冻结进 Run Catalog，因此 server 变化不会在同一 Run 中改变工具集合。
B5 又把 MCP 连接与工具发现移入 generation resource adapter：required MCP 失败阻止整个候选，optional MCP 失败
投影 degraded；只有实际 connected server 才生成资源 contract。B6 已用真实 stdio server 验证工具调用、Catalog
结构冻结、非阻塞 disable 后 generation retirement，以及连接/子进程关闭；server 变化只在下一 generation 生效。

### 4.8 in-process 与 worker 的边界需要以正确性而非沙箱为目标

`python-inprocess` 是用户主动安装并授予代码信任的系统扩展，拥有当前 Python/OS 权限，这是设计事实而不是缺陷。
全局 `sys.path/sys.modules` 带来的依赖冲突和卸载不完整已经按以下边界修正：

- Manifest namespace 映射为唯一 canonical `<namespace>_plugin` 顶层名；
- 激活前检测 canonical 已加载模块冲突，实际 generation 加载到 `_ouro_plugin_<generation_id>` 私有 module tree；
- bundled dependency 位于 owned package 并使用相对 import，新旧 generation 可以并存且按 owner 卸载；
- 任意独立依赖环境、多语言或进程崩溃隔离需求使用 worker；
- 当前不为每个插件建设 venv 管理器、wheel 仓库或 OS sandbox。

worker 也不需要立即获得万能反向 Host RPC。只有真实 worker 插件需要某项 Host 能力时，才增加一个类型化、可授权
的 protocol method。

### 4.9 durable identity 不应绑定不可重建的随机进程实例

实现已使用稳定 `execution_contract_hash` 判断能否恢复，覆盖 package digest、配置修订、传递依赖锁、Plugin API、
worker protocol 和 contribution contract。`generation_id` 只标识当前进程内的资源 owner，不作为跨进程兼容条件。
若 current selection 已更新但旧 digest、配置和依赖仍完整，runtime 构建非当前 generation 与精确 Catalog 服务旧
durable Run；缺包或重建 contract 不一致时明确失败。

## 5. 必要安全基线

OURO 只保留以下核心安全框架：

1. 第三方 package 严格路径、类型、大小、schema 和 digest 校验；
2. 安装与执行分离，用户插件默认 disabled；
3. executable user plugin 的 code trust 绑定 exact digest；
4. capability/permission 变化使旧授权失效；
5. credential 只通过声明 slot 和引用解析，秘密不进入 manifest、状态、协议和日志；
6. 用户插件工具仍经过 ToolExecutor，`auto` 不由 manifest 单方面获得；
7. tool policy 只能收紧权限；
8. user plugin 不得覆盖 builtin identity；
9. 所有插件资源都有可关闭 owner 和超时/取消路径。

明确不建设：OS sandbox、managed policy、publisher/signature trust root、企业审计平台、细粒度系统调用权限、
多租户隔离。Permission 是 Host service 的授权和用户可见声明，不承诺限制 trusted code 直接调用 OS。

## 6. 与 Pi 的取舍

Pi 值得学习的是插件能参与真实 Agent 生命周期、工具拥有执行上下文、扩展开发反馈短，以及 package 能组合
extensions、Skills、prompts 和 themes。OURO 已通过 Tool、Command、Context、Compaction、Continuation 和
Tool Policy 获得相当一部分深层能力。

OURO 不复制以下模式：

| Pi 模式 | OURO 决策 |
|---|---|
| 直接暴露完整 session manager/runtime/TUI | 使用类型化 application command 和 request context |
| 依加载顺序变换共享可变对象 | 每个语义扩展点定义自己的组合和失败规则 |
| 动态覆盖 builtin tool | builtin identity 永久保留 |
| Run 中途任意改变工具集合 | 新 catalog 只影响新 Run |
| 项目目录自动加载可执行插件 | 插件只有 builtin/user；项目扩展使用 Skill、prompt 或显式工具配置 |

Pi 的同进程 full-trust 并不与 OURO 定位冲突。OURO 的差异主要是 canonical Run、工具审批和 Host 中立边界，
不是追求更重的企业安全模型。

## 7. 明确非目标

下一阶段不实施：

- 项目/workspace 插件和多 scope overlay；
- Marketplace、远程分发 registry、签名和 publisher policy；
- OS sandbox 或企业级权限引擎；
- 每插件虚拟环境和自动第三方依赖安装；
- 自动 worker 重启、熔断和复杂健康策略；
- 通用 UI widget/renderer/keybinding API；
- 万能 middleware、动态 contribution 类型或插件自定义 extension point；
- 对旧 Manifest、旧 state、旧 Plugin API 和旧 worker protocol 的兼容层。

## 8. 建设优先级

1. [已完成] 统一 builtin/user 插件模型，删除错误 scope 和无语义 Manifest 字段。
2. [已完成] 建立不可变 `ExtensionCatalog`，让 Run 使用 catalog-local contribution snapshot。
3. [已完成] 改为候选 generation 先启动、catalog 原子切换、旧代独立 drain。
4. [已完成] 建立 dependency/observed-state reconciler。
5. [已完成] 抽取内部 `ContributionTypeAdapter`，统一现有贡献类型的生命周期。
6. [已完成] 收口 worker/in-process 正确性，并让 Plugin Skill 进入统一 Run-local Catalog。
7. [已完成] 以 `execution_contract_hash` 重建 durable recovery。
8. [已完成] 提供最小 scaffold、三类示例、兼容报告与 SDK 开发文档；之后只由真实插件需求增加 Agent、provider、
   resource、UI 或 worker Host service 扩展点。

这一顺序先修承载所有插件的底层，再增加能力面，符合“框架优化而非补丁修复”的原则。
