# OURO 插件系统扩展性架构与 Pi 对照

状态：当前实现与设计基线（2026-07-17）

本文回答的不是“OURO 能否实现某一个 `/goal` 插件”，而是：OURO 应如何在保持可恢复 Run、Host 中立、
权限边界和可审计更新的前提下，提供足以承载多类深度插件的稳定扩展能力。`/goal` 只是其中一个验收场景。
规范性契约以[插件系统规格](../dev/specs/plugin-system.md)为准。

## 1. 结论

OURO 当前已经形成四个相互分离的扩展平面：

1. **包与治理平面**：安装、来源、不可变 digest、代码信任、能力授权、配置、依赖和更新回滚；
2. **能力贡献平面**：Tool、Command、Hook、Context、Compaction、Skills、MCP 和 background service；
3. **语义控制平面**：Run continuation 与 tool policy，由 application 层解释类型化决策；
4. **Host 执行平面**：Session/Run、消息来源、排队、审批、路径约束、取消、恢复和 generation lease。

这一结构可以实现目标模式、plan/read-only mode、危险命令门禁、受保护路径、领域工具、动态上下文、专用压缩、
远端服务桥接、会话自动化和长期连接等插件。插件不需要、也不应直接接管 `RuntimeService` 或 `SessionStore`。

与 Pi 相比，OURO 不追求“把整个交互应用对象交给同进程扩展”的最大自由度，而采用“贡献能力 + 类型化决策 +
Host 执行”的模型。它牺牲一部分即时 hackability，换取跨 CLI/Desktop/HTTP Host 的一致行为、稳定组合、精确恢复、
权限单调性和 side-by-side generation。当前扩展面已经适合继续以真实插件需求增量演进，不需要重写为通用事件总线
或万能 middleware。

## 2. Pi 的设计模式

本次复核基于 Pi 官方仓库 commit `f7e060374541be0097ee015aaddb097a4f760984`，重点阅读
[`extensions.md`](https://github.com/badlogic/pi-mono/blob/f7e060374541be0097ee015aaddb097a4f760984/packages/coding-agent/docs/extensions.md)、
[`types.ts`](https://github.com/badlogic/pi-mono/blob/f7e060374541be0097ee015aaddb097a4f760984/packages/coding-agent/src/core/extensions/types.ts) 和
[`runner.ts`](https://github.com/badlogic/pi-mono/blob/f7e060374541be0097ee015aaddb097a4f760984/packages/coding-agent/src/core/extensions/runner.ts)。

Pi Extension 本质上是宿主内部 SDK：扩展可注册工具、命令、快捷键、flag、provider 和 renderer，监听或变换
agent/turn/message/tool/session/compaction/model 请求，并使用 TUI、模型选择、active tools、session manager、
event bus 等宿主能力。工具执行同时得到工作目录、AbortSignal、UI 和 session 等上下文。

它的长处很明确：

- 扩展点覆盖 Agent 应用的完整生命周期，开发者能快速组合新交互模式；
- tool call 前置事件可以阻断调用，适合 plan mode 和权限门禁；
- 工具拥有取消、工作目录和会话上下文，不必自行猜测 Host 状态；
- 自定义 session entry、renderer 和 event bus 让扩展状态与 UI 联动直接；
- 公开示例本身就是可执行设计文档，插件开发反馈周期短。

这些能力也伴随一组适合 Pi、但不应无条件复制到 OURO 的取舍：

- 扩展与宿主同进程、同权限域，项目级信任后可直接访问文件、网络、进程和宿主对象；
- 大量处理器按装载顺序串行变换共享状态，顺序成为强语义，组合结果可能依赖 load order；
- 自定义工具可覆盖 builtin，适合个人 hackability，但不适合 OURO 的 durable tool identity；
- TUI、session manager 和 runtime 对象直接进入公共 API，使插件与具体 Host 生命周期耦合；
- 包更新与运行 generation 的隔离比 OURO 简单，不承担 pending approval 精确恢复的同等约束。

因此，Pi 值得学习的是“扩展应能参与真实 Agent 生命周期”和“调用上下文必须足够”，而不是复制它的全部对象模型。

## 3. 采用、改造与延期

| Pi 经验 | OURO 决策 | 原因 |
|---|---|---|
| 工具获得 cwd、取消等执行上下文 | **采用并收窄**为 `ToolExecutionContext` | 插件能正确遵循 workspace/cancel，但不取得 Host/runtime 对象 |
| tool-call 前置阻断 | **采用并类型化**为 `tool_policies` | 支持 plan mode、危险命令、保护路径；只允许审批升级或拒绝 |
| 生命周期事件可驱动下一步 | **采用并拆分**为 continuation policy | 自动续跑需要 durable checkpoint、幂等队列和 generation 归因 |
| 扩展命令控制交互 | **采用 Host-neutral 输出** | command 返回 `SessionInput`，由各 Host 映射，不直接操作 TUI |
| session 自定义状态 | **保留插件私有 data** | 当前没有多个插件证明需要通用 session KV/CAS，不提前引入数据库抽象 |
| 动态注册/覆盖工具 | **不采用** | OURO 在 Run 开始冻结工具 contract；动态覆盖会破坏恢复和审计 |
| 共享可变 middleware | **不采用** | 参数/权限/identity 的组合需要按语义定义，而非依赖加载顺序 |
| 完整 TUI API、renderer、快捷键 | **延期** | 尚无 TUI/Desktop 共同的 Host-neutral 需求，当前使用 command/event/DTO |
| 任意 model provider 注册 | **延期** | 需要稳定的 streaming adapter、credential、模型目录和 close contract |
| 直接暴露 session manager/runtime | **不采用** | 会绕过 canonical transaction、Run lock、消息来源和恢复不变量 |

这里的延期不是用 placeholder 宣称支持。只有出现至少一个真实插件需求，并能同时定义 in-process/worker、
生命周期、权限、故障和恢复语义时，才新增稳定 contribution。

## 4. 当前扩展能力

| 扩展点 | 典型用途 | 组合与边界 |
|---|---|---|
| Tool | 领域动作、数据访问、代码工具 | schema 校验，统一审批/路径/取消/恢复；第三方 `auto` 降级 |
| Tool policy | plan mode、危险命令确认、保护路径、合规限制 | `ignore/require_approval/deny`，最严格值，失败拒绝，不能改参数或批准 |
| Command | 模式切换、配置动作、目标管理、手工同步 | canonical name；可请求合成会话输入，不能写 SessionStore |
| Hook | 观察 Run/tool/event，富化上下文 | 只暴露有真实 producer 的事件；普通 Hook 不承担语义控制 |
| Context provider | 仓库规则、领域状态、动态提示 | 追加带 owner 的片段，不改 canonical 历史 |
| Compaction strategy | 领域摘要、状态保留 | owner/contract hash 固定，不改消息事实 |
| Continuation policy | 目标模式、自动审查迭代、队列消费者 | Run 终态决策，冲突/故障暂停，稳定 queue id |
| Skills / MCP | 可移植指令、远端工具服务 | 冻结到 generation，仍经过 OURO 工具权限边界 |
| Background service | watcher、连接池、订阅、缓存刷新 | owner 监督 start/stop，不隐式获得 Session 写权限 |

### 4.1 工具执行上下文

兼容旧插件的 `handler(call)` 仍有效；in-process 插件可改为 `handler(call, context)`。context 提供：

- 当前 workspace 与 `workspace_only`；
- `is_aborted`、`abort_reason`、`raise_if_aborted()`；
- 可取消 `sleep()`；
- 与内置工具一致的 `resolve_path()` 和 `resolve_working_directory()`。

worker 工具通过 `ToolCall` 获得 workspace 字段，并在 Host request task 取消时收到 JSON-RPC `cancel`。两种 runtime
共享语义，但不伪装成相同 Python 对象，也不把内部 `AbortSignal` 序列化到协议。

### 4.2 工具策略

普通 `before_tool_call` Hook 仍用于观察。真正影响执行的策略独立注册，原因是权限结果必须满足安全单调性：

```text
Host/tool permission + session approval mode
                  |
                  v
        tool policy restrictive join
       ignore < require_approval < deny
                  |
                  v
          schema / approval / execute
```

策略按稳定 identity 排序；`deny` 短路；异常、超时和非法结果 fail-closed。它不能把 `deny/approval` 降成 `auto`，
不能批准自己的工具，也不能重写参数。若用户在审批时修改参数，最终参数会在执行前再次经过策略，避免保护规则被
“先请求安全参数、审批时改成危险参数”绕过。

## 5. `/goal` 作为验收场景

目标模式同时验证 command、plugin data、continuation、合成输入、交互并发、暂停恢复和 generation provenance：

- `/goal <objective>`：command 写插件私有目标状态并请求初始输入；
- 每个 Agent Run 结束：continuation policy 返回继续、完成、暂停或失败；
- 用户修改目标或插入引导：command 返回 steer/follow-up，或用户使用标准 Host 输入；
- 暂停/恢复：只改变插件目标状态；真正创建 Run、排队和持久化仍由 application 层完成；
- 多策略竞争、策略故障、abort 或旧 Run 被用户输入取代：Host 保守暂停或标记 superseded。

这证明插件可以扩展“跨 Run 控制”，但框架没有为 `/goal` 引入专用 workflow engine。相同 continuation 契约还可承载
自动测试修复循环、审查—修改循环、批次消费和周期性检查等插件。

## 6. 仍然明确不支持的能力

当前不宣称以下能力已经存在：

- 恶意 in-process 插件的安全沙箱；
- worker 的 OS 权限隔离、自动重启/熔断和任意反向 Host RPC；
- 动态覆盖 builtin、Run 中途改变 active tool contract；
- 通用 UI widget/renderer/keybinding API；
- 第三方 model provider contribution；
- 任意 session history mutation、用户消息伪装或直接 Runtime/Store 访问；
- catalog/signature/publisher trust root 和自动第三方依赖安装。

这些边界不会阻止强插件，而是防止扩展 API 把可恢复 Agent 的底层不变量变成插件自律。

## 7. 后续扩展判定规则

新增稳定扩展点前应同时回答：

1. 是否已有真实插件无法用现有 Tool/Command/Hook/Policy/Service 表达？
2. 输入和输出能否类型化，组合顺序、冲突和超时是否确定？
3. 失败应 fail-open、fail-closed、回到审批还是暂停？
4. in-process 与 worker 如何提供等价语义，取消和输出上限如何传播？
5. contribution 如何进入 owner transaction、generation snapshot、contract hash 和恢复？
6. CLI/Desktop/HTTP Host 是否能共享，而不暴露某个 Host 对象？
7. 是否会放宽工具权限、消息来源、Session transaction 或凭据边界？

无法同时回答这些问题时，先以插件私有实现或现有类型化边界验证需求，不增加空 manifest 字段。

## 8. 验收证据

当前测试覆盖：

- 一参数工具兼容与两参数 `ToolExecutionContext`；
- workspace/path/cancel 上下文传递；
- in-process 与 worker 的 tool policy 协议；
- 多策略最严格组合、异常脱敏、超时 fail-closed；
- policy 提升审批、硬拒绝不能被 session `auto` 放宽；
- 真实插件阻止 builtin Bash，且审批修改最终参数会重新评估；
- continuation 的多轮自动执行、冲突暂停、幂等入队、合成消息来源和交互中 steer/follow-up。

## 9. 通用性与复杂度收口审计

生产框架不包含 `goal`、`/goal`、objective 或目标状态特判；这些名称只出现在设计说明和验收插件中。框架新增的稳定语义均可独立服务于其他插件：

| 边界 | 唯一职责 | 未纳入的职责 |
|---|---|---|
| `SessionInput` | 表达带来源的 follow-up/steer 请求 | 不写 Session、不创建 Run |
| continuation policy | 根据终态 `RunOutcome` 返回下一步意图 | 不排队、不持久化、不解决并发冲突 |
| `RunContinuationService` | 在 application 层完成幂等入队、冲突处理和 checkpoint 持久化 | 不保存插件业务状态、不判断目标是否完成 |
| tool policy | 只做安全单调的审批升级或拒绝 | 不改参数、不批准调用、不替代 Host 权限 |
| bounded callback helper | 统一真实存在的同步/异步回调与超时边界 | 不成为通用 middleware 或事件总线 |

审计明确没有引入通用 workflow engine、任意 session mutation、万能 middleware、所有 registry 的抽象基类、动态覆盖机制，或尚无真实需求的 provider/UI 占位接口。continuation 与 tool policy 保持独立，是因为两者的组合与失败语义不同；强行抽成统一“策略引擎”会隐藏安全和恢复规则，而不是减少复杂度。

贡献发布仍是一个 owner 原子事务：tools、hooks、commands、compaction、continuation 和 tool policy 任一提交失败，注册表与 owner lease 一并回滚。SDK 不依赖 OURO 内部模块；Core 不反向依赖 application/plugin/CLI；这些约束由架构测试固定。
