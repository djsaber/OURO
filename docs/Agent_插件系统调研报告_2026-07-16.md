## 2. 核心结论

四个系统并不是同一种插件模型：

- Claude Code 是“声明式能力包 + 外部进程适配”，分发和组织治理最成熟；
- Codex 是“声明式资源包 + 强装载治理”，公开插件与内部 Rust 扩展严格分离；
- Pi 是“宿主内可编程扩展 API”，最接近一个嵌入式 Agent SDK；
- OpenCode 是“宿主内 Hook 中间件”，强调对行为管线的拦截、变换和快速开发。

插件能力强弱、供应链成熟度、隔离程度和开发体验是不同坐标，不能用一个总排名表达。

## 3. Claude Code：可分发的能力组合包

### 3.1 包模型与贡献面

Claude Code 插件是一个自包含目录，可以组合 Skills、旧式 commands、subagents、Hooks、MCP、LSP、
monitors、themes、output styles、settings、脚本和辅助文件。它更接近“能力部署单元”，而不是一个
JavaScript/Rust 动态入口点。参见[插件参考](https://code.claude.com/docs/en/plugins-reference)。

插件通过 `.claude-plugin/plugin.json` 描述。组件路径必须相对插件根目录，宿主将插件复制到版本化缓存，
来源目录、已安装副本和会话实际使用版本彼此分离。

### 3.2 执行边界

- Skill 和 agent 主要是指令资源；
- Hook 通过 command、HTTP、MCP tool、prompt 或 agent 执行；
- MCP、LSP 是独立服务进程；
- Monitor 是长期运行的外部命令。

这避免向第三方暴露 Claude Code 内部对象模型，降低内部 ABI 耦合并隔离进程崩溃。但进程隔离不等于
权限沙箱：command hook、monitor、MCP 和 LSP 仍可能拥有当前用户的完整操作系统权限。

插件 subagent 不能自行在 frontmatter 中声明 Hooks、MCP servers 或 permission mode。这阻止 agent
定义悄悄改变宿主安全边界。

### 3.3 Hook 模型

Claude Code 的 Hook 事件覆盖 Session、Setup、Prompt、Compact、Pre/Post Tool、Tool Failure、Tool Batch、
Permission Request/Denied、Subagent、Task、Stop、MCP elicitation、Config、CWD、File 和 Worktree 等变化。
参见 [Hooks 文档](https://code.claude.com/docs/en/hooks)。

同一事件的所有匹配 Hook 并行执行，相同命令或 HTTP URL 会去重。Host 根据退出码和结构化结果解释阻断、
允许、修改或附加上下文。异步 Hook 不阻断当前动作，但可以在完成后重新唤醒会话。

这种模型具有以下性质：

- 独立观察者不会线性累加延迟；
- Hook 之间不适合依赖共享可变状态；
- 故障策略由事件风险决定，不是全局统一的 fail-open 或 fail-closed；
- 外部进程协议比内部对象 API 稳定，但诊断链路更长。

### 3.4 命名与冲突

Claude Code 对用户和模型可见能力广泛使用命名空间，例如 `/plugin:skill`、`plugin:agent`，MCP tool
名称包含插件和服务器身份。LSP 按文件扩展名竞争，第一个有效服务器获胜。面向用户的能力尽量避免静默
覆盖，底层独占资源则采用确定优先级。

### 3.5 分发与生命周期

Claude Code 的突出优势是供应链与组织治理：

- Marketplace 与 plugin 是两层清单；
- 支持本地、Git/GitHub、子目录、URL、npm 等来源；
- Marketplace 和插件来源可分别固定 ref/SHA；
- 支持 user、project、local、managed 等作用域；
- 支持插件依赖、传递启用、依赖保护和孤儿依赖清理；
- 版本缓存允许旧会话继续运行旧版本；
- 更新后当前会话的 Hook、MCP、LSP 通常保持旧实例，直到 reload 或重启；
- 持久数据和代码缓存分离；
- 企业策略可以限制允许的 Marketplace 来源。

参见 [Marketplace 文档](https://code.claude.com/docs/en/plugin-marketplaces)。其设计重心是稳定分发、
团队治理和跨会话一致性，高于向第三方开放宿主内编程接口。

## 4. Codex：公开插件与内部扩展分层

### 4.1 两套不可混淆的机制

Codex 源码存在功能很强的 `codex-extension-api`，可以注册工具、上下文贡献者、线程生命周期和审批审查器。
但它由 app-server 在编译期安装内部扩展，例如 goals、guardian、skills、MCP、web search 和 image
generation；公开插件包不能加载任意 Rust 扩展。参见[内部扩展注册源码](https://github.com/openai/codex/blob/03bb3b12367397e14a8facc2e018d645ff4d8e83/codex-rs/app-server/src/extensions.rs)。

公开插件当前主要贡献 Skills、MCP servers、Apps/connectors 和 Hooks。Manifest 是路径和资源声明，
而不是 Rust crate 入口点。参见[公开插件构建文档](https://learn.chatgpt.com/docs/build-plugins)和
[Manifest 源码](https://github.com/openai/codex/blob/03bb3b12367397e14a8facc2e018d645ff4d8e83/codex-rs/plugin/src/manifest.rs)。

### 4.2 装载管线

Codex 将处理拆为来源 Provider、Marketplace 解析与策略检查、source materialization、manifest 验证、
Store 安装、用户配置启用和各资源 Loader 激活。重要细节包括：

- 插件 ID 同时包含插件名与 Marketplace 身份；
- manifest 路径必须以 `./` 开始，不允许绝对路径和 `..`，解析后仍须位于根目录；
- 可以识别 Codex、Claude、Cursor 的 manifest 位置；
- manifest 控制 MCP transport，用户配置只控制启用、工具白名单和 approval policy；
- 单个无效 MCP server 可以降级为 warning；
- 插件只有“已启用且无致命错误”才形成 active load outcome。

### 4.3 安装事务

Codex 先复制到同文件系统 staging，在 staging 内完成迁移和 manifest 补全，再通过 rename 激活。替换
现有版本时会先备份旧目录，激活失败则恢复，成功后清理旧版本。参见
[Plugin Store 源码](https://github.com/openai/codex/blob/03bb3b12367397e14a8facc2e018d645ff4d8e83/codex-rs/core-plugins/src/store.rs)。

事务边界只覆盖代码缓存，不覆盖所有状态：文件安装成功后才写用户配置，卸载也是先删缓存、再删配置。
它是文件系统内原子，而不是完整跨存储事务。

### 4.4 Hook 信任

当前源码实际只执行 command hook；prompt、agent、async 类型会被跳过并产生诊断。Hook 来源分为 managed、
system、user、project、session、plugin。非托管 Hook 定义会被哈希并投影为 `Untrusted`、`Trusted` 或
`Modified`，管理策略提供的 Hook 为 `Managed`。只有 trusted/managed Hook 执行。

因此“安装插件”和“信任插件中的命令 Hook”是两个独立动作。参见
[Hook discovery](https://github.com/openai/codex/blob/03bb3b12367397e14a8facc2e018d645ff4d8e83/codex-rs/hooks/src/engine/discovery.rs)。

匹配 Hook 并发运行，但结果恢复为配置顺序再交给上层。命令 Hook 一旦被信任，会直接启动用户进程，
不是自动进入 Codex shell sandbox。参见
[command runner](https://github.com/openai/codex/blob/03bb3b12367397e14a8facc2e018d645ff4d8e83/codex-rs/hooks/src/engine/command_runner.rs)。

### 4.5 评价

Codex 的主要优势是公开边界明确、来源/安装/启用/信任/运行分层、文件更新可回滚、Hook 修改使旧授权
失效，以及对局部损坏的容忍。当前不足是公开贡献面较窄、部分 schema 类型尚未执行、缓存与配置不是
同一事务，且热重载比较保守。

## 5. Pi：宿主内的完整 Agent 扩展 SDK

### 5.1 Package 与 Extension

Pi package 是分发单元，可以包含 Extensions、Skills、prompt templates 和 themes；Extension 才是运行时
编程接口。来源支持 npm、Git、本地目录，以及 global、project、临时命令行作用域。参见
[Packages 文档](https://github.com/badlogic/pi-mono/blob/5220aba61970fc9f284a7c71e95669b52b4f47a8/packages/coding-agent/docs/packages.md)。

Extension 由 `jiti` 直接加载 TS/JS async factory，和 Pi 位于同一进程、同一权限域。

### 5.2 API 能力

Pi Extension 可以注册工具、命令、快捷键、flags、模型提供商、消息/session renderer；监听或改变 Agent、
turn、message、tool、session、compaction、模型请求、headers、上下文和 system prompt；调用 TUI，切换
模型和 active tools，执行命令，写入会话事件，并通过 event bus 通信。

它更像公开 Agent 应用内部 SDK，而不只是插件 API。参见
[Extensions 文档](https://github.com/badlogic/pi-mono/blob/5220aba61970fc9f284a7c71e95669b52b4f47a8/packages/coding-agent/docs/extensions.md)。

### 5.3 顺序与冲突

大量事件按扩展装载顺序串行执行；后一个扩展可见前一个扩展的修改，阻断事件通常由第一个拒绝者短路。
大多数异常被隔离，`tool_call` 前置处理则更偏 fail-closed。参见
[Runner 源码](https://github.com/badlogic/pi-mono/blob/5220aba61970fc9f284a7c71e95669b52b4f47a8/packages/coding-agent/src/core/extensions/runner.ts)。

冲突策略按资源类型分别定义：工具和 flags 通常 first-wins，命令重复时编号并存，快捷键后者胜出并诊断，
保留快捷键不可覆盖，自定义工具允许有意覆盖内置工具并告警。Pi 优先个人定制和 hackability，而不是生态隔离。

### 5.4 信任与生命周期

项目 `.pi` 资源只有在整个项目被信任后加载，但信任是目录级而非能力级。一旦加载，扩展可以直接访问
文件、网络、进程和宿主对象。

`/reload` 会关闭旧 runtime、重载资源并使旧 context 失效。包管理则相对朴素：npm 使用共享 prefix，
Git 在现有 clone 中 reset/clean/update，没有版本化 staging、原子切换和自动回滚。参见
[Package manager](https://github.com/badlogic/pi-mono/blob/5220aba61970fc9f284a7c71e95669b52b4f47a8/packages/coding-agent/src/core/package-manager.ts)。

Pi 的强项是运行时扩展能力和开发效率，弱项是供应链隔离、依赖隔离和安装事务。

### 5.5 2026-07-17 上游复核与 OURO 取舍

为验证 `/goal` 之外的通用扩展能力，本次又以 Pi commit
[`f7e0603`](https://github.com/badlogic/pi-mono/tree/f7e060374541be0097ee015aaddb097a4f760984) 复核官方
[`extensions.md`](https://github.com/badlogic/pi-mono/blob/f7e060374541be0097ee015aaddb097a4f760984/packages/coding-agent/docs/extensions.md)、
[`types.ts`](https://github.com/badlogic/pi-mono/blob/f7e060374541be0097ee015aaddb097a4f760984/packages/coding-agent/src/core/extensions/types.ts) 和
[`runner.ts`](https://github.com/badlogic/pi-mono/blob/f7e060374541be0097ee015aaddb097a4f760984/packages/coding-agent/src/core/extensions/runner.ts)。
前述“宿主内部 SDK、同进程 full trust、串行变换和高度 TUI 耦合”的结论仍成立。

本轮最值得吸收的不是继续增加事件数量，而是两个贯穿多类插件的模式：

1. 工具必须得到当前工作目录、取消信号等 request-scoped 执行上下文；否则第三方工具无法与 builtin 共享
   路径和中止语义。
2. 工具调用前的语义阻断必须是可组合的一等契约；只提供观察型 `before_tool_call` 无法实现 plan mode、
   危险命令确认、保护路径或合规门禁。

OURO 将第一点收窄为 Host-owned `ToolExecutionContext`，将第二点实现为限制性 `tool_policies`：策略只能
`ignore/require_approval/deny`，取最严格结果，失败拒绝，不能批准、改写参数或降低 Host policy。用户在审批时
修改参数后，最终参数会再次评估。这样保留 Pi 的扩展表达力，同时避免把加载顺序、可变参数链和整个 Host 对象
变成公共 API。

本轮明确不复制 Pi 的 builtin tool 覆盖、动态 active tools、完整 TUI/session manager 暴露和任意 provider
注册。前两项会破坏 OURO 的 Run generation/contract 恢复；UI 尚无跨 Host 共同需求；provider contribution
则需要 streaming、credential、模型目录和 close contract 一起稳定后再引入，不能用 manifest placeholder
代替实现。

## 6. OpenCode：顺序执行的行为中间件

### 6.1 基本模型

OpenCode 插件是 JS/TS 函数，接收 project、client、directory/worktree 和 shell helper，返回 Hooks 对象。
当前 Hook 面覆盖事件、配置、自定义工具、认证/provider、message/params/headers、permission、command、
tool definition/before/after、shell environment，以及 system prompt、messages、compaction 等实验性变换。

参见[插件文档](https://opencode.ai/docs/plugins/)和
[Hook 类型](https://github.com/anomalyco/opencode/blob/17544802c38a4d35834275526ccf38be1cdcfbf4/packages/plugin/src/index.ts)。

### 6.2 装载与供应链

插件可以来自全局/项目配置中的 npm 或 file spec，也可以来自全局和项目插件目录。配置重复 npm 包按身份
去重，不同本地文件仍是独立插件。包解析可并行，factory 最终按配置顺序执行。参见
[Loader 源码](https://github.com/anomalyco/opencode/blob/17544802c38a4d35834275526ccf38be1cdcfbf4/packages/opencode/src/plugin/loader.ts)。

OpenCode 使用 `engines.opencode` 做兼容性门控，npm 安装禁用 lifecycle scripts，entry 必须位于安装目录。
但缓存已有包时通常直接复用，没有版本化原子切换、失败回滚和会话版本固定。

### 6.3 Hook 与权限

主要 Hook 按注册顺序串行运行并共享可变 output。后一个插件看到前一个插件的修改，顺序因此成为强公共
语义。运行 Hook 抛错通常向上传播并中止当前操作，插件导入或初始化失败则隔离并跳过。

自定义工具在内置工具之后合并，可以覆盖内置工具；多个插件同名时后者胜出。参见
[Tool registry](https://github.com/anomalyco/opencode/blob/17544802c38a4d35834275526ccf38be1cdcfbf4/packages/opencode/src/tool/registry.ts)。

Agent tool permission 只约束通过宿主权限 API 发起的操作。插件本身在宿主进程运行并获得 shell helper，
可以绕过宿主工具层直接访问系统，因此 tool permission 不能被解释为插件代码权限。

### 6.4 演进中的 TUI 与 V2

`dev` 分支已存在新的 TUI plugin runtime，包含命令、键位、模式、dialog、toast、状态、KV、主题、renderer、
AbortSignal、LIFO cleanup、超时和动态启停。但它尚不是主文档中的稳定接口。参见
[TUI runtime](https://github.com/anomalyco/opencode/blob/17544802c38a4d35834275526ccf38be1cdcfbf4/packages/opencode/src/plugin/tui/runtime.ts)。

V2 Effect 文档提出 scoped registrations、domain transforms、rebuild/reload 等模型，但明确是实施计划，
不能作为当前能力。参见 [V2 计划](https://github.com/anomalyco/opencode/blob/17544802c38a4d35834275526ccf38be1cdcfbf4/packages/plugin/src/v2/effect/PLAN.md)。

## 7. 统一比较

| 维度 | Claude Code | Codex | Pi | OpenCode |
|---|---|---|---|---|
| 核心抽象 | 可分发能力包 | 可验证资源包 | 宿主内扩展 SDK | Hook 中间件 |
| 第三方任意代码 | 外部命令/服务 | 外部 Hook/MCP；无公开 Rust 入口 | 同进程 TS/JS | 同进程 TS/JS |
| 主要贡献面 | Skills、agents、Hooks、MCP、LSP、主题等 | Skills、apps、MCP、Hooks | 工具、事件、UI、模型、provider、会话等 | 工具、provider、请求/工具/权限变换 |
| Hook 组合 | 匹配者并发 | 匹配者并发、结果恢复顺序 | 串行可变链 | 串行可变链 |
| 冲突倾向 | 命名空间优先 | 稳定身份与来源分层 | 按资源制定覆盖策略 | 后注册覆盖较常见 |
| 信任 | 安装/作用域 + 宿主审批；外部进程有 OS 权限 | 安装、启用、Hook 哈希信任、MCP policy 分离 | 项目目录整体信任 | 配置/项目信任，加载后完全可信 |
| 更新 | 版本缓存、会话保留旧实例 | staging、backup、rename、rollback | npm/Git 原地更新 | npm 缓存复用 |
| 热重载 | reload，部分服务需重启 | 偏新会话/重新发现 | 重建 runtime | server API 不强调；TUI runtime 正在完善 |
| UI | 主题、输出样式、monitor | Apps 是连接器 | 完整 TUI API | TUI 插件 runtime 正在形成 |
| 主要优势 | 分发、治理、能力覆盖 | 装载严谨、信任状态、事务更新 | 可编程性和开发效率 | 中间件表达力和直接性 |
| 主要债务 | 核心闭源，外部进程仍高权限 | 公开贡献面窄，部分能力未落地 | 无隔离、安装非原子、顺序耦合 | 无隔离、异常传播强、生命周期演进中 |

## 8. 社区经验

### 8.1 包、贡献与运行时必须分开

插件包解决发现、版本和分发；贡献描述插件向宿主提供什么；运行时决定代码在哪里执行。这三者混为一个
`load_plugin()` 会让安装、授权、兼容和卸载无法形成清晰事务。

### 8.2 进程边界、OS 权限与 Agent 审批是三个维度

外部进程可以隔离崩溃和依赖，但仍可能有完整用户权限。Agent 工具审批只约束经过宿主执行器的动作，
不能自动约束插件直接发起的文件、网络和进程访问。

### 8.3 安装、启用、代码信任和能力授权不是一个状态

Codex 的 Hook 哈希信任说明代码变更应使旧授权可见地失效。Claude 的作用域和 managed policy 也在解决
相同问题。把“目录存在”直接等同于“自动 import 并运行”会模糊最关键的信任转换。

### 8.4 Hook 调度方式决定组合能力

并发 Hook 适合独立观察者，串行 middleware 适合累积变换。选择本身没有绝对优劣，但顺序、短路、冲突、
超时和错误传播必须成为稳定协议，不能依赖偶然的文件遍历顺序。

### 8.5 故障策略应按事件风险分类

权限和工具前置检查适合 fail-closed；遥测、显示和后置通知适合 fail-open。统一吞掉所有错误或统一让所有
错误中止 Run，都会在不同事件上产生错误行为。

### 8.6 版本代码、激活状态和持久数据必须分离

原地覆盖代码无法可靠支持并发会话、更新失败恢复和旧版本回滚。卸载代码也不应默认删除用户数据。

### 8.7 冲突策略本身是公共 API

namespace、first-wins、last-wins、编号并存都可以成立；真正危险的是静默、依赖扫描顺序且无法诊断的覆盖。

### 8.8 热重载是生命周期协议

可靠 reload 涉及停止接收新调用、取消任务、关闭进程和连接、注销贡献、清理 UI、使旧 context 失效，
并处理仍持有旧实现的运行中调用，而不只是重新 import 文件。

### 8.9 供应链成熟度与扩展能力不正相关

Claude Code 的分发治理最成熟，Pi 的运行时 API 最强，Codex 的文件安装事务最扎实，OpenCode 的中间件
最直接。评估插件系统应使用多维坐标，而不是以扩展点数量或 manifest 字段数量给出总排名。

## 9. OURO 实现后二次反向审查

将规格与首轮实现逐条对照后，新增以下工程结论：

1. **启动规划必须按期望启用的根插件隔离失败。** 一个依赖缺失的插件不能阻止无关插件启动。Claude Code
   对单个无效组件采用跳过并继续加载其余组件的策略，说明“包/根级局部失败”比全局启动失败更适合作为
   插件宿主默认值。参见[插件参考](https://code.claude.com/docs/en/plugins-reference)。
2. **旧版本保留不等于升级可用。** 选择新 digest 后，只有候选 generation 完整启动成功才能提交；失败必须
   恢复旧选择和旧 generation。版本化缓存保留并发会话所需旧版本也是 Claude Code 的公开行为。
3. **credential slot 是权限作用域，不只是配置键名。** binding、SDK resolver、worker environment 和 MCP
   descriptor 必须共同校验 manifest 的 `credentials.use` scopes；秘密值不得经过 JSON-RPC initialize。
4. **“协议隔离”和“运行监督”是两项能力。** 基础 worker 具备进程崩溃隔离、超时、取消和关闭，不代表已经
   具备独立依赖环境、自动重启、backoff/circuit breaker、OS sandbox 或反向 Host service。
5. **规格必须区分目标与交付事实。** data migration、catalog/signature、通用 dry-run、request id 幂等和
   feature negotiation 在相应状态机、持久化账本或协议存在前，不得写成当前能力。
6. **机器输出是 Host 契约。** `--json` 模式必须隔离 in-process 插件的 stdout；SDK logger、worker stderr
   和 CLI stdout 是三个不同通道，不能依靠插件自律维持 JSON 纯净。

这些结论已反映到目标规格的“当前实现边界”，并作为 OURO 的回归不变量，而不是继续增加 manifest 字段。

## 10. OURO 产品决策（2026-07-17）

本报告记录社区方案与可复用经验，不直接决定 OURO 的产品范围。后续架构审查已确认三项上位决策：

1. OURO 是强扩展的个人智能体。插件安全保留包完整性、代码信任、能力授权、凭据与工具执行边界，不建设
   Marketplace、签名/publisher policy、OS sandbox 或企业权限中心。
2. 插件是 OURO 系统级扩展，只分 builtin 与 user，不存在项目/workspace 插件或多 scope overlay；Skills 与提示词
   可以拥有 workspace 来源，但不能把该模型外推给插件。
3. 当前处于开发阶段，目标契约可以直接替换旧 schema 与状态语义；默认拒绝旧格式，不以历史兼容牺牲逻辑一致性。
