# 数据迁移模块设计

> 文档类型：待确认的设计与实施规划
>
> 核对日期：2026-10-12。当前目标基线：`v0.2.0`（`0da16a0`）；历史对照基线：重构前的 `96ebb7e`（包版本 `0.1.0`）。
> 本文只提出方案，迁移命令和模块尚未实现，也尚未修改现行持久化契约。

## 1. 推荐方案与交付边界

采用 **按数据契约分域的、已验证步骤可组合的离线迁移器**。用户指定源 home 和新的目标 home，工具自动识别实际格式、选择转换路径、迁移全部受管理数据、校验后发布目标目录，源目录保持不变。

关键决策：

1. 以实际持久化格式选择转换，应用版本只用于说明来源与目标。
2. 每个历史格式变更只实现一次转换；后续版本复用已经验证的步骤。没有数据变更的产品发布不新增迁移。
3. 文件与 SQLite 分别读写，共用业务记录转换；保留原存储后端。
4. 迁移在独立进程和工作副本中完成，不装配 Runtime、启动插件、调用模型或运行后台调度。
5. 完整校验通过后才发布新目录；不原地覆写，也不自动删除、替换原 home。
6. 原生数据负责语义迁移，第三方私有数据按所有权处理；无法证明安全的转换明确阻断，不能靠丢弃记录完成升级。

本轮交付设计文档。实施时首先支持已核实的 `96ebb7e` 数据契约到当前契约，以及当前数据的验证与复制。历史 `0.1.0` 没有唯一发布标签，开发期间的所有数据不能仅凭相同包版本被宣称为已支持。更早格式按真实样本、历史源码和验收夹具逐项纳入。

迁移的当前版本指**本机所安装迁移器配套的 OURO 数据契约**，不联网寻找最新版或自动升级程序。数据迁移不包含跨后端转换、降级、实时双写或第三方插件代码升级。

## 2. 已核实的约束

### 2.1 没有一个数字能代表整个 home 的格式

以下来自上述两个 Git 基线的源码对照，数字属于各自的版本域：

| 数据契约 | `96ebb7e` | `v0.2.0` | 对识别与迁移的影响 |
| --- | --- | --- | --- |
| 文件会话 `data_layout_version` | 9 | 9 | 目录布局相同不表示内部记录兼容 |
| 会话 SQLite `metadata.sqlite_schema_version` | 7 | 7 | 表结构相同仍需迁移 JSON payload |
| Session / Event | 2 / 2 | 2 / 2 | 检查其嵌套结构及开放 payload 的具体契约 |
| Run | 2 | 5 | 新增 Driver 绑定和 checkpoint 等语义 |
| Message | 3 | 4 | 工具结果新增 producer 信息 |
| ContextSnapshot | 4 | 4 | 内嵌 `source_messages` 的版本可能不同 |
| 文件任务布局及包装记录 | 1 | 3 | 配置、执行目标与所有者结构变化 |
| 任务 SQLite `user_version` | 1 | 3 | 表结构和 payload 同时变化 |
| 用量 SQLite `user_version` | 1 | 2 | 支持插件独立用量与新的归属字段 |
| 用量记录 / 审计事件 | 1 / 1 | 2 / 2 | 包含审计事件内嵌的用量记录 |
| 插件注册状态 / manifest | 4 / 3 | 4 / 3 | 格式号与代码 API、Host 兼容范围独立 |
| Provider 模板 / TUI 输入草稿 | 4 / 4 | 4 / 4 | 需独立验证，不能随产品版本盲目重写 |

依据：[会话布局](../../ouro/sessions/layout.py)、[SQLite 会话](../../ouro/sessions/sqlite.py)、[Run / Session](../../ouro/core/state.py)、[消息](../../ouro/core/messages.py)、[上下文快照](../../ouro/core/context_snapshots.py)、[文件任务](../../ouro/automation/file_records.py)、[SQLite 任务](../../ouro/automation/sqlite.py)、[用量存储](../../ouro/billing/local.py)、[用量模型](../../ouro/core/billing.py)、[插件状态](../../ouro/plugins/models.py)。

因此不能把 `layout.json` 当作整个 home 的统一版本，也不能用 `PluginProvenance.installer_version` 推断所有用户数据的创建版本。一个 home 可以同时包含多个后端、不同年代的记录以及独立演进的插件。

### 2.2 当前校验器不能直接充当历史转换器

`VersionedOuroModel` 和 versioned decoder 拒绝不支持的版本，但基础 [OuroModel](../../ouro/core/base.py) 默认使用 `extra="ignore"`，部分字段还有动态默认值。把旧 JSON 直接交给当前模型并重新序列化，会有忽略字段、补入当前默认值乃至生成新身份或时间的风险。

配置文件也不全部带版本：[JsonConfigFile](../../ouro/config/file.py) 通过分域文件和结构规则判别；[TUI 偏好](../../ouro/tui/preferences.py) 没有格式号。缺少版本标记有时是已知历史契约，有时是损坏，必须分开处理。

检测时也不能调用当前 Store 的 `initialize()`、恢复、保存等入口。它们可能创建文件、恢复提交、重建索引；[插件状态恢复](../../ouro/plugins/store.py) 还会隔离无法读取的旧状态。检测必须直接只读检查文件与数据库。

SQLite 查询只在受限的临时数据库副本上执行，包括 `inspect`；不为读取版本而在源目录创建 `-shm`、执行 checkpoint 或恢复 journal。这里的只读指不改变源数据，不禁止创建工具自己的临时检查副本。

### 2.3 “完整”必须覆盖权威数据与引用关系

迁移范围按实际落盘位置枚举，不能只遍历当前会话列表或当前启用的后端。

| 范围 | 迁移责任 |
| --- | --- |
| 会话 | 活跃与归档会话、回收站、消息、Run、事件、压缩、上下文快照、Delegation |
| 恢复与撤销 | 全部 Harness 版本、消息前状态引用、操作回执、未完成提交决定与嵌套记录 |
| 资源 | 文件及元信息、引用关系、不可变附件、回收站附件；不能从文件扩展名推断缓存 |
| 任务 | 两种后端的定义、执行历史、活动执行身份、调度 occurrence、防重复执行记录及恢复决定 |
| 配置与界面 | 分域配置、Provider 模板、提示词、MCP / Agent / Skills 配置、TUI 偏好与草稿 |
| 凭据 | `credentials/` 中的材料、身份、状态和 revision；保持机密性，不刷新或测试登录 |
| 用量 | 当前用量事实、作用域关联、历史 record / replace / reset 审计及顺序 |
| 插件 | 注册与启用意图、不可变包、历史配置 revision、权限记录、审计与私有数据 |
| 其他文件 | 保持原路径和内容并记录为未解释文件；未知的原生存储结构则阻断 |

会话 catalog 和事件字节索引等已确认的派生数据可以重建；`context.json`、Harness、操作回执、任务防重记录不是可随意删除的缓存。不得因为当前索引未列出某条数据就遗漏它。参考[会话持久化](../specs/session-persistence.md)、[自动任务](../specs/automated-tasks.md)、[数据传输](../specs/data-transfer.md)。

home 外的工作区文件、外部插件源码、系统环境变量与远程服务不归迁移器所有。保留引用，报告必要的外部条件，不自动扫描或复制这些位置。

## 3. 格式识别与迁移步骤

### 3.1 用数据契约识别，不猜产品版本

检测结果是一份格式清单：路径或表、所属数据域、物理布局、显式记录版本、已知结构特征、数量和诊断。各域各记录分别识别；同一个数字在不同域没有等价关系。

识别顺序：

1. 检查文件布局、SQLite 元数据和表结构，定位所有原生数据域。
2. 检查显式版本的类型与值，包括所有权威记录和已知嵌套记录。不能只抽查第一条或只看外层版本。
3. 对已知无版本格式，使用从历史源码固定下来的精确结构规则识别；先验证历史契约再转换。
4. 将原生语义身份与同一 home 中的关联数据核对，识别已支持的混合格式组合。

空数据域标为 absent，不自动补造历史版本。未知将来版本、缺失本应存在的标记、重复 JSON 键、损坏记录以及多个含义不同的候选格式均阻断。显式版本不符时，不退回无版本识别来绕过错误。

目录里有数据但缺少必要标记，不能按空目录初始化；SQLite 版本为 0 也必须检查实际表和记录，不能仅凭 0 判为新库。只有当前 reader 明确允许的缺失数据域才可保持缺失。

相同结构可以来自多个产品版本，报告“适用这些已知来源契约，无法反推精确应用版本”即可。只有候选契约的解释和转换结果一致时才可合并识别；数据缺少决定性信息时，不能用一个 `--force` 或用户填入的版本号替代证据。

新增全局 home 版本文件不能补齐过去缺失的证据，也不能替代独立插件版本。本方案不要求现有运行时维护新的全局版本标记。

### 3.2 每次真实格式变化只实现一次

以实际变更为单位维护显式、有序的迁移步骤，例如：

```text
Run format 2 ──已核实的转换──> Run format 5 ──未来转换──> Run format 6
Message format 3 ───────────> Message format 4
Task format 1 ──────────────> Task format 3
```

数字不必连续；没有实际支持对象时，不为了凑齐编号编写 `2→3→4→5` 的空步骤。对于用户举例的 `v0.3.1`，只在它改变数据契约时追加步骤；历史数据复用已有路径到达新目标。

每个步骤明确：输入契约、输出契约、转换规则、必须读取的关联数据、语义不变量和失败条件。普通字段变化使用纯数据函数；涉及多个文件、表或关联记录的变化，由所属数据域的步骤一起完成。

每个已支持源契约只注册一条明确的前进路径。规划器检查闭环、断路和重复注册，不实现插件式发现、任意图搜索或“最短路径”优化。文件与 SQLite 的相同记录使用同一转换函数，物理结构变化由各自 adapter 处理。

已发布的步骤不因目标升级而改写输入/输出含义。发现缺陷可以定向修复并增加回归夹具，保留稳定步骤 ID，在报告中记录迁移器版本；不机械坚持保留错误实现。历史步骤不得依赖当前模型的可变默认值。

### 3.3 组合逻辑，避免反复搬运整个 home

一个记录在内存中依次通过适用步骤，再写出最终记录，不为每个中间应用版本生成完整数据目录。跨文件操作只在确有引用或布局变化时执行。逐步验证输入/输出边界，最终再验证持久化产物及整体关系。

若共有 K 次契约变化，主要维护对象是 K 组转换规则，而非每次发布都更新所有历史版本到最新版本的直达脚本。新增目标仍必须验证所有承诺支持的源格式到目标的端到端路径；组合不会消除这项兼容性责任。

## 4. 模块组织与依赖边界

建议使用仓库顶层独立 Python 包 `ouro_migrate/` 和独立命令 `ouro-migrate`，初期随 `ouro-agent` 发行包交付。这样用户安装当前 OURO 后即可运行迁移，不增加另一套发布、安装和版本配对机制。独立模块边界通过依赖检查保证，不要求立即拆成第二个仓库或发行包。

建议布局，实施时只创建实际需要的文件：

```text
ouro_migrate/
  cli.py                  # 参数、进度、脱敏诊断、退出码
  engine.py               # 检测、规划、执行、校验、发布
  registry.py             # 源契约及唯一前进步骤的显式登记
  workspace.py            # 独立工作目录、文件复制、发布和清理
  domains/
    sessions.py           # 会话、恢复决定、Harness 与资源关系
    tasks.py
    billing.py
    configuration.py
    plugins.py
  formats/                # 冻结的历史解码规则与小型转换函数
  target.py               # 对当前 OURO 纯数据契约的单向适配
tests/migration/
  fixtures/               # 已标注历史来源的脱敏固定样本
```

核心流程只需要格式清单、迁移计划、迁移报告这三种数据结果，以及显式步骤函数。不引入通用工作流引擎、依赖注入容器、迁移数据库、事件总线或后台服务。

依赖约束：

- `ouro` 的 Core、Application、Store、CLI / TUI 正常运行路径不导入 `ouro_migrate`。
- 历史解码与转换不导入当前 Runtime 或历史 OURO 整套代码，也不启动旧版本子进程。
- `target.py` 可以单向复用当前的纯模型、格式常量和无副作用校验函数，避免复制一套容易漂移的“当前 schema”。不调用 Store 初始化、普通导入服务或有修复副作用的读取。
- 当前模型只用于验证已明确转换的目标数据；写出以受控转换结果为准，不靠 `model_dump()` 清除未知字段或补默认值。目标模型接受的数据还需通过迁移器的字段保全检查。
- 现有文件权限和纯 I/O 工具可以在窄 adapter 中复用；引擎不获得 Application 或插件 Host 对象。

预计必要集成只有 `pyproject.toml` 的包包含规则和命令入口、文档与边界测试。若实施证明某项校验只能通过有副作用的对象取得，再单独提议抽取一个纯函数；不借迁移工作重构运行框架。

## 5. 执行流程与失败边界

### 5.1 停写源目录，输出独立新目录

一期要求源 home 已停写，包括 TUI、CLI、后台进程和会写插件数据的外部进程；优先迁移停机后制作的冷备份。目标为尚不存在的新目录，并且不能与源目录相同、互为祖先或通过链接别名重合。目标在发布前不得被 OURO 或其他程序使用。

这是强一致性的前提。当前框架没有覆盖全部 home 写入者的统一锁；迁移器自己新建一个锁不能约束旧版 OURO。已知锁占用检测、复制前后文件清单和状态核对只能发现部分误用，不能证明活跃目录的全局一致性。检测不会为此在源目录创建锁文件。

因此一期不宣称在线迁移安全，也不静默终止用户进程。若未来必须支持运行中自动迁移，需另行设计所有写入口共同遵守的 home 级屏障；这是框架能力变更，不能伪装成独立脚本就能解决的问题。

### 5.2 一次迁移的顺序

```mermaid
flowchart LR
    A[只读识别源格式] --> B[检查路径与转换覆盖]
    B --> C[建立独立工作副本]
    C --> D[按源契约恢复存储提交]
    D --> E[转换原生数据]
    E --> F[校验事实与引用并重建投影]
    F --> G[写入迁移报告]
    G --> H[发布新的目标 home]
```

1. `inspect` 给出只读规划与阻断项，不宣称迁移已经可用。`migrate` 自己重新检测，不能盲信先前报告或源目录仍未变化。
2. 在目标所在文件系统建立工具专属工作目录，先限制访问权限，再复制敏感内容。对同一目标取得迁移器间的独占锁，避免两个迁移进程相互覆盖。
3. 在工作副本上完成已知旧格式的存储级恢复；之后重新核实权威记录清单，作为迁移前事实基线。
4. 执行已登记步骤，处理嵌套记录、关联数据和后端表结构。不可解释的原生字段或关系阻断整个目标发布。
5. 验证完整性与语义，再重建当前查询投影。数据库关闭全部连接并持久化后，写入脱敏迁移报告。
6. 使用同文件系统的目录发布操作将已验证产物放到目标路径。发布前复核目标不存在，禁止覆盖已有目录。目标锁仅协调本工具，不能替代“其他程序不使用该目标”的前提。
7. 只有发布完成才返回成功和 `ouro --home <目标目录>` 的使用方式。不会自动启动该命令，启动可能触发正常插件激活和任务调度。

工作目录包含原始副本、转换产物或临时数据库的必要部分，不为每个步骤保留一整份 home。现有源目录本身就是不被覆写的回退基础。原目录仍需保留到用户验证并决定清理；新目录产生后续写入后，切回旧目录会失去这些新增事实，不是无损反向迁移。

### 5.3 SQLite、恢复决定和不可变身份

- SQLite 数据可能仍在 WAL 中。冷复制必须把主库及实际存在的 WAL / 回滚 journal 作为完整源文件组处理，不能只复制 `.sqlite3` 或先删除 sidecar。为保证不改写源，只在工作副本打开数据库并让 SQLite 完成自身恢复；必要时用 Backup API 从工作副本生成自洽目标。`-shm` 属于可重建的 SQLite 协调数据，不承担业务事实。[SQLite WAL 文档](https://www.sqlite.org/wal.html)、[Backup API](https://www.sqlite.org/backup.html)。
- 多个数据库各自的一致快照不构成整个 home 的一致快照，因此 SQLite 支持在线备份也不能取消源目录停写前提。
- 文件会话 `commit.json` 含 journal 的旧字节偏移；必须先用已核实的源格式恢复逻辑在副本中落实决定，再重写 JSONL。不能转换 journal 后继续使用旧偏移，也不能直接删除决定。任务 `transaction.json` 同理。
- 源格式的提交恢复只落实已经记录的存储决定，不重新执行模型、工具、插件回调或外部进程。源恢复契约未知或提交损坏时阻断。
- 保留 Session / Run / Message / Event / Harness / Task 等身份、时间、排序和业务 revision。新字段由历史语义明确推导，不调用当前默认工厂制造历史事实。
- 区分字节完整性摘要、历史请求摘要和执行契约摘要。覆盖已转换内容的摘要需要按其契约重算并同步引用；历史请求摘要和代码执行契约不能按新模型随意重算。无法保持幂等回执或待完成操作语义时阻断。
- SQLite 的行顺序和序列分配状态按源契约保留；重建表不能让未来事件号、消息顺序或审计游标复用过去身份。

### 5.4 中断与发布

| 情况 | 行为 |
| --- | --- |
| 未知格式、未来版本、校验不通过 | 输出定位诊断，不发布目标，不改源 |
| 读写错误、空间不足、取消、进程中断 | 保留源；工作目录不成为成功结果，可删除本次工作目录后重新执行 |
| 迁移时发现源发生变化或明显被占用 | 立即终止，要求停止写入后重新开始 |
| 校验完成但发布前崩溃 | 最多留下未发布工作目录，不自动接管或重用它 |
| 发布后、成功输出前崩溃 | 目标包含验证回执；重试检测到目标存在后只读报告，禁止覆盖 |
| 目标存在、权限不足或发布时被占用 | 不覆盖、不自动合并，明确报告失败 |

一期不实现断点续跑、每记录事务日志或整目录双重 rename 的“自动回滚”。目标发布之前所有更改都位于副本，失败时重新运行即可。正常文件与数据库应 flush / fsync，平台可用时同步目录；实际断电持久性依赖平台和文件系统，不能把 rename 的原子可见性等同于所有平台上的断电保证。

自动清理仅能作用于本次创建且已核实边界的工作目录，不能扫描名称类似的目录后批量删除。源数据、既有目标和过去备份永不由失败清理删除。

## 6. 首批迁移规则与完整性要求

### 6.1 `96ebb7e` 到当前契约

以下是已经从源码确认需要落实的转换，不是已验收的支持声明：

| 数据域 | 转换规则与验收重点 |
| --- | --- |
| Run 2 → 5 | 历史内建循环映射到已证明等价的默认 Driver 绑定，明确 checkpoint 缺省语义；保留队列、工具批次、审批与 continuation。仅加 `schema_version=5` 不足以证明恢复可靠 |
| Message 3 → 4 | 历史模型产出的工具结果补明确的 model producer；同步处理 Run 内 ToolInvocation。未知或非模型来源不得猜测 |
| 嵌套会话记录 | 同步迁移 ContextSnapshot、操作回执、截断记录、回收站 bundle 与已知事件 payload 中的旧 Message / Run；外层版本相同也不能跳过 |
| 任务 1 → 3 | 将旧 `configuration.description` 等执行设置映射到 `configuration.target.kind=agent`；`description→prompt`，保留 title / schedule。旧 execution 的 `session_id/run_id` 移入 agent target，明确 owner、result、cancel 标记的历史缺省值；保留 occurrence 与历史链接 |
| 用量 1 → 2 | 保留旧 Run 归属、金额、token 和审计顺序，明确无独立 plugin 归属；迁移当前记录与审计内嵌记录，更新查询表。已 reset 的历史用量不能重新加入当前统计 |
| 配置、凭据、模板、草稿 | 对未变化且受支持的结构直接保留；未版本化配置按具体源结构判定，不用新默认配置覆盖用户设置 |
| 插件注册与私有数据 | 格式未变化不表示插件代码兼容。保留不可变包、历史配置与启用意图，核查其 Host/API 需求并报告；不得修改包的兼容范围冒充升级 |

首批会话迁移必须覆盖终态 Run、暂停审批、AskUser、排队输入、子会话、撤销锚点和未完成存储提交。待完成外部副作用若需要不可取得的代码或缺失的执行契约，报告为待恢复能力条件或迁移阻断，不能伪造成功、重新运行工具、清空等待或自动改成 completed。

`Run 3/4`、任务 2 等开发中间格式只有在存在可核实的源码和夹具时登记。不能因为数字位于已支持区间内就宣布支持。

### 6.2 全部出现位置有明确所有者

每类格式维护出现位置清单：独立文件、JSONL 行、SQLite payload、回收站快照及已知嵌套字段。转换函数被这些位置复用，不递归搜索所有名叫 `schema_version` 的字段；插件 payload、用户 JSON 或工具参数中的同名字段不归宿主解释。

必须保留的关系包括：

- Session 头部与消息、Run、Harness、压缩记录的引用；消息序号、事件序号和当前历史 epoch。
- 父子会话、Delegation 的派遣与交付身份；同一个逻辑引用在文件与 SQLite 中的解释一致。
- 任务与 execution、活动执行、occurrence 标记及关联 Session / Run。
- 附件引用、实际文件、大小及已有完整性摘要；回收站与历史快照中的引用也要覆盖。
- 凭据引用与记录身份；插件包 digest、配置 revision、权限与执行绑定。

同一 home 中并存的文件与 SQLite 数据按各自后端的身份域验证，不自动合并、去重或把同名 ID 视为同一条事实。真正共享的资源仍按其已有存储契约验证内容一致性。

校验区分源契约允许的历史悬空引用与真正损坏，不把目标契约本就不要求存在的外部服务、工作目录或已删除外部文件强制变成全库迁移障碍。

### 6.3 插件私有数据的责任边界

迁移器负责宿主拥有的 envelope、引用、安装状态和包完整性；插件拥有私有 payload、私有数据库及其语义版本。Goal / Plan 等内建插件也遵守此边界，其历史状态转换只能通过明确登记的 owner 规则执行。

不可变插件包和配置内容摘要不随 OURO 升级重新生成。不能改写插件 `requires_ouro`、SDK 版本、已有授权或执行契约哈希；不能在迁移中加载已安装插件以“试试看能不能恢复”。

结果需要分别报告：

1. **原生数据是否完成迁移并通过校验。**
2. **私有数据是否按字节完整保留，是否有受支持的 owner 转换和验证。**
3. **运行能力是否还有前提**，如插件升级、外部工作区或凭据重新授权。

私有内容当前无需宿主解释且完整复制时，可完成原生数据迁移，并报告 `owner_validation=pending`；不能宣称该插件已经迁移至当前私有 schema 或可以继续运行。如果已知目标 owner 要求不同格式且无转换，或缺失的数据影响原生完整性，则标为未完成并阻断完整发布。代码/API 不兼容和数据损坏必须分开呈现。

一期只接受迁移器内显式登记、可离线验证的 owner 规则。第三方可提供历史契约和夹具纳入支持，或先使用其独立工具处理冷副本；不预先建立自动加载任意迁移插件的扩展框架。

## 7. 保全、权限与执行成本

### 7.1 内容和路径

每项源内容都有明确处置：转换、原样保留、按契约恢复或重建派生数据。未知普通文件默认原样保留；位于已知原生数据位置的未知记录、未知表或无法解释的字段不能降格成普通文件来绕过验证。开放 metadata 和插件 payload 则按其既有开放契约保留。

不要把 Pydantic 当前版本能忽略某个字段当作可删除该字段的授权。必须删除或合并字段时，迁移规则给出对应信息去向与语义等价依据；否则阻断。

只对明确属于 home 管理、且契约允许重定位的结构化路径做源根到最终目标根的映射，不能写入临时工作目录路径。历史请求文本、审计中的命令、外部文件引用、工作区和不透明插件字符串不能全局替换。存在不能解释的绝对路径依赖时，在运行前提中报告，不宣称迁移结果已与旧 home 完全脱离。

一期不跟随 symlink / junction / reparse point 越出源树；遇到不能安全原样保持语义的链接则阻断，要求提供普通文件构成的冷副本。目标不得与源共用可变 hard link，避免修改目标影响原数据。跨操作系统或跨机器的路径、认证环境重建另行设计。

### 7.2 机密性

工作目录和输出包含凭据及用户对话，不低于源数据的访问保护。至少对敏感目录、临时文件和报告在写入前应用仅当前用户访问的权限；Windows 需要 ACL，不能仅依赖 `chmod`。可复用现有[文件权限工具](../../ouro/auth/file_permissions.py)的纯能力。

报告只记录相对位置、记录身份、规则 ID、版本、计数与脱敏诊断，不保存对话正文、token、API key、工具参数或插件秘密。凭据解析异常也不能直接打印含原始 payload 的校验错误。凭据只做离线格式验证与完整复制，不请求刷新或向外部服务发送。

### 7.3 性能取舍

- 全量数据完整性本身需要遍历全部权威数据，不能用抽样替代；避免的是与此无关的重复扫描和运行时初始化。
- JSONL 按行处理，SQLite 使用游标 / 有界批次；多个字段迁移步骤在同一次记录流水处理中组合。
- 不变附件、包和普通文件只做一次副本复制；复制时计算摘要，目标完整性校验可以再顺序读取。不要为每个中间 schema 重复复制附件。
- 源格式恢复、转换和目标验证各有目的；无需在每个步骤后重新遍历整个 home。正常路径不追加第三份完整备份。
- 内存主要为单条记录 / 批次及必要身份索引，不加载全部对话内容。身份索引成本随记录数量增长，不能宣称整个算法恒定内存；遇到实际大数据证据再将必要索引落到临时 SQLite。
- 空间预估包含目标副本、最大正在改写的数据域、SQLite journal / 临时表和报告；给出下界与余量，真正写满时安全失败，不承诺一个固定倍数适合所有数据。
- 同一受管理数据域顺序执行，默认不并发迁移相互引用的数据。没有测量依据时不增加 worker 池、后台队列或缓存层。

## 8. 使用接口与报告

以下为**拟议命令，尚不能执行**。示例适用于 PowerShell，路径需替换为真实的冷源目录及新的目标目录。

```powershell
# 只读识别所有数据域、检查迁移覆盖与阻断项
ouro-migrate inspect --source 'C:\backup\ouro-home' --json

# 自动选择已支持的路径，在独立目录完成迁移与验证
ouro-migrate migrate --source 'C:\backup\ouro-home' --output 'C:\data\ouro-current'
```

命令显式要求源目录，避免默认操作正在使用的 `~/.ouro`；不要求用户输入源版本。`inspect` 不因“格式已是当前”而省略必要嵌套检查；`migrate` 对已是当前的数据执行验证与复制，不重写无需改变的记录。

迁移报告保存在目标内 `.migration/receipts/<migration-id>.json`，与目标一起发布，后续迁移保留已有回执。报告记录迁移器版本、目标 OURO 版本及数据契约、来源识别依据、执行步骤、各域处理计数、验证结果和运行前提。报告只证明发布时的数据状态，不充当之后每次写入的实时格式来源。

退出结果区分：完成、完成但有未验证 owner / 运行前提、源不支持或有损坏、执行失败。只有全部数据责任均完成并且无待处理前提时才能报告“完整迁移完成”；其他结果给出具体影响，不能只返回一个绿色成功提示。

自动化使用 JSON 结果，不解析人类文本；不提供忽略坏记录的 `--force`、跳过某域后冒充全量成功的开关或自动联网执行历史脚本的入口。

## 9. 验收与长期维护

### 9.1 验收矩阵

| 验收 | 必须证明的结果 |
| --- | --- |
| 历史来源识别 | 显式格式、无版本已知配置、嵌套旧记录、允许的混合格式正确识别；未知 / 未来 / 歧义格式阻断 |
| 真实历史夹具 | 从固定历史提交产生并脱敏的文件与 SQLite 数据；不能只把当前 fixture 的版本数字改小 |
| 首批差异 | Run、Message、Task、Billing 的转换与语义逐项验证；当前格式重复执行无语义变化 |
| 全部出现位置 | 当前、归档、回收站、上下文、Harness、操作回执及审计内嵌记录全部覆盖 |
| 两种后端 | 文件 / SQLite 的会话与任务独立组合；同时存在两种后端时均处理，不能只选默认后端 |
| 存储恢复 | 有 WAL 未 checkpoint 的 SQLite；文件提交中断、journal 尾部部分写入和任务 transaction 的已知恢复边界 |
| 不执行副作用 | 不调用模型、工具、插件激活、认证刷新或调度；保留待完成工作的身份及已接受决定 |
| 故障与取消 | 复制、恢复、转换、验证和发布边界注入失败；源内容不变，未验证目标不发布，重试不覆盖 |
| 保全和机密 | ID、时间、顺序、金额、审计语义、附件与私有内容保持；权限生效，日志无秘密 |
| 损坏与越界 | 重复键、未知原生字段、缺失引用、坏附件、未知表、路径重合、越界链接明确失败 |
| 规模 | 大 JSONL 与多附件夹具记录峰值内存、读写量和耗时；确认没有整库重复加载或逐版本复制 |
| 当前消费者 | 使用当前纯 decoder / 校验器读取全部转换产物，验证结构、关系和重建投影；隔离环境再做 CLI / 存储 smoke |

“当前消费者能读取”与“真实供应商、插件以及外部副作用能继续运行”分别验收，不能用离线测试替代后者。第一次打开新 home 的运行验证需要受控样本，不能让验收顺便执行用户真实后台任务。

按照本次约束执行迁移模块、受影响持久化边界和少量集成 smoke 的定向验证，不重跑已完成的全量工程测试；后续发现错误 case 只补对应规则与回归。

### 9.2 格式演进规则

每次持久化语义变化都审查：

1. 是产品版本变化，还是某个真实数据契约变化；数据语义改变必须有明确版本或可判定格式标识。
2. 是否涉及嵌套记录、回收站、恢复决定、摘要、审计和插件 owner，而不仅是主要列表中的记录。
3. 新增哪个前进步骤，旧步骤是否仍能组合到当前目标；配套增加固定输入、期望输出和失败样本。
4. 当前目标 adapter 是否覆盖新增字段、表和原生文件位置；目标契约漂移通过定向测试暴露。
5. 更新支持矩阵、用户指南、发布流程和简洁 CHANGELOG。迁移支持与程序版本升级一起审查，不能先发布不兼容格式再遗漏迁移路径。

已支持历史数据的转换不能因清理旧代码随意删除。若未来维护成本要求收缩支持，必须保留可取得的旧迁移工具及明确中间升级路径，在发布记录中说明；一期不预建淘汰框架。

## 10. 实施顺序与退出条件

1. **冻结契约和支持矩阵。** 为 `96ebb7e` 与当前基线建立数据位置清单和脱敏夹具，核实待完成执行、回收站及所有嵌套格式；逐项标注未知历史与 owner 私有契约。
2. **搭建最小迁移骨架。** 实现只读识别、新目标工作区、原样复制、校验与报告；首先证明当前数据复制、源不变及失败不发布。
3. **实现确有必要的转换。** 共用记录转换，补文件 / SQLite adapter、源格式存储恢复和首批 Run / Message / Task / Billing 规则；没有来源证据的转换不进入 registry。
4. **贯通目标验证。** 完成跨域引用、附件、审计、owner 边界与当前 reader 验证，再接独立命令和包构建。
5. **定向验收并更新现行文档。** 支持矩阵中的每项有证据后，才更新“没有迁移命令”的现行说明；本设计完成不等于迁移能力已发布。后续代码发布使用新版本，不改写已发布的 `v0.2.0` 标签或 PyPI 文件。

交付标准是：对声明支持的、已停写源数据，在不修改源、不执行用户工作、不丢失任何应保留事实的前提下，得到可由当前契约读取的完整目标及可核对报告；不支持的部分有精确原因，不伪装成成功。
