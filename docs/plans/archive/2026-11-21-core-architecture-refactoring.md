### 暂存树 `9131e7e` 的历史复核

两个版本使用同一解释器、确定性 Provider 和独立临时 home。冷重试在首个 Runtime 关闭后构造新 Runtime。问答在同一操作系统进程内构造两个共享存储的独立 Runtime，经过真实 Supervisor FIFO、执行锁与工具回调。前四项在 Files 和 SQLite 得到相同结果。

| 优先级与边界 | 实际结果与影响 | 放行条件 |
|---|---|---|
| P1 · 首条输入冷重试 | 在首条输入的受理回调中断，重开宿主并将 Prompt Policy 从允许改为拒绝。基线重评后拒绝，输入保持 pending、Run 数为 0。暂存实现只执行了原允许判断，随后完成 1 个 Run。持久的受理标记被当作本次执行已获准。[首条输入与执行](../../../ouro/application/runtime/service.py) | 同一次受理直接移交执行时只检查一次。单凭持久回执恢复时重评当前策略，拒绝后保留输入，新增消息、Run 和模型派发均为 0。 |
| P1 · 排队回答的归属 | 同一工具 Call 连问两次。Host A 为第一题提交回答且句柄为 queued，Host B 回答第一题后工具提出第二题。A 的回答随后触发第二题的回调，Run 进入 completed。基线与暂存实现均可复现。阶段 5 增加的锁内批次比较只覆盖取到目标之后的变化。[Supervisor 入队](../../../ouro/application/supervisor.py) · [锁内裁决](../../../ouro/application/runs/interactions.py) | 从观察、提交到锁内裁决保留 Call 与提问修订。迟到的回答产生 0 次回调、0 次回答提交，第二题仍可正常作答。 |
| P1 · 多个待消费输入 | 已有空闲 Session 按 `one_by_one` 依次受理 A、B，再以 B 的身份直接调用 `run`。暂存实现恰好消费了两条输入，但返回 A 的 Run。基线对该直接重试报 `SessionCommitConflict`。新增的回执重试路径把队首执行结果当作所请求输入的结果。[回执消费](../../../ouro/application/runtime/service.py) | 保持 FIFO 和忙会话的既有返回语义。返回目标输入的执行结果时，Run 必须与该输入的规范消息指向同一个 Run。 |
| P1 · Supervisor 等待同一会话的多个输入 | 使用另一个会话占用唯一许可，A、B 均已受理但尚未执行。修正前两个等待者均收到 A 的 Run，两后端可复现。单个调度 job 代表会话的一次消费，其结果可能属于前驱输入。 | 容量释放后 A、B 按序执行，各自的等待者拿到自己规范消息的 Run。已处于活动状态的会话保持既有忙态语义。 |
| P2 · 幂等返回的失败明细 | 首次结果和重试结果的 Run ID 相同。首次报告 `authentication_required`、工具错误和用量（输入 5、输出 2 tokens），重试三项分别为 `None`、`False`、`None`。将两份结果交给 CLI 退出码映射，分别得到 6 和 1。基线对该重试报冲突。[结果读取](../../../ouro/application/sessions/service.py) · [退出码映射](../../../ouro/cli/run.py) | 从已有 Run、工具结果及用量事实还原调用方可见的终态摘要。两次的错误、用量、最终文本和退出码一致，模型与工具执行次数保持不变。 |
| P2 · 完整本地宿主的受理成本 | 使用 `LocalApplication.from_runtime`，向已有空闲 Session 首次提交带稳定 ID 的输入。各版本、各后端重复 3 次。受理回调前，Files 的显式 SQL `BEGIN` 从 20 增至 21，SQLite 从 12 增至 13。外层读边界分别为 12 → 13、0 → 1，写边界保持 4 和 5 次。[受理前回执查询](../../../ouro/application/runtime/service.py) · [本地装配](../../../ouro/local_application.py) | 在受理的既有一致性边界核对身份，保留并发去重。独立 Runtime 和完整宿主中，同轨迹的额外读写事务均为 0。 |

## 1. 决策与依据

目标是按业务能力组织的本地模块化单体。Session 保存会话事实，Run 是其中一次可恢复的执行，Driver 决定下一步。基线的执行入口同时装配模型、工具与插件。框架增加一种请求能力时，多个模块各自维护同一组字段。重构保留可替换的 Driver、原生会话事务和支持热更新的插件宿主，重新分配受理、执行、装配与查询的职责。本地管理与查询可独立启动，普通调用留在进程内，选用 worker 的插件沿现有协议执行。

**最先保护工具挂起与恢复，第一笔生产改动选系统提示词与会话观察提供方。** 前者涉及已经发生的外部副作用，错误重放的代价最高。后者有刚发生的真实变更、独立的公开契约和可逐项比较的模型输入，能验证一个较窄的边界是否真的消除接线。首笔改动从已绑定的决策目录到上下文准备，发布点和持久格式均沿用当前契约。这里的“会话观察提供方”指向对话投递内容的 `context_providers`。Host 用来跟随会话事实的 `SessionObservation` 在后续读取切片处理。[提示词与观察契约](../../specs/plugins.md#102-系统提示词与会话观察) · [会话观察规格](../../specs/session-observation.md)

### 审查与实施的六项重点

1. **核心架构与抽象。** 用 Session、Run、Driver 和会话提交解释直接执行、排队与挂起恢复。检验这些原语能否独立理解，并在不同入口组合使用。
2. **模块边界、分层和依赖方向。** 沿正常入口定位规则、执行流程、外部读写与装配各自的所有者。除源码导入外，也检查通过回调或大对象取得的实际依赖。
3. **插件与扩展。** 分别检验插件作者接入已有能力、框架作者新增贡献类型的成本，以及从声明、加载、换代到调用结束的契约。按进程内与 worker 各自的信任边界核对权限、取消和隔离。
4. **连锁修改的根因。** 用真实功能变更或管线调整追踪影响范围。消息角色变化会影响真正消费该语义的模块，调整提示词组合顺序则应止于上下文用例及其契约样本。
5. **严格禁止过度设计和过重的防御性设计。** 逐层复制同一组贡献字段会放大接线成本，用 `extension_generations` 审计键选择执行分支会隐藏控制依赖。内部入口靠大量校验排除无效参数组合时，先收窄输入。新增层、状态或校验须能说明当前哪个用例、公开契约或具体失效场景需要它。已有函数、类型或事务边界足以承担时，直接复用。
6. **长期演进、可维护性、可理解性与性能稳定性。** 以维护者实际需要阅读和修改的模块检验设计。以同负载下的首段输出、运行与恢复耗时、读写量和资源释放情况验证成本。

## 2. 目标架构与所有权

**源码依赖**沿“CLI、TUI 等输入适配器 → 应用用例 → 领域规则与所需能力契约”流动。具体存储、协议和插件适配器实现消费侧需要的行为。跨应用与插件宿主共享的原生值位于内侧，插件作者依赖公开 SDK。本地组合根认识两端。运行时，用例通过已注入的能力调用外部实现。Python 的结构化协议允许外层满足契约，无需让插件载入应用服务或反向导入组合根。[现有依赖约束](../../../tests/architecture/test_boundaries.py) · [本地构造约定](../../architecture/code-organization.md)

源码沿用现有的 `ouro/application/inputs`、`runs`、`context`、`models` 和 `observations` 组织用例。`ouro/core` 放置多处确实共享的身份、消息与提交规则。`ouro/plugins` 拥有加载和执行适配，`ouro/sdk` 定义插件作者能使用的接口，`ouro/sessions/backends` 拥有物理读写。各模块直接向就近的消费者提供能力，`ouro/local_application.py` 负责装配。

| 所有者 | 决定什么，交给谁 |
|---|---|
| **会话与输入用例** | `InputAdmissionService` 负责普通用户输入的受理、去重与回执。`QueuedInputQueue` 管理排序、替换和可消费单位。宿主、插件和委派入口各自核对输入归属，再复用同一队列规则。插件命令用例把输入批次与相应的 Harness 控制变更一起提交。 |
| **调度与执行** | `RuntimeSupervisor` 拥有本进程 FIFO、任务句柄、并发许可和关闭。`RunExecutionOwnership` 持有跨进程 Session 执行锁并管理取消信号。`application/runs` 的执行用例拥有取得锁、重读、选择合法转换、提交、调用 Driver 到释放所有权的共同顺序。`RunLifecycle` 组织持久转换，`RunDriverExecution` 只负责 Driver 调用及其模型、工具和预算。直接执行入口按请求身份返回结果，后台调度按队列规则选择下一个可消费单位。 |
| **模型轮次与工具调用** | `RunDriverContext` 是算法边界，默认 Driver 和自定义 Driver 共享原生操作。`RunModelRequests` 拥有请求准备、派发和结算。`ContextPreparationService` 拥有提示词与观察的业务区别，`ContextCompactionService` 组合压缩策略。`ToolCallCoordinator` 与执行器负责授权、待处理调用、确定结果和整帧发布。Provider 适配器编码请求。用量账本以同一请求身份独立结算。 |
| **事实提交与读取** | 用例和纯领域转换形成 `SessionCommit`，`prepare_session_commit` 推导合法效果，具体 Store 在原生一致性边界中核对并发布。输入消费与对应消息、工具等待与检查点等需要同时生效的事实继续一起提交。`SessionObservation` 负责快照、分页补齐和已应用位置，Host 成功应用后确认。 |
| **扩展目录与调用** | `PluginRuntimeResource` 拥有候选、发布和退役，`ExtensionCatalog` 是已发布的不可变目录。`RunResources` 持有本次决策的租约。租约让操作在其有效期内使用已选的实现，Driver、Provider 和 Observer 各自结算并释放所需绑定。插件层解释 release、配置修订、依赖和执行契约，通用工具执行器比较已保存的调用身份，执行用例据此恢复或返回局部失败。 |
| **配套业务与本地组合根** | Agent 拥有委派和交付，Task 拥有计划、领取与对账，两者复用会话执行能力。`LocalApplication` 选择本地后端和长期协作者，启动并关闭资源。配置、认证和轻量查询入口仍可单独装配。嵌入入口适配已有调用方式，核心用例可独立构造。 |

### 一次输入的职责与调用路径

1. TUI 控制器调用 `RuntimeSupervisor.submit_user_input`，将 `UserInputRequest` 交给受理用例。受理侧按 `input_id` 重用回执，初次接受时原子发布必要的 Session 和输入事实。Supervisor 再调度执行。等待执行许可时，已受理输入仍可查询。CLI 的 `run_print` / `run_json` 则由 `RuntimeService.run` 返回本次运行边界结果。这两类入口共用规则，各自保有回执、取消和退出语义。[TUI 提交](../../../ouro/tui/controller.py) · [Supervisor 受理](../../../ouro/application/supervisor.py) · [CLI 入口](../../../ouro/cli/run.py)
2. 执行侧取得 Session 锁并重读状态。Driver 请求模型时，原生模型轮次绑定当次可用目录。上下文用例从该绑定读取提示词和观察能力。系统提示词在基础指令、Skills 之后组合，变化的会话观察先提交成带归属的消息，再发布通知。Provider 收到与请求快照相符的实际输入。[上下文构建](../../../ouro/application/context/preparation.py) · [请求执行](../../../ouro/application/models/requests.py)
3. 响应中的工具调用沿这次决策的绑定预检。需要审批时，工具调用状态和 Driver 检查点共同提交，释放执行资源。用户批准后，执行侧重新取得锁，核对确切的调用与当前权限，按持久契约恢复。确定结果按原身份复用，已开始而结果缺失的调用保持未知。完整工具帧按调用顺序发布。当前 Driver 可以继续本次 Run，释放执行权后才调度下一个排队输入单元。[等待锁与重读](../../../ouro/application/runs/ownership.py) · [恢复批次提交](../../../ouro/application/runs/lifecycle.py) · [挂起恢复](../../../ouro/application/runs/interactions.py)

输入回执用 `session_id` 和 `input_id` 定位已受理事实及其规范消息。当次策略判断只能随原受理操作直接移交给执行者。工具问答由 `ToolCallIdentity` 和持久的 `input_revision` 区分同一调用的连续提问。执行者取得 Session 锁后核对所请求的对象。[输入生命周期](../../../ouro/core/inputs.py) · [工具调用事实](../../../ouro/core/tool_batches.py)

因此，下一次只调整提示词的**组合顺序**，落点应是上下文规则及相应期望。新增一种需要持久保留的等待态，合理落点包含执行规则、提交和恢复读取。插件回收只消费这些规则产出的实现引用。引入新的模型可见消息语义，则要同步核对协议编码、历史、SDK 或归档中公开表达该语义的部分。

**恢复身份。** `generation_id` 标识一次已加载的插件代次，可用于追溯。精确执行契约相符时，重启后的新代次可以承接调用。排队的 follow-up 在受理时固定 Driver 及传递依赖的实现，下一模型决策仍可取得当前工具与上下文目录。挂起期间释放整目录租约。Driver 恢复时可按已安装的不可变包及精确配置按需装入旧实现，仅为匹配该契约的调用保留租约，当前选版、全局目录和后台服务都沿用其原有生命周期。依赖被禁用、契约不符或包缺失时报告既有错误。待完成工具按原调用身份、贡献及执行契约哈希核对，并复核当前授权。禁止仅按工具名换绑新实现。已完成历史可独立读取。包的逻辑卸载、受引用字节的保留和可执行资格分别判定。[Driver 执行契约](../../specs/runtime.md#run-driver-与原生端口) · [持久调用与卸载](../../specs/plugins.md#15-durable-run)

## 4. 切片的依赖顺序

工具副作用可能先于进程中断发生。审批、问答和子任务恢复共同依赖执行锁、持久调用身份与 Driver 检查点，因此先固定中断和换代的基线。系统指令和会话观察已有独立的输入、输出和可捕获的模型请求，适合作为第一个生产切片。上下文用例借用决策租约，插件宿主拥有目录发布权。宿主准备和执行资源的寿命明确后，再切换受理和挂起恢复。包管理的低频引用扫描消费执行侧的恢复事实，日常提交无须维持引用索引。

## 5. 实施主路线

按以下顺序交付，每个阶段只切换本切片的生产入口，从第 6 节选取受影响的契约和热路径做对照。同一个真实操作只执行所选实现，多个 Host 继续按原生锁与事务并发受理。旧版与新版仅在隔离副本中做对照。回滚在调用结算或安全停写后恢复上一版入口，保留已经发生的事实与副作用。各阶段以同一公开协议和持久格式相互接续。

### 阶段 0 · 固定最高风险的恢复行为

**前置与动作。** 以审查提交或实施时重新固定的基线，选定同一组插件包、配置和两份临时 home。先跑第 6 节所列工具中断、审批与 Driver 换代恢复场景，记录工具调用身份、尝试次序、确定结果、可见消息、检查点及关闭后的资源。审批先从既有的 `test_approval_wait_is_committed_once_without_a_snapshot_rewrite` 和 `test_modified_approval_starts_from_call_facts_without_embedding_bodies_in_run` 取得对照。另固定阶段 1 的请求输入、模型实收参数与观察结果。为长会话保留第 6 节所列的终端 TUI 打开、翻页和重进基线，供涉及会话读取或显示的切片对照。[审批提交与参数覆盖用例](../../../tests/application/test_tool_call_batches.py)

**交付与回退。** 交付可复现的样本、差分项及对应既有测试入口。优先复用已有夹具，只有现有覆盖缺少具体不变量时才在实施中补用例。本阶段仅建立对照，无生产职责迁移。样本不可复现时，先修正测试条件再进入对应切片。

### 阶段 1 · 将决策内的请求提供方交给上下文用例

**前置。** 阶段 0 已能复现保护链，已记录系统提示词、观察消息和自动／手动压缩的基线。模型轮次与手动压缩各自绑定一次操作视图，系统指令和会话观察的选择归上下文准备。[决策资源](../../../ouro/application/runs/execution.py) · [上下文准备](../../../ouro/application/context/preparation.py) · [压缩入口](../../../ouro/application/context/compaction.py)

1. **发布一份可借用的请求提供方视图。** 将两种已有原生注册表作为一个有名字的只读值，定义在上下文能力所属的原生叶模块，使应用和插件适配层都能引用。它只表达“系统指令提供方、会话观察提供方”这两个角色，保留各自的调用签名。`build_extension_catalog` 在已有注册、gate 绑定和冻结完成后构造该值。这两类提供方在 `RuntimeCapabilities` 上共用一项只读属性，`ExtensionCatalogLease` 返回目录中的同一值，原有两项独立属性随之退役。独立 Runtime 直接引用注入的两份基础注册表，保留构造后 `replace_owner` 的可见性。视图只借用引用，额外的排序、注册项复制及租约获取数均应为 0。
2. **把选择时机收回请求准备。** 给 `ContextPreparationService` 一项按 Run 取得已绑定视图的查询。实现从现有 `RunResources` 或独立 Runtime 的基础注册表读取。有绑定时即使目录为空也沿用该目录。模型分支在 `begin_model_round` 完成绑定后取一次，按该决策的活动 controller 集合筛选。手动压缩在自己的操作绑定建立后，只选择所需的系统提供方。这样删除两个 `_for_run` getter、普通轮次 lambda 的两项传参，以及压缩服务为它们维持的转发参数。保留对按现行方式直接构造 Runtime、注入注册表和调用准备能力的覆盖。
3. **维持两条交付语义。** 系统提供方只接收 workspace，其片段进入本次请求的系统指令和请求快照。观察提供方按需取得 Harness，由 `_commit_context_observations` 去重并提交。`build` 发布已提交事件。仅当本轮确实追加了消息，且第一条追加消息的序号未紧接原快照末尾时，才重读历史以补齐并发追加。序号紧接时把本轮消息追加到已读视图，本轮没有新消息时直接投影已读视图。自动压缩复用 `PreparedContext.prompt_context`，手动压缩独立解析系统指令。保持优先级、controller 条件、超时、失败诊断与标签转义。两类提供方沿用各自的 Manifest/SDK 字段和 `system_prompt.call`、`context.call` 方法。[观察提交后的读取条件](../../../ouro/application/context/preparation.py) · [压缩复用与独立解析](../../../ouro/application/context/compaction.py) · [worker 方法](../../../ouro/plugins/worker/instance.py)
4. **在正常入口验收并删除旧路。** 以无插件的嵌入 Runtime、进程内插件与真实 stdio worker 分别驱动请求。比较 Provider 实参、保存的最近请求、观察消息和失败后的派发次数。改变工作区指令、重复相同观察、改变观察修订、在两次决策间换代，并分别触发两种压缩。按当前契约，无活动观察提供方时，额外 Harness 捕获为 0，手动压缩的观察回调为 0。检查热路径的目录租约获取、RPC、存储读取和事务计数。

**完成与回滚。** 模型轮次、压缩转发和通用调度均可独立于这两类注册项的内部表示。调整两类内容的组合规则只触及上下文用例与契约样本。只有旧接线被删除且第 6 节的等价条件通过，才算交付。以“目录视图及其消费者”作为一个可回退提交单元，恢复旧选择路径即可读取同一份会话。`_commit_context_observations` 和代次发布协议始终由原所有者执行。

### 阶段 2 · 让宿主按贡献类型完成准备、哈希和投影

**前置与动作。** 阶段 1 的两种提供方已可分别在两种代码插件运行方式下对照。以它们为样本，沿 `prepare_contributions → build_contribution_contract_hashes → project_prepared_contributions` 清理宿主接线。让哈希计算和目录投影直接消费同一份已准备注册项，另行传入 Manifest 与资源契约。将类型专有的校验、身份、冲突和投影放回现有 `ContributionTypeAdapter` 对应的实现。跨所有者的身份冲突仍由候选目录统一核对。两种传输在各自边界归一到原生注册值。候选构造阶段完成适配，调用热路径继续直接访问已发布目录。[准备与哈希](../../../ouro/plugins/contributions/contracts.py) · [代次 gate](../../../ouro/plugins/catalog/gates.py) · [目录投影](../../../ouro/plugins/contributions/projection.py)

**退役与放行。** 先去掉 `ContributionContractContext` 对准备结果的逐成员镜像和 `preparation.py` 中相应的第二遍装配。本阶段交付共同哈希输入及两类请求提供方的完整路径。其余类型随实际消费者迁移，每次只消除能指认的重复声明。MCP 发现的工具和显式工具共用工具目录。改变贡献类型的登记次序时，两组工具的身份、哈希、所有者与发布顺序保持一致。保持清单延迟导入、所有者、冲突诊断、可选项降级、哈希输入和后台服务交接。以现有包对照各类贡献身份与哈希，模拟一次同类新增，通用发布器、退役流程和无关类型改动数为 0。共同哈希输入的替换整体切换及回退，其余迁移逐类切换。候选失败保留已发布目录。每次真实调用只执行已选的处理器。

**框架扩展演练。** 选 `system_prompt_providers` 作为已知样本，在隔离检出从尚无该类型专属声明与接线的状态接入。分别列出 Manifest、适用的 SDK/worker、原生类型与目录字段、类型适配和实际消费点的改动。沿两种传输走到 Provider 实收，再核对通用发布循环、退役、运行调度及无关贡献类型各自的改动数。目录构造中的恢复、投影目标、冻结和基础所有者记录均计入接线成本。若演练暴露重复规则，将该规则收回所属类型，保持热路径直接使用类型明确的字段。[类型登记](../../../ouro/plugins/contributions/inventory.py) · [目录构造与基础所有者](../../../ouro/plugins/catalog/snapshot.py) · [发布入口](../../../ouro/plugins/lifecycle/runtime.py)

### 阶段 3 · 让执行用例直接获得已装配的模型和工具能力

**前置与动作。** 决策视图和宿主的准备结果已有明确所有者。由 `LocalApplication.build/from_runtime` 与 `build_local_runtime` 一次装配进程级模型目录、基础能力、用量和插件资源。执行用例复用准备、提交和结算协作者，进入 Driver 时取得本次 Session、Run、取消信号与恢复位置。`RunModelRequests.execute` 会更新实例上的预算，当前工具查询与流开始回调也绑定于本次执行。保留这些值的 Run 或调用级寿命，每轮按所属 Run 取得有效预算和可用工具，避免并发执行相互覆盖。[本地独立 Runtime](../../../ouro/local_application.py) · [Driver 执行](../../../ouro/application/runs/execution.py) · [预算更新](../../../ouro/application/models/requests.py)

**退役与放行。** 执行用例能用给定运行资源独立构造，删除 Runtime 对已迁移注册表的中转和每次重建的固定回调。保留动态设置、授权和控制器选择。用默认、进程内和 worker Driver 验证模型与工具调用、用量、取消和旧代次释放。再让预算和工具集合均不同的两个独立根 Session 并发推进交错的模型轮次，按各自单独运行的结果核对 Provider 实收工具集合、预算生效轮次和 Run 终态。一方达到预算后，另一方仍按自身预算继续。单独核验无插件 Runtime、轻量命令的启动与关闭。按本地工厂和 Driver 入口成对回退，`RunDriverContext` 与持久 Driver 身份对两边通用。[Driver 执行上下文](../../../ouro/application/runs/drivers.py)

### 阶段 4 · 拆清受理、调度与直接执行

**前置与动作。** 在开始下一 Run 前核对当前历史代次中前一 Run 的续接是否已结算。等待执行权期间会话头变化时，使用锁内重读的事实作同一裁决。沿 `accept_user_input`、`run`、`run_pending_inputs`、`run_prepared` 和 Supervisor 的 `_execute_job` 区分直接用户请求、已受理消费单位与预留 Run。将 `RuntimeService.accept_user_input` 中的普通用户受理编排移入 `InputAdmissionService`，复用 `accept_initial`、`receipt`、`QueuedInputQueue` 和 `InputSessionSettings`。来源专属数据在各自入口解释，通用执行边界只消费该入口实际拥有的值。共享锁内重读和合法转换。首次受理的事实、执行期重新检查的策略、插件命令整批输入与控制变更各依其原提交边界。可一次提交的直接启动仍一次提交，先受理后调度的入口保留独立回执。[输入受理](../../../ouro/application/inputs/admission.py) · [原生队列](../../../ouro/application/inputs/queue.py) · [调度操作分派](../../../ouro/application/supervisor.py)

**输入身份与执行权。** 入口区分本次受理直接移交的执行准备、仅由持久事实找回的输入以及已取得的 Run 预留。直接移交可复用刚完成的策略判断，包括独立 Runtime 没有插件目录的情形。恢复持久输入时沿用预期 Run 与 Driver 身份，按执行时的绑定检查当前 Prompt Policy。`prompt_policy_checked` 只记录原受理判断。不同来源在进入共同的锁内重读与提交用例前解释清楚，`RuntimeService` 保留公开入口、调度交接和结果解释。[首条输入交接](../../../ouro/application/inputs/requests.py) · [消费时的策略契约](../../specs/plugins.md#103-prompt-policy)

**退役与放行。** 逐入口删除 `_run_input` 中靠可空参数辨别来源和启动方式的分支。保留直接运行的等待结果、受理回执时机、忙会话排队、`steer` 与 `follow_up` 区别和输入幂等身份。重复提交、两个 Supervisor 同时受理、许可耗尽、用户取消等待时，两后端的回执和副作用应与基线一致。首条输入已经受理时，使用相同 Session 和输入身份重试须复用持久绑定，并能取得原 Run 的结果。覆盖启动准备失败、运行中与完成后的重试，并在已有会话中交错两次相同输入的提交。额外副作用、重复输入事实和遗留租约均为 0。相同路径的持久写入和事务次数不得增加。按入口切回旧用例，已受理输入按原身份消费，回滚操作本身不重新提交输入。

在已有会话先受理两条身份不同的输入，再重试第二条。队列仍按既有合批或逐条规则消费，结果通过目标 `InputState` 的消息引用核对 Run。会话仍忙或挂起时保留公开入口的相应运行边界，禁止将其他输入的已完成结果作为目标结果返回。对已完成、已失败的同一 Run，比较首次和重试的 `final_text`、`error_code`、`had_tool_error` 及已结算 `usage`。使用现有事实和按 Run 的查询，重读不触发通知、模型、工具或全历史扫描。

### 阶段 5 · 统一挂起恢复的提交顺序与资源收尾

**前置与动作。** 阶段 0 的工具中断与换代矩阵仍通过，受理和执行寿命已明确。先迁 `approve_tool`，再迁 `answer_user`、`resume_agent_wait`。复用 `RunExecutionOwnership.parked_run`、`RunLifecycle.save_resolved_batch` 和 `_continue_resolved_batch`。各入口保留自己的身份核对与决定，例如批准及参数覆盖、回答后仍可能继续提问、子任务按完整 Call 身份交付确定结果。让同一执行用例拥有“锁内重读和裁决 → 原子提交 → 通知 → 继续或保持等待 → 释放执行权后调度”的顺序。沿原格式集中解释已有绑定标记，插件层继续解释实现和依赖契约。[审批、回答与子任务恢复](../../../ouro/application/runs/interactions.py) · [工具执行身份比较](../../../ouro/tools/executor.py)

**跨 Host 问答。** 交互 Host 将所见的 Run、批次、Call 与 `input_revision` 随回答传到调度入口。仅给出 Run 的已有调用方式，在首次接收回答时固定当时的待答项。Supervisor 排队、等待执行许可和取得 Session 锁都保留该目标。执行者用锁内事实核对后才调用恢复处理器。用一个已占用的许可、同一工具连续两次提问和两个共享 home 的 Host 验证。后到的第一题回答应报告过期，第二题的修订、等待状态与可答性保持有效。根会话和委派会话沿各自的公开接入验证。复用既有提问修订与 Call 身份，保留原有磁盘格式。[Host 交互投影](../../../ouro/application/contracts/tool_activity.py) · [提问修订](../../../ouro/core/tool_batches.py)

**退役与放行。** 删除三个入口平行维护的共同提交与收尾步骤。保持 Run 等待、授权收紧、迟到确定结果和已发布未知反馈的区别。省略审批 ID 时，决定归属调用方选中的待审批项。两个调用者先后取得同一等待项时，后到决定不能落到下一项；问答也须核对原提问。放行需要已知结果额外执行 0 次、未知结果自动重放 0 次，撤销的代次无法再接新调用，停驻 Run 释放进程内资源。按一种交互入口独立回退。先让当前调用结算，切换后从同一持久批次继续，不回放已经产生的外部效果。

### 阶段 6 · 收窄读取和跨业务引用，退役内部外观

**前置与动作。** 写事务和恢复规则已有唯一归属。先让观察页与 Draft 读取者声明所需读取，沿用同一个 `session_read` 短读边界。`TaskService` 直接取得模型解析，`TaskExecutionCoordinator` 直接取得执行与状态查询。把“未完成工作引用哪些插件实现、归属哪个 Session/Run”的查询移给了解队列、控制和恢复规则的应用侧。插件管理据此判定包保留。保持旧冷扫描口径和必要依赖引用。让 `TuiController` 从本地组合根直接取得会话、资源和模型用例，替换经 Runtime 取得它们的路径。CLI 轻量命令继续只装配所需服务。对 Files 与 SQLite，只合并相同的前置事实选择，日志定位、跨文件发布与原生 SQL 事务分别归后端。[观察页](../../../ouro/application/observations/facts.py) · [任务模型解析](../../../ouro/application/tasks/service.py) · [Files 提交](../../../ouro/sessions/backends/files/commits.py) · [SQLite 提交](../../../ouro/sessions/backends/sqlite/commits.py)

**退役与放行。** 删除 `tasks.runtime` 的穿透访问、插件管理对 Run/Call 状态的逐项解释以及只读用例对 Store 写入、归档等方法的类型依赖。草稿读取可直接接收一个绑定方法，在调用方已打开的同一个一致读内调用。包回收只声明会话头、待消费输入、Run、工具状态与开始记录的读取。模型绑定在同一会话变更边界内读取权威设置。需要多次一致读取的读者共用该后端实例。按第 6 节在终端 TUI 对照长会话的打开、翻页与重进，同时验收观察追赶、归档往返、冷恢复、包 GC 保留集合及查询工作量。每次按一个消费者回退，两个后端始终使用同一领域提交契约。最后以真实调用方清单决定哪些 Runtime 兼容入口继续提供，清除仅供旧内部实现使用的转发。

最终验证覆盖独立 Runtime 与 `LocalApplication.from_runtime` 的真实绑定。对已有空闲 Session，分别首次提交带稳定 `input_id` 的请求、重试待消费输入、读取终态结果。在受理回调与完整请求两个边界计数，区分 `session_read`、`session_mutation`、引擎实际事务和同步写。身份核对优先复用原有短读或锁内提交，既有并发去重和进程间竞争的断言继续生效。

## 6. 差分、性能与放行

### 怎样获得可信对照

用基线与候选两个检出，各冻结相同的依赖、配置、插件包字节、权限、时钟条件和输入脚本。从同一份**已停写**的测试快照复制出两个独立临时 home。模型使用 FauxProvider、捕获型 Provider 或录制的确定性流。工具用仅在各自临时目录追加计数的替身，worker 使用受控的本地 stdio 夹具。需要中断时，在指定持久边界结束夹具进程，再从所属副本重启。两个版本都使用受控替身与各自的临时数据，产生的副作用仅落在对应夹具内。

对照回执、CLI 输出与退出码、Provider 实收参数、提示词及消息顺序、请求头与用量、工具身份和尝试、Run 终态，以及重连后的 Host 视图。随机 ID、绝对临时目录和墙钟时刻可做一一映射，保留所有引用关系、先后次序和因果归属。模型流按现有语义段比较拼接内容、首段及时交付和边界事件。相同包与配置的贡献和执行契约哈希、原包 digest 逐值相等。身份错误类别和结果确定性的含义也要一致。

### 性能等价与退回条件

`tui_sessions` 提供无界面环境下的投影条数、分页和输入处理样本。真实终端另行记录从按键到屏幕出现字符的耗时。把两组数据与存储读取量和峰值内存一起保存。现行受控目标是按键到 Composer 更新的 P95 ≤ 50 ms。屏幕回显包含终端绘制，首屏、补页、重进与屏幕回显各自按下述基线波动规则放行。[TUI 会话进入与展开基准](../../../dev/benchmarks/README.md#tui-会话进入与展开) · [受控输入目标](../../specs/performance.md#io-所有权与响应性验证)

**放行规则。** 同一语义轨迹的额外模型派发、工具副作用、传输往返、持久读写事务及同步写次数均为 0。原来有界的查询只读取活动窗口。未启用的 worker 额外启动数、关闭后遗留的租约和进程数均为 0。时延、读取量和内存以独立的 A/A 数据预先确定等价边界。A/A 和 A/B 使用相同采样单位、分组方式、样本规模及分位估计量，保留跨进程或轮次的相关性。预先固定 A/B 组数或独立确认批次，分别以 P50、P95 差值的单侧 95% 置信上界判定。出现超界时在验收记录中列出原测量结果，按已固定门槛复验。环境或规模确需改变时，重新独立校准再测候选。可重复的实质退化退回所属切片。流式背压、短读事务和取消收尾分别验收。

|---|---|
| 本地优先 | 独立 home 下可管理、读取和恢复会话，轻量入口按需启动。 |
| 插件扩展能力 | 新增已有类别的普通插件，框架生产文件改动数为 0。升级、撤销和恢复分别通过生命周期样本。 |
| 轻量高效 | 同语义热路径的调用、I/O、事务、RPC 及内存符合上述硬指标和测量门槛。 |
| 长期可维护 | 重演同类变更，改动集中在所属贡献与消费用例，通用调度和无关类型改动数为 0。 |
| 原语易懂 | 从正常入口能直接定位受理、执行、原子提交和资源释放的各自所有者。 |
| 功能与性能等价 | 双版本得到等价的持久事实、用户结果和调用轨迹，相关平台各自通过性能比较。 |
| 严格禁止过度设计和过重的防御性设计 | 每个新增抽象都能对应本切片实际发生的变化或需要维护的契约。取代旧接线时，在同一切片删除旧路径。每项额外校验都能指出需要保护的事实以及前提可能失效的位置。只透传同一组内部字段的包装、重复维护同一事实的状态、对未变化的可信值反复做的全量校验，均应在迁移相应用例时消除。 |

## 7. 使用范围与待确认项

| 已确认的使用情况 | 对实施与验收的影响 |
|---|---|
| 日常入口是命令行和终端 TUI，用户没有自行编写脚本接入 OURO。 | 个人使用按 CLI 的结果与退出码、TUI 的受理回执与交互时序验收。插件 SDK、worker、公开 Host 契约和仓库内使用的构造方式继续按第 3 节验收。删除内部转发前核对其真实调用方，无须为假设的个人脚本另设兼容层。 |
| 偶尔打开很长的会话。 | 阶段 0 记录长会话基线，涉及会话打开、分页、观察或显示的切片按第 6 节复测。1,000 条和 10,000 条是仓库既有基准的样本规模，实际会话长度无需预先统计。 |
