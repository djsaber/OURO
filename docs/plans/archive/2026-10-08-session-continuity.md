# OURO 核心稳定与架构减负计划

> 文档类型：已完成重构记录
> 当前阶段：核心重构及集成修复完成。
> 本文保留目标、实施明细、设计分析和验收条件。现行契约以[架构总览](../../architecture/README.md)和[领域规格](../../specs/README.md)为准。

目标是让 OURO 成为**轻量、高效、灵活、强拓展的个人 Agent**：用户能够在环境变化后继续已有任务，扩展能够在清晰边界内改变能力与行为，核心只承担可信事实、执行秩序和必要资源管理。轻量体现在较少的长期维护承诺、常驻资源和重复工作；强拓展体现在组件易于接入、替换和退出，不以扩展类型或配置开关数量衡量。

**以问题本质决定架构，不把现有类、状态机、快照和兼容承诺作为必须保留的前提。清晰、干净、规范合理的改进是必要的；禁止无依据的防御式编程、特例补丁、通用框架堆叠和偏离任务目标的复杂度。**

本计划聚焦会话继续、局部操作收尾、环境绑定寿命、Harness 与输入队列、子 Agent 及当前能力投影。重构应减少跨生命周期的耦合，复用单一 Agent 循环与现有提交机制，在交付新行为时清理被取代的路径，避免以长期兼容分支或重复状态换取短期可运行。

## 核心见解与设计判断

Agent 循环根据已有事实和当前可用能力作出决策、执行行动并接收反馈。框架、插件、工具、技能和模型共同参与构成这个可交互环境；Harness 同时包含环境规则和会话业务状态，需要按职责区分。

| 职责 | 需要表达的内容 | 稳定性要求 |
|---|---|---|
| 当前运行环境 | 可用能力、模型路由、技能、策略及其当前实现 | 可以变化；一次请求与具体调用的绑定清楚，变更不能静默改变已接受操作的含义 |
| 会话事实 | 用户意图、消息、任务进展、回答、已发生的调用与结果、归属和授权记录 | 可持久化、可读取、可解释；环境变化不改写过去，不把未执行或未知结果伪装为完成 |
| 具体操作承诺 | 待审批动作、待回答问题、执行中的副作用、已接受的结算与结果投递 | 保持相关身份、授权、幂等和结果语义；只在确有依赖的范围内阻塞 |

以下判断作为设计的共同方向：

- **会话连续性独立于环境复刻。** 恢复的目标是利用可信事实继续任务，不要求重建整个旧插件集合或旧进程。环境变化、缓存失效、工具减少本身不应使整段会话不可继续。
- **继续决策与收尾旧操作分别处理。** 普通消息和新的模型决策可以使用当前环境；审批、回答、未完成写入和结算需要先解释对应操作。新建还是延续 Run 服务于真实执行记录，不决定会话是否具有连续性。
- **一致性收敛到有因果关系的边界。** 消息帧、事务、身份、授权和副作用状态仍是硬约束；过去观察到的环境与当前环境不同，通常属于决策输入变化。当前必需策略无法建立时阻止受其约束的动作，不能静默绕过。
- **运行保证限于可验证的协议。** 框架维护显式操作依赖、身份与提交去重，阻止恢复机制自动重放结果未知的调用；Agent 根据真实反馈判断后续行动的业务依赖。任意外部副作用不承诺恰好执行一次，更强保证由具体工具的操作 ID、状态查询或外部幂等协议提供，不建设通用因果分析或副作用去重系统。
- **持久事实与执行资源分离。** 等待用户数天的请求不应仅为保留身份而持有整个可执行环境。哪些操作确实需要保留旧实现，由具体恢复协议决定，不上升为所有 Session 的统一承诺。
- **能力变化必须可理解。** 模型获得当前可用能力，受影响的操作返回明确状态；必要时提供简洁的变化说明。历史保留原始事实，不批量重写，也不把内部代次和配置摘要倾倒进模型上下文。
- **扩展有退出路径。** 插件缺失、禁用或升级时，目标、历史和用户输入仍有归属；允许结束无法继续的局部操作，再由 Agent 在允许的范围内重新决策。不能按同名组件猜测旧操作已被正确承接。

这些是职责边界，不预设必须新增 Environment 类、统一快照协议、兼容性推理引擎或另一套恢复状态机。现有设计中有价值的边界可以直接复用；无法服务目标的承诺应连同实现一起删除。

## 必须保持的核心边界

| 边界 | 必须保持的性质 | 现行规格 |
|---|---|---|
| 会话与执行 | 身份隔离、唯一执行所有权、可解释的状态转换；换 Run 不丢失任务事实 | [运行时](../../specs/runtime.md) |
| 工具与交互 | 当前 deny 和撤销有效；审批不扩大授权；回答关联原问题；未知副作用不盲目重放 | [工具与交互](../../specs/tools-and-interactions.md) |
| 持久化与撤销 | 原子提交、幂等、历史撤销和附件归属有效；保留损坏或不支持的数据供诊断 | [持久化](../../specs/session-persistence.md)、[撤销](../../specs/session-undo.md) |
| 上下文与模型 | 工具消息帧完整；请求符合目标协议；出现可见输出后不自动重发请求 | [上下文](../../specs/context-and-compaction.md)、[Provider 协议](../../specs/provider-protocols.md) |
| 资源与观察 | 开始的线程、进程和调用有收尾者；事件可追赶，慢观察者不改变运行事实 | [资源与监督](../../specs/resources-and-supervision.md)、[会话观察](../../specs/session-observation.md) |
| 扩展与委派 | 包完整性、凭据保护和权限下放成立；插件不是 OS 沙箱；子 Agent 不获得未经允许的新能力 | [插件](../../specs/plugins.md)、[子智能体](../../specs/subagents.md)、[安全策略](../../../SECURITY.md) |

放宽环境一致性不等于放宽上述边界，也不要求所有旧格式永远可执行。稳定的数据表示、明确的不支持范围和显式数据维护路径应与组件发布版本分开设计，不隐式迁移或清空用户数据。

## 整体框架审视

审视范围覆盖 Agent 循环、会话与操作恢复、插件生命周期、Harness、输入队列、子 Agent、上下文投影及观察链路。以下结论来自职责和调用关系，不构成已测得的性能收益。

主要耦合在于：一次决策的能力视图、一次调用的执行资源、长期会话事实和委派权限上限，过多地绑定到了 Run 及其完整环境快照。应按各自所需寿命持有与校验，不以减少类或文件数量代替职责收敛。

| 当前设计证据 | 判断 | 改进重点 |
|---|---|---|
| Core 内循环通过端口请求上下文、模型和工具批次；Host 通过 Application 操作 | 分层具有可复用价值，Agent 循环已有较清楚的边界 | 保持单一 Agent 循环，收拢环境绑定与恢复编排 |
| Run 保存完整插件代次集合，Catalog 恢复要求集合和执行契约匹配 | 继续任务承担了复刻旧环境的成本 | 将普通决策与待完成操作的恢复依赖分开 |
| continuation 已有持久化结算方案，但外层仍先恢复旧 Catalog | 已形成的决定与重新执行插件代码仍存在耦合 | 审视结算真正需要的事实、当前授权和回调，缩小阻塞范围 |
| 排队用户输入保存 prospective Run 和完整 Catalog 绑定 | 接受输入、策略裁决与未来执行环境被长期绑定 | 区分接收条件和执行条件，保留输入事实，收敛队列资源寿命 |
| 父 Run 保存 AgentCatalog，Delegation 保存完整定义和有效工具引用 | 派遣意图与工具实现版本共同进入长期契约 | 保留任务和权限边界，允许子 Agent 在环境变化后继续决策 |
| Harness 已按 Session 和 owner 保存状态，上下文已有投影边界 | 事实与运行资源分离已有基础 | 明确插件退出、控制权失效和当前环境投影，无需另建状态存储 |

## 会话连续性与局部操作恢复

**证据。** [Catalog.matches](../../../ouro/plugins/catalog/snapshot.py)比较完整插件集合；[snapshot_for 与恢复目录重建](../../../ouro/plugins/lifecycle/runtime.py)恢复旧包、配置和依赖；[Runtime 恢复入口](../../../ouro/application/runtime/service.py)依赖这些绑定。现行[持久 Run 规格](../../specs/plugins.md#15-durable-run)对不匹配的 builtin 还要求使用新 Session 开始新工作。

**建议方向。** 以可读取的会话事实为连续性基础，在同一 Session 内用当前环境继续允许的工作。Run 保留真实执行身份和生命周期；不为延续聊天而伪造原操作完成，也不要求用户通过复制历史或创建新 Session 绕过组件更新。

- [x] 梳理消息提交、审批、回答、手动继续、自动继续和子 Agent 结果到达各入口：区分读取事实、兑现已接受操作、进行下一次决策，复用所属边界的规则。
- [x] 为待完成操作保留必要的请求身份、参数、问题内容、授权范围、阶段、结果及幂等依据；优先使用现有 ToolCallBatch、交互和结算记录，删除无消费者的环境镜像。
- [x] 定义局部恢复失败后的有效状态及收尾：工具不可用、原问题已结束、控制权撤销、结果不确定。保留原调用身份，准确表达已执行、未执行或未知，按显式协议处理依赖；不由框架猜测任意后续行动的业务因果。
- [x] 明确何时保留原 Run、何时结算后开启新 Run，以及旧交互退出、工具帧闭合和执行所有权交接的顺序，保持用量归属、队列和 Delegation 关联完整。局部受阻不通过新增并行会话循环或遗留悬空工具帧解决；避免长期维护“严格恢复”和“灵活恢复”两套执行模式。

局部操作采用以下默认收尾方向，具体状态转换在首批实施前落实到所属规格：

| 已有操作状态 | 默认处理 |
|---|---|
| 已持久化有效结果 | 直接读取或完成幂等提交，不要求旧插件存在 |
| 尚未执行，原操作绑定无法满足 | 返回明确的未执行结果，让 Agent 基于当前能力重新选择；不按同名工具替换执行 |
| 等待审批或回答 | 保留交互身份、问题和已接受输入；无法承接时明确结束原操作，旧批准不转授新动作，旧回答不自动成为新授权 |
| 已开始，结果未知 | 保留未知状态与可用核查依据，恢复机制不自动重放；有明确查询协议时查询，否则如实报告无法自动确认 |

工具帧可通过真实的“结果未知”反馈闭合，外部结果仍保持未知。复用 [RunRecoveryService](../../../ouro/application/runs/recovery.py) 的中断反馈路径，完成必要收尾后再进入下一次允许的决策；消息帧完整不能被解释为副作用已确认。

默认允许结束无法承接的旧操作，不以尽可能恢复所有旧操作为目标。只有具体工具存在真实承接需求时，才定义其最小稳定契约与支持范围。优先采用协议能够验证的少量字段；同名、相同 schema 或相同版本号不能单独证明授权含义未变，也不引入通用代码语义兼容推断。

**退出条件。** 无关插件变化不阻止已有会话继续；已完成调用无需旧插件即可读取；相关组件缺失时准确处理待办状态，既不无条件重放，也不扩大成全会话锁死。实施需同步[运行时](../../specs/runtime.md)、[插件](../../specs/plugins.md)和[工具交互](../../specs/tools-and-interactions.md)。

## 环境生效边界与插件生命周期

**证据。** [插件运行时](../../../ouro/plugins/lifecycle/runtime.py)同时维护 active、retired 和恢复 Catalog，并拥有后台服务交接；[Catalog.acquire](../../../ouro/plugins/catalog/snapshot.py)为整个目录中的代次取得租约。长期等待的 Run 和队列因此可以延长整组环境的寿命。

**建议方向。** 普通环境更新在明确的决策边界生效。一次模型请求使用一致的能力描述，响应形成的具体调用有明确执行绑定；下一次决策可以使用当前能力。已开始的调用由原 owner 收尾，权限撤销仍在行动边界生效。

包摘要用于完整性验证和来源审计；旧操作能否继续依据对应行为与数据契约判断，不把整个环境摘要相等作为统一恢复条件，也不将摘要不同直接解释为操作不兼容。

- [x] 优先评估模型轮次边界作为环境更新点；覆盖请求在途、响应已生成但工具未开始、整批待执行、正在执行和等待用户几种情形。环境更新不能把模型选择的调用静默重定向到另一个同名实现。
- [x] 将进程内资源保留范围收敛到实际在途调用、必要依赖和观察者排空。待审批、待回答和重启恢复优先依赖持久数据；确实需要旧实现的操作单独定义承接方式和可用期限。
- [x] 分别决定包安装、配置修改、启停和实现替换何时生效。涉及不可并存的共享资源或后台服务时，允许安全空闲点或重启生效，不为任意指令位置的热替换承担永久成本。
- [x] 在待操作恢复协议确定后，清理仅服务整套旧环境复刻的恢复重建、配置历史保留和代次分支。保留包完整性验证、真实组件依赖、候选发布原子性、禁止新调用的 gate 与完整关闭路径。

需要取舍的是“下一决策边界生效”与“部分组件重启生效”的产品范围，以及旧操作是否存在必须跨版本继续的真实需求。会话能在新环境继续不以全面进程内热替换为前提，目标也不包含历史环境仓库或完整依赖图回放平台。

**退出条件。** 更新不会改变正在执行调用的归属；新决策可看到新能力；disable 后不能启动被禁用的动作；等待用户不会无依据地保留整个旧环境。以活动代次数、租约存活时间、常驻资源和恢复耗时验证收益，不能以丢弃任务换取降低内存。

## Harness、输入队列与自动继续

**证据。** [HarnessState](../../../ouro/core/harness.py)和[扩展状态](../../../ouro/core/session_extensions.py)已有持久 owner 边界；[QueuedInput](../../../ouro/application/inputs/queue.py)携带完整环境绑定；[RunContinuationService](../../../ouro/application/runs/continuations.py)已有结算方案，但 Runtime 先恢复旧 Catalog，继续动作的提交也会检查当前 registration。

**建议方向。** 业务事实、控制权和环境实现各自负责。目标、进展和用户输入不因插件退出而消失；执行资格由当前有效规则判断。已经接受的决定按其事实结算，不重新调用插件推导一遍，也不把曾经接受输入视为永久执行授权。

- [x] 对 continuation 区分尚待策略决定与已经持久化的结算方案。逐项核实后者的提交依赖，保留 history epoch、Harness 版本、身份和授权检查，移除与兑现决定无关的旧 Catalog 前置条件。
- [x] 控制限制是否仍有效依据 Host 持有的控制事实判断，不以插件或回调是否存在代替解除决定。能明确限定影响范围时只阻止对应动作；不能解释必需限制的范围时暂停相关执行，同时保留历史读取、诊断、取消和显式释放控制的管理入口。
- [x] 复用 [SessionControlCoordinator.force_release](../../../ouro/application/session_controls.py) 明确控制器失效后的退出路径：显式释放不依赖失效插件成功执行清理，未确认的私有清理单独报告。未知 owner 私有状态不解释、不清空；人工继续本身不豁免仍有效的限制。
- [x] 区分输入接收校验、排队事实和消费时的执行策略。初始禁止接收或保存的输入仍在原边界拒绝；已接受输入在消费受阻时保持可见且可处理，不能因旧环境缺失而丢失或重复投递。
- [x] 收敛 prospective Run 与长寿命队列租约的必要范围；保持 FIFO、原子输入单元、来源归属、附件、撤销与幂等。不新增第二份输入或控制状态，不把所有来源压成无类型事件。

**退出条件。** Goal、Plan 或第三方控制器更新后，已记录的目标和进展仍保留，无法解释的私有状态明确报告；已经形成的结算不会重调决策回调；插件失效不能阻断无关的人工会话操作，也不能静默解除限制。拒绝、撤销和历史回退仍准确限制后续执行。

## 子 Agent 的任务承诺与当前能力

**证据。** [子智能体规格](../../specs/subagents.md)要求 parent Run 冻结完整 AgentCatalog，Delegation 冻结定义和 EffectiveToolRefs，child 的 resume/follow-up 使用该契约；[恢复对账](../../../ouro/application/agents/recovery.py)还验证父子记录之间的冻结契约一致性。

**建议方向。** Delegation 记录实际委派的任务、父子身份、工作范围、预算及权限上限。可用工具和执行实现属于运行时能力。父子记录一致性保护真实派遣事实，不能直接推导出工具实现必须永久不变。

- [x] 区分用户明确委派的承诺与可重新解析的执行选择。任务指令、workspace、授权上限和明确指定的模型要求不得因定义更新被静默改写；新派遣可使用当前定义。
- [x] 让后续决策的可用能力与委派上限、当前权限和撤销求交。新增工具是否进入已有 child 必须有明确选择规则；同名 owner 替换、`all` 选择和权限放宽不得自动扩大授权。
- [x] 只对待完成的调用绑定必要的旧操作契约，审视整个父 Run AgentCatalog 与 child 长期工具快照的必要范围。工具缺失可作为当前能力事实反馈；确属任务必需能力时明确受阻，不静默承诺仍能完成。
- [x] 保留 Delegation 身份、派遣幂等、结果唯一交付、sync 等待释放许可和真实父子关联。child 使用普通 Session / Run，不另建长期 Agent 执行内核。

**退出条件。** 无关组件升级后 child 可在既有权限范围内继续；父模型看到的 SpawnAgent schema 与实际选择一致；既有任务不被新定义替换。同一持久操作身份下不重复派遣、提交或交付；结果未知的外部调用不由恢复机制自动重放，不将内部去重扩大为任意外部写入恰好执行一次的保证。

## 历史上下文、当前能力与数据契约

**证据。** [上下文准备](../../../ouro/application/context/compaction.py)已经投影完整工具帧、压缩历史与可使用的 Provider continuation；[Core 内循环](../../../ouro/core/inner_loop.py)通过端口获取上下文和模型请求。历史记录无需天然承担当前工具可调用性的证明。

**建议方向。** 历史描述过去发生的事，当前能力描述下一步可做的事。前缀缓存、token 估算和 Provider 私有续接服务效率，不能成为会话依赖整个环境不变的理由。

- [x] 在首条会话继续链路中同步贯通当前能力投影和执行绑定：工具描述、执行协调器、技能及有效策略遵循选定的决策边界，执行前仍校验当前撤销与权限。用户明确激活并已接受的技能正文等输入事实保持原内容。只在影响决策时提供简洁变化说明，不生成永久环境变更消息流。
- [x] 保留旧工具调用与真实结果，即使当前工具已删除；保持 request/result 关联和当前协议格式。不能为了继续决策而删掉未知副作用记录或伪造工具成功。
- [x] 延续 Provider 私有状态的局部适用性检查；可由规范历史表达时重新构造请求，无法无损表达的必要数据明确报告。缓存失效与自动重发已输出请求分别处理，不以降级为名丢失事实。
- [x] 审视持久记录中的环境摘要：审计来源、操作绑定和派生缓存分别说明用途；只保留实际消费者需要的字段。主会话事实可独立读取，插件私有 payload 在对应操作使用时按其数据契约解释。
- [x] 明确本次连续性承诺支持的会话记录与 owner 状态版本。当前[持久化规格](../../specs/session-persistence.md#数据布局)只接受当前格式，不能将移除 Catalog 校验等同于已支持跨数据版本恢复；无法解释 owner 状态时保留原数据，不推断其业务含义。
- [x] 首批改造优先保持当前持久记录可读；确需改变格式时，在交付前明确版本支持、显式维护路径及可读取、导出和继续使用的范围，并同步相关规范。以改造前创建的会话验证声明支持的升级路径，不只验证新建数据；不支持的格式明确拒绝，不隐式迁移或清空。

格式支持范围与组件发布版本分别维护。轻量方案优先采用少量稳定记录与明确的数据处理方式，不建设通用 schema registry、无限兼容层或为了每次插件发布迁移整个会话的机制，也不以临时兼容分支长期承担本次改造成本。

**退出条件。** 模型、技能和工具集合变化后仍能利用规范历史；真实请求的审计内容不被重写；必要消息帧和资源归属有效。缓存或计算优化须独立测量，不能将正确性改动直接宣称为端到端加速。

## 执行准备与资源所有权

**证据。** [InnerAgentLoop](../../../ouro/core/inner_loop.py)已有上下文、Run 和轮次端口；[RuntimeService](../../../ouro/application/runtime/service.py)组合输入、恢复与执行；[RunResources](../../../ouro/application/runtime/resources.py)聚合进程内绑定和工具协调器。

**建议方向。** 复用单一 Agent 循环、现有应用用例与原子提交机制，让执行准备、持久事实和资源收尾各有明确所有者。按职责与生命周期收敛依赖，保持普通执行路径直接可追踪。

- [x] 随恢复语义调整收拢 Application 的输入接受、环境绑定和操作恢复边界，使普通消息、回答、审批与继续共享恰当的执行准备。只提取具有独立职责的流程，保留必要差异，不按文件行数拆类。
- [x] 保持模型调用、工具执行、持久提交和取消所有权清楚；对已建立的内部契约直接使用类型，外部输入和副作用边界保留必要检查。Run 资源在所有合法创建入口具有一致的登记与释放规则。
- [x] 环境绑定变化时同步处理依赖它的工具协调器和控制视图，避免新能力描述与旧执行实例混用。跨组件状态修改继续通过明确提案和提交完成，不增加第二份控制或恢复状态。

现有依赖方向是审视的起点，模块归属可以调整；任何调整都应使领域逻辑远离 UI、存储和厂商协议，并让相邻能力更容易添加。通用事件总线、万能 hook、流程 DSL、全局服务定位器和另一个 Agent 框架不作为默认方案。

**退出条件。** 普通 Agent 循环容易追踪，恢复入口无隐含初始化前置条件；扩展不需引用 Host 或存储内部实现；卸载与失败有局部结果。被取代的分支与状态在同一交付中清理。

## 实施顺序与待定事项

优先完成一个可验证的会话继续链路：已有会话 → 处理旧操作 → 取得当前有效能力 → 构造模型请求 → 按对应绑定执行 → 记录真实结果。最小上下文投影、执行绑定和必要 Host 状态必须随首条链路交付；再决定需要多少热更新基础设施，不先建设环境管理平台。

| 顺序 | 交付重点 | 完成依据 |
|---|---|---|
| 1 | 定义普通继续、局部操作收尾和控制失效的规则；明确 Run 身份、更新边界及数据支持范围 | 工具帧闭合、未知结果、审批与回答归属、控制释放和人工继续可验证；现行规格冲突及数据处理方式明确 |
| 2 | 贯通同一 Session 在组件变化后的完整继续链路，同步当前能力投影与执行绑定，处理 Harness、队列和已接受结算；收拢恢复入口 | 删除与实际下一步无关的 Catalog 恢复要求；新请求看到的能力与实际绑定一致；身份、撤销、权限与幂等成立，已有数据上的声明支持路径通过验证 |
| 3 | 调整决策边界上的环境生效和资源寿命，清理不再需要的旧环境恢复设施 | 在途调用不受错误替换，等待资源有界，重启与禁用行为明确 |
| 4 | 将任务与能力绑定调整贯通到子 Agent，完善父子上下文和 Host 表达 | 父子任务连续、授权不扩大，当前能力与实际执行一致；既有 API 没有悬空语义 |

各交付单元进入代码实施前，应在上述默认方向下明确其相关取舍：

1. 环境更新默认在哪个决策边界生效，哪些资源需要空闲点或重启。
2. 旧审批、问题及执行中操作各自的收尾状态；哪些具体操作确需承接，以及对应最小契约和支持范围。
3. 环境缺失时自动继续与人工继续各自允许的范围、必需限制的作用范围及显式解除方式。
4. 已有 child 对工具集合变化的选择规则，哪些定义字段属于不可静默改变的委派承诺。
5. 支持的会话数据和 owner 状态版本；涉及格式变化时的显式维护路径与验收数据。

这些决策复用正常设计评审，不增加审批层级、通用评分体系或独立治理流程。涉及持久格式或 SDK 的变化必须同步明确支持范围、数据处理方式与调用方更新；不遗留长期双轨实现。

## 验证与完成条件

优先复用现有集成与边界测试，用下面的行为证明设计成立；不通过增加固定等待、放宽断言或吞异常换取通过。

| 场景 | 必须观察到的结果 |
|---|---|
| 会话闲置期间增删无关插件、修改技能或切换模型 | 历史与目标可读；下一次允许的决策使用当前能力 |
| 模型响应已产生调用后环境更新 | 调用身份和参数不会被静默重新解释；当前权限仍检查；不可执行时产生真实局部结果 |
| 同一批次同时存在已完成、未执行及无法承接的调用 | 复用已提交结果，按原身份记录各调用真实状态；旧交互明确退出，工具帧完整后再进入下一次允许的决策 |
| 审批前后权限收紧、工具替换或用户修改参数 | 原批准不扩大到不同动作；必要检查与重新审批发生在相关边界 |
| 已接收回答后重启、原问题取消或 owner 缺失 | 回答仍关联原问题；不重复消费，不误认作新授权，不清空历史 |
| 副作用已发出但结果未落盘 | 真实未知反馈可闭合工具帧，未知状态与核查依据保留；恢复机制不自动重放，显式协议依赖仍有效，不要求框架推断任意新行动的业务因果 |
| 必需控制器缺失、更新或回调失效 | 限制不会随插件消失而解除；按可解释范围阻止动作，管理入口仍可用；显式释放可完成，私有清理未确认如实报告 |
| 已接受 continuation 结算后插件更新 | 不重调已经形成决定的回调；提交遵守身份、撤销和当前有效授权 |
| 队列、子 Agent 和并发 Host 跨重启或撤销 | 不丢已接受输入、不重复派遣或投递；控制权与权限下放保持有效 |
| 插件禁用、worker 退出、旧调用取消与观察者积压 | 故障范围清楚；禁止非法新调用；线程、进程、租约及事件有完整收尾 |
| 改造前创建的会话在声明支持的环境升级后继续 | 已有记录仍可按支持范围读取，首个新请求使用当前能力与对应执行绑定；必要数据维护先完成，不以新建会话测试替代升级验证 |
