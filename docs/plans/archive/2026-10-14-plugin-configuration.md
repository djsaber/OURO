# 插件配置实施与验收

> 文档类型：已完成实施计划与验收记录
> 状态：阶段 A–E 已完成，2026-10-14
> 契约来源：[插件配置规格](../../specs/plugin-configuration.md)

## 1. 交付目标

落实与具体插件无关的配置骨架：框架定义结构和处理管线，插件声明独有字段，Host 自动构建配置交互，
所有入口通过同一个 application 用例接受并应用配置。

契约的表达能力与 Host 控件能力分开验收。实现必须覆盖通用的嵌套、数组、动态映射、联合、条件、依赖和
复用结构，不能按记忆、搜索或调度等示例建立特例。原生控件无法完整表示的结构仍能通过通用 JSON 编辑
提交和校验，不能因 TUI 的首期能力而缩减协议。

本记录保留实施任务、依赖、验证与退出条件；字段语义、生效规则及错误边界以现行规格为唯一来源。
实施遵循[English coding guidelines](../../development/coding-guidelines.en.md)和
[文档维护规范](../../development/documentation.md)。

## 2. 范围与实施基础

### 交付范围

- 完整静态 Schema 发现、通用表达与共享规范化/校验。
- credential slot 描述、必填绑定、仅凭据插件的配置入口。
- 类型化配置视图、预检、编辑冲突与明确的应用结果。
- 修订和 SDK 配置快照的深层不可变性。
- 与现有候选 generation、依赖闭包、Catalog 和精确恢复机制集成。
- CLI 的完整配置及 JSON 文件输入，TUI 的通用配置面板。
- 开发者指南、使用指南、通用契约夹具和配置展示示例。

桌面端本次验收其可复用的 application 契约，不创建桌面应用。Builtin 配置、通用秘密存储、自定义 UI
脚本、配置叠层、通用资源插值、热更新回调和自动迁移不在本次实施范围。

### 复用边界

| 现有边界 | 实施要求 |
|---|---|
| `PluginService` | 保持 Host 的统一管理入口，配置用例按职责分解，不继续把解析与界面逻辑塞入入口 |
| `PluginConfigurationRevision` / activation | 保留内容寻址、按 digest 引用及精确执行保留规则 |
| `PluginRuntimeResource` | 复用候选构建、依赖闭包、发布及资源交接，不创建平行配置运行时 |
| `PluginPackageStore` | 复用原子持久化与 compare-and-commit，增加编辑基线检查的用例语义 |
| `PluginContext` / worker initialize | 交付配置快照及既有凭据通道，不暴露内部配置文件 |
| 原生 Task 与插件 data | 分别拥有计划和业务数据，配置应用不跨域写入 |

## 3. 实施顺序

```text
A 通用定义与静态处理
  -> B 修订、快照与凭据
  -> C Application 管线及运行时集成
  -> D CLI/TUI 通用交互
  -> E 样例、文档与综合验收
```

每个阶段先建立行为验收，再实现最小充分变更。阶段之间以明确的模型和用例衔接；不在 Host 中临时绕过
尚未完成的框架管线。
每个阶段运行针对项和相关项回归；全部阶段完成后执行贡献指南规定的全量门禁。

## 4. 阶段 A：通用配置定义与静态处理

- [x] 在 `ouro/plugins` 建立职责单一的配置模块，集中定义加载、规范化和静态校验；安装、readiness 和
  configure 共用实现。
- [x] 扩展 Manifest 配置描述，覆盖可选普通 Schema、业务版本和 credential 元数据，检查声明与权限一致性。
- [x] 静态解析 Draft 2020-12、自包含引用及必需 vocabulary；拒绝外部引用，验证期间不执行代码或联网。
- [x] 保留完整 Schema，不为表单生成将其降格为仅支持扁平字段的内部类型。
- [x] 实现确定且幂等的默认值处理、严格 JSON 输入以及完整对象替换语义。
- [x] 将错误投影为稳定 code、JSON Pointer 路径和安全消息，保留可定位的组合约束问题。
- [x] 使用与业务无关的 fixture 覆盖全部建模维度，并加入非法默认值、递归定义和有限展开边界。

主要落点：`ouro/plugins/manifest.py`、`package.py`、`readiness.py` 及独立配置模块。
验证目标：PC-01、PC-02、PC-03、PC-04。

退出条件：不实例化插件即可发现完整模型并校验候选；动态映射、联合、条件及递归结构的有效和无效输入
均有行为证据；自动补值的边界不会削弱完整 Schema 校验。

## 5. 阶段 B：修订、快照与凭据

- [x] 将共享规范化接入初始值与配置修订创建，明确未就绪初始配置和可提交候选的区别。
- [x] 保留既有配置业务版本、包引用及历史修订关系，修订读取和恢复不重新填默认值。
- [x] 消除修订、application DTO、草稿及 SDK 配置之间的嵌套可变别名。
- [x] 明确并实现 SDK 的只读对象/序列形态，保证 worker 序列化和插件业务模型转换可用。
- [x] 校验必填 credential 绑定及 env reference；分离静态就绪与当前 Host 的可解析性。
- [x] 候选激活在执行插件前检查必填凭据，保持 in-process、worker 和 declarative 凭据通道语义一致。
- [x] 检查错误、日志、初始化消息、DTO 和导出，不传播秘密或原始校验 payload。
- [x] 根据实际契约变化统一确定 Manifest/SDK/worker 版本及 engines 要求，确保不支持语义的 Host 明确拒绝。

主要落点：`ouro/plugins/models.py`、`installer.py`、`api.py`、`runtime.py`、`worker.py`、
`mcp.py` 和 `ouro/sdk/plugins`。
验证目标：PC-04、PC-06、PC-07，以及版本拒绝边界。

退出条件：修改任意可见嵌套对象不能使修订与摘要分离；缺少必填引用和本 Host 无法解析引用得到不同且
安全的结果；凭据秘密不进入可公开读取的配置数据。

## 6. 阶段 C：统一 Application 管线

- [x] 定义配置视图、完整候选、预检问题和应用结果 DTO，外层使用明确类型，动态内容使用 JSON 类型。
- [x] 提供 selected 或指定 installed digest 的配置查询，返回完整 Schema、固定目标和编辑基线。
- [x] 提供无副作用预检，返回规范化结果、问题及预计范围；不将 preview 的瞬时结果当成提交票据。
- [x] 应用时检查 `expected_configuration_revision_id`，并保留构建期 compare-and-commit。
- [x] 相同规范化配置返回无变化；未启用/未选中包只保存；期望启用的选中包通过 runtime 构建候选。
- [x] 明确无 runtime、失败实例修复、selection 并发变化和过期表单的结果，不改绑用户的目标包。
- [x] 复用依赖闭包重建及 Catalog 发布，处理候选失败、取消、清理和提交后的后台服务降级。
- [x] 返回已保存/已发布/未变化及观察状态，保持与多 Host 同步和精确恢复契约一致。
- [x] 将配置导入导出的数据处理接入同一用例，不创建新配置真源。

主要落点：`ouro/application/plugins.py`、`plugin_models.py`、按职责拆出的配置用例模块，
以及现有插件 runtime/store 边界。不向 Core 引入 Manifest、JSON Schema 或 UI 依赖。
验证目标：PC-08、PC-09、PC-10、PC-11、PC-12、PC-13。

退出条件：通过 application 即可完成 CLI、TUI 和未来桌面端所需的配置工作；保存和运行结果可区分；
失败与竞争不会造成部分配置提交、错误选版或持久调用偷换实现。

## 7. 阶段 D：CLI 与 TUI 通用交互

### CLI

- [x] 提供可脚本消费的完整配置描述及结构化预检结果。
- [x] 接入 JSON 候选与文件输入/导出，固定目标 digest 和编辑基线，复用完整候选模型；离线编辑不得在导入时自动刷新基线。
- [x] 支持只有凭据的配置，不要求用户虚构普通字段。
- [x] 预检入口不启动插件；应用入口按 application 的运行时要求装配。
- [x] 输出区分配置错误、冲突、激活失败和已发布降级；不输出秘密。

### TUI

- [x] 根据框架配置视图显示入口，不通过是否存在普通 Schema 判断全部配置能力。
- [x] 基于类型、枚举、说明、必填及约束生成通用标量控件，复用现有输入、选择、分组与主题组件。
- [x] 明确未设置、`null` 和空值的区别；普通对象可以分层，动态映射、列表/元组、联合、条件和递归模型
  均有完整 JSON 编辑路径，不以专用复杂控件作为交付前提。
- [x] JSON 输入提供基于 Schema 示例或有限结构骨架的占位提示；占位内容不自动写入草稿，也不作为校验结果。
- [x] 切换原生表单与 JSON 不改变数据类型或丢弃未知可接受字段；分支修改的有效性由框架预检判断。
- [x] 凭据使用独立绑定控件；不把掩码写回普通配置或引用。
- [x] 预检定位字段与分支问题；失败保留草稿，冲突要求刷新基线，取消不保存。
- [x] 保持显式提交，呈现实际生效范围和发布后诊断，不按插件 ID 选择专用界面。

主要落点：`ouro/cli/plugin_commands.py`、`parser.py`、`ouro/tui/plugin_workflows.py`、
`controller.py` 和按职责拆分的 Schema 表单代码。避免继续扩充通用配置 screen 文件的无关逻辑。
验证目标：PC-01、PC-05、PC-07、PC-13、PC-14。

退出条件：只修改 Schema 的通用插件 fixture，即可生成相应编辑入口；CLI、TUI 和直接 application
调用得到等价的规范化配置和错误。复杂模型可以完整编辑和应用，不被原生控件覆盖率阻断。

## 9. 验证安排

| 验证层次 | 核心场景 | 证据形式 |
|---|---|---|
| 通用模型 | 类型、动态键、列表/元组、组合、条件、依赖、递归、引用与默认值 | 独立有效/无效实例及规范化预期，不复制实现算法 |
| 配置安全 | 嵌套修改、秘密、非法引用、输入回显、仅凭据声明 | 单元与边界测试，使用合成秘密 |
| 管理用例 | 指定包、过期草稿、全量替换、无变化、无 runtime | 直接 application 测试及错误 DTO 断言 |
| 激活集成 | prepare/start 失败、依赖重建、发布后降级、取消与资源保留 | 真实生命周期夹具、状态及 generation 断言 |
| 并发与恢复 | 两个编辑者、构建期间状态变化、多 Host、旧执行契约 | 多实例/共享临时 home 测试和持久引用验证 |
| Host 等价 | CLI、TUI、直接 application 通过同一候选契约提交 | 使用真实应用服务的入口测试，检查规范化、结构化问题及完整字段保留 |
| 文件与业务边界 | 完整候选导入/导出、固定目标和基线、配置与领域数据职责 | 隔离文件测试与写入调用链审查，不通过插件业务行为代测配置管线 |
| 交互与呈现 | 复杂 JSON 编辑、选择菜单、错误和草稿恢复、宽窄布局 | Textual headless 交互与实际 App 渲染；真实终端兼容性单独记录 |

不依赖真实 API Key 验证基础管线，不为文档或低影响界面样式新增镜像实现的测试。
配置模块以合理大小的模型检查重复 I/O 和 validator 构建次数；没有性能问题证据时，不新增持久缓存或 watcher。

### 配置处理成本

对具有 21 个顶层字段的配置展示包连续执行 10 次查询和 10 次预检，共加载 20 次定义，每个用例一次；
预检在同一定义对象上完成规范化与校验。该次本机查询和预检的中位耗时分别为 15.86 ms 与 16.05 ms。
测试与全量回归并行，未清空系统缓存；这些数值仅用于检查当前调用链，不能推导通用性能指标。
没有引入跨请求缓存或后台配置 watcher。
