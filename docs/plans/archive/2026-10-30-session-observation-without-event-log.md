# 会话事实存储与增量观察改进计划

> 文档类型：完成归档
> 日期：2026-10-30
> 范围：会话数据存储、运行通知、通用观察管线及 TUI 消费边界
> 性能对照基线：`1705cec1664cac2680623f6c0cb0c101511b7b95`

## 目标与原则

会话保存用户输入、工作成果、执行事实和继续工作的依据。实时通知用于及时显示进展，不永久落盘。
跨进程观察、重新进入会话和通知遗漏后的补齐使用同一条事实读取管线。

事实决定当前状态，消息构成历史，当前草稿保存未完成内容。观察者只取得尚未消费的内容和变化后的状态，
不需要重建过去每一次通知。实时会话中的键入、切换、审批、排队和中止保持原有产品语义。
空间节省不能抵消明显、可复现的交互性能退化；小幅计时波动可接受。

## 数据与状态所有权

| 数据 | 保存内容与用途 |
|---|---|
| Session 与 Harness | 当前设置、控制状态、历史代次、消息位置、不可变检查点与撤销锚点 |
| Input 与 InputState | 已接受原文、附件意图、来源，以及排队、消费、取消状态 |
| Message | 有序的用户与模型内容、工具帧；引用输入、调用和结果已有正文 |
| Run | 执行状态、恢复检查点、取消、失败原因、当前请求和压缩阶段、继续运行决议 |
| Call、Start、Outcome 与 CallState | 已接受参数、实际执行开始、确定结果、授权与当前交互状态 |
| 请求小头与 Manifest | 请求身份、时序、结算和重试状态；最近普通请求的固定输入 |
| 当前 Draft | 未完成回答的文字与思考，可按请求偏移接续；正式响应提交后清除 |
| 摘要、资源与委派 | 已采用摘要及范围、附件与元信息、父子任务关系与交付事实 |
| 用量账本 | 真实供应商用量及其修订审计 |
| 事实位置 | 每会话一个当前修订号；可变事实各自的最新修改号 |

只有当前记录保留最新修改号，同一对象变化多次不会积累多份状态历史。消息使用已有顺序，草稿使用请求内偏移。
事实页的位置只存在于观察者内存中；数据库不保存通知、消费队列或变更清单。
InputState 与其他可变状态在原生数据库内共同提交，Files 的不可变 Input 正文保存在文件中。

## 提交与即时交付

事实及修订号在同一次原生事务中提交。跨文件发布使用有限 `commit.json` 决定，完成后清理；
只有消息正文、输入、Harness 或 Manifest 等文件参与发布时才需要该决定，决定本身不保存在线通知。
独立 Run、请求结算、工具结果及委派写入也推进会话修订号。Draft 追加只推进自身偏移，不重写 Session/Run 头。

执行者提交后直接发布已持有的内容，不为通知补读参数或结果，也不增加持久化写入。
通知队列有界，慢消费者不阻塞执行者。在线 sequence 只用于当前交付来源的排序，不能作为跨进程位置。
一个提交的最后一项通知携带完整确认位置，前面的通知不能提前确认整个提交。

## 统一观察管线

| 阶段 | 处理方式与成本边界 |
|---|---|
| 建立观察 | 先登记订阅，再在同一短读边界取得快照和位置；快照包括选定历史、当前状态与草稿 |
| 共享跟踪 | 同一 Supervisor 的每个被观察会话共享一个跟踪器，初始活动与起始位置一同读取 |
| 检查变化 | 读取当前修订号与请求小头；事实未变化时只续读当前草稿，不读取旧历史与工具正文 |
| 补齐事实 | 按修改号和身份分页取得变化后的记录，按消息顺序取得缺少的正文 |
| 补齐草稿 | 正文和状态追齐后，从当前请求的已确认偏移继续读取，保持展示顺序 |
| 确认消费 | 消费者应用一页后确认自己的位置；未确认时重复读取返回同一页 |
| 关闭观察 | 释放当前订阅；最后一个正文或状态观察者关闭后停止后台读取 |

后台事实页最多 128 条；运行或排队时最多每 100 ms 检查外部写入，空闲时每 500 ms。
本地连续输出即时交付，不等待轮询；本地发现前缀缺口时立即唤醒同一补齐管线。
所有磁盘读取在受管理线程执行，存储边界在脱敏、排版和异步等待前释放。

分页使用修订号、记录类别和身份共同定位，同一提交中的多条记录不会相互覆盖位置。
分页期间再次变化的对象由下一轮读取发现，不保留旧副本。本地交付与后台读取重叠时，以已消费位置为准，
过时的读取结果不能回退实时状态。快照中的草稿已经按请求偏移排列，内容投影直接消费一次，TUI 复用投影结果。

## 历史与交互边界

普通追加与继续运行保留已呈现历史。历史窗口通过消息索引定位，摘要按消息顺序范围关联已有索引，
不为每页构造随消息数量增长的查询参数，也不反复扫描历史正文。向前翻页不推进实时消费位置。

撤销改变历史代次，观察者才重新建立快照；共享跟踪器同时重置消息位置、事实页位置和草稿偏移。
旧 Run 可以保留执行事实，但迟到通知、结果和交互不能进入当前历史或恢复为当前活动。
工具等待、审批与问答直接从当前 Call 状态恢复；`wait_run` 读取目标 Run 的终态事实，不依赖完成通知必达。
观察不会重执行业务、接管 Run 或修改授权规则。

## 模块职责

| 层 | 职责 |
|---|---|
| Core | 事实模型、提交语义、身份与观察位置 |
| 存储后端 | 原生事务、事实索引、短读边界及有界后缀查询 |
| Application | 通用观察、共享读取、独立确认、内容与活动投影 |
| TUI | 消费 Application 结果，维护显示、滚动、焦点与导航 |

框架不判断 TUI、页面或前端 host 类型，TUI 不直接读取存储。
查询与转存接口表达消息、执行事实和当前状态；现行读写只接受当前 layout/schema。
设计不包含永久事件回放、历史格式分支、双写开关、额外消息中间件或第二套持久同步状态机。

## 性能验证

### 环境与方法

测量环境：Windows 11 10.0.26300，Python 3.14.6，SQLite 3.53.1，20 个逻辑处理器。
以下箭头均为本文对照基线 → 测量源码；除另行注明外为独立样本的中位数。

基准入口为 `dev.benchmarks.session_refactor_comparison`。相同机器、解释器、依赖和合成输入，
每组在独立源码目录和进程执行，交替前后顺序；操作系统缓存不清空。基准不与回归测试并行。
Files 和 SQLite 分别测量；不同场景的运行不混成一个总分。

| 场景 | 每个后端、规模和版本的样本数 | 输入与完成条件 |
|---|---:|---|
| long_run | 3 | 64 轮工具调用，每轮参数和结构化结果各 64 KiB，31 次摘要；核对最终结果及消息数量 |
| stream_io | 5 | 10,000 条历史消息，32,768 × 256 字节输出，共 8 MiB；两个观察端接收全部正文后收尾 |
| interaction | 20 | 1,000 / 10,000 条历史；接受输入、首字、排队、取消排队、进入运行会话和中止 |
| navigation | 10 × 每操作 30 次 | 1,000 / 10,000 条历史；首次加载、上一页、重进，固定 200 条窗口 |
| tui | 10 | 10,000 条历史、48,070 字符思考草稿；首次进入、600 条缓存恢复、键入和新增输出 |

持续输出使用相同公开 `observe_session` 接口。另一个观察者是同一基准进程内独立 Runtime 和存储实例，
不共享生产者的在线通知；真实双进程观察另有针对性正确性测试。这里的延迟不是网络延迟。
进程 I/O 计数包含操作系统缓存命中的读取和数据库日志，不等同于物理设备写入量。
TUI 使用 Textual 测试终端，不代表真实终端绘制、输入法、鼠标选择或缩放性能。

### 数据占用的边界

只写静态消息、没有运行事件的种子数据不会获得删除日志的收益。它需要承担事实定位索引：
1,000 条消息时 Files 增加约 20 KiB、SQLite 增加约 40 KiB；10,000 条时分别增加约 20 KiB、288 KiB。
因此“每个会话一定更小”不成立；实际执行长会话的约 6% 减少与静态种子数据的索引增加必须分别解释。
当前 Draft 仍用于恢复未完成内容，正式响应提交后清除；用量审计保留在独立账本，不属于被移除的通知日志。
