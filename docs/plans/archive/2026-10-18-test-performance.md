# 测试成本与时序稳定性优化

> 日期：2026-10-18
> 范围：测试执行、TUI 测试边界、纯视觉回归、审批检查点交接和 GitHub CI。

## 判断依据

每个测试都应能指出它拦截的真实错误，并在足以发现这个错误的最小边界运行。
覆盖率用于发现盲区，不单独决定测试的保留或删除。仅冻结外观、复述构造器约束或测试辅助函数自身的
用例可以删除；持久化、并发、权限、恢复、资源释放和协议差异仍有独立价值。

当前测试从 336 个模块、3,195 个测试函数、6,050 个展开用例，调整为 335 个模块、
3,160 个测试函数、5,952 个展开用例。删除 36 个函数、100 个展开用例，新增 1 个函数、
2 个提前审批回归用例；净减少 35 个函数、98 个展开用例。
依据包括 CI 失败日志、测试和生产调用链、删除候选的替代覆盖，以及本地全量 JUnit 成本分布。
没有把这次审查表述为对全部测试代码的逐行人工审查。

第一次四进程全量运行中，Application 和 TUI 的单用例累计时间分别约 1,502 秒和 1,144 秒，
合计占总单用例累计时间约 84%。Core 的 270 项测试累计约 0.5 秒，Provider 的 677 项累计约 19 秒。
这些是并发用例的累计时间，不能当成各目录独占的墙钟时间，也不支持按数量删减低成本契约测试。

## 时序问题

原 GitHub Windows 日志共收集 6,050 项，6,046 通过、3 失败、1 跳过，耗时 3,556.90 秒。
Provider 与提示词两项可通过临时延缓对应 I/O 重现相同断言失败；后台提交的 5 秒启动超时
在本机单项连续 10 次未复现，不能据此进一步断定其底层性能瓶颈。

- 添加 Provider：选择后模板目录读取仍在后台进行，测试在原 ACTIONS 页面断言新页面内容。
  等待 ADD PROVIDER 页面和挂载完成，并在检查保存结果前等待 Provider 实际进入目录。
- 个人提示词：固定 0.15 秒休眠不能保证配置提交完成。改为等待编辑页、管理页和返回页，
  让排序、激活、删除及版本冲突的断言发生在相应操作完成后。
- 后台提交：显式建立输入焦点并等待模拟 Provider 的启动事件；挂起保护只设上限，不增加固定等待。
  公共等待函数在失败时报告当前页面、焦点与 worker 状态。
- 会话菜单：连续 `Enter, Tab, Tab` 可在目录加载完成前丢失一次域切换，停在 TASK。
  逐次等待 USER、TASK、SUBAGENT 页面；重命名菜单必须在加载完成后取得新编辑界面的引用。
  配置保存只等待对应选择 worker，持续运行的模型流和订阅仍保持运行。
- 审批面板：预检请求早于可恢复检查点保存；只等面板出现就按回车，会在后台仍运行时提交，
  得到 `ValueError: run is not waiting for approval: running`。这是真实产品竞争，不能通过
  让测试等待后台结束来回避。`TuiController.resolve_approval` 先捕获目标 Session，再通过
  Supervisor 的 `wait_run(until=waiting_approval)` 等待持久化检查点，随后提交一次决定。
  此等待复用事件订阅，终态会结束等待，取消时释放订阅，没有固定休眠或重新提交。
  业务投影更新也早于面板绑定和布局刷新。只检查投影或焦点会读到零尺寸布局，
  或把按键发给仍绑定旧请求的面板。等待请求身份、可输入状态及刷新屏障；短终端验证实际拒绝工具，
  不再要求固定高度和装饰邻接位置。

临时故障注入将模板读取延缓 0.4 秒、提示词排序提交延缓 0.5 秒：旧测试重现两个原断言失败，
修改后的相同流程通过。这些延缓没有进入仓库。另以 Event 阻塞审批面板重新绑定，验证键盘
测试在面板绑定正确请求前不会返回。新增的 `test_preflight_interactions.py` 则阻塞真实检查点保存，
在 Run 仍为 `running` 时提交允许／拒绝，并等待真实订阅建立后放行，验证准确一次的持久化决定和
文件副作用。两个用例在生产修复前均重现相同 `ValueError`，修复后通过；不启动完整 Textual App。
受控实验中的内置 AskUser 在该检查点前尚未发布可交互请求，本次没有改动问答路径。

## 执行配置与测量

`pytest-xdist 3.8.0` 进入开发依赖及锁文件。CI 使用四个 worker 和 `worksteal` 调度，
并输出最慢的 20 项。Windows、Linux、macOS 都执行完整功能回归和安装检查，
lint、格式和类型检查在独立 job 执行一次；该 job 的平台和依赖按下述 CI 复核修正。
快速局部测试仍可使用串行命令。

同机、同 Python 和生产依赖下，对比相同的 14 个保留用例：单用例累计时间从 25.702 秒
降到 18.283 秒，减少 28.9%。两个提示词流程分别从 5.548 秒、4.325 秒降到 3.024 秒、2.370 秒。
这组对比没有把删除用例带来的时间差计入加速幅度。

验证环境为 Windows、Python 3.14.6 和冻结依赖，使用独立临时环境运行，避免更新被运行中
`ouro.exe` 占用的开发环境。其他操作系统及 GitHub runner 上的实际耗时需要由 CI 验证。
原 59 分钟来自远端 CI，不能与本机全量耗时直接换算加速倍数。

## CI 静态门禁复核

后续 GitHub 的 `Lint, formatting and types` job 在 Linux 上执行 mypy，报告 16 个文件中的
65 条错误。拆分静态检查时遗漏了完整源码类型检查的两个前提：主题实现需要实际安装 `arrayfunc`，
Windows 原生适配器需要 Windows 标准库的类型目标。

本机分别复现了缺少主题依赖的 8 条 `import-not-found`，以及完整主题环境使用 Linux 类型目标时的
57 条 Windows API `attr-defined`，合计与日志一致。原先的无主题 mypy 验证还受到了增量缓存影响：
以完整依赖生成缓存后，在无主题环境复用同一缓存仍会通过；禁用增量读取则报告这 8 条错误。
因此先前本机检查通过不能证明原 Linux 静态门禁配置有效。

静态 job 改为 Windows，显式同步及选择 `themes`，mypy 使用 `--no-incremental --platform win32`。
保留缺失导入和属性检查，完整检查全部源码；Windows、Linux、macOS 的功能和安装门禁仍独立执行。
贡献说明与测试策略同步记录相同的类型检查前提。

在新建的独立环境中逐条执行修正后的 job 命令：Ruff lint、835 个文件的格式检查，以及无增量缓存的
mypy 均通过，mypy 检查 461 个源码文件。本次只修改 CI 配置和文档，运行时源码及测试未变，
没有重复运行上述完整功能回归；GitHub runner 的实际执行仍待后续 CI 确认。
