# OURO 核心稳定与架构减负计划

> 文档类型：未完成工作
> 当前阶段：第一批与第二批已通过定向验收；条件性工作待决策。
> 当前契约以[架构总览](../architecture/README.md)和[领域规格](../specs/README.md)为准。

本计划以核心稳定为前提，减少没有实际收益的状态、协议、校验、计算和长期维护承诺。改良必须保持代码架构规范、依赖清晰、边界合理、计算高效，使 OURO 能够长期维护和迭代。

**清晰、干净、规范合理的改进是必要的。严格禁止过度设计、无依据的防御式编程、特例补丁，以及偏离问题本质的冗余复杂度。不得以减负为名破坏核心保障，也不得以稳定性或未来扩展为名不断叠加框架。**

本计划定义待办、依赖和退出条件，不改变现行行为。热更新、恢复范围、扩展面和存储后端的收敛属于待决策事项；在相关取舍落实前，不默认删除能力或放宽执行契约。

## 第一性原理与实施约束

OURO 的核心工作是接受用户意图、准备模型上下文、执行获得授权的工具、持久化可信事实，并在中断后恢复到可解释的状态。每项改动应从阻碍这一过程的真实问题出发，明确因果和责任边界。

实施时在对应任务或变更说明中简要回答：问题如何复现，必须保护什么事实，根因属于哪一层，最小改动是什么，以及哪些旧逻辑可以同时删除。复用现有评审和测试流程，不新增审批层级、通用评分体系或独立治理平台。

- **工程判断先于功能堆叠。** 主动判断需求是否值得实现、既有承诺是否值得保留，以及局部方案是否损害整体。完成标准包含设计质量；功能可运行、测试通过不足以证明改良成立。
- **设计品味体现为清楚的代码。** 名称准确，抽象少而恰当，正常路径按业务顺序可读，失败处理停留在真实边界，相邻改动能在自然的位置完成。统一的是概念和表达，不强求不同领域具有相同代码形状，也不用晦涩技巧追求行数更少。
- **先收敛职责，再收敛代码。** 同一事实只设一个权威来源；同一规则由所属边界定义。跨进程、持久化和副作用前的必要复核应复用规则，不能维护相互漂移的版本。
- **新增复杂度必须解决当前问题。** 没有实际消费者的接口、假设性兼容路径、通用 manager、注册层和配置开关不进入实现。允许以“不需要改动”结束缺少收益证据的候选项。
- **修复根因，不补单个输入。** 不按特定工具名、插件名、文件名或异常文本增加分支；先确定统一的数据语义、资源职责和失败范围，再修正其所有相关调用方。
- **禁止无依据的防御式代码。** 不对已建立且未失效的内部契约反复探测类型，不猜测任意回调形式，不以宽泛捕获、空值、成功结果或多层回退掩盖程序错误。外部输入解析、权限判定、持久化一致性和并发前置条件属于必要边界，不能一并删除。
- **不引入技术债务。** 每个交付单元完成旧分支、旧状态、重复规则及失效测试的清理，不遗留“后续再统一”的双轨实现。重构与公开行为变更分别说明，避免留下不可判断的中间状态。
- **计算优化先减少工作量。** 优先消除重复读取、转换、扫描和反射；缓存、后台任务、索引和数据布局变更由测量触发。不得用跳过校验、丢弃事实或遗弃资源换取表面性能。
- **不追求形式上的精简。** 不按文件长度拆文件，不按行数删功能，不为减少类型数量改成无约束字典，不为统一形式合并具有不同失败语义的边界。

## 必须保持的核心边界

下表只说明本计划的保护范围，精确规则继续由链接的规格维护。

| 边界 | 改良必须保持的性质 | 权威来源 |
|---|---|---|
| Session 与 Run | 会话身份隔离、唯一执行所有权、合法状态转换，取消后运行事实与资源状态一致 | [运行时](../specs/runtime.md) |
| 工具与交互 | deny、审批及有效权限不可绕过；审批修改参数后重新校验；副作用结果不确定时不能盲目重放 | [工具与交互](../specs/tools-and-interactions.md) |
| 持久化与撤销 | 提交、幂等、撤销检查点和恢复保持一致；损坏数据不得静默清空；索引及缓存可重建 | [会话持久化](../specs/session-persistence.md)、[会话撤销](../specs/session-undo.md) |
| 上下文与模型 | 工具消息帧、压缩边界和模型续接语义完整；出现可见输出后的请求不能任意自动重发 | [上下文](../specs/context-and-compaction.md)、[Provider 协议](../specs/provider-protocols.md) |
| 资源与观察 | 文件归属、内容完整性、事件顺序、快照与订阅衔接有效；任务、线程和进程有完整关闭路径 | [资源与监督](../specs/resources-and-supervision.md)、[会话观察](../specs/session-observation.md) |
| 凭据与扩展 | 凭据不泄露，受管理认证并发提交有效；插件权限不被描述为不存在的 OS 沙箱 | [认证架构](../architecture/authentication.md)、[插件](../specs/plugins.md)、[安全策略](../../SECURITY.md) |

依赖方向继续遵循 Host 调用 Application、Core 表达领域规则、基础设施实现外部边界、LocalApplication 负责本地装配和生命周期。Agent 与自动任务复用现有 Session 和 Run 链路，不增加另一套执行内核。Host 不接管事务，插件不成为持久状态的第二个所有者。

## 范围与执行顺序

每批工作围绕所属边界建立行为证据，验证正常执行和失败范围。本次执行相关模块与受影响调用链测试，
以及静态检查、编译、构建和文档检查，不运行全量测试。本地离线测试不代表真实外部服务、真实终端或跨平台验收。

| 批次 | 工作 | 前置条件 | 退出条件 |
|---|---|---|---|
| 第一批 | 统一参数规则、隔离配置读取、明确插件哈希职责 | 核实当前契约并建立对应行为证据 | 规则不再漂移，故障范围收敛，必要执行约束保持有效 |
| 第二批 | 收拢 Run 资源所有权、统一内部回调签名 | 核实实际资源生命周期与所有调用方 | 创建和释放由单一所有者管理，旧状态表和猜测分支清理完成 |
| 条件性工作 | 评估插件长期承诺、双后端和轮询成本 | 真实使用需求或可重复成本证据 | 完成明确取舍；获选方案完成相应规格与验收，未选方案说明保留理由 |

第一批各任务可独立交付。第二批不以完成所有第一批任务为前提，只要求本次涉及的契约已经明确。条件性工作不阻塞已确认问题，也不通过预留接口提前进入实现。

## 第一批工作

- [x] Read、Write、Edit、Glob、Grep、TodoList 和命令行工具使用参数模型生成 schema，并在处理器入口解析为类型化参数；共享整数语义，显式定义默认值、空值和未知字段，执行路径不再维护平行的类型规则。AskUser 使用现有交互模型，Agent 和外部工具保留所属边界的动态契约。现行规则见[工具规格](../specs/tools-and-interactions.md#内置工具参数)。
- [x] 领域配置只读取自身文件；组合操作显式读取所需配置，共享文件读取负责自身的布局检查。保留原子读写、修改锁和跨域引用检查。现行规则见[配置所有权](../specs/data-transfer.md#配置所有权)。
- [x] Builtin 契约包含 Manifest、包内 Python 代码和显式运行资源；普通说明文档不影响该身份。User package 保留完整包摘要，恢复要求精确匹配。现行输入范围及不匹配处理见[插件类别](../specs/plugins.md#52-plugin-class)和[持久 Run 恢复](../specs/plugins.md#15-durable-run)。
- [x] 完成相关模块及受影响调用链测试、静态检查、编译与构建，以及受影响文档的链接与示例验证。

验收覆盖 schema 与执行的整数语义、非法参数的副作用隔离、TodoList 读取和清空、权限与审批修改，
独立配置读取和原子修改、组合配置错误，以及实际 Plan 插件等待、重启和恢复。
文档变化应允许同契约恢复；代码或声明运行资源变化应阻止续跑并保留原 Run 事实。
第一批验收范围限定为相关模块和受影响调用链；全量回归、真实外部服务和跨平台运行不在当前验收范围内。
定向测试中的符号链接用例受本地环境能力限制；文件后端专用的回放用例在 SQLite 参数下不适用。

## 第二批工作

- [x] 用单一 Run 资源对象及索引承载同寿命的运行绑定与协调器；持久化 Run、执行锁、排队租约、观察者租约和应用级服务各自保持明确所有权。现行边界见[架构所有权](../architecture/README.md#状态与资源所有权)与[Run 进程内资源](../specs/runtime.md#run-进程内资源)。
- [x] 绑定入口承担失败与取消清理；恢复验证完整后登记资源；释放时先移除 Run 引用，再调用租约回调。相关验证覆盖初始化失败、等待、终态、队列转交、独立观察者、关闭错误及恢复重试。
- [x] 内部工具采用确定的执行和恢复签名；所有内部调用方遵循同一契约，公开 SDK 的可选上下文形式只在装配时适配。删除执行路径的签名探测，保留同步隔离、取消收尾和结果不确定语义。现行规则见[工具契约](../specs/tools-and-interactions.md#工具契约)。
- [x] 完成受影响的 Runtime、队列、Agent、插件、MCP、工具及 Host 调用链验证，以及静态检查、编译、构建与文档检查。

第二批按相关模块与受影响调用链进行定向验收；全量回归、真实外部服务及跨平台运行不在当前验收范围内。
性能证据限于删除执行与恢复中的签名探测、取消多表枚举清理和减少重复对象查找，不声明未经测量的端到端加速。

## 由证据触发的取舍

### 插件热更新与恢复范围

当前 Run 保存完整插件 generation 集合，[Catalog 匹配](../../ouro/plugins/catalog.py)及恢复要求集合与契约一致。该机制保护原环境下的精确续跑，同时增加多代租约、依赖锁、配置历史、恢复重建和服务交接成本。

- [ ] 核实运行期间切换插件、保留多个活动代次和重启后精确续跑的实际需求。若安全边界或重启后生效已满足需求，优先评估收敛更新时机，并据此删除不再需要的多代生命周期。
- [ ] 若仍需缩小恢复范围，先定义待恢复操作的完整依赖闭包，包含工具、策略、控制器、运行资源及恢复处理器。不能仅以“尚未调用过”判定插件无关，不能在省略安全策略后继续旧 Run。
- [ ] 区分继续原操作与结束旧执行后开始新 Run。后者必须明确处理未完成工具、审批、输入队列、continuation 和审计事实，不伪装成无缝恢复。
- [ ] 若证明现有范围确有必要，保留该机制并记录理由；不为形式上的轻量引入第二套恢复模式。

进入实现前明确用户可见行为、现有未完成 Run 的处理方式，以及[插件](../specs/plugins.md)、[运行时](../specs/runtime.md)和[会话撤销](../specs/session-undo.md)的同步改动。退出条件是选定方案完成切换、失败、权限撤销、取消和重启恢复验收，并清理被替代的状态及分支。

### 扩展面与存储后端

插件的 13 类贡献贯穿 [Manifest 与贡献适配](../../ouro/plugins/contribution_types.py)、SDK、worker 和应用消费者；[SessionRepository](../../ouro/sessions/base.py)则由文件及 SQLite 同时实现。长期成本取决于这些承诺是否服务当前使用需求，不能仅凭接口多或实现相似就删除。

- [ ] 逐项核对高级扩展面的实际消费者，保留 Goal、Plan、Agent 和现行可用插件依赖的语义；对只有假设需求的增量停止扩充。收敛某类能力时同步处理 SDK、worker、实现、测试和文档，不用万能事件总线替代明确契约。
- [ ] 核实文件和 SQLite 两种后端各自不可替代的使用场景，以事务恢复、查询、备份、可检查性和维护成本作取舍。选择单一权威后端只是候选，不预设结果。
- [ ] 双后端保留时复用领域决策并保留同一组存储契约测试；若决定收敛，先完成已有数据读取、校验、导出及迁出的明确路径，不混读、不隐式切换、不丢数据。

该项与[路线图](roadmap.md)当前保留双后端及 SQLite 产品化的方向共同评审。决策前不将候选写成现行架构，也不为平衡两种实现增加 ORM、通用工作单元或第二套领域恢复规则。退出条件是保留理由或收敛方案明确，获选实现没有遗留双轨入口和悬空契约。

### 轮询与重复计算

[Run 取消轮询](../../ouro/application/run_ownership.py)默认每 50ms 读取持久状态；[会话事件跟随](../../ouro/application/session_event_stream.py)同时承担本地事件与跨进程事件衔接。二者有真实职责，不能因存在轮询就认定冗余。

- [ ] 在实际并发量下测量读取次数、空闲唤醒、取消延迟、事件延迟和关闭时间，区分本地即时信号与跨进程兜底成本。
- [ ] 仅在重复成本可复现且具有实际影响时，评估减少无效读取或调整等待频率；明确可接受的响应延迟并验证远端取消、事件缺口和读取失败。
- [ ] 保持事件顺序、持久化追赶与完整收尾；优先使用已有通知机制，不引入守护进程、消息中间件或第二份状态缓存。

其他摘要、序列化、资源读取和索引候选统一按[性能规划](performance.md)进入，不另设性能治理流程。退出条件是工作量或真实场景成本得到可重复改善，相关延迟与稳定性约束成立；没有收益证据则保持现状。

## 验证与完成条件

验证直接保护发生变化的规则及失败边界，不以测试数量或覆盖率变化代替设计判断。结构重构使用现有行为与必要集成证据；公开行为调整先明确目标契约。禁止通过放宽业务断言、增加固定等待或吞掉异常使测试通过，也不增加只复述实现的测试。

本次验收按上述定向范围执行，尚未执行的全量回归不得记为通过；后续发布的工程门禁见[贡献指南](../../CONTRIBUTING.md)。纯文档变更按[文档规范](../development/documentation.md)验证链接、标题、锚点和示例，不重复执行无关功能测试。架构、规格与指南各自维护职责内内容，避免复制新的权威来源。

每个交付单元同时满足以下条件才结束：

- 真实问题在所属边界解决，回归覆盖受影响的正常与失败路径；涉及取消、并发、恢复和安全的变化有相应证据。
- 从完整调用链审视代码，职责、命名和执行顺序清楚，相邻变化有自然落点；不依赖补丁分支或大量解释才能理解设计。
- 依赖方向清楚，状态和资源有单一所有者；未增加隐藏耦合、通用框架、无用配置或临时兼容路径。
- 被替代代码、重复状态、失效测试和过期文档在同一交付中清理，不留下后续必须偿还的结构债务。
- 计算收益与测量范围相符，核心事实和必要校验未被省略；现有数据、凭据和用户操作不会被静默改变。
- 实际通过、失败、跳过及未验证范围如实记录，不能将局部验证扩展为完整支持声明。

本计划结束时，第一批和第二批任务完成验收；条件性候选各自有明确的保留、取消或继续实施结论，获选改动完成对应验收。仍需外部环境或产品前提的工作保留为明确待办，不能标记完成。已完成记录按文档规范归档，现行设计与契约回到架构及规格维护，删除不再需要的规划重复内容。
