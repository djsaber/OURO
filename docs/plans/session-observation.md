# 会话执行、观察与 TUI 协作改进计划

> 文档类型：未来规划
> 状态：实施中；完成范围与验证记录见文末
> 核对日期：2026-10-19
> 实施基线：`9351bcc347d46449ece2c593041e7562271f83a7`

本计划围绕执行归属、会话观察和 TUI 展示的边界，解决 Agent 状态通知积压，并完善多会话、
会话切换和多终端观察。任务按可独立验证的阶段推进；本文描述目标与待办，不声明目标已实现。

现行契约以[会话观察规格](../specs/session-observation.md)、[运行时规格](../specs/runtime.md)、
[子智能体规格](../specs/subagents.md)、[TUI 规格](../specs/tui.md)和[性能规格](../specs/performance.md)为准。
实现阶段发现契约需要调整时，随对应实现和回归同步更新权威规格，不在本文维护第二份现行契约。
长期性能目标和窗口化条件沿用[性能规划](performance.md)；未来 Host 复用本计划形成的 Application 边界。

## 目标与完成范围

| 目标 | 必须得到的保证 | 主要验收阶段 |
|---|---|---|
| 通用框架与 Host 解耦 | Core/Runtime 不感知界面；Application 提供执行与观察语义；TUI 不控制存储事务或复制领域恢复规则 | P1、P3、P4、P5 |
| 一个 TUI 中多个后台会话稳定运行 | 输入与执行归属明确；切换视图不取消运行；完成、失败、取消及草稿按 Session 隔离 | P3、P5、P7 |
| 随时切换且内容完整 | 正式消息、未提交流式内容和后续增量可靠衔接；过期切换不得提交；工作量避免重复历史扫描和排版 | P4、P5、P6、P7 |
| 多个 TUI 观察同一运行会话 | 单一执行归属，共享持久事实，各观察者独立消费；慢观察者不阻塞执行者或其他观察者 | P2、P3、P4、P7 |

会话隔离包括状态、控制、生命周期与故障隔离；共享 CPU、磁盘及数据库仍存在资源竞争。
Supervisor 的并发限制是其管理范围内的执行限制，不将它扩展为跨进程全局配额。
关闭共享 Application 上的单个 Host 只释放该 Host 的资源；整个应用进程退出仍遵循明确的 shutdown policy。
本计划不增加“执行者进程退出后运行仍继续”的承诺。

## 验证边界

功能与成本验证使用临时 home、合成 Provider 和受控 Event/进程握手，不访问个人会话或真实账号。
Files 与 SQLite 分别验证；同进程双 TUI、真实进程 headless 和实际终端是不同证据层次。
Windows 与 Ubuntu/WSL 的定向进程回归已通过；实际终端的 paint、操作系统键盘链路仍待验证，自动测试不替代终端验收。

## 目标边界与设计决定

### 执行、事实和展示分别归属

| 层 | 本计划中的职责 |
|---|---|
| Core / Runtime | 通用运行管线、领域状态转换、模型与工具执行、规范事件 |
| Application / Supervisor | 输入受理、长期任务归属与调度、会话观察、通用恢复投影、显式执行恢复 |
| 存储适配器 | 原子提交、一致性读取、按游标查询、执行锁及各后端实现 |
| TUI | 当前选择与草稿、布局、Rich/Markdown 排版、滚动、刷新节奏和交互映射 |

普通交互式提交进入 Application 管理的执行路径，返回受理结果；长期执行由 Supervisor 持有。
`Runtime.run` 可以保留为底层可等待接口，Host 关闭不再通过等待链隐式取消已受理任务。
输入受理失败、受理完成和实际执行完成是不同边界；复用已有 input identity、持久输入与排队语义。

通用观察入口只读取并重建显示所需事实。显示恢复不隐含接管、继续执行、提交输入或 abort。
控制会话选择如需触发执行恢复，由 Host 策略显式调用 Application 命令，并尊重现有执行归属。

### 正文事件与状态通知采用不同语义

正文从一致快照开始，按观察者自己的已应用游标补读和消费后续事件。实时队列是有界加速缓存，
不能决定事实是否丢失；追赶跨度不受队列容量限制。已读取、已入队和已应用游标必须区分，恢复使用已应用位置。
应用内容投影后才推进该位置，不能因把事件交给 renderer 或从队列取出就提前确认。

AgentTree 和活动摘要合并变化通知，消费者按需取得最新状态。相关变化在进入订阅队列前筛选，
状态归约继续复用现有逻辑；不为文本片段逐次查询完整树。沿用 canonical projector，暂不新增长期树缓存或第二套状态机。
快照读取期间发生的变化保留为下一次待刷新；一个订阅最多一个快照查询在途，读取在受管理线程边界执行。

同一 Supervisor 内继续按 Session 共享跟随器。正文订阅和状态订阅各自保留消费状态，A 的读取或关闭不消耗 B 的通知。
跟随器在两类订阅全部关闭后停止；观察订阅关闭与执行停止相互独立。不同进程各自读取共享存储是必要成本。
Agent 树跨 Session 的摘要允许最终一致，不引入跨整个子树的全局事务或伪造全局事件序号。
每 Session 的事件游标、树投影标识和视图切换版本分别服务自己的边界。

读取失败保留原 diagnostic 的原因与级别，关闭失败观察并允许明确重试；正常落后通过持久补读恢复。
观察者自身渲染失败不影响其他观察者；同一个持久数据源的故障可以影响所有依赖它的观察者，不能承诺掩盖共同故障。

### 读取与视图安装分离

正式消息、未提交内容与 high-water 必须来自可证明的一致边界。优先扩展已有窄快照查询；
SQLite 使用读事务，文件后端使用必要的短 Session 锁。读取结束后释放边界，再计算和排版。
轻量活动查询不加载完整消息或 Run 历史；无关附加信息不得扩大正文快照的事务范围。

TUI 的一次视图切换拥有目标 Session、有效版本、订阅、内容投影与排版结果。
后台准备的结果只有在目标仍然有效时才提交；过期结果释放自身资源，不补做尚未开始的完整历史排版。
已经开始的不可取消阻塞调用按既有资源规则收尾，其结果失效后丢弃，不假定取消协程可以停止线程。
事件应用与界面绘制解耦，不能让长历史排版阻塞正文追赶。

### 范围约束

- 复用现有 Supervisor，不增加第二调度器、按根会话公平调度层或跨进程全局配额。
- 不引入常驻服务、跨进程消息总线、ORM/UoW、通用响应式框架或持久化 UI 投影数据库。
- 不以扩大队列、增加 sleep、反复全量重载或无限重试代替语义修正。
- 不弱化 canonical 提交、fsync、权限、输入归属或 history_epoch 规则；不让观察者直接重放工具执行。
- 不将普通用户输入改装为不同用途的 scaffold Host 输入；完整保留附件、技能和队列行为。
- 数据格式迁移不是预设任务。仅当具体实现证明必要时，再明确兼容范围和独立验证。
- 长历史窗口和更深缓存由 P6 测量决定，复用既有缓存，不预先增加全会话常驻内存状态。

## 推进顺序与进度

建议按下表顺序推进；依赖表示必须已经具备的行为，不要求增加相应模块或抽象层。
每阶段只改对应边界，并随实现更新相应规格。阶段结束填写证据和剩余问题后再勾选完成。

| 阶段 | 内容 | 依赖 | 初始状态 |
|---|---|---|---|
| P0 | 契约差异、复现与资源成本基线 | 无 | 已完成 |
| P1 | 一致性只读边界 | P0 | 已完成 |
| P2 | Agent 状态合并与多观察者生命周期 | P1 | 已完成 |
| P3 | 普通输入受理与执行归属统一 | P0 | 已完成 |
| P4 | 通用会话观察、恢复投影与分页追赶 | P1、P2 | 已完成 |

### P1：一致性只读边界

定位：[SessionService](../../ouro/application/sessions.py)、[Supervisor](../../ouro/application/supervisor.py)、
[存储端口](../../ouro/sessions/base.py)、[文件后端](../../ouro/sessions/local_files.py)、[SQLite 后端](../../ouro/sessions/sqlite.py)。

- [x] 复用 `load_session_observation` 和后端读取能力，将确需组合的轻量事实通过窄查询在同一只读边界取得。
- [x] 审查观察、activity/status、按 history_epoch 解析消息等纯读取中的 `session_mutation`；逐项保留其一致性保证并替换错误的写事务语义。
- [x] 将 TUI 所需组合读取收回 Application，去掉 Host 对 `runtime.store` 和事务生命周期的依赖。
- [x] 避免为状态读取调用完整历史快照；将投影计算、格式化和 UI 操作移出锁定范围。
- [x] 保留真实修改所需的写事务和执行锁；不以取消一致性边界换取并发。
- [x] 同步修正会话观察规格中用 mutation 描述只读一致性的条款。

验收：两后端均验证快照与 high-water 一致、历史改写竞争和读取失败资源释放；SQLite 验证读取 A 时另一连接可写 B。
文件后端允许必要的同 Session 短锁，不要求提供 SQLite 的 MVCC 能力。读事务不延伸到排版或订阅生命周期。

退出条件：Host 不掌握存储事务；轻量观察无全历史读取；真实写入原子性和既有恢复测试保持有效。

### P2：状态通知合并与独立观察者

定位：[AgentTree](../../ouro/application/agent_tree.py)、[AgentService](../../ouro/application/agents.py)、
[Supervisor](../../ouro/application/supervisor.py)、[事件跟随器](../../ouro/application/session_event_stream.py)。

- [x] 在现有共享事件来源上提供轻量状态观察，相关活动及关系变化在进入状态订阅缓冲前识别；不另起一套磁盘轮询。
- [x] 每个订阅独立维护待刷新状态；重复变化合并，不排队保存历史树快照。
- [x] 先注册变化观察再取得初始状态；读取期间的变化保留为下一次更新，动态 child 加入/退出也遵循该边界。
- [x] 消费者请求更新时复用 canonical projector；查询在线程执行，同一订阅最多一个查询在途。
- [x] 将正文与状态订阅共同纳入共享跟随器的存活判断；关闭唤醒等待者并释放本订阅资源。
- [x] 保留真实读取/投影失败原因；删除将所有上游 diagnostic 转换为 overflow 的逻辑。
- [x] 审计并调整不再适用的树队列参数、FIFO/lag 规格和测试；保留正文有界缓存与故障隔离契约。

验收：65/256 条无关文本突发不使状态订阅溢出或逐条重读树；慢状态观察者最终取得最新树。
两个观察者各自收到更新，A 读取或关闭不影响 B；关闭正文订阅后状态观察仍工作，全部关闭后停止跟随。
覆盖读取中发生变化、child 新增/终止、初始读取取消和源读取失败；通过查询次数与资源回收验证，不使用机器时间阈值。

退出条件：状态消费速度不会形成旧快照 FIFO；诊断准确；单一共享事件来源保持不变。

### P3：统一普通输入与长期执行归属

定位：[TuiController.submit](../../ouro/tui/controller.py)、[Supervisor](../../ouro/application/supervisor.py)、
[RuntimeService](../../ouro/application/runtime.py)、[执行归属](../../ouro/application/run_ownership.py)、[LocalApplication](../../ouro/local_application.py)。

- [x] 扩展现有输入受理与 Supervisor 入口，完整传递模型、推理、workspace、权限/交互模式、附件、资源、技能、input ID 和 queue mode。
- [x] 保持用户输入身份和既有持久输入协议；运行中追加输入不因等待新执行槽而延迟受理，也不触发第二个执行者。
- [x] 明确受理前取消、受理完成后 Host detach、受理结果暂未显示时重试的行为；复用 input ID 去重，回执不等同于运行完成。
- [x] 将普通 TUI 提交纳入 Supervisor 持有的任务，Host 只等待自身请求结果或观察会话，取消 Host 等待不传播为已受理任务取消。
- [x] 保留同 Session 跨进程执行锁、现有 FIFO/并发限制、waiting 边界释放执行槽，以及显式 abort 的持久控制链路。
- [x] 检查审批预检到持久 waiting 边界的衔接；继续运行、审批和 AskUser 不回退为 Host 直接持有执行。
- [x] 区分单 Host detach 与 Application/进程 shutdown，完整回收任务与回执，不永久保留已结束 job。

验收：真实 TUI 普通提交参与 Supervisor 并发限制；A/B 后台持续运行，离开视图不改变执行。
`close_application=False` 时关闭 TUI 不取消运行，显式 abort 能终止，Application shutdown 按既定策略完成。
覆盖受理竞争、重复 input ID、队列追加、附件/技能、等待子任务和失败后的任务清理；多终端提交继续遵循既有串行化与输入策略。

退出条件：长期执行所有权与界面 worker 分离；不新增调度器，不损失普通输入能力。
此阶段可以保留现有正文显示入口，P5 负责完成观察迁移和旧路径删除。

### P4：通用会话观察与有界追赶

定位：[SessionService](../../ouro/application/sessions.py)、[Supervisor](../../ouro/application/supervisor.py)、
[观察 DTO](../../ouro/application/supervisor_models.py)、[当前恢复逻辑](../../ouro/tui/app.py)。

- [x] 在现有 Application 服务中形成通用观察入口，返回一致快照、history_epoch、高水位及独立后续观察；名称和 DTO 以调用方审计结果确定。
- [x] 正文、活动 Run 和待处理输入共用同一快照边界；只读输入投影不清理持久队列，Host 不二次读取队列来拼接旧快照。
- [x] 将正式消息覆盖、未提交 text/reasoning、工具与交互恢复等通用语义收回 Application，复用已有 reducer；Rich、布局和滚动不进入框架。
- [x] 明确模型流结束与正式消息提交之间的窗口；不能仅凭 `model_message_completed` 就删除未被正式消息覆盖的内容。
- [x] 实现按观察者已应用游标分页追赶，回放页大小与实时缓冲容量分开；较大积压不再只返回 lag 后交给 TUI 全量重载。
- [x] 在统一观察内部处理 snapshot/replay/live 重叠、持续新写入和再次落后，保持有界临时内存；复用已有有序跟随器。
- [x] 保持历史代次校验；代次变化重新建立快照，导入历史允许有序但不连续的 sequence，不凭序号差臆造事件。
- [x] 将显示恢复与显式执行恢复拆开；observe/close 不创建 Run、不取得执行归属、不触发工具重放。
- [x] 保留 typed/redacted Host DTO；源读取失败停止失败观察并暴露原原因，不启动无止境重载。

验收：快照覆盖 100 后加载期间新增 101 至 120，最终按序完整应用且无重复；再覆盖积压大于多个缓存容量的场景。
验证提交消息前后边界、history_epoch 改写、连续多个 Run、取消初始化、慢消费者和源故障。
观察者读取进度不得当作内容已应用进度；慢消费者恢复处理能力后可追赶，执行者和其他观察者继续前进。

退出条件：不导入 TUI 的 Application 测试可以重建同样的会话语义；初始读取和后续交接无需 Host 自行拼接事务及恢复流程。

## 组合验收与测试选择

核心组合：TUI A 同时运行多个 Session，快速切换其中的运行中会话；另一进程的 TUI B 观察同一 Session。
暂时阻塞 B 的消费或渲染，同时继续 A 的输入和其他 Session 执行；恢复 B 后，两端与 canonical 记录一致。
随后依次关闭一个观察者、显式中止一个 Run、结束剩余运行，验证不同生命周期的结果。

| 场景 | 关键断言 | 验证边界 |
|---|---|---|
| 普通输入、并发超出调度容量、运行中追加 | 输入归属与去重正确，执行并发受控，追加输入不创建第二执行者 | Application + 真实 TUI 提交 |
| 共享 Application 的 Host 关闭 | 仅观察资源释放，运行继续；显式 abort 与整体 shutdown 按契约生效 | Host 集成 |
| 单源、多状态观察者、突发及慢消费 | 各自收敛、互不抢通知、不逐文本重读树、最后一个观察关闭才释放源 | Application 订阅 |
| 快照读取、消息提交、实时增量交错 | 正式消息与未提交内容衔接正确，已应用游标不越过缺失内容 | 两后端持久化集成 |
| 积压大于实时缓存、持续写入与断开重进 | 分页补齐、无重复、内存有界，其他观察者与执行者继续前进 | Application + 真实进程 |
| history_epoch 改写及旧结果晚到 | 不混合历史代次，不由旧任务覆盖新状态 | Application / TUI |
| A→B→C 快速切换和旧加载取消 | 仅有效结果可提交，草稿/焦点/滚动归属正确，旧目标不继续启动剩余排版 | TUI 集成 |
| 读取失败、投影失败、初始化取消 | 原因准确、失败范围明确、资源释放，无自动无限重载 | 最小受影响边界 |
| 两终端观察连续多个 Run 和工具交互 | 每次运行只有一个执行归属，文本与终态摘要完整，操作身份准确 | 真实进程 + 实际终端 |
| 长历史与后台不可见会话 | 查询/排版成本符合阶段目标，无隐形正文渲染或资源持续增长 | 计数回归 + 独立基准 |

### 性能证据

命令和探针口径见[基准说明](../../dev/benchmarks/README.md)。原始 JSONL 在本地忽略目录
`.ouro-dev/session-observation/`。测量为 120×40 headless 窗口，不包含真实终端 paint 或操作系统键盘传输。

- `p6-chat-window.jsonl`：两后端各 120/1,000/10,000 条消息，重复三次。合成模型容量为 2,000,000 tokens，
  明确验证 chat purpose 和未提交正文，首帧被动等待。10,000 条消息的中位数如下。

| 后端 | 冷进入就绪 / 首帧 ms | 缓存重进就绪 / 首帧 ms | 正文流重进就绪 / 首帧 ms | 正文流重进读取传输量 |
|---|---|---|---|---|
| Files | 370 / 201 | 70 / 53 | 139 / 110 | 约 0.43 MB |
| SQLite | 324 / 183 | 88 / 68 | 148 / 118 | 约 1.10 MB |

冷进入排版 200 项，缓存重进不重排；正文窗口读取量为 201/201/202 条。读取传输量包含缓存 IO，
不是物理磁盘流量，也不包括完整 context 内嵌消息的条数。窗口和 context header 查询分别约束正文与状态成本。

- `p6-gc-diagnostic.jsonl`、`p6-instant-burst.jsonl`：普通流 loop lag p99 约 15ms，gen2 GC 停顿 84–113ms；
  每轮 400 片零间隔突发的 p99 约 32ms，gen2 GC 停顿 103–123ms。按键 p95 约 15–19ms，
  SQLite 动画最大间隔约 243ms。严格响应性目标未达到。
- `p6-collaboration-root-read.jsonl`：每后端 20 轮、60 次切换，三个运行中会话、两个观察者。每端一个正文订阅
  和一个跟随器，历史缓存数量 2/0，任务数在 219–224 间波动；detach 后订阅与跟随器为零。
  双方均不可见的 Run 正文排版数为零。持续新增正文时工作集增长，不能仅据 RSS 判断泄漏。
  切换中位数 Files 262ms、SQLite 504ms，最大值约 462/1,426ms；树查询 p95 为 30/70ms。
- `p6-collaboration-profile.jsonl`：持续按键下 Files/SQLite 按键 p95 约 8.3/9.4ms，loop lag p99 约 17.2/17.9ms、
  最大值 185/294ms，gen2 GC 最大值 171/282ms。Store 调用均未落在 TUI 线程。长停顿跨越读取与视图提交，
  仍需定位剩余分配和回收成本，不能由增加正文缓存推导出解决方案。
- Textual 8.2.8 的整行 `Strip.divide` 自引用已独立复现：1,000 次划分产生 18,000 个待循环 GC 对象。
  [上游 #6738](https://github.com/Textualize/textual/issues/6738)于 2026-10-19 仍开放。
  隔离进程去除该引用环后，普通流和突发仍有约 82–103ms 的 gen2 停顿；该缺陷不能解释全部尾延迟。
  数据为 `p6-strip-cycle-normal.jsonl`、`p6-strip-cycle-burst.jsonl`。生产代码未修改依赖或 GC 策略。
- 堆诊断 `p6-heap-census.jsonl` 中，第 1/4/8 轮存活 Widget 均为 156 个，样式缓存条目为 124/142/166，
  Strip 为 4,303/5,668/8,589 个。Textual 的实例方法缓存滞留已卸载组件的样式缓存，
  [上游 #6665](https://github.com/Textualize/textual/issues/6665)于 2026-10-19 仍开放。
  隔离进程同时去除样式缓存的实例引用和 Strip 引用环，Strip 为 4,229/4,680/5,025 个，循环 GC 仍需 74–93ms。
  该诊断主动 GC 并遍历堆，只用于定位对象归属，不作为响应性数据；持续新增正文的占用也不能全部归为泄漏。
- `p6-stable-tail-after.jsonl`：稳定 assistant 活动组件下，Files 20 轮、60 次切换的中位数 356ms、最大值 622ms，
  loop lag p99 18.1ms、最大值 129ms，按键 p95 13.4ms，GC 最大值 122ms。任务数 221–227，detach 后正文订阅
  与跟随器为零。稳定组件消除了每轮和每次切换的 assistant 挂载/卸载成本，严格尾延迟目标仍未达到。
  独立堆诊断 `p6-stable-tail-heap.jsonl` 的第 1/4/8 轮，样式缓存均为 118 项、Widget 均为 156 个，
  Strip 为 4,187/4,635/5,049 个；循环 GC 仍需 85–99ms。生产代码只调整 TUI 组件所有权，未修改 Textual 缓存。
- `p6-gc-floor.jsonl`：Windows Python 3.14.6 隔离进程中，仅导入 Textual 的 7 次完整 GC 为 4.6–8.4ms；
  导入 `ouro.tui.app` 后、尚未创建组件或运行会话时，为 45.1–50.6ms，跟踪对象数约 16.7 万，每次回收对象均为零。
  导入图未加载 OpenAI、Anthropic 或 MCP SDK。该静态堆扫描说明 GC 成本不限于会话切换和待回收组件，
  不能据此将全部停顿归因于渲染依赖，也不能用延迟或禁用回收声明响应性达标。该数据为显式 GC 诊断，不代表正常运行的触发频率。
- `p6-history-snapshot.jsonl`：每后端一个 10,000 条消息样本，初始读取 201 条、显示近期 200 条；
  整个初始窗口在线程中分块准备后一次发布，Files/SQLite 首个正文帧为 255/220ms，缓存重进为 42/43ms，
  流式重进为 92/74ms。缓存重进不重新排版已有条目。该单次 headless 测量验证窗口成本，不替代终端或尾延迟验收。
