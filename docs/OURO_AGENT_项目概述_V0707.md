# OURO Agent 项目概述

## 项目定位

OURO Agent 是面向个人用户的通用智能体运行环境。它不是单一聊天应用，而是为模型提供上下文、工具、会话、权限、恢复、扩展和界面的个人自动化平台。

OURO 的核心目标是让个人用户能够安全、可控、可持续地把 AI 用在本地工作流中，包括文件操作、命令执行、代码编辑、资料整理、任务规划和自动化脚本。当前阶段优先服务技术型个人用户，后续再通过插件扩展浏览器自动化、生活助手、第三方服务连接等更广泛场景。

OURO 强调本地优先、用户可控和能力可扩展。它不追求企业级多租户、高可用、审计合规、复杂权限隔离或云端服务化；这些能力可以在未来通过部署形态或插件增强，但不进入当前项目概述的核心目标。

## 设计原则

1. 核心极简：核心只保留智能体运行所必需的通用能力，避免把所有高级工作流都内置进主程序。
2. 能力可组合：复杂能力优先通过工具、扩展点、插件和官方能力包组合完成，而不是堆叠大量配置开关。
3. 用户可控：涉及文件写入、命令执行、网络访问、外部服务调用等高影响操作时，默认提供清晰的确认与授权路径。
4. 本地优先：会话、配置、插件、技能和运行记录优先存放在用户本地，用户应能理解和迁移自己的数据。
5. 可恢复：中断、崩溃、挂起、模型错误或工具错误不应破坏会话，用户应能从可理解的状态继续。
6. 可观察：运行过程必须对用户和开发者可见，能够展示模型响应、工具调用、审批、错误和最终结果。
7. 能力自生长：OURO 可以帮助用户编写新工具、脚本或插件，但新能力进入可执行状态前必须经过明确的用户确认或信任配置。
8. 不过度设计：当前无法验证价值的复杂能力不进入核心；先保证个人单机体验稳定，再逐步扩展。

## 范围边界

### 当前核心范围

- 本地会话与多会话管理。
- 模型对话、流式输出、工具调用和结果回灌。
- 文件读取、文件写入、文本编辑、命令执行、向用户提问等基础工具。
- 工具权限确认、用户中止、人工审批和挂起恢复。
- 基础上下文组装、内置 LLM 摘要压缩、运行记录和 provider usage 记录。
- 插件机制、技能加载、模型供应商配置、本地配置文件和凭据配置入口。
- MCP 官方集成与服务器生命周期管理。
- Interactive 与 Print / JSON 的首期运行模式，并为 SDK、RPC、Desktop 预留共享核心。

### 适合作为官方插件或后续增强的能力

- 浏览器自动化、网页操作、生活助手类集成。
- 可替换摘要策略、高级长期记忆、知识库检索。
- 会话全文检索、高级资源管理和数据清理策略。
- 子智能体、探索模式、复杂任务编排。
- Todo/计划管理、自动提交、沙箱执行、远程执行。
- 更多持久化后端、团队协作、云端同步。

### 暂不作为核心目标

- 企业级权限隔离、审计合规、多租户、细粒度组织管理。
- 高可用服务端架构、分布式调度、大规模并发任务平台。
- 内置通用长期记忆系统。
- 内置复杂浏览器或桌面自动化系统。
- 内置完整插件市场或商业分发体系。

## 技术选型

| 层 | 暂定技术 | 说明 |
|---|---|---|
| 语言 | Python 3.12+ | 核心运行层、工具层与宿主应用 |
| 基础运行框架 | OURO 自研 RuntimeAdapter / Provider / Tool / Event / Persistence 基础设施 | 自主维护智能体运行闭环，不绑定外部 Agent 框架 |
| 持久化 | 本地可读文件优先，SQLite 可选 | JSONL 主要追加保存消息与事件；JSON/YAML 保存会话状态、系统配置等；SQLite 作为同等职责的可选后端 |
| TUI | Textual + Rich | 终端交互、流式展示、工具调用可视化 |
| 桌面应用 | PyWebview + FastAPI | 本地 Web UI 与后端 API，后续可按实际体验调整 |
| 插件/技能 | Python 包、本地目录、配置声明 | 插件提供工具、命令、上下文、UI 扩展等能力 |

OURO 决定自主构建基础运行设施。核心运行层需要直接维护自己的运行闭环、事件输出、工具执行、持久化恢复、人工介入、扩展钩子和 provider 适配边界。项目文档、代码和插件接口都应以 OURO 自有概念为准，不绑定外部 Agent 框架。

## 总体架构

OURO 可以分为四层：

| 层 | 职责 |
|---|---|
| 核心运行层 | 管理会话、运行、上下文、模型调用、工具执行、事件流、中止与恢复 |
| 官方能力层 | 提供基础工具、模型供应商、权限确认、内置摘要压缩、技能加载等默认能力 |
| 扩展生态层 | 通过插件、MCP、技能、长期记忆和自定义工具扩展系统 |
| 宿主界面层 | TUI、Desktop、Print/JSON、RPC、SDK 等不同入口共享同一核心 |

核心运行层不依赖具体 UI。不同宿主只负责输入、渲染、配置入口和用户交互，不应复制智能体运行逻辑。

运行层采用 application/core 双层 Agent Loop。外层由 application `RuntimeService` 负责会话生命周期、active run 防重入、run lock、用户中止、审批/AskUser 恢复和 queued follow-up input，`RunLifecycle` 集中维护 durable message、usage 与 run/session 生命周期快照，流式 partial output 只进入 append-only event journal 并由其承担崩溃恢复；`ToolCallCoordinator` 维护工具调用在 hooks、executor、事件和消息之间的协调。内层由 core `InnerAgentLoop` 负责单个 active run 内的模型请求、流式事件、工具调用、工具结果回灌和多轮 continuation，不拥有额外 checkpoint 持久化端口。这样后续加入用户中途插话、子智能体回调或上下文压缩后重启时，可以扩展外层编排而不污染模型交互循环。

queued follow-up input 由 application 层的持久化队列组件维护，而不是散落在运行服务的私有 metadata 拼装里。队列项只有在对应 user message 持久化后才确认消费，并使用 queue_id 去重崩溃窗口中的已写消息。这样用户中途插话、后续 steering/follow-up 模式和未来子智能体回调可以共享同一类队列边界，同时不会因先出队后崩溃而丢失输入。

运行事件由 application 层的事件记录组件维护，统一负责事件持久化、`on_event` hook 分发以及 hook failure 事件化。这样可观测性不会被埋在运行服务私有方法里，后续替换事件后端或增加 tracing/metrics 时也有稳定入口。

Provider 的协议、模型元数据、流事件和 usage 契约属于 core；具体供应商、HTTP/SSE 传输和请求响应编解码属于外层实现。core 只依赖自身契约，不反向依赖 provider 包、配置层或提示词包。

会话可选模型目录、`provider/endpoint` 持久路由和 request-local adapter 选择属于 application 用例，不属于具体供应商适配。`ouro.providers` 只包含厂商实现、transport/codec 和 adapter factory；application 通过组合根注入的 factory 构建 adapter，不反向依赖 provider 实现。

当前代码级模块地图和依赖约束以 `docs/OURO_AGENT_开发架构.md` 为准。

## 核心概念

### 会话、运行与回合

- 会话：用户与 OURO 的持续对话空间，包含消息历史、配置、状态、分支和运行记录。
- 运行：一次从用户输入、恢复或排队消息开始，到当前任务结束、挂起、出错或被中止为止的执行单元。
- 回合：一次模型调用及其后续工具执行。一个运行可以包含多个回合，直到模型不再调用工具，或运行被终止。

会话用于长期保存；运行用于区分一次任务的边界；回合用于理解模型和工具之间的循环。

### 消息、事件与状态

- 消息是会话的用户可见历史，包括用户消息、智能体消息、工具结果和系统注入的合成消息。
- 事件是运行过程的实时记录，用于 UI 渲染、调试、追踪和回放。
- 状态是会话与运行的当前配置和中间数据，例如当前模型、工具启用状态、待审批请求、上下文窗口策略等。

消息与状态是恢复会话的主要依据；事件流是运行过程的观察窗口。OURO 默认长期保存完整事件流，用于追踪、回放和调试；关键事件必须能和消息、运行、工具调用关联。

合成消息必须有明确标记，避免 UI 将框架注入的提醒、摘要、计划或状态当成真实用户发言。

### 工作区与资源

OURO 需要明确当前工作区概念。工作区是文件、命令、项目配置、技能和本地资源的默认作用范围。

工作区相关能力包括：

- 当前目录和允许访问的路径范围。
- 项目级配置和全局配置的合并。
- 项目说明、技能、提示模板和上下文文件的加载。
- 文件引用、图片引用、命令输出等资源在上下文中的表达。
- 用户显式选择的附件、生成文件和外部资源引用的归属记录。
- 对项目配置、脚本、技能和自动加载资源的信任确认。

工作区信任是个人本地安全的重要边界。来自当前项目的脚本、配置、技能或自动加载资源不应在未确认时拥有高权限。插件属于 OURO 系统能力，不按项目归属划分。

资源不应被简单等同于消息文本。OURO 需要记录资源来源、类型、路径或引用方式，以及它和会话、运行、工具调用之间的关系。具体的复制、快照、清理和导出规则留给后续规格定义。

### 工具与能力

工具是模型可以调用的外部动作。每个工具应具有：

- 名称与说明。
- 参数结构。
- 来源信息。
- 权限策略。
- 执行结果格式。
- 中止和错误处理方式。

能力不一定都表现为工具。插件也可以提供上下文、命令、UI 面板、配置项、快捷键、模型供应商或后台监听能力。

## 功能特性

### 智能体运行

- 支持从用户输入、排队消息或恢复点启动运行。
- 支持模型流式输出，并能实时显示文本、思考状态和工具调用。
- 支持工具调用解析、参数校验、权限确认、执行、结果回灌。
- 模型工具调用应作为 assistant tool-call 消息持久化，工具结果再作为 tool_result 消息回灌，保证 OpenAI 兼容历史链路完整。
- 支持并行工具和串行工具，但对用户只暴露“正在执行哪些操作”和“结果是什么”。
- 支持在运行中插入转向消息，或在当前运行结束后追加跟随消息。
- 支持用户中止当前运行，中止后会话仍保持可继续状态。
- 支持模型错误、工具错误、权限拒绝、超时和取消的统一呈现。
- 支持对临时性模型或网络错误进行可见、可中止的重试；重试策略不应隐藏已经发生的错误事件。
- 支持会话内待处理输入的基本队列状态，避免用户连续输入时丢失意图。

### 上下文管理

- 支持可配置系统提示，作为智能体行为基线。
- 支持把会话历史、当前工作区、用户选择的文件、技能、状态和插件注入内容组合成发送给模型的上下文视图。system prompt 与 Skills 元数据说明是原生上下文字段，不伪装为会话消息；插件动态上下文使用独立的 synthetic context 边界。
- 支持区分长期存储的原始历史和发送给模型的上下文视图。
- OURO 内置 LLM 摘要压缩，按已关闭回合生成摘要并保留近期原文，不能拆开 assistant tool-call 与其连续 tool_result。
- 原始消息历史保持追加只写；摘要以独立记录持久化并通过 active pointer 投影到发送视图。
- 内置与插件摘要实现遵循同一 typed strategy contract；插件可显式替换策略，但失败时不降级为会话截断。
- 长期记忆不作为核心运行模块，但核心应为最小本地记忆插件和后续记忆能力预留上下文注入入口。

### 工具执行

核心默认提供以下基础工具：

- Read：读取文件、目录结构和必要的二进制/图片资源。
- Write：创建或覆盖文件。
- Edit：对文本文件进行局部编辑。
- Bash：执行本地命令，捕获输出、错误和退出码。
- AskUser：向用户提问或请求确认。

工具执行应遵循以下原则：

- 所有工具走统一入口，便于权限控制、事件记录和错误处理。
- 一次模型响应中的多个工具调用构成一个完整批次；assistant 消息必须保存全部调用，不能因审批或执行顺序丢弃后续调用。
- 批次先完成全部参数校验、权限判断和人机交互，再进入执行阶段；自动调用不得越过同批次尚未解析的审批或 AskUser 屏障。
- 批次执行支持有界串行或并行配置。单个工具失败不取消无关调用；并行完成顺序不改变按模型源顺序提交的 tool_result 历史。
- 工具权限保持简单：每个工具默认落在自动执行或用户批准两类策略中，用户可以按工具或来源调整。
- 工具错误以模型可理解的结果返回，允许模型自我修正。
- 工具执行应尽量响应中止信号，不能让用户长期无法取消。
- 工具结果至少支持文本和结构化数据；图片、文件引用等资源结果在后续规格中定义。
- 插件工具必须标记来源，用户可以查看、启用、禁用和调整权限。

SetTodoList、Agent/Subagent、浏览器等不进入最小核心，可作为官方插件或后续能力提供。MCP 作为官方集成能力，负责服务器生命周期管理和工具接入。

### 人机协同与权限

OURO 需要提供最小但完整的人机协同能力：

- 批准：在工具执行前请求用户批准。
- 拒绝：用户可以拒绝执行，并将拒绝原因返回给模型。
- 修改：用户可以在批准前修改工具参数。
- 提问：智能体可以在关键信息不足时向用户提问。
- 挂起：等待用户回答时，运行可以暂停，UI 可以回到可操作状态。
- 恢复：用户回答后，从挂起点继续运行。
- 中止：用户可以中止挂起或运行中的请求，当前运行结束，但会话不关闭。

默认权限策略建议：

- OURO 不追求企业级细粒度隔离，权限设计以个人用户的可理解、可调整为主。
- 工具权限只区分自动执行和用户批准。基础读取类工具可以默认自动执行；写入、编辑、命令执行、网络访问等高影响工具默认需要用户批准。
- 插件权限只保留读写能力和网络访问两类关键声明，用户可以在启用插件时统一授权或后续调整。
- 官方插件、第三方插件、AI 自主生成插件采用一致授权逻辑；区别只体现在来源标识和默认信任提示上。
- 用户可以把确认策略持久化到全局、会话或工作区配置，但不引入项目插件权限模型。

### 会话管理与恢复

- 支持创建、打开、切换、重命名、归档和删除会话。
- 支持会话标题、更新时间、运行状态、模型、工作区等基础元数据，用于会话列表展示和检索。
- 支持基础会话搜索或过滤，至少能够按标题、时间、工作区和归档状态定位会话。
- 支持会话惰性加载，首次访问时恢复消息、状态和配置。
- 支持多会话并存，不同会话之间的运行状态互不影响。
- 支持按会话获取消息历史快照、当前运行状态和待处理审批状态，便于宿主在切换会话时正确恢复页面。
- 支持按会话观察正在进行的事件流；用户切换到其他会话时，后台运行不应被中断，消息流也不应混入当前选定会话。
- 消息、事件和运行状态必须能稳定归属到具体会话和运行，并保持可排序，避免多会话并行时 UI 渲染错位。
- 同一会话同一时间只允许一个主运行；运行中收到的新输入进入转向或跟随队列。单机多进程防重入使用进程持有的操作系统文件锁，不能仅凭可能遗留的锁文件判断运行仍然存活。
- 运行产生的消息和关键状态应尽快持久化，降低崩溃损失。
- 崩溃、取消或挂起后，系统应能恢复到可解释状态。
- 会话应支持分支或派生：用户可以回到历史节点继续，原历史不被破坏。

OURO 默认使用本地可阅读文件完成持久化。JSONL 主要用于追加保存消息、事件和运行日志；会话状态、系统配置、索引和临时状态可以使用 JSON、YAML 或其他适合人工查看与迁移的文件格式。SQLite 是可选的同等职责后端，可在数据规模、查询效率或一致性需求提高时启用。导入导出、日志和回放数据应按数据类型选择合适文件格式，不强制绑定单一存储。

### 模型供应商

- 支持 OpenAI、Anthropic、Google 等主流供应商。
- 支持 OpenAI 兼容或 Anthropic 兼容的第三方接口。
- Provider 表示供应商连接、认证、超时和重试边界，同时可配置默认的 `base_url` 与 `api_path`；Endpoint 表示一个具体模型调用端点。一个 Provider 可以配置多个 Endpoint，并选择默认 Endpoint。
- Endpoint 独立配置 model id、base URL、API path、temperature、context window、最大输出、多模态、工具调用、流式、结构化输出、推理能力和支持的思考等级；Endpoint 的 `base_url` 与 `api_path` 可选，未配置时自动继承 Provider 级对应字段并按 `provider_type` 推断默认值。
- 支持用户添加、查看、切换和删除自定义模型端点，并允许运行时显式选择 Provider/Endpoint；Provider 的 `default_endpoint` 字段指向已配置的端点之一，而非独立的默认端点概念。
- 支持模型供应商凭据配置、连通性检查和错误提示。
- 支持测试用模型供应商，便于离线开发和自动化测试。
- 支持模型能力描述，例如工具调用、图像输入、流式输出、结构化输出和推理等级。
- 支持按会话切换模型。
- 支持记录 token 用量、缓存命中、调用次数和费用估算。
- 模型回退链可以作为增强配置提供，不作为最小可用能力的前置条件。

### 凭据与外部连接

OURO 需要处理模型供应商、MCP 服务器、第三方插件和外部服务的凭据。

基本原则：

- 凭据属于本地用户配置的一部分，不进入项目配置和会话消息。
- 普通配置文件可以保存凭据引用、环境变量名称或本地密钥条目名称，不应强制把明文密钥写入可阅读配置文件。
- 凭据缺失、过期或不可用时，应提供清晰错误提示和重新配置入口。
- 插件和 MCP 使用凭据时必须带来源标识，并受插件读写能力和网络访问授权约束。
- OURO 不追求企业级密钥管理，但需要避免凭据和普通运行数据无意混杂。

### 扩展系统

插件是 OURO 扩展能力的主要方式。插件可以贡献：

- 工具。
- Slash 命令。
- 上下文提供器。
- 权限策略。
- 模型供应商。
- 技能或提示模板。
- UI 扩展点。
- 自动化脚本和后台监听能力。

插件系统应满足：

- 插件属于 OURO 系统能力，不按全局插件或项目插件划分。
- 插件来源分为官方插件、第三方插件和 AI 自主生成插件。
- 支持启用、禁用、显式重载。
- 插件加载失败不能破坏核心启动。
- 插件能力必须带来源标识。
- 三类插件采用一致授权逻辑，授权重点是读写能力和网络访问能力。
- 插件热重载可以作为开发体验增强，不应成为核心稳定性的前提。

### 命令系统

- 支持 Slash 命令作为用户主动控制入口。
- 内置命令应覆盖帮助、模型切换、会话管理、权限配置、压缩、导出、插件重载等常用操作。
- 插件可以注册命令。
- 命令执行结果应进入事件流或会话状态，便于 UI 展示和调试。

### MCP 集成

MCP 是外部工具接入方式之一，不等同于 OURO 的核心扩展系统，但应作为官方集成能力提供。

当前定位：

- 核心提供统一工具接入能力。
- OURO 负责 MCP 服务器的生命周期管理，包括配置、启动、连接、认证、状态查看、重启和停止。
- MCP 工具必须继承 OURO 的来源标识、权限确认、事件记录和禁用机制。
- 大量 MCP 工具应通过工具分组或按需加载降低上下文压力。

MCP 的协议细节、配置字段和异常恢复策略不放在项目概述中展开，留给后续规格文档。

### Agent Skills

OURO 支持 Agent Skills 作为可复用操作知识和流程说明。

- 自动发现全局技能与工作区技能。
- 首先只加载技能元数据，用于判断何时使用。
- 仅在显式调用或匹配条件满足时加载完整技能内容。
- 技能可以引用本地文件、脚本和示例，但执行相关操作仍受工具权限控制。
- 技能启用状态可配置和持久化。

技能不应无条件全部注入上下文，避免污染模型注意力和浪费上下文。

### 任务规划与进度

OURO 应支持用户理解当前任务进度，但不必把 Todo 系统作为最小核心。

建议定位：

- 简单任务直接执行，不强制生成计划。
- 复杂任务可以展示计划、步骤、当前状态和阻塞点。
- 计划模式可作为官方能力提供：先只读分析并输出计划，不执行写入或命令。
- 任务进度列表可作为官方插件或 UI 功能实现。
- 任务状态应对用户可见，但不应让模型为了维护列表而偏离实际任务。

### 子智能体与探索

子智能体适合复杂任务拆分、独立探索和并行研究，但不是最小核心能力。

建议定位：

- 首期可以提供轻量探索模式或官方插件。
- 子智能体以工具形式被主智能体调用。
- 子智能体输出最终结果和必要事件摘要，不直接混入主会话消息流。
- 子智能体调用应受深度、工具范围、超时和权限限制。
- 子智能体持久化恢复、跨进程重建、审批透传等复杂能力留给后续规格。

### 长期记忆

OURO 不内置通用长期记忆系统，但应提供一个最小本地记忆插件，并保留后续扩展入口。

最小本地记忆插件可以提供：

- 用户偏好。
- 常用项目信息。
- 跨会话事实。
- 任务经验摘要。
- 可检索知识片段。

长期记忆必须可查看、可删除、可禁用，并应明确哪些内容会进入模型上下文。

### 可观测与回放

- 运行过程产生标准化事件流。
- UI 使用事件流展示文本、工具、审批、错误和运行状态。
- 默认长期保存完整事件流，用于调试、回放和问题追踪。
- 支持按会话和运行过滤事件流，便于宿主只渲染当前选定会话，同时保留其他会话的运行状态提示。
- 支持模型调用、工具执行、子任务、插件调用的层级追踪。
- 默认事件流可以包含提示词、模型输出、工具参数和工具结果内容，不做额外脱敏或采样处理。
- 支持统计 token、费用、调用次数、延迟、错误率和首字响应时间。

可观测性是调试和用户信任的重要组成部分，但不要把项目概述写成追踪系统规格。具体字段、格式、导出方式留到后续规格定义。

## 用户界面与运行模式

OURO 共享同一核心，提供多个入口：

1. Interactive
   - 终端交互模式。
   - 支持流式输出、工具调用展示、审批、会话管理和命令。

2. Print / JSON
   - 一次性执行模式。
   - Print 输出最终文本。
   - JSON 输出事件或结构化结果，便于脚本调用。

3. SDK
   - 供 Python 程序直接嵌入。
   - 适合批处理、本地应用或自定义宿主。

4. RPC
   - 供编辑器插件、本地代理或其他语言进程接入。
   - 协议细节后续规格化。

5. Desktop
   - 桌面图形应用。
   - 提供更友好的会话管理、文件拖拽、模型配置、权限确认和运行可视化。
   - 未来应支持多个会话同时存在、后台生成和快速切换；对话页面渲染选定会话的历史消息与正在生成的消息流，非选定会话只展示必要状态提示。

首期实施 Interactive 和 Print / JSON 运行模式。SDK、RPC、Desktop 作为未来宿主入口，应复用同一套核心运行逻辑，不应各自实现一套智能体逻辑。

## 配置与数据管理

配置范围：

- 全局配置：跨项目生效。
- 项目配置：当前工作区生效，覆盖全局配置。
- 会话配置：当前会话内生效。
- 运行时设置：本次运行临时生效。

配置内容包括：

- 模型供应商和模型端点。
- 凭据引用、环境变量名称或本地密钥条目名称。
- 当前模型和推理等级。
- 工具启用状态和权限策略。
- 插件启用状态。
- MCP 服务器配置。
- 技能启用状态。
- 系统提示和上下文策略。
- 持久化与日志策略。
- 会话列表索引、资源引用索引和数据维护策略。

配置优先级建议为：

运行时显式设置 > 会话配置 > 项目配置 > 环境变量 > 全局配置 > 默认值。

涉及项目脚本、配置或技能时，必须考虑工作区信任。未信任工作区不应自动执行项目本地高影响能力。

数据管理默认采用本地可阅读文件。消息、事件和运行日志适合用 JSONL 追加保存；会话状态、系统配置、插件配置、MCP 配置和技能启用状态适合用 JSON 或 YAML 保存；SQLite 可作为可选后端承担同等职责。导入导出不需要独立抽象成复杂系统，按数据类型生成可阅读文件即可。

长期保存完整事件流会带来数据增长，因此 OURO 需要提供基础数据维护能力，包括数据目录查看、会话导出、会话归档、历史事件清理和配置迁移提示。清理默认由用户主动触发，不在后台静默删除数据。

## 建议的阶段优先级

### 第一阶段：最小可用核心

- 单用户本地会话。
- Interactive 基础交互入口。
- Print / JSON 一次性运行模式。
- 基础模型供应商。
- 基础凭据配置、本地多 provider 配置文件、provider 管理 CLI 和模型连通性检查。
- Read / Write / Edit / Bash / AskUser 基础工具。
- 工具审批与中止。
- 本地可阅读文件持久化。
- 内置 LLM 摘要压缩与持久化 context projection。
- 基础事件流、长期保存和会话恢复。
- 基础插件加载与一致授权模型。
- provider usage 进入运行记录和 JSON 输出。
- 已有 active run 时不创建第二个主运行；后续输入进入持久化队列并在当前运行完成后串行处理。
- 会话基础元数据和列表展示。

### 第二阶段：完整个人工作流

- Interactive 体验完善。
- 会话树、分支、导出和回放。
- 会话标题生成、搜索和过滤。
- 多会话切换、后台运行状态和按会话事件流观察。
- 附件、生成文件和资源引用管理。
- 技能系统。
- 模型管理 UI。
- 项目级配置和工作区信任。
- MCP 服务器生命周期管理。
- 官方插件：计划、任务进度、最小本地记忆、浏览器或自动化能力；摘要插件改为可选策略贡献。
- 为子智能体官方插件预留清晰的接入空间。
- Desktop 基础应用。

### 第三阶段：高级扩展

- 子智能体和探索模式官方插件。
- 高级长期记忆和知识库检索。
- SDK 和 RPC 接入。
- 工具分组和大规模工具按需加载。
- 更完整的追踪、指标和离线分析。
- 更多持久化后端、数据迁移和远程执行能力。

## 已明确的设计决策

1. 基础运行框架：OURO 自主构建 RuntimeAdapter、Provider、Tool、Event、Persistence 和 Hooks 等基础设施，不基于外部 Agent 框架实现核心运行闭环。
2. 持久化策略：默认使用本地可阅读文件。JSONL 主要追加保存消息、事件和运行日志；JSON/YAML 保存会话状态、系统配置等结构化数据；SQLite 作为可选同等职责后端。
3. 插件信任模型：插件属于 OURO 系统能力，不存在项目插件或全局插件划分。插件来源分为官方插件、第三方插件和 AI 自主生成插件，授权逻辑暂定一致。
4. 权限粒度：不引入复杂权限体系。工具权限区分自动执行和用户批准；插件权限区分读写能力和网络访问能力。
5. 首期运行模式优先级：第一阶段实施 Interactive 和 Print / JSON，让系统先具备交互运行和脚本调用能力。SDK、RPC、Desktop 服从共享核心，未来阶段实施。
6. 上下文压缩策略：OURO 内置 LLM 摘要压缩并持久化 active projection；插件可替换 typed strategy，失败时不再截断历史。
7. 子智能体范围：子智能体作为官方插件后置，但核心设计需要预留集成空间，避免后续重构。
8. MCP 范围：OURO 不只加载 MCP 工具，还需要管理 MCP 服务器生命周期。
9. 长期记忆范围：提供最小本地记忆插件，但不把通用长期记忆系统内置进核心运行层。
10. 事件持久化范围：默认长期保存完整事件流，不做额外脱敏、采样或敏感内容过滤。

## 后续规格化重点

- 定义 OURO 自研基础运行设施的稳定接口。
- 明确本地文件持久化的目录结构、文件命名、写入时机和恢复规则。
- 明确多会话快照、运行状态查询和按会话事件流观察接口。
- 明确凭据引用、本地密钥来源和连接检查流程。
- 明确会话标题、搜索索引和资源引用索引的维护方式。
