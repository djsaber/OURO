# OURO 编码准则

> 文档类型：开发规范
> 适用范围：当前代码、测试、文档与贡献流程

这份准则的目标不是让 Agent 少写代码，而是让 Agent 写出来的东西像一个被设计过、可维护、可演进的项目。

---

## 一、目标与完成标准

- 你的目标不是“把功能跑通”，而是“把新行为安放进一个可长期演进的系统里”。
- 所有功能实现、架构设计和系统改进都要遵循第一性原理。先识别问题的核心本质、真实约束、关键不变量和必要因果，再选择实现，不要被既有表层形态、惯例或局部补丁牵着走。
- 不要把“功能可运行”当成完成标准。完成必须同时包括：行为正确、边界清楚、依赖合理、错误可见、测试可信、未来可改。
- 永远警惕“所有测试都通过但系统更难改了”的结果。可维护性下降也是一种失败。
- 完成任务前，至少做一次整体审视：功能放在这里是否自然？未来加相邻功能是否容易？错误是否能暴露？测试是否真的保护行为？

## 二、理解项目与分层判断

- 修改代码前，先理解项目结构、模块职责、依赖方向、调用链、数据流和已有风格。不要在不了解整体形状的情况下直接堆实现。
- 每次实现前，先判断需求属于哪个层级：领域逻辑、应用服务、基础设施、接口适配、配置、测试、脚本工具。
- 代码必须放在正确层级。API、CLI、任务队列、定时任务只是入口，不是业务本体。
- 入口层负责解析输入、调用应用服务、格式化输出，不承载核心业务规则。
- 不要把业务逻辑塞进入口文件、路由层、CLI、任务调度器、ORM model、数据库访问层、测试 fixture 或工具函数里。
- 当不确定架构意图时，不要猜着扩展。先从现有代码、README、测试、命名和调用关系中推断设计；仍不清楚时说明假设和取舍。

## 三、模块职责与依赖方向

- 每个模块都应该有明确职责。一个模块应该能用一句话说清楚它负责什么，也能说清楚它不负责什么。
- 一个模块最好只有一个主要变化原因。不要把因业务规则变化而变化的代码，和因技术实现变化而变化的代码混在一起。
- 保持清晰、稳定的依赖方向。高层业务逻辑不应依赖底层实现细节；核心逻辑不应被数据库、HTTP、文件系统、CLI、框架或第三方 SDK 绑死。
- 优先让外层依赖内层。接口层调用应用层，应用层编排领域逻辑，基础设施实现外部依赖。
- 不要让“方便 import”决定架构。import 路径应该反映设计关系，而不是临时拼凑关系。
- 发现循环依赖时，不要用局部 import 糊过去。循环依赖通常说明职责划分或依赖方向出了问题。
- 不要用全局状态隐藏依赖。配置、客户端、数据库 session、时间、随机数、外部服务都应该尽量显式传入或集中管理。

## 四、接口契约与数据结构

- 设计公共接口时要谨慎。函数签名、返回值、异常、类型和副作用都属于契约。
- 保持公共接口稳定。修改被多处调用的函数、类、schema、事件、配置项时，要检查所有调用方和兼容性影响。
- 不要让调用方猜测隐含规则。输入约束、默认值、错误情况、状态变化和边界条件都要显式表达。
- 类型是设计工具。Python 项目应尽量使用类型标注表达输入、输出、可选值、领域对象和错误边界。
- 数据结构要表达意图。优先使用 dataclass、TypedDict、Pydantic model、Enum、Protocol 或领域对象，不要让 dict[str, Any] 和裸字符串在系统里到处流动。
- 类不应只是函数收纳盒。只有当它封装状态、策略、生命周期、协议或清晰概念时，才使用类。
- 函数应该小而完整。它可以做一件复杂的事，但不能同时承担校验、查询、转换、业务决策、持久化和响应格式化。

## 五、外部依赖、配置与资源边界

- 对外部依赖建立边界。数据库、缓存、消息队列、文件系统、第三方 API、模型调用都应该被封装在基础设施层。
- 第三方库必须被隔离在适配层。不要让整个项目到处散落某个 SDK 的对象、异常类型和调用细节。
- 新增依赖前，先判断是否真的需要。依赖会带来版本、安全、启动时间、学习成本和抽象泄漏。
- 配置必须集中、类型明确、可验证、可覆盖。不要在业务代码中到处读取环境变量。
- 时间、随机数、UUID、当前用户、当前环境、网络、文件系统等非确定性来源，应通过可替换边界进入核心逻辑，方便测试和复现。
- 资源必须可关闭。文件、连接、客户端、线程池、临时目录、锁都应有清晰生命周期。

## 六、错误处理与可观测性

- 错误是系统行为的一部分，不是意外附属品。每个外部调用、解析、状态变更、权限检查、数据转换都要考虑失败路径。
- 不要静默吞掉异常。捕获异常必须有明确目的：转换错误类型、补充上下文、重试、回滚、降级处理、记录后重新抛出或返回明确结果。
- 错误信息应该帮助定位问题。异常和日志应包含关键上下文，但不能泄露密钥、token、密码、隐私数据或完整敏感 payload。
- 不要用日志代替错误处理。记录了错误但系统继续产生错误状态，比直接失败更危险。
- 关键流程应具备可观测性。重要操作、外部调用、失败原因、重试、降级和状态变更应该有适当日志、指标或追踪点。

## 七、测试策略

- 测试不只是证明代码能跑，还要证明错误能被发现。
- 重要功能应覆盖正常路径、错误输入、边界条件、依赖失败、权限失败、空数据、重复执行和状态冲突。
- 测试应该验证行为和契约，而不是锁死无关实现。不要把实现细节复制到测试里造成同错同对。
- 对 bug 修复，先写能复现 bug 的测试，再修复。修复后测试应证明 bug 不会回来。
- 对架构性改动，要补充集成级测试或边界测试。只靠单元测试不足以证明模块协作正确。
- Mock 要谨慎使用。Mock 外部系统、慢操作和非确定性边界可以；Mock 自己的核心逻辑通常会掩盖设计问题。
- 测试命名要表达场景和预期结果。读测试应该能理解系统行为，而不是只看到函数调用顺序。

## 八、数据、事务、幂等与兼容性

- 数据持久化要有明确边界。不要让 ORM 细节污染业务规则，也不要让数据库表结构决定整个领域模型。
- 数据库操作要有清晰事务边界。不要让半个业务流程成功、半个失败后留下不可解释的状态。
- 重要状态变更要考虑幂等性。任务重试、接口重复请求、消息重复消费都不应轻易造成重复写入或脏状态。
- 当前实现不提供历史数据、旧 API 或旧配置的兼容和迁移代码；格式不符时明确拒绝，由用户使用新目录或按明确的数据维护流程处理，不能自动清空用户数据。
- 脚本和一次性任务也要按生产代码标准处理。它们同样会破坏数据。

## 九、安全、并发与性能

- 安全不是最后一步。输入校验、权限检查、路径处理、反序列化、命令执行、SQL、模板渲染和密钥管理都要主动审视。
- 不要硬编码密钥，不要记录敏感信息，不要信任外部输入，不要拼接 SQL，不要绕过权限检查。
- 并发和异步代码必须明确共享状态、锁、超时、取消、重试、事务、幂等性和资源释放。
- 性能优化要基于证据。不要提前复杂化，但要避免明显的 N+1 查询、重复 IO、无界缓存和全量加载。

## 十、命名、抽象与文件组织

- 命名要暴露设计意图。类、函数、模块名应该让读者知道“这是什么”和“为什么存在”。
- 不要使用 vague 名称，比如 manager、helper、utils、processor，除非它们在项目中已有明确语义。
- 工具函数必须克制。utils 往往是架构腐烂的早期信号；如果工具函数承载业务概念，应移动到对应领域模块。
- 不要过度抽象。只有当重复是真实的、变化方向清楚、抽象能降低认知负担时，才引入新抽象。
- 也不要把所有逻辑写成一坨。长函数、巨大类、跨多个概念的模块，应拆成有名字、有边界、有测试的单元。
- 文件组织应服务理解。目录结构应该让新读者能猜到代码在哪里，而不是只能通过全文搜索找到功能。
- 不要让一个文件持续膨胀。文件过大通常说明职责扩散，应按概念、流程或边界拆分。

## 十一、重构、演进与交付

- 修改已有代码时，尊重项目现有模式。除非现有模式明显有害，否则不要引入风格完全不同的新架构。
- 功能实现、系统改进和问题修复应采用能解决根因的最小必要改良。不要为假设性的未来需求扩大范围或增加不必要的层次、抽象、状态和兼容路径。新增复杂度必须由当前问题和可验证收益证明。
- 不要顺手重构无关代码。重构必须服务当前目标，范围清楚，行为可验证。
- 重构必须保持行为不变。功能变更和结构重构尽量分开，避免难以判断问题来自哪里。
- 当发现当前架构承载不了新功能时，先指出结构问题，再做最小必要整理。不要把新复杂度硬塞进旧缝隙里。
- 大改动要分阶段。先建立边界和测试保护，再迁移实现，最后清理旧代码。
- 每次改动后，要检查是否增加了不必要的耦合、重复、隐式依赖、全局状态或测试盲区。
- 每次提交或交付都应说明：改了什么、为什么这样设计、影响哪些模块、如何验证、还有什么风险。

## 十二、文档与代码审查

- 文档应解释“为什么”，不是重复“做了什么”。复杂设计、边界选择、非显然约束和权衡需要留下记录。
- 更新文档时，直接描述当前设计、实现和有效契约，不加入变更说明、前后对比、修订注记或历史演进。待办与扩展条件放在规划文档中。
- 注释应服务于理解复杂性。不要给显而易见的代码写注释，也不要用注释掩盖糟糕命名。
- 代码审查时，优先看系统性问题，而不是只看局部语法：依赖方向、边界泄漏、错误路径、测试可信度、长期可维护性。
- 如果需求推动项目架构变差，要明确指出风险，并提出更稳的实现路径。

## 十三、代码格式与风格呈现

- 清晰、规整的代码格式能提升阅读者的愉悦度。保持一致的缩进、空行、换行和对齐，让代码在视觉上易于扫描和分层。
- 完善、规范的关键处注释能提升代码的易理解性。在复杂算法、非直观决策、边界假设和外部契约处留下精炼注释，帮助读者快速建立上下文。
- 代码风格向顶级开源项目靠齐，追求开源级别的高质量代码呈现。遵循社区广泛接受的格式规范（如 PEP 8、Black、Ruff 等），让代码在任何读者面前都经得起审视。

---

## 一句话总原则

- 写代码不是把功能塞进项目，而是把新行为安放进已有系统。能跑只是底线，能理解、能修改、能发现错误，才算做好。
