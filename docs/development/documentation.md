# 文档维护规范

## 分类与权威来源

| 位置 | 职责 | 内容边界 |
|---|---|---|
| 根目录 README | 项目入口、环境要求、最小启动与导航 | 不承载完整命令手册或领域状态机 |
| `docs/guides/` | 面向使用者的操作指南 | 前提、步骤、结果、限制和常见失败 |
| `docs/architecture/` | 架构与设计理由 | 分层、所有权、数据流、取舍及扩展条件 |
| `docs/specs/` | 独立的正式规格与验收契约 | 模型、状态、不变量、配置、权限、失败和验证依据 |
| `docs/development/` | 贡献者规范与扩展开发 | 工程实践、开发流程和维护约定 |
| `docs/plans/` | 尚未完成的工作 | 目标、依赖、任务、退出条件与未验证范围 |
| `docs/plans/archive/` | 已完成工作的记录 | 当时的审查范围、决策、测量与验收结果 |
| 包、示例和开发工具旁的 README | 就地说明 | 运行方式、局部职责及通往权威文档的链接 |

同一精确契约只由一个领域规格负责。概述和指南可以摘要说明，但应链接到契约，不复制长表、状态转换或完整实现清单。不同语言的规范是明确标注的翻译，不视为应删除的重复文档。

领域规格（Spec）是实现与回归验收共同遵循的约束，统一放在 `docs/specs/`，按业务主题独立维护。指南说明如何使用，架构说明职责与设计理由，规格定义必须满足的行为及边界。修改公开行为时，同步评审对应规格和验证依据；发现规格与代码不一致时，先确认偏差根因，再修正文档或实现。

## 文件与标题

- 普通文件使用简洁英文 kebab-case 名称，例如 `provider-configuration.md`；不重复项目名，不把日期放入持续维护的文件名。
- 翻译使用语言后缀，例如 `coding-guidelines.zh-CN.md`、`coding-guidelines.en.md`。
- 已完成记录使用 `YYYY-MM-DD-topic.md`；日期只表示记录归属，不自动代表支持或验证时间。
- `README.md`、`CONTRIBUTING.md`、`SECURITY.md`、`RELEASING.md`、`CHANGELOG.md` 和 `SKILL.md` 保留生态约定。
- 面向读者的文档只有一个一级标题；标题使用自然语言，章节围绕业务主题组织。状态机或协议文档可保留稳定编号供精确引用。作为运行输入的 `SKILL.md` 遵循技能格式，不为文档排版改动提示词。

## 内容与示例

- 现行指南、架构与规格直接描述当前行为；历史变更放在 CHANGELOG 或完成记录，未来能力放在规划。
- 分清实现、离线测试、真实账户验证与跨平台验收。记录实际证据及范围，不把计划、模板声明或一次成功推为普遍支持。
- 配置默认值和限制从当前模型、解析器和测试核对。厂商服务能力及发布时间不得由本地模板反推；外部材料保留来源和核对时间。
- 命令注明 shell；占位符明确说明替换方式。框架生成的 ID 从命令输出取得，不从显示名称推导。
- 示例使用临时 home、示例域名和环境变量引用，不包含真实秘密。JSON 代码块保持可解析；片段应明确标注上下文和缺省项。
- 保留中文主文档和已有英文规范；标识符、命令与公开 UI 名称使用代码或界面的精确拼写。

## 变更验证

移动或重命名文档时，同时更新 Markdown 链接、章节锚点、源码注释和索引。检查本地目标存在、锚点有效、代码块闭合、JSON 语法，以及示例与 CLI / 配置模型一致。

文档改动按影响范围验证：纯文字与路径变更不要求重跑全部功能测试；命令示例应进行解析或隔离 smoke 验证，包内文档与根 README 变更后检查构建产物。工程门禁由[贡献指南](../../CONTRIBUTING.md)统一维护。
