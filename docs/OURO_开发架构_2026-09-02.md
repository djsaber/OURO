# OURO 开发架构

> 文档类型：现行架构
> 代码基线：2026-09-12
> 事实来源：包依赖矩阵、composition root、公开 Protocol 与架构测试

本文是 OURO 当前代码结构的权威说明。新代码必须先确定职责、依赖方向和持久化边界，再选择目录；
目录位置本身不能替代架构判断。

各领域的详细数据契约、失败语义和验收证据见 [规格索引](../dev/specs/README.md)。

## 分层与依赖方向

```text
CLI / TUI / Desktop hosts
        |
        v
application orchestration
   |        |             |
   v        v             v
 core    config    session/resource/tool ports
   ^                        ^
   |                        |
provider adapters    file / SQLite / local implementations
```

- `ouro.core` 定义稳定领域记录、Provider/Tool 契约、上下文构建、取消信号和单次 active run 的状态机。
  它只能依赖 `ouro.core`。
- `ouro.application` 编排用例、状态转换和持久化事务。它可以依赖 core、配置契约和基础设施端口，
  不能依赖 CLI 或具体 provider 实现。
- `ouro.local_application` 是本地部署组合根，统一拥有 Runtime、MCP 和关闭生命周期；`ouro.cli` 只是界面
  适配器，负责解析、调用 application service 和格式化输出。
- `ouro.providers`、`ouro.sessions`、`ouro.tools` 是外部能力的具体适配与实现。
- `ouro.config`、`ouro.skills`、`ouro.plugins`、`ouro.mcp` 维护各自契约与策略，不反向依赖
  application 或 CLI。

架构测试位于 `tests/architecture/test_boundaries.py`，用于阻止低层反向 import。

## 包职责

| 包 | 负责 | 不负责 |
|---|---|---|
| `core` | 领域记录、协议、纯规则、inner loop | 文件、网络、CLI、具体厂商 SDK |
| `application` | 会话与运行用例、事务编排、Host DTO | 参数解析、终端渲染、HTTP 细节 |
| `config` | 集中配置模型、校验、持久化和运行参数合并 | 模型请求和 UI 查询用例 |
| `sessions` | 后端中立 SessionRepository/Catalog port、文件与 SQLite 后端、Session 资源引用 | 会话命令与 Host DTO |
| `resources` | ResourceStore port、不可变 blob 与 blob 元数据 | Session 引用、Host DTO 与运行调度 |
| `providers` | Provider 实现、transport、codec、adapter factory | 会话模型选择和运行状态 |
| `tools` | 工具注册、schema 校验、权限执行和批调度 | 模型轮次状态机 |
| `skills` | 标准 Skills 发现、解析、内容加载和安装管理 | 提示词运行编排 |
| `plugins` / `mcp` | 插件注册；MCP transport、协议适配、工具投影和连接生命周期 | 核心业务状态 |
| `cli` | 命令定义、组合、输入输出 | 领域规则和持久化事务 |

## 核心运行链

```text
CLI / TUI / Desktop Host
  -> LocalApplication async lifecycle
    -> MCPRuntimeResource.from_config(home, runtime.tools)
      -> start auto-start servers + atomic ToolRegistry projection
    -> RuntimeService
    -> session lock + recovery
    -> RunLifecycle.start
    -> InnerAgentLoop
       -> ContextPreparationService
       -> RuntimeAdapter -> Provider
       -> ToolCallCoordinator -> ToolBatchExecutor
       -> RunLifecycle complete / fail / pause
    -> queued input drain
```

默认 CLI 的单次 Run、Interactive 和审批恢复均通过 `LocalApplication` 启动并关闭 Runtime、插件与 MCP；Runtime
自身又关闭模型 adapter、事件 worker 和专用压缩 adapter。TUI/Desktop 必须复用同一 async lifecycle，
不得从 Session adapter 路径推导部署配置，也不得只构建 RuntimeService 后绕过扩展资源装配。

`RuntimeService` 拥有跨协作者的运行事务：恢复、人工交互恢复、terminal settlement 和排队输入串行化。
进程内 session run lock 与 abort signal 由 `RunExecutionOwnership` 唯一管理；`RunLifecycle` 集中承载模型循环中的
durable Run/Session 状态转换。`InnerAgentLoop` 只拥有一个 active run 内的模型轮次状态机；其端口按 context、
run boundary、turn boundary 三个变化原因分组，事件和工具批次保留为两个直接边界，并在三个协作面之间传递
成组依赖。模型路由与审批模式是请求边界设置，不争用 Run ownership：Host 可在活动 Run 中原子更新 Session，
InnerAgentLoop 在每次模型请求准备时重新绑定路由，并在工具预检前刷新 Session 策略；已发出的请求和已产生的
审批不被追溯改写。

取消采用同一条两阶段协议。`RuntimeService.abort_run` 先持久化 `abort_requested` 并发出
`run_abort_requested`，活动 owner 随即取消它拥有的模型或工具任务；只有 owner 完成资源收尾、工具调用与批次写入终态后，
Runtime 才把 Run 转为 `aborted` 并发出 `run_aborted`。Session execution lock 是跨 Runtime/进程的唯一 owner barrier，
进程内 `AbortSignal` 只负责低延迟通知；没有活动 owner 的等待态 Run 可以直接终止。Host 投影在两阶段
之间显示 `cancelling`，且终态单调，任何迟到事件都不能把 terminal Run 重新投影为 running。

LocalApplication 完成 Plugin catalog、Supervisor、AgentDefinitionService 和 AgentService 构造后，用一次性的
`RuntimeService.bind_extensions` 绑定完整 Host 扩展组合。绑定不可重复，运行前不会暴露“有 definitions 但没有
controls”等半装配状态。裸 Runtime 明确是无扩展 Host。

运行事务读取 `RuntimeSessionSnapshot`，其中只包含 Session、messages、runs 和 compactions；包含完整
events 的 `SessionSnapshot` 只服务查询、回放、导出和活动投影重建。正常 Run 在取得锁前后复用同一份运行态
快照，并用轻量 SessionRecord 重读检测竞争更新；上下文准备和 catalog 刷新都不得反向加载 replay events。

`RuntimeSupervisor` 位于 RuntimeService 之外，只拥有跨 Session 的进程内 FIFO 调度、并发上限、Host
订阅和 shutdown 生命周期。它不写 durable Run 状态机；submit/abort 最终调用 RuntimeService，重启恢复
仍从 SessionStore 读取。`RuntimeActivitySnapshot` 把 durable Run/ToolBatch/ToolCall 与模型、压缩事件投影为
Host 可直接消费的细粒度活动状态；它不是第二套状态机，并可从 Session 事件重建。订阅可选择接收活动变化，
且在创建时取得同一边界的 initial activity。每个订阅使用有界队列，慢 Host 不反向阻塞 Run；发生 lag 后
Host 通过 activity 快照和 durable event cursor 重新同步。

`model_tool_call_delta` 在完整 ToolCall 形成前投影为 Host-neutral 的 `streaming` 工具活动；工具名按 source index
聚合，未完成的序列化参数只保留有界原样后缀，并在正式 request 到达时提升为 canonical tool-call identity。
高频内容仍只通过有序 event channel 逐片通知，后缀用于 activity 查询与 lag 后重同步，不为每个参数 delta
重复发布 activity notification。Application 不规定单行化、窗口宽度、动画、颜色或详情布局，这些均由
CLI、TUI、Desktop 各自适配。

### 子智能体运行链

子智能体不是另一套 Agent 内核。`AgentDefinitionService` 管理 builtin/custom 能力模板；primary Run 启动时把
可用 definition、精确工具 identity、最低 permission mode、执行能力和 `AgentSpawnPolicy` 冻结为
`AgentCatalogSnapshot`。目录先与 agent/model pattern、sync/async、bound lifecycle 以及
write/network/MCP/external-path hard cap 求交；`SpawnAgent` 的 schema 和 application handler 使用同一 Run 快照。
`SpawnAgent` 等 product-owned
工具只在普通工具校验、权限和审批边界内产生类型化控制请求，真正的 Session/Run/Delegation 写入由
application 层 `AgentService` 完成。subagent instance 是独立 `SessionRecord(session_kind="subagent")`，每次执行或
follow-up 是新的普通 `RunRecord`；`DelegationRecord` 只保存父子关系、冻结能力、结果和交付 identity，不镜像
child Run 的运行状态。

sync 使用原 SpawnAgent ToolBatchCall 中的 durable `AgentWaitRequest`：父 Run 进入 `waiting_child/subagent_join` 后释放
Supervisor execution permit，child 终态再按原 tool_call_id 恢复同一父 Run。async 复用显式声明
`role=system, scaffold=true` 的 Host input
队列，以稳定 delivery/queue identity 实现 next-boundary 的一次性交付；Host input 持久接收后返回 receipt，模型消费由后续普通
Run 调度独立完成。父已 idle 时由同一 Host 边界创建后续 Run。child Approval/AskUser 始终
保存在 child canonical Run，根 Host 通过 AgentService 聚合并按 child_session_id、child_run_id、tool_call_id 和
request_id 精确路由。运行契约限制为单层和 bound lifecycle；subagent 的工具、workspace、审批与
RunBudgetPolicy 只能从父级能力上限收紧。

循环交互 CLI 作为长期运行 Host，用单一行读取协调器把 stdin 经线程边界接入 async 循环，并与 AgentTree
subscription 同时等待。底层始终只有一个阻塞 reader；interaction 到达时只重定向当前提示，由原 reader 接收
明确答案，AskUser 空行继续等待。因此 sync parent 处于 `waiting_child` 时可在原 Run 内继续，async subagent 在
父 Run 已完成或继续运行时也能把 Approval/AskUser 投影到同一主窗口。CLI 用完整 child identity 路由批准、拒绝、
参数修改、终止或回答，并在 application 决议与 canonical inbox 投影收敛的短暂窗口内去重已提交 identity；只渲染
主智能体行动轨迹与 subagent HITL 提示。subagent text/reasoning/tool stream 保留在其 canonical Run，供 Desktop
等树形 Host 按需展开。CLI 不读取 child Store、不轮询，也不建立第二套审批状态机。

AgentService 不设置 root active/queued subagent 配额。每个通过派遣策略、深度、预算与幂等校验的请求都建立
durable relation 并提交现有 RuntimeSupervisor；Supervisor 的通用 `max_concurrency` 与 FIFO 决定实际并发和排队。
AgentService 在 relation 创建前拒绝 depth > 1。工具 effect、write capability 与权限不参与调度；同一 Delegation 的
生命周期竞争由 AgentService 的 per-delegation lock 与 repository CAS 收敛，控制工具无需声明 batch exclusive。
subagent 直接复用冻结的 `RunBudgetPolicy`；InnerAgentLoop
每次 model round durable boundary 先执行本 Run 检查，再由 application callback 聚合 parent Run 与其所有 child
Session 的 Run usage/model rounds，返回相同 `RunBudgetReason` 并进入现有 paused 路径。模型轮次是 RunRecord 的
持久累计字段，不通过反复扫描 `model_request_started` 事件计算；聚合以 Run identity 去重，
所以 child follow-up/resume 各计一次而不会重复计算旧 Run。AgentTree 的 root usage 同样从这些 canonical Run
聚合。Supervisor 继续使用原跨 Session FIFO；waiting 状态不占 execution permit，已完成 child result 不受后续
root budget 耗尽影响。

child 不继承或投影父 Session 的消息、压缩摘要、工具结果、reasoning/provider state 或脚手架上下文，也不接受
canonical message id。它的文本上下文固定由 OURO
platform/base system instructions、冻结的 `AgentDefinition.system_prompt` 和 `SpawnAgent.task` 组成：
前两者形成 system instructions，task 作为 child 第一条 canonical `user` message。主智能体负责在 task
中提供完成委派所需的全部文本上下文；Agent 专用 system prompt 与 task 都进入 child 自己的 ContextView
预算，但不进入 SpawnAgent 描述、根树或关系事件。

资源引用同样不隐式继承。ResourceService 在源 Session mutation boundary 内验证不可变内容，再显式附加带来源的
child 引用；child 输出资源进入 Host list、sync SpawnAgent result 或 async result 的父 canonical message 前，必须从 child 到 parent
重新验证并复制引用。Delegation 只保存 child 初始 message identity、task digest 和显式 resource identity，
不复制父 prompt、资源 blob 或 child 最终文本。

Agent control names 是 ToolRegistry 的产品保留名称；仅 `source=builtin` 且带 Host marker 的 Run overlay 可注册，
plugin/MCP 不能通过伪造 metadata 覆盖。AgentService 只属于 application，并由 LocalApplication 组合；tools、plugins、
SDK 和 CLI command 不直接导入其实现，PluginContext 也不暴露调度 handle。AgentDefinition 的 `source/editable` 只在
管理 DTO 中存在：list 隐藏 system_prompt，显式 detail/edit 才返回；执行用 Core AgentDefinition 不按来源分支。
child task 不进入 Delegation 文本、handle、根树或关系事件，application control error 继续经过统一 redaction。
child shell/path 仍走 ToolExecutionContext；不允许 external paths 时 Runtime 强制 `workspace_only=true`。多个
write-capable subagent 可并发派遣；写工具冲突作为各 subagent 的普通 ToolResult 返回，由各自模型在现有循环中
调整，不把工具权限提升为调度概念。Delegation constraints 只持久化 workspace 与 external-path 这类独立运行
约束；工具名、write、network 和 MCP 能力只由冻结的 EffectiveToolRefs 表达。

Local files 与 SQLite 使用同一 Delegation repository 契约。进程恢复先由现有 Session recovery 把失去 live job 的
active Run 转为 recoverable，再由 `AgentRecoveryService` 双向核对 child Session、Delegation 和 child Run provenance。
Delegation 是 root-local 聚合：运行中的 child 归属查询必须同时携带 `root_session_id`，主 Session 热路径不查询
Delegation；全局恢复逐 root 隔离持久化错误，任一旧 root 的不兼容记录不得传播到其他 Session。
只有唯一可归属的半提交 child Run 会补齐 relation；identity、冻结 policy 或 definition contract 无法证明一致时，
relation fail-closed 并产生 Host-neutral startup diagnostic，原 Session/Run/Delegation 证据全部保留且不会自动重放。
AgentService 随后从 child Run 终态重建缺失结果、重试未完成交付并重新挂接 parked parent wait；这些诊断并入
`LocalApplication.startup_report`。旧 Delegation 只与 parent Run 冻结目录和 child Run contract 对账；当前可编辑
Agent config 的正常 next-run 漂移不会改写或阻断历史 child。

Delegation 更新使用 revision compare-and-swap；仓储以类型化 `DelegationRevisionConflictError` 区分并发竞争与真实
持久化故障。AgentService 为每个 delegation 保留 process-local 生命周期锁，串行化 result finalize/delivery、interrupt、
follow-up 与 close。结果 CAS 的唯一赢家发布 `agent_result_ready`；竞争失败者只接受同一 child Run 的 canonical 结果，
delivery CAS 也只接受同一 delivery identity 的已交付赢家，因此 terminal/interrupt 和消息已提交/delivery flag 未提交的
崩溃窗口不会重复发布、排队或启动父 Run。该锁不替代 durable revision，也不声称提供多进程 active scheduler。

bound parent aborted/failed 时，AgentService 并发中断直接 child，并以统一 deadline 限定等待；超时产生
`cascade_timeout`，child Run 的未知结果保持原样。根 Session 归档根据 child Run 这一执行事实源拒绝 active 或无法
判定的 descendant。Session trash 是显式的根树生命周期操作：正常路径根据 `SessionRecord.parent_session_id` 解析根与
全部 subagent；已获用户确认但 canonical 无法可靠解码时，强制路径改用 Catalog 的稳定 identity/lineage 投影，且不以
`session_kind`、Catalog health 或 canonical 可读性二次授权。正常路径对确有 live owner 的 Run 先复用 canonical abort
state transition 并等待其释放锁；强制路径直接竞争完整 scope 的锁。两者都由存储后端一次发布到同一 trash entry，删除
scope 不从 Run/Delegation 反推，因此被严格执行契约拒绝且没有 live owner 的旧记录仍可删除；live owner 未退出则
fail-closed。

`AgentTreeProjector` 只 join canonical Delegation、Session、Run、ToolBatch 和 RuntimeActivity，生成包含 edge、
usage/budget、pending interaction 及 result/delivery 状态的有界根树快照。
`RuntimeSupervisor.subscribe` 和 `AgentService.subscribe_agent_tree` 是异步初始化 API，调用方必须 `await`；
返回时已完成有界回放或初始树快照。订阅先注册 live 队列，再在线程中读取持久状态，按 sequence 合并并去重回放与
并发通知；失败、取消或关闭都会解除注册，队列溢出仍显式报告 lag。树的队列、任务和订阅归事件循环所有，
Store 查询与整批快照投影在线程完成。`subscribe_agent_tree` 不建立第二条事件总线，
而是组合 Supervisor 已有的 per-Session subscription：root relation event 负责动态发现 child，child stream 只用
activity change 触发树摘要，text/reasoning/tool delta 仍留在各自 Session stream。终态 child 退出 live subscription
但保留历史节点；慢 Host 收到 lag diagnostic 后按 canonical snapshot/revision 重连，关闭订阅不会取消 child。
交互式 Host 必须通过这一根树投影发现 descendant approval/user-input，并用 DTO 中完整的 delegation、child Session、
child Run、tool call 和 request identity 调用 AgentService 解析；不能把 child 的 per-Session sequence 混入 parent
事件投影，也不能只展示 parent 的 `waiting_child` 而留下用户不可达的 child 交互。CLI、TUI 与后续 Desktop 共用
同一 application 事实源，只在各自 Host 层决定提示形态。
AgentService 产生的关系事件与 Runtime 事件统一经过 `RuntimeEventRecorder` 的先持久化、后观察边界，不能直接写
Store 绕过 Host/Observer 边界。

`RuntimeEventRecorder` 先在线程外持久化事件，再把 Host sink 与每个 Observer 投递到彼此独立的有界 mailbox；
慢观察者不会持有跨 Session 全局锁，也不会回滚 durable event。每个 sink/observer 都有超时和脱敏诊断，关闭
生命周期会 drain 已接收事件。Host 收到的是类型化 `RuntimeEventView`，不需要重复解释任意 payload。

排队输入的提交时机是应用层契约：`follow_up` 在当前 Run 完整结束后进入新的 Run，`steer` 在当前
model turn 完整提交后进入同一 Run 的下一次模型请求。工具请求与结果是不可拆分的 turn 边界，因此
steer 不会插入二者之间。消费批量由 `queued_inputs.consumption_mode` 配置决定；`one_by_one` 每个边界
只取一条，`all_at_once` 在同一边界取出全部符合时机的消息，二者都保持符合条件消息的入队顺序。审批或
用户输入请求恢复完成后，application 必须先释放原 Run 的 session run lock，才能为 follow-up 获取新锁并启动
后续 Run；run lock 保持非重入，不能用重入掩盖事务边界错误。

Host 通过 `RuntimeService.pending_user_inputs` 读取类型化的直接用户待消费视图，不解释 Session metadata。
`RuntimeService.cancel_pending_user_input` 只允许按稳定 queue identity 撤回仍未形成 canonical message 的直接用户
输入；撤回与运行时的“仍在队列校验—canonical message 持久化—出队”共用同一 Session mutation 边界，成功撤回
的输入不能再被先前读取的陈旧队列快照消费。Host/plugin/delegation 输入不属于用户可撤回范围。
入队事件只携带 queue identity 与状态，不复制 prompt；canonical user message 持久化后，`user_message_added`
或 `queued_input_consumed` 携带稳定 `message_id`，Host 再通过 `SessionService.message` 读取唯一消息。TUI 因此
不得在提交时乐观插入对话：未消费输入只显示在队列视图，收到 canonical message identity 后才按事件顺序进入
conversation。进程恢复时同样从 durable queue 重建视图，不维护第二份界面队列事实。

队列 producer 来源是类型化的 `user | host | plugin | delegation`，与 model role、scaffold 和 semantic tag 正交。
每个输入在入队前已由提供方定义这三个消息字段；Application、队列与 Store 只校验和原样传递，不根据来源、role
或标签补全其他字段。直接用户输入显式使用 `role=user, scaffold=false`，专用 `DelegatedTaskInput` 显式使用
`role=user, scaffold=true`，后者还携带稳定 `delegation_id`，且只允许启动已准备好的 child Run。
OURO Host/Application 输入必须携带稳定 `host_source_id`，插件输入必须携带完整 Generation/contract attribution；
它们选择的 role 不会改变 producer、变成直接用户输入或取得用户授权。插件输入不能携带资源；OURO Host
input 只可携带已经由 application use case 验证并附加到目标 Session 的显式资源引用。
`RuntimeService.submit_host_input` 与 `submit_plugin_input` 共享同一入队、锁、幂等消费和 canonical persistence
边界。

Session 输入模型提供以下与具体插件无关的变化轴；Goal 对这些能力的组合见
[OURO Goal 插件](OURO_Goal插件_2026-09-02.md)：

- `SessionInputBatch` 表达必须保持顺序、原子入队并在同一安全边界消费的非空输入组；全局
  `one_by_one | all_at_once` 只能选择完整消费单位，不能拆分或交错 batch；
- batch 在 durable queue 中只增加稳定 identity 与组内顺序，不增加状态机、优先级、依赖或嵌套；
- `SessionInput` 显式携带 role、scaffold 与可选 semantic tag；三者与 producer provenance 彼此正交；
- owner-scoped coalesce key 只允许新批次替换同一 Session/owner/boundary 下尚未消费的旧控制投影，不能撤回
  canonical message，也不能跨 owner 搜索或重排队列。

这些变化由 Application 继续拥有校验、Session mutation、持久化和消费；插件只返回类型化输入意图。Goal 的状态、
预算和 activation 不进入 Core，也不能成为 Runtime 按 plugin id 分支的理由。

工具调用以一次完整模型响应为批次边界，但 Provider 不截断流式观测。流式 Provider 把供应商 chunk 逐个
规范化为 `tool_call_delta`；其中 `index` 是响应内从零开始的工具调用序号，不得泄漏供应商原生 content-block
坐标。`InnerAgentLoop` 同步产生 `model_tool_call_delta` 事件，并在响应 `done` 边界
聚合、解析和校验整批 tool calls。无法提供分片的非流式 Provider 也在 adapter 边界把完整响应规范化为一个
delta，Core 不接受完整 `tool_call` event；`done` 只表达响应结束和 usage。随后按配置选择顺序或并行执行。assistant tool-call 消息必须先持久化，tool result
按 provider 原始顺序提交。

会话批准模式保存在 canonical `SessionRecord` 中，取值为 `inherit`、`auto`、`approval` 或 `deny`。工具定义
通过 `permission_control` 明确最终权限的控制权，避免用两个可产生非法组合的布尔开关表达同一概念：

- `host` 是默认值。工具定义权限先由用户 `config permissions` 覆盖，再由 Core 的单一策略解析边界计算最终
  权限：`inherit` 沿用配置权限，`auto` 可放宽 auto/approval，`approval` 可收紧 auto，但配置或工具的 hard
  `deny` 是不可放宽上限；限制性插件
  `tool_policies` 最后只能提高限制。
- `tool` 表示工具定义拥有最终控制权，只允许 `permission_mode="auto"` 或 `"deny"`。用户覆盖、会话批准模式和
  Host permission override 不参与决策；限制性 `tool_policies` 仍对这类工具评估。它只免受 Host 审批模式干预，
  不能借此逃逸其他编排扩展的工具策略。

`ToolCallCoordinator` 在预检时把会话模式交给 `ToolExecutor`，最终权限和控制权写入 durable
`ToolInvocation`。对 child，parent Run 解析出的最低 permission mode 也随 EffectiveToolRef 冻结，后续配置只能收紧。
每个尚未执行的 invocation 在 handler 启动前再次评估当前 permission 和 ToolPolicy；若变为 deny 则不启动 handler，
若变为 approval 则回到同一 ToolBatchCall 的 durable approval 状态。内置、插件和 MCP 工具都通过这一边界。新增会话策略
只需扩展 Core 策略类型和解析函数，执行与入口层不承载策略分支。handler 抛错、返回非 `ToolResult`，或返回的
`tool_call_id`/`tool_name` 与当前 invocation 不一致时，`ToolExecutor` 必须在 contract 边界转换为绑定当前调用的错误结果，
不能让异常或错误身份进入消息历史。每个 Tool contract 还显式携带
`effect = read_only | state_changing | unknown` 和 `batch_behavior = compatible | exclusive`。builtin 与插件
在定义处声明 effect；MCP 依次采用用户 override、协议 `readOnlyHint` 或 `unknown`，不按名称和描述猜测。
归一化后的 effect、batch behavior 和 resumable 能力都进入 execution contract hash。工具策略只接收 canonical
identity、owner、这些归一化语义、schema 校验后的参数及 Session/Run 上下文；包含 exclusive 工具的混合批次
必须在任何 handler 执行前整批拒绝。

`ToolExecutor` 是内置、MCP 与插件工具的统一取消所有者：它竞速 Host `AbortSignal` 与实际 handler task，取消后必须等待
handler 完成资源收尾，再把调用定性为 `aborted` 或 `unknown_outcome`。异步 handler、MCP 调用和 worker RPC 通过 task
cancel 传播到底层；worker 在该路径发送协议 `cancel`。Python 进程内同步 handler 无法被安全强杀，因此必须通过同一个
`ToolExecutionContext.raise_if_aborted` 在长循环中协作退出；若它不协作，Host 不遗弃后台线程，而是持有到退出并记录
`unknown_outcome`。取消批次保留 durable ToolCall 审计，但不提交模型可见的 `tool_result`。Tool contract 不声明
脱离具体执行形态的 `cancellable` 布尔值；取消能力由 handler、transport 和进程所有权共同决定。

批次的 durable suspension 由纯 `tool_batch_suspension` 统一选择，优先级为 approval、child join、user input，
同时投影 Run status/phase 与 batch phase。preflight、并发 checkpoint、执行结束和恢复入口不能分别手写扫描逻辑。
每个 Run 复用一个 ToolCallCoordinator；它持有 Run-frozen registry 以及动态 controller scope，terminal 后统一释放。
工具 handler 可以返回
`ToolInputRequest`，以独立于审批的用户输入协议挂起 Run；其中的请求和回答都是 Core 不解释的 JSON 值。
需要根据回答继续执行的工具必须声明 resumable 并提供 resume handler；恢复仍绑定原 Catalog 与精确工具 contract，
允许再次请求输入或产生最终工具结果。非 resumable 工具保留直接把回答作为结果的单阶段协议。`AskUser` 只是该
协议的内置生产者，不被会话批准模式转换成普通工具批准。`ToolExecutionContext` 集中限制内置文件路径和宿主
检测到的 Shell cwd 只能落在 workspace 或 Host 管理的 `OURO_HOME/artifacts` 制品根目录，并在 executor 边界统一
限制结果长度；它不会放开 `OURO_HOME` 的配置、会话或插件私有数据，Shell cwd 限制也不等同于操作系统沙箱。
Shell 的 stdout/stderr 从进程启动起并发排空，并在 pipe 消费边界共享一个硬保留预算；超过预算后继续 drain，
但不保留超额内容。每个流保留独立 truncated 标志，timeout/abort 终止进程树后只做有界 EOF 等待。Builtin Shell
只负责方言包装、PowerShell CLIXML 解码与结果投影。已解析出的 shell executable 必须以 argv 直接交给
`ToolExecutionContext.run_process`；不得经 `create_subprocess_shell` 再套一层平台 shell，否则 Windows 的 quoting、
进程树所有权和 pipe EOF 会偏离实际工具进程，可能在已有完整输出后仍被错误标记为 timeout。

用户交互策略与批准策略正交保存：`SessionRecord.interaction_mode` 为 `interactive | unattended`。AFK 是
application/Host 的命名预设，原子设置 `approval_mode=auto` 与 `interaction_mode=unattended`，Core 不持久化第三个
重复布尔字段。`ToolCallCoordinator` 是唯一解释 interaction mode 的执行协调边界；`ToolExecutor` 保持 Session-neutral。
无人值守时，残余软审批以 `resolved_by=host_policy` 和稳定 resolver id 持久化后继续执行；硬 `deny` 不可降级。

工具输入恢复使用判别式 `AnswerResolution | UnattendedResolution`。请求与 answer 的任意 JSON payload 仍由工具
拥有，Core 不猜测 `null`、第一项或默认布尔值。只有 contract 声明 `supports_unattended` 的 resumable tool 才收到
无人值守 resolution；未声明能力时产生 `UserInputUnavailable`，收到 resolution 后再次提问则产生
`UnattendedInteractionLoop`。request、resolution、revision 与 provenance 在 active ToolBatch checkpoint 中先持久化，
再调用 resume handler；顺序与并行 batch 都在 resolution 归一化后决定是否暂停。Plugin SDK 与 worker protocol 传输
同一 resolution，能力字段进入 contribution/execution contract hash。

## 模型路由与 Provider 边界

持久化模型路由只有一种格式：`provider_id/endpoint_id`。

- `application/models.py` 负责列出、解析和持久化会话模型路由。
- `config` 负责 provider/endpoint 配置模型与运行参数合并。
- `providers` 负责通过构造器注册表把已解析参数构建为具体协议 adapter。
- Provider 保存供应商级连接默认值；Endpoint 保存模型 id、采样参数、能力和可选连接覆盖。

模型路由不接受 model id 或 endpoint id 短名。这样持久化值、CLI 输入和运行时解析使用同一契约，
不会因多个 provider 出现同名模型而产生歧义。
活动 Run 不冻结整段运行的模型路由。每个模型 round 在上下文准备前从 Session 解析一次路由与 reasoning，
因此运行时切换只影响下一次尚未开始准备的 Provider 请求；当前流继续由原 adapter 完成。Run 事件和 usage
仍记录每次请求实际使用的 provider、endpoint 与 model。
同一份已解析 endpoint 配置复用 adapter 与 HTTP client；配置指纹变化时重建 adapter，Supervisor shutdown
统一关闭其拥有的连接。调用方注入的 HTTP client 不由框架关闭。
当前协议类型包括 Faux、OpenAI Chat Completions 和 Anthropic Messages。配置域的协议档案集中声明默认 API
path 与连接要求，产品档案声明允许/默认协议；厂商模板只组合产品类型、协议和 Endpoint 数据，不进入 adapter
factory 分支。OpenAI 与 Anthropic 协议实现共享 provider-neutral HTTP JSON/SSE transport 和重试执行器：只在
尚未发出模型流事件时重试明确分类为 transient 的失败，开始输出后禁止重放。结构化 `response_format` 受
Endpoint capability gate 约束，重试计划通过 durable runtime event 暴露给 Host。流式请求只对 connect、write 和
连接池等待应用 Endpoint timeout；已建立 SSE 连接没有被动 read deadline，长时间模型思考由调用取消和协议终止边界管理，
不能因一段时间没有可见 chunk 被误判为连接失败。

模型思考使用四段式边界：core 的 `ReasoningRequest` 表达统一意图，Endpoint 的 `ReasoningCapability` 表达
真实能力，config 的 `ReasoningProfileConfig` 声明解析后 variant 对应的原生请求片段，provider encoder 只负责编码。
解析严格拒绝不支持的开关和 effort，不在厂商等级之间近似。OpenAI 协议解码思考文本时同时接受
DeepSeek 风格 `reasoning_content` 与 OpenRouter 风格裸 `reasoning` 两种响应字段（流式 delta 与非流式
message 一致，`reasoning_content` 优先），续接回放统一规范化为 `reasoning_content`。可展示 reasoning
与工具续接状态分开建模；
续接状态使用路由绑定的 `ProviderContinuationArtifact`，OpenAI-compatible 只回放声明过的
`reasoning_content` 文本，Anthropic 只在工具续接时原样回放同 provider/protocol/model 的签名 thinking blocks。

## 消息、工具与上下文

`MessageRecord` 使用类型化字段表达工具关系：

- `role` 是封闭的 `system | user | assistant | tool_result` 模型身份枚举；
- `scaffold` 独立标记消息是否由 Harness 有意构造和注入，任何 role 都可以取任意 scaffold 值；
- `semantic_tag` 是独立、可选的模型可见语义标签，不存在默认推断；
- assistant 工具请求写入 `tool_calls`；
- tool result 关联写入 `tool_result`；
- 可展示思考写入 `reasoning_content`，协议私有续接状态写入 `provider_continuation`；
- `metadata` 只保存非结构化附加信息，不保存工具请求、关联身份或思考续接状态。

这三个消息属性统一由消息提供方定义。Core、Application、queue persistence 和 Provider adapter 不从角色、来源、
标签或正文猜测 scaffold，不自动添加标签，也不重写 role。

一个 assistant 工具请求及其结果共享 `turn_id`。压缩以该模型回合为原子帧，不能把请求和结果拆开。
没有模型回合身份的普通消息按用户请求分组；不完整工具交换及其后续恢复上下文作为受保护后缀。

`ContextPreparationService` 负责把 canonical messages 投影为模型上下文，应用 Skills 指令、压缩摘要、
snapshot-bound Context Provider 和 token 预算。Context Provider 在模型请求构建前返回带 owner 的类型化 fragment；
fragment 默认只参与本次模型请求；声明 `persistence="message"` 时，Application 必须先通过 `RunLifecycle` 将它以
提供方声明的 role/scaffold/semantic tag 写入 canonical history，并记录 plugin、provider、generation、model round
和幂等 delivery key，
成功后才能调用模型。同一 Run/model round 的重试不能重复落盘。optional provider 失败时省略自身，required
provider 失败时阻断本轮，不能借用 Observer 修改语义。canonical history 永不被压缩覆盖；`CompactionRecord`
通过 message id 前缀和 digest 验证摘要来源。

压缩策略任务由 `ContextPreparationService` 统一拥有：它竞速 Run 的 `AbortSignal` 与策略 task，中断一旦可见即成为
terminal 结果，不能继续尝试 fallback；策略 task 必须完成取消和资源收尾后，Run 才能进入 `aborted`。异步 SDK handler
和 worker RPC 通过 task cancel 传播到底层；进程内同步 handler 可选择接收 Host-owned `CancellationContext` 并在长循环中
调用 `raise_if_aborted`。同步代码无法被安全强杀且不协作时，Host 保留线程所有权直至其退出，不激活迟到的压缩摘要。

Context Fragment 还可声明 `target="system_prompt"`。这类请求级片段在基础 system prompt 和 Skills 之后稳定追加，
必须保持 ephemeral，不创建 canonical message；提供方声明 `semantic_tag` 时，Core 将原始正文投影为与 message
target 相同的 semantic envelope；未声明时保留原文。两者都进入统一 token 估算、请求快照和 ProviderContext digest。
Context Provider call 同时携带本次 Session 中 Agent 的 workspace。

内置 `dev.ouro.agent_context` 通过两个相互隔离的 Context Provider 实现这一契约：`agent-instructions` 在每次
请求中发现并按用户级、Git 根到 workspace 的顺序拼接标准 `AGENTS.md`；`runtime-facts` 保持原系统环境信息
并以更高排序值留在末尾。加载器只拥有静态操作准则，不接管 `MEMORY.md` 的记忆生命周期、`SYSTEM.md` 的
整段替换语义或 `SKILL.md` 的渐进加载。`PluginContext.host_home` 由 composition root 显式提供配置后的
`OURO_HOME`，避免 builtin 从 artifact 私有路径反推 Host 布局。

脚手架正文以原文持久化；构建统一 ProviderContext 时，Core 对 message 与 system-prompt fragment 使用同一个
semantic envelope renderer，仅把显式且经过校验的 `semantic_tag` 投影成 `<semantic-tag>...</semantic-tag>`。
提供方声明标签语义但不手写包络。正文中只有可能改变当前同名包络边界的标记会转义，其他内容保持原样；标签
只能使用小写字母、数字和连字符，且不能冒充模型角色。Context Fragment 可以选择标签，使运行时提醒、插件上下文、
Goal/Plan 状态和子智能体消息在不改变协议角色的前提下保持可辨别语义。包络参与 token 估算与 Provider 内容 digest。

模型产生无工具的候选完成后，`InnerAgentLoop` 在完成 Run 前评估同一 Catalog 的 Turn Policy。策略只能返回
`allow`，或返回带 feedback 的 `continue`；后者把候选回复和带 provenance 的 scaffold feedback 持久化到同一
Run，再进入下一模型轮次。策略异常、超时或非法输出 fail-closed 并暂停 Run。跨 Run 的 Continuation Policy 与此
保持分离：前者约束当前 Run 的轮次收束，后者只消费终态 `RunOutcome`。

用户附件采用同一投影原则：canonical message 只保存 `resource_refs`。ResourceService 在 Run/Message 提交前
校验 Session 归属、digest、size、媒体类型和 Endpoint 能力，再把受支持文本或图片仅注入本次模型请求；附件
内容参与上下文预算与压缩，但不回写历史。

`MessageRecord` 到统一 Provider 的投影以 `ModelMessage` 为硬边界。后者只包含 role、模型可见 content、语义标签、工具调用/
结果关联和路由绑定的 continuation，不携带 message/session/run identity、metadata、resource references 或仅供 Host
展示的 reasoning。这里的“真实 Provider 上下文”特指 `RuntimeAdapter` 交给统一 `Provider.stream` 的
`system_prompt`、`messages` 和 `tools` 三项，不是任何厂商 HTTP endpoint 的最终 payload；厂商 codec 在该边界之后
继续负责协议编码。
OpenAI-compatible codec 在完成语义标签的模型可见 envelope 投影后，将独立 `system_prompt` 与所有 system role
消息按原顺序合并为唯一的首条 system message；压缩摘要等脚手架消息的标签和正文均不得在此归一化中丢失。

每次上下文构建只计算一次类型化 `ContextMetrics`：发送前的 input token 估算、固定部分、模型窗口、预留输出、
可用 input budget、剩余量和占用率。估算用于预算与实时状态；Provider `done` 后单独补记供应商报告的 input token，
两者不互相覆盖。内置 estimator 对文本、工具 schema 和 continuation 计数；图片使用有界保守值，不把 data URI 的
base64 字节错误当作文本 token。

请求审计采用 write-through latest snapshot。上下文准备完成后，在模型请求前原子替换 Session 的最新
`ContextSnapshotRecord`；记录保存 ephemeral 注入、压缩/恢复后的 source messages、工具、指标、路由和实际
Provider 内容 digest。资源 blob 不复制进快照，审计内容查询通过不可变 resource reference 还原后校验 digest。
`SessionService.context_status/context` 是最近请求事实的唯一查询边界，供 `/context`、`session context`、运行活动、
Provider usage 和诊断共同使用。status 只读取指标；full/content 从快照还原统一 `ProviderContext` 并校验 digest，
因此会包含模型实际收到的请求级 ephemeral Context Provider 注入。查询不能从 canonical history 重新推演
prospective context，也不能为了展示而执行插件。没有请求快照时明确返回空状态。手动压缩不会伪造一次 Provider
请求；新摘要只在下一次真实请求准备时进入替换后的快照。

## Provider Usage 与全局费用账本

Provider adapter 只在 `done` 边界产生类型化 `Usage`，数据源必须是供应商响应。`core/context.py` 的 token
estimator 属于上下文预算域，只负责溢出判断和压缩触发；它与费用账本没有回退、同步或推导关系。

`UsageService` 把普通模型回合和压缩模型请求统一写入 `UsageLedger`。每条有效记录绑定 provider、endpoint、
model、Session、Run、用途、请求身份和接收时间；Run 通过 `usage_entry_ids` 保持幂等聚合。压缩在收到
Provider `done` 时立即记账，因此即使后续摘要格式校验失败或路由回退，已经发生的供应商调用也不会漏记。

本地实现使用 `OURO_HOME/billing/usage.jsonl` 追加事件和独立跨进程写锁。`record` 保存供应商事实，
`replace` 保存带原因的人工修订，`reset` 在当时的有效视图上选择性失效匹配记录；查询重放事件得到当前
有效视图，历史审计事件始终保留。入口层只解析过滤条件和格式化输出，日期/路由过滤、汇总与修订规则位于
应用层，文件和锁细节留在基础设施层。
Local ledger 的输入、entries 与 events 都在公开边界深拷贝；调用方修改 metadata 不会反向修改 append-only cache。

## 本地持久化

`SessionRepository` 是 canonical 后端契约，`SessionCatalogStore` 是可丢弃查询投影契约；二者都不暴露
Path、初始化、文件索引或 ORM。默认 `LocalSessionStore` 在 `OURO_HOME` 下保存可读文件：

```text
OURO_HOME/
  layout.json
  config/config.json
  skills/
  locks/sessions/
  locks/session-mutations/
  locks/billing-mutations.lock
  billing/usage.jsonl
  artifacts/
    <plugin-id>/
  sessions/
    index.json
    <session_id>/
      session.json
      messages.jsonl
      events.jsonl
      compactions.jsonl
      context.json
      runs/
      resources/index.json
  resources/
    records/<resource_id>.json
    blobs/sha256/<digest>
    index.json
    staging/
  trash/sessions/
```

`SQLiteSessionStore` 是同一契约的第二实现，默认数据库位置为 `OURO_HOME/sessions.sqlite3`。它使用标准
`sqlite3`、WAL、外键和显式事务，事件 after-sequence 查询由索引支持；表结构只存在于 adapter 内。高频模型 delta
保持逐事件原子提交和跨连接可见性，但使用 WAL `synchronous=NORMAL` 避免每个分片独立同步；下一非 delta 事件以
`FULL` 提交并建立该前缀的 durable boundary。该策略与文件事件日志的分组 fsync 语义一致，不影响其他 canonical
mutation 的 FULL durability。
`LocalApplication.build(..., session_backend="sqlite")` 可选择该实现。Host 的选择规则集中在
`ouro.deployment.resolve_session_backend`：显式参数优先于 `OURO_SESSION_BACKEND`，默认使用 `files`。CLI 的
交互、run、session、resource 与审批入口都接受 `--session-backend files|sqlite`，命令层只透传选择值，不包含
后端分支或存储实现。该部署参数不写入 `config.json`，避免在尚未选定存储时反向依赖存储内配置。

选择后端不等于迁移数据；文件和 SQLite 数据集保持隔离。`import_sessions_to_sqlite` 在一个目标事务中复制、
逐 Session 验证并在失败时整体回滚；文件后端继续作为可读实现和导出来源。

`ouro.local_io` 与 `ouro.local_locks` 是共享本地基础设施，提供原子替换、短 mutation lock 和带 owner diagnostic 的
进程锁；Resource、Session、Config、Billing adapter 只依赖这些顶层模块，不跨 feature adapter 借用实现。
`tests/architecture/test_boundaries.py` 用显式 allow-edge matrix 递归检查全部 `ouro/**` import，包括相对 import；
新增顶层 package 或依赖边必须经过架构审查并更新矩阵。

`session.json`、messages、events、runs、compactions、Harness 版本和提交回执是 canonical Session 事实；`context.json` 是可替换的最新
Provider 请求快照，SQLite 使用对应的 `latest_contexts` 单行记录；`sessions/index.json` 是可重建
查询投影，SQLite 使用独立 `session_catalog` 投影表。`read_catalog` 只读索引自身，不抢锁、不扫描或校验 canonical
Session；缺失/损坏明确要求显式重建。Canonical mutation 后只重算受影响 Session 的有界 `latest + count` 条目，
索引失败不得破坏 canonical 写入，并通过 diagnostic 暴露。全量 canonical 扫描只属于显式 maintenance 或版本迁移，
不能隐藏在会话列表查询内。文件实现构造单条投影时最多读取 64 KiB 消息尾部并按 `last_run_id` 读取单个 Run；SQLite
用单 Session 聚合查询更新投影。Catalog 不含完整 transcript，预览忽略显式 `scaffold=true` 的消息，文本查询只
覆盖 title、160 字符最后消息预览、workspace、model 与 tags。未来全文搜索必须使用独立、可重建且可关闭的索引能力。
影响后续会话行为的原生和插件状态统一进入 Harness：Session 持有当前版本指针，每条消息记录其之前的状态版本。
状态按稳定 owner 隔离；SDK 和 worker 只能通过调用范围内的状态视图提交变更提案，应用层把状态、消息及相关
队列/运行变化归入同一个 `SessionCommit`。File layout 8 以持久化决定和回执恢复，SQLite schema 6 以事务提交；
恢复只应用已保存的决定，不重调插件。撤销恢复消息前的状态并推进 history epoch，旧运行和事件保留审计用途。
branch 对完整保留版本闭包应用 `copy/reset/reject`；快照、导出和后端转换保留状态与回执，trash 随 Session 封存。
`billing/usage.jsonl` 是独立的全局 canonical 账本，不随 Session 归档或进入回收站而删除。
messages/events JSONL 同时提供稳定 byte cursor 分页端口；增量读取不依赖完整 `SessionRecord` 装载，append 后
已有 cursor 仍可继续使用。

独立持久化的核心 record 使用封闭的当前 `schema_version` 类型，并在 File、SQLite、Resource 和 Billing adapter
的真实读取入口经过同一个 versioned decoder。payload 必须显式携带版本；缺失、非整数、旧版本和未来版本均
产生 `MigrationRequiredError`，不能由 Pydantic 默认字段静默补全。整体 `data_layout_version`、SQLite schema
version 与插件 manifest/state schema 各自独立演进，不共用数字或迁移规则。

Provider text/reasoning delta 只追加到文件后端的 `events.jsonl`，由下一个非 delta 事件执行组提交；状态边界
事件仍同步落盘。快照只在消息提交和生命周期状态转换时写入。SQLite 在同一语义契约下使用数据库事务。
所有 Store 读取均无副作用；`SessionRecoveryService` 是显式 application command，从 durable messages、run
状态和最后模型轮次事件重建未完成输出，不重放结果未知的外部副作用。

`layout.json` 的 `data_layout_version` 标识整套本地数据契约。遇到不兼容版本时初始化必须抛出
`MigrationRequiredError`，不能在加载过程中猜测字段或隐式改写数据。

每个 session 同时只允许一个 active run。`RunRecord` 是执行状态事实，`SessionRecord.status` 与
`active_run_id` 是可恢复的查询投影；显式恢复命令会校准悬空引用、跨存储写入中断和不可继续的人机等待状态。
长生命周期 session OS lock 表示 active run 的进程所有权；独立的短生命周期 mutation lock 只覆盖
单次 canonical 读改写、JSONL 追加和事件序号分配，两者不能互相替代。锁文件仅用于诊断。

全局 resource record/blob 是 ResourceStore 的 canonical 数据；Session 到 resource 的引用只由
SessionRepository 拥有，文件实现保存 Session 子记录，SQLite 实现保存引用表。Resource adapter 不读取或
推断 Session adapter 的目录/表结构。`resources/index.json` 只是 blob 元数据的可重建投影。
资源导入先 staging 并计算 SHA-256，再原子发布。分支的消息与资源引用在同一 Session staging 目录发布，
避免先出现带悬空 resource id 的分支。分支读取、资源引用校验和目标发布持有源 Session mutation lock，
因此源会话删除或资源移除必须在线性化点之后执行，垃圾回收不会删除正在复制的最后一份可达内容。

Session 的通用 `branch` 只表达 canonical history 边界：传入任意 message id 时包含该边界，传入空边界时
创建空历史分支，不限制 Host 可选择的消息角色。TUI 的 `/fork` 在会话输入框命令菜单中统一投影分支目标：首项
`Full` 复制完整当前历史，后续 `#N` 项显示对应 user message 文本，并将所选 user message 映射为其
前一个 canonical message 边界后回填为草稿。上述选择与映射完全属于 TUI 交互规则。
分支原样继承源 Session 的 `title`、`title_source` 和 `title_locked`，并通过 `parent_session_id`、
`root_session_id`、`forked_from_message_id`、`forked_from_run_id` 诚实记录 lineage。框架不向标题拼接“分支”等
展示标记；Host 是否以及如何呈现 lineage 属于前端策略。
分支只继承 active compaction lineage 中对新历史仍然可用的前缀：`covered_message_ids` 必须精确匹配新分支
canonical prefix，且 `history_boundary_message_id` 也必须位于分支内。复制时统一重建 message/compaction identity、
previous 指针和 source digest，并与 Session、资源引用、扩展状态在同一个新 Session 快照中原子发布；最新
Provider 请求快照不是新分支实际发生过的请求，因而不复制，TUI 的初始上下文占用由继承的 active compaction
metrics 加上压缩关联边界之后的分支消息增量提供，下一次真实模型请求会生成该分支自己的 context snapshot。

## 配置契约

配置集中保存在 `config/config.json`，由 `ouro.config` 的类型化 manager 读写。各分区只接受当前权威字段：

- 系统提示词：`prompts.system`；
- Provider：`providers.default` 与 `providers.items`；
- Endpoint：每个 provider 的 `endpoints`；
- 工具执行：`tool_execution`；
- 运行预算：`run_budget`；
- Agent：`agents.revision`、`agents.definitions` 与 `agents.runtime`；
- 排队输入：`queued_inputs`；
- 压缩：`compaction`；
- Skills：`skills`。
- MCP server：`mcp.servers`。

Provider 配置同时持久化实例 `provider_id`、产品配置 `provider_type` 和线协议 `protocol`。产品档案负责约束
允许/默认协议，adapter factory 只按 `protocol` 分派。无效结构必须抛出 `ConfigError`，不能静默降级、推导
缺失协议或猜测另一种格式。凭据通过 `CredentialRef` 进入 provider factory，业务代码不直接读取环境变量。
Endpoint 的 `reasoning.capability/profile` 是同一权威配置的一部分；profile 与 `request_options` 的字段所有权
冲突、协议无法保存的 continuation 以及运行时不支持的 effort 均在 HTTP 前失败。
CLI 与未来 Host 通过 `ConfigurationFacade` 的类型化 DTO/query/command 访问这些分区，包括 MCP；Facade
只暴露凭据 configured/missing 状态，并报告配置变更的生效范围。所有 JSON 配置 command 在同一跨进程
文件锁内完成 read-validate-write，避免 CLI/TUI/Desktop 并发修改不同 section 时丢失更新。

`agents` 使用一个 expected revision 保护 definition 与 runtime policy，避免两个 Host editor 交叉覆盖。runtime
只接受 `max_depth=1`、bound lifecycle 和 agent id allowlist；LocalApplication 在 composition start 读取，
变更从 next runtime 生效。definition 由 AgentDefinitionService 管理并从 next Run 冻结；root budget
继续读取通用 `run_budget`，child default budget 继续使用 AgentDefinition 的 `RunBudgetPolicy`，不增加 Agent 专用
预算引擎。allowlist 过滤后没有可用 definition 时，Run overlay 不注册 SpawnAgent，但保留管理既有 child 的其他
控制工具。

## CLI 契约

CLI 命令使用资源层级表达职责：

- `provider add/update/replace` 分别表达 Provider 创建、同类型更新和完整替换；
- `provider endpoint set` 只管理 endpoint；
- `provider endpoint set --reasoning-preset/--reasoning-config` 为内置或自定义模型声明思考契约；
- `provider templates` 查询类型化的只读厂商模板目录；
- `provider add <id> --type <type>` 统一创建 Provider；内置厂商类型原子装载模板参数与 Endpoint，compatible
  类型创建空 Provider 并由 endpoint 命令补充模型；同 id 冲突提示显式使用 `update` 或 `replace`；
- 内置厂商的 `provider update` 以持久化模板基线做三方合并：未修改模板值跟随升级，用户修改、删除、未知
  Endpoint 与同名冲突保留并报告；`provider replace` 按新类型完整替换；
- 内部 Faux Provider 不进入用户侧目录、默认展示或连接检查；
- `provider check` 负责连接检查；
- `mcp list/show/set/remove` 管理 MCP server 配置，`mcp check` 执行一次临时连接检查；
- `session compact` 负责手动压缩；
- `session context` 读取最近 Provider 请求的指标，`session context --content` 显式读取同一请求的统一
  Provider 内容；
- `session messages/events` 通过 cursor 和 limit 增量读取历史；
- `resource import/list/show/export/remove` 管理 Session 资源；
- Interactive `/attach`、`/attachments`、`/detach` 管理只属于当前 Session 下一条用户消息的 composer
  attachment state；提交仍统一进入 `RuntimeService.run(..., resource_refs=...)`；
- Interactive `/skills` 从 `RuntimeService.available_skills()` 查询当前扩展 Catalog，`/skill <name> [task]`
  只把终端语法适配为 `SkillInvocationRequest`，随后与普通用户输入共用 `RuntimeService.run`；
- `agent definition list/show/tools/create/update/delete/copy` 通过 provider-independent composition 管理定义；
- `agent list/show/spawn/wait/send/interrupt/close/tree/interactions` 通过 LocalApplication/AgentService
  管理 durable subagent；
- `config agents` 使用 expected revision 配置 depth 和 agent id allowlist；
- `run --resource` 将已导入资源附加到本次输入；
- `skills remove` 负责移除 OURO 管理的 Skill。

命令入口不得实现运行规则。跨 Host 可复用的查询和命令进入完整、内聚的 application service
（SessionService、ResourceService、UsageService、RuntimeService、ConfigurationFacade）。这些 façade 在构造时即具备
完整依赖，不以运行期“缺少某项能力”表达半装配状态。MCP CLI 只适配参数和格式化输出；原子更新、transport 字段重置、
完整校验和脱敏公共视图都由 `ConfigurationFacade` 编排。
Agent CLI 同样不读取 config/canonical 文件，也不导入 AgentService 实现。短生命周期 CLI 从 completed parent Run
的冻结目录进行 unattended Host spawn，并在进程退出前等待 terminal；模型派遣仍绑定 active parent。长期 Host
直接保持 LocalApplication 与 subscription，可使用同一 application service 对 active parent 派遣。CLI spawn 固定
notify-only，避免启动它无法持续拥有交互/subscription 的 parent delivery Run。
Interactive 的 attachment draft 同样只属于 CLI adapter。它保存待提交的 `ResourceView` 与稳定顺序，
不保存图片字节、不编码 Provider payload、不替代 Session resource reference；只有 `RuntimeService.run` 接受输入后
才清空，能力或资源错误会保留 draft 供切换 Endpoint 后重试。Session 切换会清除旧 Session 的待发送选择。

显式技能激活同样遵守 Host adapter 边界。CLI 不发现或读取 `SKILL.md`，不拼接模型提示词；Application 在
prospective Run 的 `ExtensionCatalogLease` 中解析名称，校验 `enabled` 与 `user_invocable`，再按 Catalog 记录的
精确路径加载。激活结果以 `SkillActivationContent` 固化名称、来源、位置、基础目录、正文和内容摘要，并与可选
用户任务共同作为 user message 持久化。Provider 投影才把该类型块转为带边界的用户角色文本，因此
`disable_model_invocation` 不会误阻止用户显式选择，技能正文也不会被提升为 system 指令。

`/skill` 是单次 Run 输入，不建立 Session 级粘性状态；无尾随任务也合法。active Run 接收该输入时只允许
follow-up queue，不允许 steer。队列在接受时保存完整激活快照和 Catalog contract，Prompt Policy 只获得有界的
技能身份与摘要；恢复、热更新和后续消费不重新读取正文。当前 Agent Run 的所有 frame 在压缩时受到保护，避免
激活说明在同一 Run 尚未结束时被摘要替换。技能激活不解释 `allowed_tools`，也不修改工具目录、Tool Policy、
审批或权限。

每次完成的 Provider 调用把路由、请求起止时间和可选 reasoning 结束时间固化为类型化
`ModelResponseRecord`，并与对应 assistant `MessageRecord` 在同一消息提交边界持久化。一次 Run 可以包含多条
assistant 消息，因此工具续跑、turn policy 续跑及运行时切换 Endpoint 后的每轮模型调用都有独立记录；
`RunRecord.started_at/ended_at` 仍是运行总耗时的权威事实，不复制每轮思考状态。Host 实时展示消费既有事件，
重载则只连接消息与轻量 Run 历史，不为展示耗时回放高吞吐 text/reasoning delta journal。

Interactive 的动态终端效果同样只属于 CLI adapter：`TerminalStatusLine` 管理 MCP/压缩等单一状态行，
`TerminalStatusRegion` 管理按 tool call identity 固定的工具行，`InteractiveOutput` 把既有 Run 事件投影为
`mcp_connection`、`compaction`、`tool_input`、`tool_execution` 语义。Core/application 不感知 spinner 帧；
真实 TTY 对工具参数生成、执行与结果进行原位重绘，非 TTY 则让每个工具只输出最终稳定行。工具参数 delta 保持
durable 事件与完整累积；参数摘要仅在等待审批时进入工具行和审批提示，批准、拒绝或开始执行后隐藏，避免把
不可操作的信息持续留在终端中。

循环终端在提交用户输入前启动本地单调时钟；`run_started` 表示请求与上下文准备阶段，
`model_request_started` 表示等待 Provider 阶段，首个 reasoning/text/tool-call delta 结束等待。状态行动态显示
当前阶段秒数和本轮上下文估算，并在响应开始时稳定输出总等待及分阶段耗时；自动压缩作为独立阶段计时，手动压缩不伪装成
模型等待。

## 扩展边界

- Observer 失败由 `RuntimeEventRecorder` 隔离并转为脱敏事件，不允许破坏 durable run；每个 registration 的
  mailbox、timeout 和 scope isolation 相互独立。
- 插件只能通过 owner-aware candidate Catalog 贡献工具、限制性 tool policy、Prompt Policy、Observer、Host-neutral command、
  上下文 provider、turn policy、压缩策略、Skills、MCP、Run continuation policy 或受监督后台服务。manifest 的
  `official` 自报不构成信任；有效 provenance 由安装来源传入，capability/permission 必须覆盖实际贡献。
  安装默认禁用，enable/select/reload/rollback 显式接受目标 digest；启用后插件工具权限与内置工具使用相同语义，
  不按来源降级，运行时 SDK 贡献不得偏离 Manifest 契约。
- 插件命令使用 `<plugin_id>:<name>` 稳定 identity 和类型化 request/result；CLI/TUI 可映射为 slash command，
  Desktop 可映射为 action，但 core 不定义 UI extension DSL。当前 Interactive 中 builtin 优先，canonical
  `/<plugin_id>:<name>` 始终可用，唯一 local name 才获得 `/<name>` 短别名。Manifest 的
  `requires_session=true` 显式声明 handler 前置条件；Interactive 在首条 Session 级命令前懒创建并绑定 Session，
  无状态命令不触发该行为。参数型命令可在 Manifest 声明 Host-neutral 的单 token `argument_options`；这是命令契约与
  `usage` 的结构化补充，由各 Host 自行映射为补全或选单，不把 TUI 状态和渲染组件带入插件 API。
- Session 级长期控制统一由 `SessionControlCoordinator` 仲裁。插件以 `session_controllers` 声明 canonical controller、
  `domain + exclusive|shared` claims 和生命周期，Command/Tool 只返回 transition intent；Host 不读取 Plan、Goal 或
  私有 state 来判断冲突。Tool/Context/Prompt Policy/Tool Policy/Turn Policy/Continuation/Observer 可用 `active_when` 绑定 controller，
  Runtime 每个模型轮次冻结 active controller refs，避免切换期间权限放宽。`/control` 是 Host-owned 状态、正常释放和
  force release 逃生口；activation-bound pending interaction 与 queued continuation 随 release 取消。
- 插件不得取得 `RuntimeService` 或 `SessionStore`。获得 `sessions.write` 与 `background.run` 后，command 可以
  返回带独立 producer provenance/model role 的类型化 `SessionInput`，continuation policy 可以在终态 Agent Run 后返回
  `continue/complete/pause/fail/ignore`。`RunContinuationService` 负责冻结 generation、冲突处理、幂等入队和
  durable checkpoint；`run_finished` Observer 仍是 fail-open、非阻塞通知。
- SDK 可提供绑定当前 plugin identity 的窄 Session state view；它只登记版本化 JSON 状态、branch policy 和
  scaffold projection tags，不提供任意 Session 查询或通用数据库能力。候选 Generation 在正式发布前不能写
  canonical Session。Goal、Plan、Todo 使用该入口，旧插件私有 Session JSON 通过显式 migrator 一次性迁移，
  运行时不保留 fallback。
- 插件工具可选接收 Host-owned、request-scoped `ToolExecutionContext`，复用 workspace/Host artifact 路径边界与
  协作式取消语义；
  worker 得到等价 workspace 字段并通过协议 `cancel` 中止调用。`tool_policies` 对 host-controlled 和
  tool-controlled 工具统一评估，只能把最终权限提升为审批或拒绝，失败时拒绝，且
  审批修改后的最终参数以及每个尚未执行的调用都必须重新评估。`permission_control="tool"` 只隔离 Host permission
  维度，不隔离插件策略维度。
- 插件输入通过 canonical queue 进入合法边界，保存 plugin/contribution/generation/decision provenance，并原样保存
  提供方声明的 role、scaffold 和可选 semantic tag；producer 仍为 plugin，且 role 不能作为用户授权证据。旧 Run 的
  续跑决策若遇到用户已排队输入或更新 Run，会被标记为 superseded；目标插件在下一 Run 重新评估。
- `prompt_policies` 只检查 Host 路由后的直接用户提示并返回 `allow | deny`。Application 在 message、durable queue 和 Run
  之前 fail-closed 评估；user plugin 必须声明 `sessions.prompt.inspect`。允许后，直接或排队的 prospective Run 都固定
  同一 Catalog execution contract；拒绝路径不记录提示正文。
- 插件是 OURO 系统级扩展模块，来源只分 `builtin` 与 `user`。workspace/project 只作为一次请求的执行上下文，
  不提供项目插件、scope overlay 或按项目安装的插件运行时；plugin state、provenance、CLI 与 DTO 不携带
  activation scope。
- Builtin 由 application composition root 的显式 definition registry 装配，不扫描磁盘、不写入 user immutable
  store，也不伪造 install/provenance。definition registry 是 builtin identity、默认启停、依赖 contract 和公开名称
  保留的唯一事实来源；user installer、dependency resolver、application services 与 runtime 都消费该 registry 的派生视图。
- Builtin 与 user 的差异止于供应和管理操作。启用后两者进入同一个 candidate reconciliation，拥有正常
  Generation、gate、owner、Catalog projection 和 durable execution contract；可关闭 builtin 不能放入 Host baseline，
  也不新增 `builtin` runtime kind 或第二套插件 runtime。
- `PluginPackageStore.state.json` 保留 user install/activation，并另存稀疏 builtin enablement override；builtin code 随
  OURO distribution 发布，私有 data 继续使用 `OURO_HOME/plugins/data/<plugin-id>/`。没有 override 时使用 definition 的
  product default，显式用户选择跨重启保留。需要交给模型内置文件工具编辑的用户制品使用独立的
  `OURO_HOME/artifacts/<plugin-id>/`，不混入插件私有 data 或 canonical Session 存储。
- 插件系统将 package、install/provenance、activation 和 runtime generation 分层，并提供完整管理与运行闭环。
  [插件系统规格](../dev/specs/OURO_插件系统规格_2026-09-02.md)定义当前权威契约；同进程插件为 full trust，worker
  提供进程与协议边界，但不宣称 OS 沙箱。
- `PluginPackageStore` 分离 immutable code、mutable state 与 plugin data；installer 从真实 local/Git/archive
  来源生成 provenance。安装阶段只校验包、路径、schema、MCP 描述符和兼容范围，不 import 或启动插件代码；
  激活前重新验证存储树和 digest，避免被修改的“不可变”包进入执行边界。
- plugin state 内容不满足当前 schema/编码契约时，启动读取在 mutation lock 内隔离原文件并以空 Catalog 降级；
  文件系统 I/O 错误保持为类型化 persistence failure，不能触发隔离。`LocalApplication.startup_report` 投影同步插件、
  Runtime 和 Agent 恢复诊断；进程级 MCP 因后台启动而通过 Manager 的实时 record/diagnostics 独立投影。各 Host 的
  MCP 状态查询必须读取该实时投影，不得把仍在连接误报为失败。
- enable/select/reload/rollback 只接受显式目标 digest；disable 先关闭 generation gate 并发布不含受影响 generation
  closure 的新 Catalog，再异步 drain owner。配置使用包含 credential binding
  reference 的内容寻址 immutable revision，selected digest 通过 active revision id 引用；配置/选版与候选 Catalog
  在同一成功边界提交；失败时 selection、configuration revision 和 generation pointer 保持不变。
- 启用依赖图只使用显式选择的已安装 digest；digest/configuration 改变会按拓扑重建传递 desired dependant closure，
  active dependent 存在时不能禁用依赖项。不同 digest 共用 plugin data，候选 Host API 写入先进入隔离 staging，
  发布成功才提交；只有最后一个安装被移除时才允许 purge。
- `ContributionCoordinator` 只负责把 generation contribution 校验、归一化为 owner set；`ExtensionCatalog` builder
  从稳定 Host baseline 与 active generation set 构建结构冻结的 Tool、Prompt Policy、tool policy、Observer、context provider、
  turn policy、command、compaction 与 continuation registry。候选失败不会改写 baseline 或 current Catalog。
- `ouro.plugins.contribution_types` 是 Host-owned 封闭清单，把每种 Manifest capability 的 SDK、worker、prepare、
  optional、contract、resource 与 Catalog projection facet 绑定在同一记录。主流程遍历清单且不接受用户动态注册；
  Skill/MCP 是 generation-owned resource facet，只有准备成功的资源进入 contract。Background Service 唯一属于
  `activation-singleton`，其 projection 明确为空；其他 contribution 属于 Run `snapshot-bound`。
- 清单当前冻结为 13 类；每类的 builtin/example/contract 与真实 Host consumer 证据记录在 plugin spec。没有可运行
  producer 和具体语义消费者时不得新增 capability；失去消费者的开发期类型应整链删除，不保留空 adapter。
- Skill metadata 也是 Catalog 的 snapshot-bound 目录：Runtime 装配时发现的 user/workspace Skill 作为 Host baseline，
  Plugin Skill 作为 generation resource 加入同一名称空间。候选按名称拒绝冲突；每轮上下文从 Run lease 生成提示词，
  不通过 Observer 二次注入。disable 只改变新 Catalog，旧 lease 保留不可变包内的 `SKILL.md` 路径。
- Python in-process 的 canonical owned module 为 `<namespace>_plugin`（已带后缀时保持不变）；激活检查 canonical
  冲突，实际加载键为 `_ouro_plugin_<generation_id>`。插件内依赖必须放在 owned package 并使用相对 import；关闭
  generation 时删除其完整私有 module tree。需要独立第三方环境时使用 worker。
- Runtime 在直接用户提示持久化前取得 `ExtensionCatalogLease`，并把同一 Catalog 贯穿 Prompt Policy、context、model
  tool list、tool execution、Observer、turn completion、compaction 和 continuation。current pointer 仅在短同步临界区交换；旧 Catalog
  由自身 lease 自然 drain，插件 import、worker/MCP 启停、回调和 I/O 均不在 pointer lock 内。
- Catalog generation 采用显式稳定顺序：依赖始终早于依赖方，彼此独立时 user plugin 早于环境级 builtin，
  同类再按 plugin id 排序；插件清单同样先展示 user plugin。新增 builtin 的名字不能偶然改变用户插件在 Run
  metadata 或 CLI 中的位置。
- 插件生命周期 mutation 由单一 runtime lock 串行化；候选 generation set、required MCP 与 Catalog 全部成功后，
  Store 以 expected state 比较提交，并在无 `await` 的发布段打开新 gate、交换 pointer。Background Service 不进入
  Run Catalog，发布后按“旧代停止、新代启动”串行转交。
- Catalog registry 的结构在构建后冻结；Observer 的 per-Run isolation 只存在于 application dispatcher。builtin/Host 与 user
  contribution 都有 canonical identity、owner 和 contract hash；插件激活不会修改进程级 Host registry。
- `LocalApplication` shutdown 先关闭 Runtime 并释放其 generation snapshot，再关闭插件 owner 与全局 MCP；插件
  runtime 等待 lease drain 到 deadline，逾期记录诊断后继续清理，避免资源 owner 先于消费者失效。
- 本地 store、credential resolver、registry 和 runtime 的具体装配只属于 `ouro.local_application`；
  `ouro.application.plugins.PluginService` 保持 Host-neutral，不提供隐藏的本地构造入口。
- pending Tool/Approval、Continuation 和 Run Catalog 持久化 `execution_contract_hash`；摘要覆盖 release identity（user
  package digest 或 builtin contract hash）、有效
  配置修订、传递依赖锁、Plugin API/worker protocol 和全部 contribution contract；Tool 的归一化 effect、batch
  behavior 与 resumable 能力属于该 contract。恢复忽略随机 `generation_id`，但会
  复核所有稳定事实与 ToolExecutor 契约，绝不按同名工具猜测替代。
- 插件更新后，若 durable Run 的旧 digest、配置修订和依赖仍保留，runtime 可重建一个非 current generation 与精确
  Catalog；该 Catalog 只由恢复 Run 持有，不修改 selected/desired state，不启动 activation-singleton Background
  Service，lease 释放后按 owner 回收。缺包、禁用或重建 contract 不一致时恢复显式失败；durable reference 释放前
  application service 阻止移除旧 digest。
- `PluginService.scaffold/reload` 是 Host-neutral 开发用例：scaffold 原子发布经验证的最小 user package；reload 先
  并排安装 immutable candidate，只有配置、依赖和包完整性都有效时才复用 candidate activation 切换 current。
  CLI 只负责参数与 DTO 映射。
- Git source 在 checkout 前以 tree metadata 校验 portable path、文件数和字节上限；shallow/blob-filtered fetch、
  subdirectory sparse checkout 和禁用 LFS smudge 共同避免先物化范围外内容。所有 source 最终仍进入统一 package
  validation。社区 compatibility inspection 只读资源并输出四类 outcome 与显式 OURO target，不执行未知代码。
- `ouro.mcp` 是官方 MCP Python SDK 的唯一适配边界；协议对象不得进入 core、application 或 tools。stdio 与
  Streamable HTTP 使用 SDK transport；`ouro.mcp.sse_transport` 只拥有 legacy SSE 的 GET/POST 数据通道，
  并将其适配回 SDK session stream。
- 每个 MCP server 由单一 owner task 打开、监督并关闭 transport context；`start_background` 只确保 owner 已调度并
  立即返回实时 record，显式 `start` 则等待共享的首次连接结果。Manager 的 start/stop 只通过事件
  协调 owner，session stream 的连接丢失同样只发送事件唤醒 owner，避免跨任务退出 AnyIO 取消域。legacy SSE
  的读取与 POST 失败进入同一生命周期；长连接读取不承担存活性判断，统一由 owner 的有界 health ping 监督。
- MCP 工具以 `<server_id>__<remote_name>` 形成稳定 identity，通过 ToolRegistry 原子替换 projection，并继续
  经过 OURO schema、effect 归一化、权限/策略、批次和恢复边界。用户可以按 server 内的 remote tool name 显式
  覆盖 effect；override 改变会产生不同 contract hash。
- Plugin MCP 由 generation resource owner 启停：required 连接失败中止候选，optional 失败投影 degraded；只有
  connected server 生成 contract，已发现 Tool 冻结进 Catalog，server 的后续变化只在下一 generation 可见。
- `MCPRuntimeResource` 把 Manager 适配到 RuntimeSupervisor 的通用受管资源协议；Host start 只调度所有 auto-start
  server，不等待网络或子进程握手，startup records 始终从 Manager 当前状态读取。连接成功后的工具投影与重连移除
  仍由 owner 原子完成；shutdown 关闭 session、HTTP client、stdio 管道和子进程。TUI 只在自身挂载生命周期内按有界
  间隔读取这一进程内快照，并在摘要变化时重绘连接和工具计数；轮询不执行网络调用，也不拥有第二份 MCP 状态。
- TUI 输入表面只接收 Screen 的单一 resize 信号，以常数次边界更新把终端可用尺寸交给 Textual 布局系统：欢迎页
  保留百分比宽度及 48/116 列偏好边界，但视口硬边界优先；命令与审批面板只约束可用最大高度，内容测量、居中、
  滚动和选中项可见性仍由组件布局负责，不在 resize 路径遍历组件树或重算渲染内容。
- TUI 把 Application 的流式工具活动投影为 keyed tool row：参数后缀只在本层单行化并裁成固定 cell 窗口，
  正式 request 沿 source index 复用原行；执行开始后清除流窗口并恢复既有详情与计时，不建立第二套工具状态机。
- 外部 Agent Skills frontmatter 在 skills parser 边界校验；`skills` 层拥有发现、解析和按冻结元数据精确加载，
  Application 拥有显式激活、Run/Queue/Policy 编排，Core 只拥有可持久化内容块及 Provider 投影不变量，Host 只做
  输入与展示适配。

## 未来演进触发条件

只有出现独立变化轴时才新增层级：

- 第二种 Supervisor 后端或跨进程调度出现后，再拆分当前进程内调度实现；
- Desktop 配置界面直接扩展现有 `ConfigurationFacade` 用例，不另建 UI 专用 manager；
- TUI 与 Desktop 直接消费 application DTO、`RuntimeEventView`、activity snapshot 和增量 cursor，不解析后端；
- 第二种压缩后端独立演进后，拆分策略执行与上下文准备；
- 第二种资源后端出现后，再扩展 ResourceStore，当前只支持本地 immutable blob；
- 只有第二种 MCP SDK 或 transport 需要运行时选择时，才抽取通用 transport provider；client port 与独立的
  legacy SSE 数据通道模块负责隔离官方 SDK、兼容传输和测试实现。

这些边界应由真实用例驱动，不能为了缩短文件或统一命名而增加空转 service、回调层或通用 manager。

## 验收要求

每次架构改动至少验证：

```bash
uv run --frozen pytest -q tests/architecture tests/core
uv run --frozen pytest --cov=ouro --cov-report=term-missing
uv run --frozen ruff check ouro tests
uv run --frozen ruff format --check ouro tests
uv run --frozen mypy ouro
uv run --frozen python -m compileall -q ouro
git diff --check
```

pytest 将 `ResourceWarning` 与 `PytestUnraisableExceptionWarning` 视为失败。任何文件、流、连接或子进程都必须由
创建边界显式关闭，不能依赖对象析构器。同时检查依赖方向、持久化失败路径、并发锁、取消、公开数据结构和文档
是否仍与实现一致。
