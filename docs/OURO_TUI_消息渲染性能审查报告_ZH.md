# OURO TUI 消息渲染性能审查报告

- 审查日期：2026-08-05
- 审查范围：长对话历史加载、单次长思考、单次长正文/代码块流式输出、消息栏跟随滚动
- 运行栈：Python 3.12+、Textual 8.2.8、Rich 15.x
- 结论：确认存在可复现的渲染放大、字符串复制、布局放大、后台任务生命周期和滚动控制问题。本轮已完成低复杂度、框架层的主链路治理；超长历史虚拟化和未闭合 Markdown 代码围栏的增量渲染仍建议作为后续独立优化。

## 一、结论摘要

原始实现把“事件到达频率”直接等同于“终端重绘频率”：每个模型 delta 都会进入 Markdown/思考控件，并无条件调用 `scroll_end()`。这会同时造成：

1. 上千行代码输出时，Markdown 解析、语法高亮、布局与滚动请求被重复触发；
2. 思考与投影文本以不可变字符串逐段拼接，累计复制成本随输出增长；
3. 用户滚动到历史位置后，下一个 delta 立即将视口拉回底部；
4. 每个历史 assistant 消息都会创建一个常驻 Markdown 后台任务；
5. 历史消息逐条挂载，反复触发布局，打开长会话的耗时随消息数明显增长。

本轮将链路调整为：

```mermaid
flowchart LR
    A["规范运行时事件"] --> B["TUI 事件帧缓冲，最多 20 帧/秒"]
    B --> C["投影逐事件归约，文本分片线性累积"]
    C --> D["连续同类 delta 合并"]
    D --> E["Markdown / 思考控件单次写入"]
    E --> F["Textual 原生 anchor 跟随滚动"]
```

事件没有被丢弃或延迟写入规范状态；只对昂贵的呈现动作做帧级合并。工具调用、用户消息、思考与正文切换仍是强制刷新边界，因此不会破坏消息时序。

## 二、发现与证据

### P1：每个 delta 触发完整呈现链路

原链路在每个 `model_text_delta` / `model_reasoning_delta` 上依次等待控件追加，并在每次追加后安排滚到底部。即使 Textual 的 `MarkdownStream` 能在自身落后时合并输入，外层仍会逐事件执行消息循环、方法调度和滚动请求。

长代码围栏尤其明显。Textual 8.2.8 的 `Markdown.append()` 会重新构造 `source + fragment`，并从最后一个可确认完成的 Markdown 行开始解析。对于尚未闭合的 fenced code block，可确认边界可能长期停留在围栏起点，导致增长中的代码块被反复解析和语法高亮。

影响：流式输出越长，单次渲染越慢；渲染落后后又积压更多 delta，最终表现为不均匀刷新、输入响应下降和输出结束后仍需追赶。

### P1：无条件 `scroll_end()` 夺取用户视口

`ConversationView` 的新增用户消息、assistant delta、reasoning delta、工具状态和通知路径都无条件调用 `scroll_end()`。视口状态没有表达“用户是否仍希望跟随底部”，因此任何新内容都会覆盖用户的手动位置。

这不是缺少一个额外布尔标志，而是没有使用滚动容器已有的锚定语义。Textual 的 `anchor()` 已定义所需状态机：位于底部时跟随；用户移动视口后释放；再次到达底部后恢复。

### P1：流式文本存在重复前缀复制

`TuiSessionProjection` 原先通过 `assistant_text += delta` 和 `reasoning_text += delta` 累积文本；`ReasoningView` 也采用相同方式。Python 字符串不可变，持续追加会反复复制已有前缀，累计字符复制量接近二次增长。

影响：大量小 delta 比少量大 delta 更差；长思考与长正文都会放大 CPU 和临时内存压力。

### P1：Markdown 流任务生命周期无边界

原 `AssistantTurn.on_mount()` 会为每个 assistant 控件立即创建一个 `MarkdownStream` 任务，包括只读历史消息。该任务只有控件卸载时才结束。长历史和多轮工具调用会留下与 assistant 段数成正比的等待任务。

影响：任务数量、事件对象和调度扫描负担随会话增长，且资源生命周期与实际流式阶段不一致。

### P2：长历史逐条挂载并全量保留

原 `load_messages()` 逐消息 `await mount()`，使 DOM 变更和布局提交被重复执行。控制器又会读取会话的全部消息，通用 `VerticalScroll` 不提供消息级虚拟化，因此 DOM 数量、Markdown 控件数量、解析成本和内存仍会随完整历史线性增长。

本轮已消除逐条挂载，但“全量读取 + 全量 DOM”仍是超长会话的剩余瓶颈。

### P2：思考控件仍需替换完整可见文本

思考流不解析 Markdown，这是正确的成本控制；但 `Static.update()` 仍需接收当前完整文本。帧级合并已经显著降低调用次数，然而超长思考在每个渲染帧仍会重新生成完整可见文本。

这是 Textual 普通静态控件的能力边界。只有在真实测量仍显示它占主导时，才值得引入“已完成行增量存储 + 当前行更新”或虚拟纯文本控件。

### P2：持续过载时 UI 事件缓冲尚无显式上限

帧缓冲选择保留每个规范事件，以保证投影状态和诊断完全一致。如果提供方长期产生事件的速度高于 Markdown 呈现速度，事件 sink 会快速返回，但 UI 所有的待呈现列表会继续增长。通常模型吞吐和 `MarkdownStream` 的内部合并足以限制该窗口，但它尚未形成可验证的内存上限。

不建议简单丢弃事件。若聚合指标确认存在持续积压，应在 TUI 适配边界用带序列终点的 typed delta batch 合并相邻正文/思考事件，同时保留所有结构事件；投影恢复仍以规范持久化事件为准。

## 三、本轮已落地的优化

### 1. 帧级事件呈现

`OuroTuiApp` 将到达事件先放入 UI 所有的缓冲区，按 50 ms 间隔唤醒呈现，即呈现上限约 20 帧/秒。显式运行结果同步会立即排空缓冲，不额外等待计时器。

设计保证：

- 规范事件仍逐个进入投影，序列去重、活动状态和诊断行为不变；
- 只合并相邻、同类型的思考或正文片段；
- 用户消息、工具状态变化、思考/正文切换会先排空前一段；
- 运行完成、失败、中止或暂停是立即呈现边界，不等待下一帧；
- UI 消费变慢不会阻塞运行时事件 sink 回调。

### 2. 线性文本累积

投影文本改为分片追加、按需拼接并缓存；赋值接口保持不变，运行结果恢复路径无需特殊兼容逻辑。思考控件也采用分片累积，避免追加动作本身复制完整前缀。

### 3. 原生锚定滚动

消息栏启用 Textual `anchor()`，并移除所有新增内容路径上的强制 `scroll_end()`：

- 初始打开会话时位于底部并自动推进；
- 用户向上滚动后保持当前位置，流式输出继续但不夺取视口；
- 用户重新滚到底部后自动恢复推进；
- 切换/重新加载会话时按产品原行为从底部开始。

### 4. Markdown 流的明确生命周期

`MarkdownStream` 只在 assistant 首次收到流式文本时创建；在工具轮次边界、运行完成/失败/中止或控件卸载时停止并排空。历史消息不再创建空闲流任务。

### 5. 历史消息批量挂载

历史记录先构造有序控件列表，再通过一次 `mount_all()` 挂载。用户/assistant 交替顺序由回归测试保护，避免批处理引入重排。

## 四、性能测量

以下是 Windows 本机、100×32 headless Textual 视口下的诊断性微基准；它用于比较渲染放大，不是跨机器 SLA。

| 场景 | 原实现 | 优化后 | 说明 |
|---|---:|---:|---|
| 300 行 fenced HTML、302 个突发 delta | 3.468 s | 中位数 0.148 s | 优化后含事件归约、帧合并、Markdown 最终排空；3 次为 0.148/0.313/0.148 s |
| 1000 行 fenced HTML、约 31K 字符突发 | 未单独记录 | 0.283 s | 1002 个 delta，经一个呈现批次完成 |
| 200 条含 Markdown 的历史消息 | 3.166 s | 约 1.2–2.9 s | Textual 调度波动较大，只能确认逐条布局已消除，不能据此承诺固定提升比例 |

突发测试展示的是最容易触发放大的边界。真实模型若以较慢速度持续输出，UI 会按最多 20 次/秒更新，而不是把整个响应合成一次；因此实时可见性被保留，实际收益取决于 delta 频率、代码块大小和终端宽度。

## 五、验证结果

已增加或扩展以下行为测试：

- 位于底部时，新内容自动推进；
- 用户滚动到历史位置后，新内容不改变视口；
- 用户重新到底部后恢复自动推进；
- 200 个运行时正文 delta 在一个事件突发中只触发一次 Markdown 写入，投影内容完整；
- 批量历史挂载保持 user/assistant 原始顺序；
- 历史 assistant 控件不创建 Markdown 流任务；
- 原有“首段思考及时可见”“思考突发不能饿死正文”“事件 sink 延迟后可恢复”测试继续通过。

最终验证：TUI 的 65 项测试全部通过；全项目 Ruff 通过；Mypy 检查 246 个源文件通过。

## 六、后续优化建议

### 优先级 A：为超长历史建立分页与视口窗口

当前剩余风险最大的场景是数百到数千条历史消息。建议从存储接口开始增加“读取最新一页/向前翻页”的稳定契约，而不是在控件层隐藏已经全量加载的节点：

1. Session 查询层提供反向游标或 `before_message_id`；
2. TUI 初次只读取最近一页；
3. 用户接近顶部时加载更早一页；
4. 前插控件后补偿新增高度，保持用户正在阅读的行不跳动；
5. 设定在内存中的消息窗口，并对已离开远端视口的页面卸载或折叠。

这样才能同时降低磁盘读取、Pydantic 解码、Markdown 解析、DOM 数量和布局成本。仅在现有全量结果上做“隐藏旧消息”不会解决底层问题。

### 优先级 B：为未闭合大代码块设计块级流式渲染

若真实负载测量表明 20 FPS 限流后，大型代码围栏仍出现明显尾延迟，建议在 Markdown 适配层实现块级策略：

- 已闭合 Markdown block 只解析一次；
- 当前未闭合 fenced block 使用低成本纯文本增量呈现；
- 围栏闭合时只对该 block 做一次语法高亮并替换；
- 最终消息仍由标准 Markdown 渲染器生成，避免维护第二套语义。

不建议复制或修改 Textual 私有 Markdown 实现，也不建议按语言堆特殊判断；优先推动可复用的 renderer boundary，或确认新版 Textual 是否提供完成块/开放块接口后再实现。

### 优先级 B：把长历史读取移出 UI 事件循环

控制器的会话读取目前是同步调用。分页契约建立后，可将每页持久化读取放入明确的异步基础设施边界，并以可取消的导航 worker 返回。不要直接零散地添加 `to_thread()`：控制器会同时更新当前 session 状态，必须先定义取消、切换竞争和过期结果丢弃规则。

### 优先级 C：增加低开销性能可观测性

建议只记录聚合指标，不记录 token 内容：

- 每个呈现批次的事件数、字符数和耗时；
- 待呈现事件峰值；
- 最老待呈现事件的等待时间；
- Markdown 最终排空耗时；
- 当前消息控件数和活跃 Markdown 流任务数；
- 会话首屏加载耗时及加载消息数。

这些指标应有采样或调试开关，避免性能日志本身成为新瓶颈。

## 七、建议的性能契约

后续可将以下约束写成基准或集成测试，而不是依赖主观观感：

- delta 接收和投影累积为摊销 O(1)，读取完整文本时才 O(n)；
- 正常流式呈现频率不超过 20 次/秒；
- 历史只读 assistant 消息不创建后台 Markdown 流任务；
- 用户离开底部后，任何 delta、工具状态或通知都不得改变其纵向位置；
- 返回底部后无需额外按键即可恢复跟随；
- 建立历史分页后，首屏工作量应与页大小有关，而不是与会话总长度有关。

## 八、风险与边界

- 50 ms 呈现窗口带来最多约 50 ms 的刻意 UI 延迟，换取稳定帧率；对终端流式体验通常不可感知，并已由“首段思考及时可见”测试覆盖。
- 全量历史 DOM 尚未虚拟化，极长会话仍会线性占用内存和布局时间。
- 未闭合大型 Markdown block 仍受 Textual 增量解析策略影响；本轮通过限频与合并控制放大倍数，没有侵入第三方私有实现。
- 思考控件仍会在每个呈现帧更新完整可见文本；应先用真实长思考样本确认是否成为新主瓶颈，再决定是否引入专用纯文本流控件。
