# OURO TUI 技术选型与界面交互设计

> 日期：2026-08-03
>
> 状态：目标设计
>
> 范围：OURO TUI 的终端 UI 技术栈、整体视觉、动态反馈和交互逻辑
>
> 不在范围：Application/Core 架构、领域模型、业务规则、事件协议和具体功能实现

## 一、结论先行

OURO TUI 推荐采用 **Textual 8.2.x + Rich 15.x**，保持 Python 3.12 单运行时；以 Textual
负责终端布局、输入、焦点、快捷键、滚动、弹层和局部刷新，以 Rich/Textual Markdown 负责 Markdown、
代码高亮及终端文本样式。

调研当日 PyPI 稳定版为 Textual `8.2.8`、Rich `15.0.0`；选型中的主版本范围基于这组已发布版本，不能把
未来版本号当作实现前提。[Textual PyPI](https://pypi.org/project/textual/)
[Rich PyPI](https://pypi.org/project/rich/)

首期依赖建议：

```toml
dependencies = [
    "textual>=8.2,<9",
    "rich>=15,<16",
]

```

仓库当前使用 Pytest 9，而调研当日可解析的 `pytest-textual-snapshot 1.1.0` 通过 Syrupy 约束
`pytest<9`，因此首期不直接加入该插件。交互测试先使用 Textual 内置 Pilot；视觉基线通过 Textual
`export_screenshot`/SVG 能力生成并由仓库自有测试比较。待插件发布 Pytest 9 兼容版本后再评估引入，不能为视觉
测试倒退全仓测试框架。

其中 Textual 当前要求 `rich>=14.2.0`；OURO 若直接导入 Rich 的 `Text`、`Syntax`、`Table` 等公开 API，
应将 Rich 声明为直接依赖，否则可以只声明 Textual 并由其解析兼容版本。版本上限用于避免 TUI 样式和控件
行为被跨主版本升级静默改变，后续按视觉快照测试主动升级。

OURO TUI 的产品形态定义为：

- 全屏、单会话主视图，默认进入终端 alternate screen，退出后恢复原终端；
- 终端默认背景贯穿整个界面，不铺设应用级实色背景；
- 顶部只保留一行会话上下文，中部是可滚动事件时间线，底部是固定 composer 与一行状态；
- 信息以“文本层级、留白、细线和少量语义色”组织，不以大色块和密集边框组织；
- 动画只表达真实进行中的状态，不作为常驻装饰；
- 用户无需记忆快捷键也能从 `/` 命令面板完成所有操作，熟练用户则可完全键盘驱动；
- Assistant Markdown 按增量流式呈现，但刷新经过合并；历史块一旦完成即保持稳定，避免全屏反复重排；
- 工具、MCP、压缩和子智能体都使用同一套“进行中 → 成功/失败/等待”的状态语法，但各有可辨识图标；
- 所有颜色都有图标和文字冗余，`NO_COLOR`、低色深和非 TTY 环境仍可正确理解。

Textual 的 `Markdown.get_stream()` 会在高频 append 超过界面消费速度时自动合并更新，正好对应 OURO 的
模型 token 流；Textual 又与 OURO 当前 asyncio 生命周期一致，不需要引入 Bun/Node、Rust sidecar 或跨进程
UI 协议。[Textual Markdown 文档](https://textual.textualize.io/widgets/markdown/)

## 二、设计目标与边界

### 2.1 核心目标

1. **快**：输入始终跟手；模型流、多个工具和动画并发时不阻塞键盘；长会话滚动不出现明显卡顿。
2. **活**：OURO 标志、模型工作、工具调用、MCP 连接、上下文压缩和等待用户都拥有清晰的动态反馈。
3. **静**：动态只发生在当前活动点，完成后的时间线迅速安静下来；界面大部分区域使用终端原生背景。
4. **清**：默认只显示理解本轮进展所需的信息，参数、长输出、推理和诊断按需展开。
5. **顺**：提交、排队、steer、停止、审批、AskUser、切换会话和模型都有稳定、可预测的键盘路径。
6. **稳**：终端 resize、宽字符、粘贴、SSH/tmux、Windows Terminal、低色深和无动画环境都有降级规则。

### 2.2 明确不做

本文不定义：

- TUI 如何构建或拥有 Runtime/Application service；
- RuntimeEvent、DTO、Session 和 Run 的新增字段；
- TUI 与 Core/Application 的依赖边界；
- 工具、审批、AskUser、MCP、插件或子智能体的业务语义；
- 数据持久化、恢复、重试、订阅和 cursor 的实现；
- Desktop Host 或 Web UI 的视觉规范。

文中出现的状态和信息均指“已有语义在 TUI 中如何呈现和操作”，不是另建一套业务状态。

### 3.2 OpenCode：组件化全屏工作台

OpenCode 当前 TUI 已独立为 `packages/tui`，技术栈是 Bun/TypeScript、SolidJS、`@opentui/solid` 和
`@opentui/core`。OpenTUI 的渲染核心由 Zig 编写，提供 TypeScript bindings，并明确以高性能和正确性为目标。
[OpenCode TUI package](https://github.com/anomalyco/opencode/tree/1882c33827cf0ce5c948b69ab5a87ed8f6790cf8/packages/tui)
[OpenTUI 仓库](https://github.com/anomalyco/opentui)

视觉与交互特征：

- 首屏将品牌 logo、主输入框和少量提示居中，降低第一次使用的认知负担；
- 会话页采用主时间线加可切换侧栏，侧栏承载上下文、文件、LSP、MCP 和 Todo 等次级信息；
- composer 是富输入区域，支持附件、文件引用、历史、自动补全和 shell/agent 等上下文模式；
- `Ctrl+P` 打开统一命令面板，leader key 组织低频快捷键，常用输入仍沿用终端编辑习惯；
- 工具详情、thinking、sidebar、scrollbar 和动画均可切换，用户可主动降低视觉噪声；
- 主题层覆盖 Markdown token、diff 和语义状态，但仍提供 system theme；
- permission/question 在会话下方就地接管交互，而不是让新输出覆盖正在输入的 prompt；
- 支持 session tree、队列、快速切会话、时间线和多种列表选择器，所有列表均有方向键路径；
- 动画可以全局关闭，注意请求还能通过终端通知/声音补充提示。

可迁移结论：

- 统一命令面板比记忆大量 slash command 更易发现；
- composer 需要独立、长期稳定的焦点和草稿状态；
- 次级状态适合按需侧栏或弹层，不应常驻挤压主时间线；
- 快捷键应当是动作名到按键的可配置映射，而不是散落在控件里的条件判断；
- 动画必须是用户可关闭的产品设置。

不直接采用其栈的原因：OURO 当前是 Python 3.12 单包应用。引入 Bun、OpenTUI native artifact 与第二套
TypeScript 工程会显著扩大安装、发布、调试和跨平台测试面；其性能优势不足以抵消 OURO 首个 TUI 的集成成本。

### 3.3 Kimi Code：克制时间线与高密度过程反馈

Kimi Code 当前是 TypeScript/Node 工程，TUI 建于 `@moonshot-ai/pi-tui` 之上，并通过单二进制分发隐藏
Node 运行时。它强调毫秒级启动、长时间 Agent session、图片/视频输入、MCP 和并行 subagent。
[Kimi Code 仓库](https://github.com/MoonshotAI/kimi-code/tree/e22479a62eed9c3b78a67b313f4332c2c0ba9670)

视觉与交互特征：

- 时间线整体很少使用框；用户、assistant、thinking 和工具主要靠 bullet、缩进和颜色区分；
- live thinking 只展示尾部少量行，使用 braille spinner 和 `thinking...`；完成后变成 dim italic 内容；
- thinking、工具长输出统一使用 `Ctrl+O` 展开/折叠，并显示剩余行数；
- 工具卡根据 Read/Write/Edit/Shell/Agent 做专用摘要，默认只呈现路径、行数、耗时、token 等关键信息；
- 并行 subagent 被分组，活动阶段、最近工具、耗时、token 和成功/失败可在单组中持续更新；
- 进行中的 Bash/Agent 超过一定时长后才出现 background 提示，不抢占短任务注意力；
- 渲染层对 finalized thinking、工具内容和长会话做宽度相关缓存，并限制 live output 预览；
- composer 扩展 `pi-tui` Editor，处理 Kitty keyboard protocol、Windows 粘贴差异、双 Esc 等终端细节；
- theme 明确区分 primary、accent、text、textDim、textMuted、border、success、warning、error、diff 和 role，
  并根据终端明暗选择 palette；
- MCP、plugin、background task 都有专用状态面板，但遵守同一组成功/失败语义符号。

可迁移结论：

- Agent TUI 的性能重点不只是语言，而是“完成块不再重排、活动块局部刷新、长输出有界、宽度缓存”；
- 动态 thinking 应只显示尾部预览，完成后安静折叠；
- 工具必须按用户可理解的结果摘要显示，原始 JSON 参数不应成为默认 UI；
- 同一快捷键可统一控制 thinking 和 tool detail，减少心智模型；
- 长任务提示要延迟出现，避免每个瞬时状态都增加说明文字。

### 3.4 Codex：默认终端色、稳定历史 cell 与专门的 Markdown 流

Codex TUI 使用 Rust、Ratatui 和 Crossterm。Markdown 由 `pulldown-cmark` 解析，代码高亮使用
Syntect；输入、状态、审批、MCP、history cell 和 Markdown streaming 都有独立组件。
[Codex TUI Cargo 依赖](https://github.com/openai/codex/blob/bb5054fe47abe73ecbbd454751066a28c89f4bb9/codex-rs/tui/Cargo.toml)

视觉与交互特征：

- 样式规范明确要求大部分文本使用终端默认前景色，次级文本用 dim；
- 避免硬编码 white/black 和大量自定义色，以确保不同终端主题下仍有对比度；
- cyan 表示用户提示、选择和状态，green 表示成功，red 表示失败，品牌 magenta 仅少量使用；
- history cell 将用户、assistant、命令、diff、MCP、approval 等输出冻结为稳定的时间线单元；
- Markdown streaming 与最终 Markdown 渲染分别处理，避免每个 delta 都把整个文档当作新内容；
- composer 支持多行、slash command、历史搜索、附件、Vim 模式和外部编辑器；
- approval 采用底部 overlay，选择项、理由和影响保持在同一视觉上下文；
- 动画、shimmer、raw output、alternate screen、status line 和 keymap 都可配置；
- alternate screen 支持 `auto/always/never`，raw output 为需要终端原生选择/复制的用户提供路径；
- TUI 使用 vt100/snapshot 测试固定窄屏、换行、approval 和 history 的视觉行为。

可迁移结论：

- OURO 的“终端原生背景”还应扩展为“默认前景色优先”，不能只保留背景却强制全套 RGB 文本；
- 流式块和 finalized history block 应有不同刷新策略；
- 可复制的 raw/print 路径是全屏 TUI 必须保留的出口；
- 视觉样式必须通过不同宽度的快照固定，而不是只在开发者当前终端目测；
- animation、keymap 和 terminal screen mode 都属于用户偏好，不应写死。

| 维度 | OpenCode | Kimi Code | Codex | OURO 采用原则 |

| 颜色 | 完整主题系统 | 明暗 palette | 默认色优先 | 默认色优先，品牌金为点缀 |

| 审批/提问 | bottom prompt | panel | bottom overlay | composer 原位切换交互卡 |

## 四、技术栈选型

### 4.1 候选方案评分

评分 1—5，权重体现 OURO 的现状而非框架的绝对优劣。

| 方案 | Python/现有 asyncio 集成 30% | 流式与长会话性能 25% | Markdown/组件 20% | 输入与测试 15% | 分发维护 10% | 加权结果 |
|---|---:|---:|---:|---:|---:|---:|
| Textual + Rich | 5 | 4 | 5 | 5 | 5 | **4.65** |
| prompt_toolkit + Rich | 5 | 4 | 3 | 5 | 5 | 4.20 |
| Rust/Ratatui sidecar | 2 | 5 | 4 | 4 | 2 | 3.40 |
| OpenTUI + SolidJS sidecar | 2 | 5 | 5 | 4 | 1 | 3.50 |
| Urwid/自定义 Markdown | 4 | 4 | 2 | 3 | 5 | 3.55 |

### 4.2 选择 Textual 的理由

1. **同一异步模型**：Textual 基于 asyncio，OURO 已有 Runtime event sink、异步工具状态和交互协调，不需要
   在 Python 与 UI 进程之间再建立 transport。[Textual App 基础](https://textual.textualize.io/guide/app/)
2. **流式 Markdown 是内建能力**：`MarkdownStream` 会合并过快的 append，避免 UI 追赶积压；不是用普通
   `Static.update(full_markdown)` 模拟 streaming。
3. **输入组件足够强**：`TextArea` 支持多行、选择、光标移动、主题和自定义 binding；composer 只需扩展
   提交、历史、slash/@ popup 与附件 token。[Textual TextArea](https://textual.textualize.io/widgets/text_area/)
4. **完整 TUI primitives**：Screen、ModalScreen、VerticalScroll、OptionList、ListView、LoadingIndicator、
   Markdown、TextArea、Toast 等覆盖 OURO 所需交互，不必手写 ANSI 光标所有权。
5. **局部绘制**：Textual 的 advanced widget 可使用 Line API；Rich renderable 只用于适合整体重绘的小块，
   大型时间线和状态列表保留局部更新空间。[Textual widget guide](https://textual.textualize.io/guide/widgets/)
6. **测试路径完整**：Pilot 可模拟按键和点击，官方 snapshot plugin 可生成不同终端尺寸的 SVG 快照，适合固定
   Markdown、CJK、弹层和 resize 行为。[Textual 测试文档](https://textual.textualize.io/guide/testing/)
7. **依赖成本可控**：纯 Python 包与 OURO 当前 Hatch/uv 体系一致，Windows/macOS/Linux 不增加本地编译前提。

### 4.3 为什么不首选 prompt_toolkit + Rich

`prompt_toolkit` 的编辑器、key binding 和 completion 很成熟，适合现有 readline 式 CLI 渐进增强。但完整 Agent
TUI 还需要稳定时间线、多个活动工具行、overlay、响应式侧栏、局部失效和焦点路由；将 Rich Markdown 嵌入其
layout 需要 OURO 自行维护更多绘制、滚动和 invalidation 逻辑。它应作为非全屏 interactive fallback 的候选，
不是目标 TUI 的首选。

### 4.4 为什么不首选 Rust/Ratatui 或 OpenTUI

两者在绝对吞吐和可控绘制上更强，且已经被 Codex/OpenCode 大规模验证。但 OURO 需要为此增加：

- 第二语言或第二 runtime；
- Python 与 TUI 间的进程生命周期、序列化、取消和错误展示；
- 多平台 binary 构建、签名、升级和兼容矩阵；
- 两边同步变更的开发成本。

除非 Textual 原型在本文性能门槛上失败，否则这些成本没有必要。若失败，**第二选择是 Rust/Ratatui sidecar**，
而不是继续叠加 Python 低层 ANSI：Ratatui 的 buffer diff、Crossterm 事件流和 Codex 的成熟案例使其成为清晰的
性能兜底。

### 4.5 组件使用清单

| OURO UI 部件 | 首选组件 | 使用方式 |
|---|---|---|
| TUI 根 | `textual.app.App` | 全局 bindings、theme、screen mode、terminal capability |
| 主会话页 | `Screen` | 顶栏、时间线、activity、composer、状态栏 |
| 时间线 | 自定义 `VerticalScroll` 容器 | 每个消息/工具/系统事件为独立稳定 block |
| Assistant 内容 | `textual.widgets.Markdown` | 每轮一个 widget，活动轮使用 `MarkdownStream` |
| 代码/差异预览 | Rich `Syntax` / 自定义行组件 | 仅可见、有界片段高亮；diff 使用语义行色 |
| Composer | `TextArea` 派生控件 | 多行编辑、提交、新行、历史、附件占位、slash/@ trigger |
| 命令/文件选择 | `OptionList` 或轻量自定义 popup | fuzzy filter、上下键、Enter、Esc、分页 |
| 审批/AskUser | `ModalScreen` 或 bottom overlay | 与 composer 同区域出现，焦点被明确接管 |
| 工具/子智能体 | 自定义 leaf widget | 单行 summary + 可折叠 detail + 局部动画 |
| MCP 状态 | 自定义 status list | server 粒度状态、工具数、错误摘要 |
| 通知 | `Toast` + terminal notification adapter | TUI 内短提示；失焦时可选系统通知 |
| 异步任务 | Textual Worker + custom Message | 后台等待，UI 线程只消费可渲染状态 |
| 交互测试 | Textual Pilot | 按键、焦点、弹层、队列、resize 行为 |
| 视觉测试 | `pytest-textual-snapshot` | 120×36、80×24、60×20 等基线 |

不建议直接把整个 transcript 放进 `RichLog`：它适合连续日志，但 OURO 需要消息级折叠、焦点、链接、工具状态
和单块 Markdown stream。`RichLog` 可用于 debug/raw event viewer 或 shell 原始输出的详情页。

## 五、整体设计

### 5.1 设计语言：Quiet Motion，安静但活着

OURO 的视觉核心不是“赛博终端”，而是**安静的原生终端上，只有当前行动点在呼吸**。

- 终端默认背景是画布；不设置全局 background RGB；
- 默认前景色承载正文，避免深色/浅色主题下反差失真；
- 品牌金只标记 OURO、当前焦点和需要用户决定的关键点；
- cyan 用于链接、可操作项和选择；green/red 用于完成/失败；dim 用于次级元数据；
- 不同时运行超过 3 处动画；不可见、滚离 viewport、失焦或 reduced-motion 时暂停；
- 完成状态在 150—250 ms 内由动态符号落为静态符号，之后不闪烁；
- 不用 emoji 作为核心状态，因为字宽和字体覆盖不稳定；优先使用单 cell Unicode，ASCII 可降级。

### 5.2 OURO 品牌标志

OURO 的品牌意象取自 ouroboros 的闭环，但避免复杂 ASCII art。首次启动宽度足够时使用 3 行 wordmark：

```text
      ╭──◈──╮
      ╰──┬──╯  OURO
         ╰─ agent runtime
```

常规会话顶栏只保留 compact mark：

```text
◈ OURO
```

设计规则：

- `◈` 是 OURO 的静态核心符号，等宽、单 cell、没有 emoji variation；
- wordmark 正文用 terminal default foreground，`◈` 和 `OURO` 可用 brand gold；
- `agent runtime` 使用 dim，不显示版本营销语；
- 高度不足 24 行或宽度不足 80 列时，首屏直接使用 compact mark；
- 启动动画只播放一次：外环字符依次出现，核心 `◇ → ◈`，总时长 480—720 ms；
- 连接和配置读取仍在继续时，核心符号进入慢速 6 fps 环形动画；就绪即静止；
- reduced motion、`NO_COLOR` 或启动超过 800 ms 时跳过入场动画，直接显示静态标志和真实加载状态；
- 不因品牌动画推迟 composer 获得焦点。

ASCII fallback：

```text
[O] OURO
```

### 5.3 页面骨架

标准宽度（80—119 列）：

```text
┌ ◈ OURO · session title ────────────────────────────────────────────────┐
│ general · provider/model · cwd                                  63% ctx │
│                                                                         │
│  You                                                                    │
│  修复登录失败并运行相关测试。                                            │
│                                                                         │
│  ◇ OURO                                                                 │
│  我会先检查鉴权入口和失败测试。                                           │
│                                                                         │
│  ✓ Read  ouro/auth.py · 184 lines · 38ms                                │
│  ◐ Bash  pytest tests/auth -q · running · 2.4s                          │
│                                                                         │
│  OURO response streams here… ▍                                           │
│                                                                         │
├─────────────────────────────────────────────────────────────────────────┤
│  [image.png]                                                             │
│  > Add a follow-up…                                                      │
│    Enter send · Ctrl+J newline · / commands · @ files                    │
├─────────────────────────────────────────────────────────────────────────┤
│  FOLLOW-UP · gpt-5 · high                1 running · Esc interrupt       │
└─────────────────────────────────────────────────────────────────────────┘
```

图中的外框只用于说明区域，实际标准主题不绘制四周整框：顶栏以下用空行分隔，composer 仅绘制一条上边线或
焦点左线，状态栏无背景色。这样视觉仍属于用户的终端，而不是终端中的“网页卡片”。

宽屏（≥120 列）允许右侧轻侧栏：

```text
┌──────────────────────────── main timeline ─────────────────────┬─ activity ──────┐
│                                                                │ Session         │
│  conversation and active work                                  │ model / effort  │
│                                                                │ context 63%     │
│                                                                │                 │
│                                                                │ MCP             │
│                                                                │ ✓ filesystem    │
│                                                                │ ✓ github        │
│                                                                │ × browser       │
│                                                                │                 │
│                                                                │ Agents          │
│                                                                │ ◐ explore · 12s │
├────────────────────────────────────────────────────────────────┴─────────────────┤
│ composer                                                                          │
└───────────────────────────────────────────────────────────────────────────────────┘
```

侧栏默认关闭；只记住用户在当前终端宽度档位的选择，不因为一次 MCP 或 subagent 活动自动弹出。需要用户立即
处理的审批/AskUser 仍在主区域底部出现，不放进侧栏。

### 5.4 区域层级

#### 顶栏

两行以内，承担定位而不是控制台：

- 第一行：`◈ OURO · 会话标题`，右侧可显示 session activity；
- 第二行：agent、model/endpoint、reasoning、cwd、context usage；
- 宽度不足时按优先级隐藏：cwd → endpoint provider → reasoning label → session title 中段；
- model 和 cwd 使用 dim，危险权限/AFK 使用显式 warning 文本，不能只靠颜色；
- 顶栏不会随 token stream 重绘，context usage 只在准备完成或 turn 完成时更新。

#### 时间线

时间线是主视觉区域：

- 每个 user turn 以 `You` 小标题和正文开始；品牌金仅用于 `You` 前的细标记，不给整段背景；
- Assistant 使用 `◇ OURO` 或单独的 `◇` 起始；流式时 `◇` 可轻微轮转，完成后静态为 `◈`；
- reasoning、工具、system 和 subagent 均缩进两个 cell，形成“OURO 行动轨迹”；
- 相邻同类短工具可折叠成组，避免 Read/Glob/Grep 淹没对话；
- 历史 turn 之间留一个空行，不画贯穿全宽的 divider；
- 当前活动 turn 与 composer 之间始终至少有一行空白，避免视觉粘连；
- 用户向上滚动后取消自动跟随，在底部显示 `↓ 24 new lines · End to follow`，新内容不得抢回滚动位置；
- 返回尾部后恢复 anchor，resize 后保持当前可见语义 block，而不是按旧行号跳转。

#### Activity strip

Activity strip 位于当前 turn 尾部，只展示正在发生的事项：模型等待、一个或多个工具、compaction、subagent
摘要。任务结束后对应项转为稳定 history row，strip 自动收起。它不是独立永久面板，因此不会在 idle 时留下
空壳。

#### Composer

Composer 固定在底部，最小 3 行、最大占窗口高度 40%，内容继续增加时内部滚动：

- 第一层：附件/资源 chip，仅有附件时出现；
- 第二层：多行编辑区，以 `> ` 标记首行，续行用两个空格对齐；
- 第三层：上下文提示，idle 显示提交/换行/命令，running 显示 follow-up/steer/interrupt；
- 焦点用左侧 brand gold 细线或 `>` 颜色表达，不给输入框整块上色；
- placeholder 采用 dim，输入第一个字符后立即消失；
- 错误不清空草稿和附件，在 composer 上方显示单行可恢复提示。

#### 状态栏

状态栏只保留高价值、低频信息：

- 左：当前输入语义 `READY / FOLLOW-UP / STEER / APPROVAL / ASK USER`；
- 中：model + reasoning，宽屏再显示 approval mode；
- 右：运行计数、队列计数、键盘下一步；
- 不常驻显示 token 输入/输出明细、价格、所有 MCP 数和 session ID；这些进入 `/status`；
- 窄屏只显示 `FOLLOW-UP · 1 running · Esc stop`。

### 5.5 色彩系统

#### 基本 token

| Token | 默认 | 用途 |
|---|---|---|
| `canvas` | ANSI default background | 全屏画布、时间线、composer |
| `text` | ANSI default foreground | 正文、Markdown、核心信息 |
| `muted` | default foreground + dim | 时间、路径元信息、提示、thinking |
| `brand` | dark `#D6A84B` / light `#805A00` | OURO mark、当前焦点、关键决定 |
| `action` | ANSI cyan | 可操作项、链接、当前选择 |
| `success` | ANSI green | 完成、连接成功、diff add |
| `warning` | ANSI yellow | 审批、AFK、高风险、退化 |
| `error` | ANSI red | 失败、断开、diff remove |
| `border` | default foreground + dim | 细边、分隔、树枝 |

终端明暗可通过能力探测或用户配置选择 brand 变体；无法可靠判断时采用 ANSI yellow + bold，并同时以符号/文字
保证可理解。禁止把 `#000000`、`#ffffff` 作为正文或背景默认值。

#### 用色规则

- 每一行最多一个高饱和主色；
- brand 不表示 warning，warning 也不表示“正在运行”；
- success/error 只在结果确定后使用；进行中使用 action 或 brand；
- 整块背景色仅用于当前列表选项的 `reverse`/轻 tint 和高风险确认，不用于普通消息；
- Markdown 标题默认前景 + bold，不让每一级标题拥有不同彩色；
- code block 继续使用默认背景，必要时只加 dim 左 gutter；
- `NO_COLOR` 下去掉所有颜色，但保留 bold、dim、underline、符号和文案。

### 5.6 排版、宽度与字符

- 所有布局以 terminal cell 计算，不能用 Python `len()` 推断可见宽度；
- 正文优先自然换行，路径/命令优先中段省略，ID 只显示可辨识前后缀；
- CJK、组合字符和全角标点必须通过宽字符测试；核心图标选择单 cell 字符；
- emoji 只允许出现在模型正文，不作为布局所依赖的 UI 图标；
- 标题使用 bold，次级信息使用 dim，避免大面积 italic；thinking 可 dim italic，但终端不支持 italic 时仍可读；
- 默认左右内边距为 2 cell；窄屏降为 1；代码块内部再增加 2 cell；
- 连续空行最多保留 2 行，模型输出中的更多空行在渲染层视觉折叠但复制仍保留原 Markdown；
- 表格宽于 viewport 时优先横向裁切/详情页，不能把每列压成不可读字符；
- URL 显示 label，焦点/复制时可查看完整地址。

### 5.7 Markdown 视觉规范

| Markdown 元素 | 视觉 |
|---|---|
| 段落 | terminal default foreground，自然换行 |
| H1/H2/H3 | 保留 `#` 层级或以 bold 表示；上下各一行，避免大色块 |
| strong | bold |
| emphasis | italic；不支持时不额外着色 |
| inline code | action/cyan，默认背景，不做反色胶囊 |
| fenced code | dim 左 gutter + syntax foreground；顶部显示 language，底部无框 |
| quote | `│` dim gutter + dim text |
| unordered list | `•`，嵌套使用 `◦`，缩进 2 cell |
| ordered list | 保留序号并做 hanging indent |
| link | underline + action，点击可选，键盘可复制/打开 |
| horizontal rule | dim，最大宽度为正文宽度而非全屏 |
| table | header bold、列间 2 cell；超宽时提示 Enter 打开详情 |
| task list | `□` / `✓`，不依赖 emoji checkbox |

流式 Markdown 行为：

1. token/delta 先进入 30—50 ms 的 coalescing window；
2. 每个 frame 只向当前 `MarkdownStream` 写入新增 fragment；
3. 未闭合 code fence 使用 plain code preview，不在每个字符上重新 syntax highlight；
4. fence 闭合或流完成后执行一次完整高亮；
5. 未闭合表格、链接和 emphasis 不应造成整屏闪烁，允许短暂按普通文本展示；
6. 完成后 stop stream，把 block 标为 immutable；
7. 用户复制时使用 canonical Markdown，不复制 spinner、gutter、折叠提示和 ANSI。

Textual 官方说明普通 Markdown 每秒二十次以上 append 可能追赶不及，`MarkdownStream` 会按需合并更新；OURO
必须使用 stream API，而不是依赖无限提高刷新频率。[Textual MarkdownStream](https://textual.textualize.io/widgets/markdown/#get_stream)

### 5.8 响应式规则

| 宽度 | 布局 | 变化 |
|---|---|---|
| ≥120 | wide | 可开 26—32 列侧栏；顶栏完整；tool summary 信息较全 |
| 80—119 | standard | 单列主视图；侧栏变为 overlay；状态栏三段 |
| 60—79 | compact | 顶栏一行；路径中段省略；工具详情默认更少；composer hint 轮换 |
| 40—59 | narrow | 左右 padding 1；不画 box；弹层全宽；表格转 key/value |
| <40 | minimal | 明确提示建议加宽；仍允许输入/停止/审批，非关键元数据隐藏 |

高度规则：

- `<20` 行：隐藏第二顶栏和普通 composer hint；
- `<14` 行：logo、sidebar、toast stack 全部取消，只保留时间线、composer、单行状态；
- 弹层高度不超过 viewport 的 70%，超出部分内部滚动；
- approval/AskUser 永远优先于普通状态栏占位。

### 5.9 动效系统

动效遵循“一个语义、一组帧、一个结束态”。同一状态不可在不同区域随机换 spinner。

| 语义 | Unicode 动态帧 | 稳定结束 | 建议频率 |
|---|---|---|---:|
| OURO/model working | `◇ ◈ ◆ ◈` 或轻 shimmer | `◈` | 6—8 fps |
| 普通等待 | `◜ ◝ ◞ ◟` | `✓/×` | 8 fps |
| 工具参数生成 | `◱ ◰ ◳ ◲` | `◇` | 6 fps |
| 工具执行 | braille spinner | `✓/×/⊘` | 10—12 fps |
| MCP 连接 | `⋯ ⇢ ⇄ ⇠` | `●/×` | 6—8 fps |
| compaction | `▱ ▰ ▱ ▰` | `✓ compacted` | 6 fps |
| streaming cursor | `▍` 显隐或亮度变化 | 无 cursor | 4—6 fps |
| attention required | 静态 `!`，可一次短亮 | `!` | 不循环 |

限制：

- UI 总帧率上限 30 fps，常规动画 12 fps 以下；
- 相同 tick 合并全部 dirty leaf；
- spinner 不更新 elapsed 文本到小数点后一位；运行 10 秒内按 1 秒更新，之后按 5 秒更新；
- viewport 外的动画暂停，侧栏关闭后不刷新其内容；
- terminal unfocused 时降低至 2 fps 或暂停，仅保留系统通知；
- `animations=false` 时进行中以静态 `…` 表示；
- ASCII fallback 使用 `| / - \`，结束态使用 `[ok] [fail] [stop] [!]`；
- 动画 task 在 run 结束、异常、screen pop 和 app 退出时都必须消失，界面不能留下幽灵 spinner。

### 5.10 性能体验合同

技术实现完成前即以用户可感知结果定义门槛：

- 正常输入时 keypress-to-paint p95 ≤ 50 ms，任何单次停顿不超过 100 ms；
- 模型 delta 到可见文本 p95 ≤ 100 ms；允许合并 token，不要求一 token 一 frame；
- 3 个并行工具 + Markdown stream + 2 个 spinner 时，输入延迟仍满足上项；
- 已载入 10,000 行、200 个 history block 时，PageUp/PageDown p95 ≤ 50 ms；
- 用户离开尾部后，新 delta 不触发 viewport 跳动；
- resize 后 100 ms 内出现可操作画面，syntax highlight 可延迟补全；
- idle 时不应存在持续高频刷新；动画关闭后 CPU 应接近普通等待进程；
- 长工具输出默认预览有界，UI 不因模型返回 10 MiB 文本而立即创建等量可见行；
- 首屏在本地配置正常时目标 ≤ 500 ms 可输入；MCP 连接不阻塞 composer 出现。

若 Textual 原型在 Windows Terminal、macOS、常用 Linux terminal 三类环境中无法满足 keypress、长会话和多活动项
三项门槛，再启动 Rust/Ratatui sidecar 技术验证；不能通过降低视觉验收或继续增加手写 ANSI 绕过。

## 六、交互功能设计

### 6.1 启动与首次进入

启动分两阶段呈现：

1. **立即可见**：OURO compact logo、当前 cwd 和 composer；目标是用户感知应用已响应。
2. **渐进就绪**：模型配置、插件和 MCP 状态在时间线顶部的 startup strip 中逐项落定。

示例：

```text
◈ OURO
  C:\work\project

◐ Starting · loading local configuration
◐ MCP · filesystem · connecting
✓ Provider · openai/gpt-5

> Ask OURO to work on this project…
```

规则：

- 成功的 startup 项在 1.5 秒后折叠为一行摘要：`✓ Ready · 3 MCP · 18 tools`；
- 失败项保留，但只显示脱敏摘要和一条可操作建议，Enter 打开详情；
- MCP 自动连接不阻止用户编辑；若提交依赖尚未就绪，composer 保留草稿并展示具体等待项；
- 首次无 provider 时不显示空白对话页，直接打开 provider selector；Esc 可退出，不能陷入无焦点状态；
- 恢复 session 时先显示 cached history skeleton/文本，再补充当前活动状态，避免长时间空屏。

### 6.2 普通对话与流式回复

用户提交后：

- 用户消息立即冻结进入时间线；
- composer 清空文本，但 follow-up 仍可继续输入；
- `◇ OURO · preparing` 出现在新 turn，下方依次更新 context preparation、model wait、thinking 和 text；
- 首个可见 token 到达时，等待行在原位变为 Assistant block，不额外打印一条“完成等待”；
- Assistant 正文保持 Markdown；最末尾显示 streaming cursor；
- 完成后 cursor 消失，`◇` 落为 `◈`，右侧 dim 显示耗时；token/费用默认不常驻。

如果模型只产生工具、不产生正文，Assistant block 不保留空壳；工具组成为本轮主要内容。如果模型没有任何 delta
就结束，显示明确 `No text response` 或对应稳定结果，不能留下永久 spinner。

### 6.3 Composer 编辑

#### 基本输入

- `Enter`：提交；
- `Ctrl+J`：插入换行，所有终端必须支持；
- `Shift+Enter`：终端能够区分时也是换行；不能区分时 footer 只宣传 `Ctrl+J`；
- `Alt+Enter`：Agent 运行时将当前输入作为 steer 立即发送；idle 时等同 Enter；
- `Up/Down`：优先在多行文本内移动；仅在第一/最后视觉行继续越界时访问历史；
- `Ctrl+R`：打开输入历史搜索；
- `Ctrl+A/E`、`Alt+B/F`、`Ctrl+W/K/U`：遵守常见 Emacs/readline 编辑语义；
- bracketed paste：作为一次原子编辑，可撤销；粘贴多行不自动提交；
- 大段粘贴显示 `Pasted text · N lines` chip，Enter 可预览，提交时仍保持原始内容；
- 鼠标可以定位和选择，但所有能力必须存在键盘路径。

#### 草稿与错误

- 切换会话前保存每会话草稿；返回后恢复光标和附件；
- provider 不支持附件、资源准备失败、运行启动失败时不清空 composer；
- 提交成功以 Runtime 接受输入为界，不以按下 Enter 为界；
- 失败提示位于 composer 上方，`Esc` 关闭提示但不清除草稿；
- 输入为空时 Enter 不产生空消息；仅附件存在时允许提交，并提示补充说明但不强制。

### 6.4 运行中输入：follow-up、steer 与 queue

运行期间 composer 仍可输入，状态栏切换为 `FOLLOW-UP`：

- `Enter`：按 OURO 默认 queue mode 提交 follow-up；
- `Alt+Enter`：steer 当前 Run；
- 输入框提示明确变化：`Add a follow-up…`；
- 提交后在 composer 上方生成队列 chip：`1  Fix the failing snapshot`；
- 队列 chip 显示顺序、类型和单行摘要，`Ctrl+Up/Down` 选择，Enter 编辑，Delete 仅在应用允许时移除；
- steer 成功后使用 action 色短提示 `↳ Steering current run`，不伪造成 user history message；
- 队列消费时 chip 过渡到时间线的正式 user turn；
- 队列失败保留文本并标为 error，用户可重新编辑。

状态栏必须持续显示 `Enter queue · Alt+Enter steer · Esc interrupt`，避免 running 时相同输入框语义不透明。

### 6.5 Slash command 与统一命令面板

#### Slash popup

在 composer 首个非空字符为 `/` 时打开 popup：

```text
  /model        Switch model endpoint
  /sessions     Open a saved session
  /attach       Attach image or text resource
  /compact      Compact current context
  /context      Show latest provider context
  ─────────────────────────────────────────
  ↑↓ select   Enter run   Esc close
```

- 输入继续做 fuzzy/filter，匹配命令名、alias（若有）和描述；
- 高亮只标命中字符，不给整个列表强背景；
- 命令分组顺序：当前最相关 → session/run → model/context → resources/skills → settings/diagnostics；
- 不可用命令 dim 并显示原因，不应消失导致用户怀疑；
- 选中需要参数的命令后保留 `/command ` 并切换参数 provider；
- popup 最大 8 项，更多项滚动；当前选择始终可见；
- `Esc` 只关闭 popup，保留文本；第二次 Esc 才执行上层语义。

#### `Ctrl+P` command palette

命令面板显示所有动作，包括无 slash 形式的 UI 动作，如切换 sidebar、展开 tool、复制 response、关闭动画。
每项右侧显示当前绑定键。它是帮助与执行的统一入口，不再维护一套不可执行的快捷键说明。

子智能体配置位于 Actions 的 Subagents 分组，沿用现有 grouped choice、inline edit 和 destructive confirmation：

- Dispatch policy：配置全局 agent/model allowlist、sync/async 与 write/network/MCP/external-path 能力；固定 depth 和
  lifecycle 只读显示；agent/model 复用目录 Choice 页多选，不手输 ID、model key 或 pattern；
- List subagents：展示 builtin/user 的统一目录、稳定 agent_id 和 compatibility；builtin 使用既有 disabled 样式，user
  可继续进入 Edit/Delete 管理页；
- Create subagent：编辑稳定 agent_id、name、description、system prompt、单选 model 与 all/selected tools；model 默认
  继承当前 Session model；
- Edit subagent：展示 builtin/user 分组，builtin disabled；user 的 agent_id 只读；
- Delete subagent：展示 builtin/user 分组，builtin disabled；user 使用统一 ConfirmationScreen；
- 创建/编辑页只显示简短、逐字段校验提示，不把底层 Pydantic 错误详情放进菜单行；
- 工具选择从当前 live Tool catalog 生成，不设置人为数量上限，也不在 TUI 复制权限规则；Choice marker 是选择状态的
  唯一表达，不重复显示 selected/not selected；
- Subagents 的正常导航、取消和成功保存/删除保持静默，只有 warning/error 使用已有 notice/notification。

OURO 现有 `/help`、`/new`、`/sessions`、`/open`、`/models`、`/model`、`/thinking`、
`/approval-mode`、`/afk`、`/config`、`/export`、`/abort`、`/compact`、`/context`、`/control`、
`/history`、`/events`、`/skills`、`/skill`、`/attach`、`/attachments` 和 `/detach` 均应进入同一动作目录，
但 TUI 可将其展示名本地化为自然语言。

### 6.6 文件引用与附件

#### `@` 文件/资源引用

- 输入 `@` 后打开文件/资源 popup；
- 默认搜索工作目录内路径，结果显示文件名、相对目录和类型；
- 上下键选择，Enter 插入结构化 token，Esc 关闭；
- token 显示为 action 色但仍属于文本流，可用 Backspace 整体删除；
- 同名文件必须显示足够目录消歧；
- 搜索进行中显示静态 `… indexing`，不阻止普通输入；
- 找不到时保留用户键入内容为普通文本，不吞字符。

#### 附件 chip

图片、文本资源和大段粘贴显示在 composer 顶部：

```text
[▧ screenshot.png · 1.8 MB] [≡ api.log · 240 lines]
```

- chip 不使用彩色背景，以细边/括号表达；
- 左右键在 chip 间移动，Delete/Backspace 删除，Enter 预览；
- 鼠标点击可选择/删除，但删除按钮不能依赖 hover 才可发现；
- 粘贴图片失败时显示原因并保留文本剪贴板行为；
- 当前模型不支持图片时，提交被阻止，附件与文本都保留，提供“切换模型/移除附件”两条动作；
- 附件数量、大小和类型边界在添加时提示，不等到请求发出后才失败；
- 时间线中的 user message 只显示附件摘要，Enter 打开详情；不在 terminal 内强制渲染六像素/Kitty 图片。

### 6.7 Reasoning / Thinking

Reasoning 默认显示为 dim 的有界过程块：

```text
◐ Thinking · 4.2s
  正在定位 session 切换与资源草稿之间的关系…
  … 3 more lines · Ctrl+O expand
```

规则：

- live 时只显示最近 3 行；新行从下方进入，不让整个历史块上下抖动；
- 完成后默认保留前 2—3 行摘要或折叠为 `› Thought for 4.2s`，具体取决于是否有可显示 reasoning；
- `Ctrl+O` 展开/收起当前选中的 reasoning/tool；
- 全局 `/thinking` 控制模型 reasoning 配置，与“是否展示 reasoning”是两个不同动作，文案必须区分；
- raw reasoning 若因策略不可见，不显示空的 thinking block；
- reasoning 失败不使用 tool error 语法，跟随模型/Run 的真实错误呈现。

### 6.8 工具调用

#### 状态行

每个工具调用保持稳定 identity，在原位经历状态变化：

| 阶段 | 图标 | 默认文案 | 参数可见性 |
|---|---|---|---|
| 参数生成 | 动态 `◱` | `Write · preparing input` | 隐藏 |
| 已请求/排队 | `◇` | `Write · queued` | 隐藏 |
| 等待审批 | `!` | `Write · approval required` | 显示有界安全摘要 |
| 执行中 | braille | `Write · src/app.py · 1.4s` | 隐藏敏感/冗长参数 |
| 成功 | `✓` | `Write · src/app.py · 42 lines · 1.8s` | 默认摘要 |
| 失败 | `×` | `Write · failed · permission denied` | 默认一行错误 |
| 中止 | `⊘` | `Write · interrupted` | 无 |
| 未知 | `?` | `Write · result unavailable` | 无 |

这延续 OURO 当前 Interactive 已有的约束：流式参数只驱动单行状态，不逐片打印 JSON；只有等待审批时显示
有界参数摘要，进入执行后立即隐藏。

#### 专用摘要

- Read/Glob/Grep：路径、match/line 数、耗时；连续读取可组合为一组；
- Write/Edit：目标路径、added/removed 行数；Enter 打开 diff；
- Shell：命令首行、exit code、耗时；默认显示 stdout/stderr 尾部至多 5 行；
- Web/Fetch：域名、状态、结果项数；URL 脱敏并可打开；
- MCP：`server › tool`、耗时、结果摘要；server 与 tool 使用不同 dim 层级；
- Agent：agent 名、任务摘要、阶段、工具数、耗时；子轨迹默认折叠；
- AskUser：不是普通 tool row，直接切换为交互卡。

#### 展开与选择

- PageUp 后可用 `J/K` 或 `Alt+Up/Down` 在可交互 history block 间选择；
- 选中 block 只显示一条 action 色左线；
- `Ctrl+O` 展开/折叠；Enter 打开详情 overlay；
- 展开只影响本地显示，不改变 canonical output；
- 同一 turn 的“展开全部”只通过 command palette 提供，避免误按造成大规模重排；
- 超长详情分页/虚拟显示，不能一次 mount 全部行。

### 6.9 并行工具与子智能体

并行工具使用稳定分组：

```text
◐ Tools · 2 running · 1 done
  ✓ Read   ouro/core/events.py · 221 lines
  ◐ Grep   "tool_call" · 1.2s
  ◐ Agent  explore · finding TUI boundaries · 8.4s
```

- 分组标题给出总数，子项仍按 source order 固定，不按完成顺序跳动；
- 完成项不立即移除，直到整个批次结束；结束后组落为静态 history block；
- 子智能体默认只显示任务摘要、状态、最近活动、耗时和最终一行结果；
- 多个子智能体使用树枝 `├─/└─`，但窄屏改为普通缩进；
- 只有 subagent 请求 root 用户审批/输入时提升为主交互卡，并明确来源：`explore › approval required`；
- backgrounded/async agent 出现于 activity sidebar 或组摘要，完成时在主时间线插入稳定通知；
- 不以高速轮播方式展示多个 agent 的最近文字，防止主视图持续抖动。

### 6.10 MCP 服务器连接与状态

启动时：

```text
◐ MCP · connecting 3 servers
  ✓ filesystem · stdio · 12 tools
  ◐ github · oauth
  × browser · timeout · Enter for details
```

交互规则：

- 每个 server 一行，连接完成后固定；summary 显示 connected/failed/tool count；
- server 名与 transport 可见，命令、环境变量、headers 和 credential 永不回显；
- OAuth/用户授权需要动作时用 `!` 静态 attention，并将 Enter 动作写清；
- retry 不新增重复行，状态在原 server 行更新；
- 所有连接完成后，成功项折叠为 `MCP · 2 connected · 18 tools`，失败项继续保留；
- `/status` 或宽屏 sidebar 可查看完整 inventory；主时间线不永久列出全部工具名；
- Run 中 MCP tool 断线重连时，工具行显示 `reconnecting github`，不会弹回启动面板；
- MCP failure 不伪装成全局 OURO failure，除非它实际阻断当前操作。

动态符号采用“连接”的水平运动而非普通 tool spinner，使用户能从周边视觉识别状态类别；动画关闭后用
`… connecting`。

### 6.11 Context preparation 与 compaction

准备阶段使用一条 replaceable status：

```text
◐ Preparing context · 42k / 128k
```

- context metrics 到达后原位补充，不为每个阶段打印日志；
- model wait 与 preparation 分开计时，但默认只显示总等待和当前阶段；
- 自动 compaction 开始时转换为专用状态：`▰ Compacting context · 83% used`；
- 完成后稳定输出 `✓ Context compacted · 96k → 41k · 1.8s`；
- skip/failure 使用真实语义：`– Compaction skipped` / `× Compaction failed`；
- compaction 不清空 composer，不抢占输入焦点；
- footer context 使用比例 + absolute token 的其中一种，标准宽度显示 `63% ctx`，详情由 `/context` 提供。

### 6.12 审批

审批卡原位替换 composer 的主要交互面：

```text
! Approval required · Write
  Agent: general
  Target: C:\work\project\config.toml
  Change: overwrite · 18 lines

  › Allow once
    Allow for this session
    Reject
    Edit input

  ↑↓ choose · Enter confirm · Esc reject
```

视觉规则：

- warning 色只用于 `!`、标题和当前风险关键字，不给整卡黄色背景；
- 当前选项用 action 色 `›`，不靠 reverse 后的整行亮色；
- 参数只显示有界、脱敏、对决定有帮助的字段；JSON 原文进入详情 overlay；
- subagent 请求必须显示 agent/delegation 来源；
- 多个 pending interaction 按到达顺序排队，标题显示 `1 of 3`；完成一个后平滑切到下一个；
- 数字键 `1..4` 可直接选择，但仍需 Enter 确认高风险持久授权；
- `Esc` 的含义在 footer 明写，不能有时关闭、有时 reject 而无提示；
- 决定提交后卡片冻结为时间线摘要 `✓ Approved once` / `× Rejected`，composer 恢复原草稿和焦点；
- 提交失败时保留卡片和选择，不让用户重复阅读全部参数。

### 6.13 AskUser

单选问题：

```text
? OURO needs input · deployment target

  › Staging       Use the shared test environment
    Production    Deploy to customer traffic
    Type an answer…

  ↑↓ choose · Enter answer · Esc abort
```

多问题：

- 顶部显示进度 `Question 2/3`；
- 每题独立确认，Backspace/Left 返回上一题且保留答案；
- free text 复用 composer 编辑能力，但视觉标记为 `ANSWER`；
- 空行不是有效答案，Enter 后保持焦点并显示短提示；
- 多选使用 Space toggle、Enter submit，选中项同时显示 `✓` 和文字；
- 问题来源是 subagent 时展示来源；
- 回答完成后形成一条简洁时间线记录，不重复整段选项描述。

### 6.14 Session、模型、Skills 和设置选择器

所有资源选择器使用统一操作模型：

- `Up/Down` 移动，`PageUp/PageDown` 翻页，Home/End 首尾；
- 输入即搜索；Backspace 清搜索；Esc 关闭；Enter 选择；
- 左侧 `›` 是当前光标，`✓` 是已经生效的值，两者不能混淆；
- 列表项第一行名称，第二行 dim metadata；
- 当前项、recent、favorite 分组优先，但搜索结果按匹配质量；
- loading、empty、error 各有明确状态；错误不会使 overlay 自动关闭；
- 选择后显示短 toast，并在顶栏/状态栏的事实位置更新，避免双重确认文本。

Session selector 项显示 title、更新时间、model、activity；当前 active Run 显示 spinner，等待审批显示 `!`。切换前
保存草稿；若目标有 pending interaction，进入后优先聚焦它。

Model selector 项显示 provider/endpoint、vision/tools/reasoning capability 和最近使用；不支持当前附件的 model dim
并解释原因。Skills selector 显示名称、短描述和来源，不把完整 SKILL.md 放在列表。

### 6.15 Help、状态与诊断

`Ctrl+P` 搜索动作，`Ctrl+H` 打开 contextual help；`/help` 打开完整帮助页。

`/status` 建议分四组：

- Session：title、id 短写、model、reasoning、approval/interaction mode；
- Context：usage、snapshot 时间、compaction；
- Connections：provider、MCP、plugin degradation；
- Activity：run、queue、subagent、pending interactions。

默认只展示用户可操作信息。raw events、完整 ID、transport error 和 stack trace 进入 `/events` 或 debug overlay，
并继续遵守凭据脱敏。

### 6.16 滚动、复制与链接

- `PageUp/PageDown`：整页；`Ctrl+U/D`：半页；Home/End：首尾；
- 鼠标滚轮可滚动时间线，但 composer focus 不丢失；
- 用户离开尾部后显示 new-lines indicator，End 回到底部；
- `Ctrl+O` 展开当前 block，`Ctrl+Shift+C` 复制选中 block 的 canonical Markdown；
- `/copy` 或命令面板可复制最近 Assistant response；
- 外部终端原生选择与 TUI mouse capture 冲突时，提供 `Shift+drag` 绕过和 `/raw`/print 路径；
- 链接 Enter 打开、`y` 复制；打开外部程序前暂停 TUI 并完整恢复终端模式；
- 默认 full-screen 退出后不把整个 transcript 污染原 shell scrollback；需要脚本/复制时继续使用现有 Print/JSON/export。

### 6.17 中断与退出

`Esc` 采用严格的上下文优先级：

1. 关闭 autocomplete/popup；
2. 取消 history block 选择；
3. 关闭非阻塞 overlay；
4. active Run 时发起 interrupt；
5. idle composer 中不执行退出。

`Ctrl+C`：

- 有 active Run：interrupt，并显示 `Press Ctrl+C again to force abort`；
- approval/AskUser：按该卡明确的 cancel/reject 语义；
- idle 且 composer 非空：第一次清当前选择或保持草稿并提示 `Ctrl+U clear input`，不直接丢稿；
- idle 且 composer 空：显示 `Press Ctrl+C again to exit`，1.5 秒内再次按下才退出。

`Ctrl+D` 在 idle 且 composer 为空时退出；有文本时沿用 delete-forward。`/exit` 始终是明确退出动作。退出前若有
Run、queue、未提交草稿或 pending interaction，显示摘要确认；普通空闲退出不弹确认。

### 6.18 错误、降级与通知

错误分三层：

- **局部错误**：工具、MCP server、附件；留在对应 block；
- **Run 错误**：当前 turn 尾部显示 error block，composer 恢复可输入；
- **Host 错误**：顶部 banner/全屏 error screen，但尽可能保留 session identity 和 export 动作。

错误文案结构固定为：`发生了什么 · 对当前操作的影响 · 下一步`。默认隐藏 traceback；Enter 展开 detail。相同错误
短时间重复时合并计数，不连续刷屏。

终端失焦并且需要用户输入或 Run 完成时，可以发系统通知；焦点在 TUI 时不发。通知必须可关闭，不包含 prompt、
tool arguments、文件内容或凭据。

| Running | `Esc` | interrupt |
| Transcript | `PageUp/PageDown` | 整页滚动 |
| Transcript | `Ctrl+U/Ctrl+D` | 半页滚动；仅 transcript focus |
| Transcript | `Home/End` | 首部/尾部，End 恢复 follow |
| Transcript | `Ctrl+O` | 展开/折叠 thinking/tool |
| Transcript | `Alt+Up/Down` | 上/下一个可交互 block |
| Selection | `Up/Down` | 移动选择 |
| Selection | `PageUp/PageDown` | 翻页 |
| Selection | `Enter` | 确认 |
| Selection | `Esc` | 关闭/按明确语义取消 |
| Multi-select | `Space` | 切换选中 |
| Approval | `1..4` | 快速定位选项 |

Leader key 超时建议为 1 秒；按下 `Ctrl+X` 后 footer 临时显示 `S sessions · M models · B sidebar · E editor`，
超时或 Esc 取消。最终 runtime 只宣传当前终端可区分且实际已绑定的键；所有动作始终能从 `Ctrl+P` 或 slash
command 到达。

### 7.2 快捷键设计规则

- binding 以语义动作命名，允许用户配置；
- 同一 physical key 在不同 focus context 可以复用，但 footer 必须显示当前含义；
- composer 的文本编辑键优先于全局键；
- popup/ModalScreen 拥有明确焦点并阻止无关全局动作穿透；
- 不依赖 terminal 无法稳定区分的组合；
- Kitty keyboard enhancement 是增强而非基本前提；
- Windows Terminal、macOS Terminal/iTerm2、Kitty/WezTerm、tmux/SSH 至少各覆盖一组按键测试；
- 用户解绑后 help/footer 自动反映新 binding，不保留硬编码提示。

## 八、终端能力与无障碍降级

### 8.1 能力分层

| 环境 | 行为 |
|---|---|
| TrueColor TTY | 完整 palette、Unicode、动画、鼠标可选 |
| 256-color TTY | ANSI 语义色、Unicode、动画 |
| 16-color TTY | 默认色 + cyan/green/yellow/red，减少 tint |
| `NO_COLOR` | 无颜色，保留属性、符号和文字 |
| `TERM=dumb` / 非 TTY | 不启动全屏 TUI，转现有 print/JSON 或给出明确提示 |
| reduced motion | 静态进行中图标，无 shimmer/入场动画 |
| ASCII mode | `[>] [ok] [!] [x]` 与 `|/-\` |

### 8.2 无障碍规则

- 状态永不只靠颜色区分；必须至少同时有图标或词语；
- warning/error 不做持续闪烁；attention 最多一次 150 ms 亮度变化；
- 可配置关闭动画、声音、鼠标和 terminal title；
- selection 使用 `›` 和 focus line，不只靠背景反色；
- 文案不使用 `red means failed` 一类颜色依赖说明；
- 用户输入、模型输出和系统状态有固定 textual label，复制时可保留 speaker；
- 提供 print/export/raw 路径服务屏幕阅读器和终端原生复制；
- Markdown link 显示可理解 label，完整 URL 可单独查看；
- 窄屏隐藏元数据但不隐藏当前风险、等待输入、停止和提交动作。

## 九、性能与视觉验收清单

### 9.1 必测场景

1. 100k 字符 Markdown 以 5、20、100 delta/s 流入，包含未闭合 fence、表格、CJK 和超长 URL。
2. 3—8 个并行工具交错完成，source order 不跳动，活动动画仍可输入。
3. 200 turn / 10,000 可见行历史，滚动、resize、展开 tool 和回到底部。
4. composer 中 10,000 字符、多行粘贴、undo、history 和 slash/@ popup。
5. 多个 subagent 同时产生 approval/AskUser，当前 prompt 不被 background event 覆盖。
6. MCP 连接成功、失败、OAuth、retry 和 tool 中重连。
7. compaction 与模型 stream、工具状态相邻发生，不留下 stale spinner。
8. dark/light、16/256/truecolor、`NO_COLOR`、animations off、ASCII mode。
9. 120×36、100×30、80×24、60×20、40×14 resize snapshot。
10. Windows Terminal/PowerShell、macOS、Linux、tmux、SSH 与 CJK locale。

### 9.2 视觉快照基线

至少固化：

- welcome：ready / MCP loading / provider missing；
- standard session：user + Markdown + tool；
- live streaming：paragraph / code fence / list；
- parallel tools：running / partial failure / all complete；
- approval：standard / narrow / subagent source；
- AskUser：single / multi-select / free text；
- composer：empty / multiline / attachments / slash / @file / queued input；
- MCP：connected / mixed / OAuth；
- long path、CJK、wide glyph、ASCII fallback、NO_COLOR；
- light/dark terminal palette；
- compact/narrow responsive layout。

### 9.3 完成门槛

- 通过第 5.10 节全部用户感知性能门槛；
- 关键动作全部有键盘路径，鼠标关闭后无功能损失；
- stream、工具和 prompt 并发不会破坏 composer 草稿或焦点；
- 退出、异常、external editor 后 terminal raw mode、光标、mouse capture 和 alternate screen 完整恢复；
- 非 TTY 不输出动画帧或 ANSI 垃圾；
- 所有 tool/MCP/provider 错误展示都经过脱敏；
- 视觉快照在规定尺寸稳定，差异需人工确认后更新；
- TUI 与现有 print/JSON/export 的语义一致，但视觉表现可以不同。

## 十、推荐实施顺序（仅 UI 层）

本文不定义架构实现，但为了控制视觉与交互风险，UI 组件建议按以下顺序验证：

1. Textual spike：terminal default background、MarkdownStream、TextArea、固定 composer、resize；
2. 标准 session shell：顶栏、时间线、composer、状态栏、滚动跟随；
3. streaming/finalized Markdown block 与性能基准；
4. tool row、并行 tool group、thinking 和统一折叠；
5. slash/@ popup、附件 chip、history 与 running queue/steer；
6. approval/AskUser bottom overlay 与焦点仲裁；
7. MCP、compaction、subagent activity 和可选侧栏；
8. theme、NO_COLOR、animations off、ASCII、通知和 terminal 恢复；
9. 全宽度 snapshot、跨平台按键测试和长会话性能 gate。

第一阶段 spike 不是另建产品原型；它只需证明三个最有风险的点：流式 Markdown 不阻塞输入、长历史能滚动、
默认终端背景能在深浅主题下保持清爽。三项通过后再扩展全部交互区。
