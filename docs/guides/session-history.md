# OURO 消息撤销与会话继续

会话由有序 canonical 消息与当前 Harness 状态组成。每条新消息保存 `before_harness_version`；撤销指定
消息及其后缀时，框架保留此前消息并恢复该锚点，`history_epoch` 增加一次。撤销无需解释插件业务数据，
也不调用插件恢复钩子。计划等外部文件保持原样，真实 usage 和 Run/工具审计继续保留。

## 框架与应用边界

- `SessionStore.commit_session` / `SessionCommit.before_message_id` 支持任意角色消息节点，包括工具结果
  内部节点。同批消息各有正确锚点；物理批量提交不限制逻辑切口。
- `SessionService.undo` 选择直接用户输入。撤回已进入历史的输入时，先取得执行所有权，再原子提交历史与队列变更。
  `RuntimeService.undo` 随后协调受影响的子会话。
  活跃执行未完成取消结算时返回忙碌，由用户先中断。应用入口仅允许直接用户输入，包含
  已提交但尚未消费的排队输入；插件或 Harness 产生的 user-role 消息不冒充用户输入。
- 无参数 undo 优先选择最新待消费用户输入，否则选择最新 canonical 用户输入。取消尚未消费输入只改变
  队列，不回退 Harness 或递增代次；已经消费则按准确消息节点撤销。
- 状态、消息、队列效果和提交回执通过同一原生提交机制持久化。恢复只完成已持久化决定，不重调工具。

## 在 TUI 编辑历史消息

`/edit` 使用与 `/fork` 相同的消息编号，候选仅包含用户直接提交的输入。输入框底部的编辑目标标明将被替换的消息。
选择目标只改动草稿。操作步骤见[编辑历史消息与继续运行](sessions.md#编辑历史消息与继续运行)。
启用草稿记忆后，切换会话或重启都可继续编辑同一条消息。

提交使用所选消息的身份。应用按这条输入之前的 Harness 状态检查新输入，在一次提交中截断旧后缀并受理替换输入。
Supervisor 随后在原会话启动新的 Run。提交前历史已变化或输入未通过校验时，界面保留编辑内容并显示原因。

撤销后保留的其他待消费用户输入维持身份与顺序，撤销本身不自动消费。旧执行许可、插件续跑和子会话
迟到交付不得进入新历史。运行收敛由既有 Runtime 所有权负责；未知外部副作用只保留审计，不尝试回滚文件。

## 会话继续

`/continue` 从持久化消息恢复未完成任务，不追加用户或 system 提示词。同一历史代次复用合法的中断 Run，
保留用量、轮次和预算；历史撤销后从当前消息创建新 Run，不复用旧审批、工具恢复输入或续跑许可。

执行链路先取得执行所有权并复核最新 Run 与历史代次，再结清待处理终态决定和中断工具交换，随后进入通用
模型循环。已有工具结果直接复用，未知结果标记为中断事实，不自动重做工具。上下文投影只发送完整工具帧，
不为补齐工具帧再次裁剪用户指定前缀。canonical 消息仍严格保留所选前缀。

下一次请求在预算检查后绑定 Session 当前模型与推理设置。会话继续不绑定原模型，也不解析供应商私有字段。
`provider_continuation` 是与通用正文、工具调用和结果并存的原生协议附件；预算准备排除其他 provider/model
或历史代次的附件，目标 codec 再验证协议与账户兼容性。兼容时按原生协议重放，不兼容时使用通用消息帧，
保留历史中的原附件。需要重放的附件损坏或与工具帧矛盾时明确失败。普通消息提交与 `/continue` 共用这些规则。

## 观察与错误

snapshot、活动状态和消息点查携带同一 history_epoch。TUI 先过滤旧代次事件，再查询消息身份；历史变化
时重载标准 snapshot/live 交接。当前代次缺失消息仍是持久化错误，不通过吞掉异常掩盖。增量事件与终态快照
遵守同一代次规则，重开会话不得恢复已撤销 Run 的“准备上下文”状态。

只支持当前数据格式；版本不符时明确拒绝。请使用新的数据目录或清理失效测试数据，框架不转换旧消息或插件状态。

规范依据：[会话撤销与 Harness 状态规格](../specs/session-undo.md)。
