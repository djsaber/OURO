# OURO 子智能体设计范式调研与目标方案

> 调研日期：2026-07-22  
> 核心样本：OpenAI Codex、OpenCode、Pi coding agent、Kimi Code CLI  
> 关注范围：执行模式、会话中断与恢复、前端可观测性、HITL、工具权限  
> 结论性质：产品文档和公开源码的事实与面向 OURO 的设计建议分开陈述

## 0. 结论先行

OURO 最合适的目标范式不是“在 Agent 工具处理器里递归调用 RuntimeService”，而是：

1. **子智能体是普通 Session + Run**：复用 OURO 已有的持久化、恢复、事件、审批、AskUser 和工具执行语义。
2. **父子关系是一等的 durable DelegationRecord**：它与 Session fork/branch 是不同关系，不应复用 forked_from 字段表达。
3. **底层统一采用异步 spawn，前台模式只是 spawn + durable join**：模型和 Host 可选择等待，也可继续做别的工作。
4. **根会话拥有 HITL 展示权，子会话拥有请求状态**：审批和提问由子 Run 持久化，统一汇聚到根 Host，并清楚标注来源。
5. **权限按最小权限求交**：子智能体只能缩小父会话授予的能力，不能通过自己的 Agent 配置或“自动批准”模式扩大权限。
6. **系统通过父子树投影感知执行流**：子 Run 继续发普通事件，新增少量 delegation 生命周期事件；前端订阅 root subtree，而不是轮询每个子进程。
7. **“恢复上下文”和“复活执行”必须分开**：历史、关系和结果可以持久化；进程崩溃后的在途工具不能假装无事发生，更不能自动重放未知副作用。

一句话概括目标架构：

    AgentDefinition
          │
          ▼
    DelegationRecord ──► child Session ──► child Run ──► ordinary OURO events
          │                   │
          │                   ├── approvals / AskUser
          │                   └── messages / tool batches / recovery
          ▼
    root activity tree + root interaction inbox + exact-once result delivery

## 1. 研究口径与一个关键区分

本报告把“同步/异步”拆成两层，否则容易把产品 UI 和运行时原语混为一谈：

- **调度原语**：spawn 是否立即返回句柄，还是占住父循环直到子任务完成。
- **编排语义**：主智能体是否选择 wait/join，最后再合并多个子智能体结果。

例如 Codex 的底层控制包含 spawn、wait、steer、interrupt；典型产品体验仍是“并行启动，等待全部，汇总回复”。这不是纯同步，而是异步原语上的 fork-join。

另一个必须区分的概念是：

- **会话可恢复**：历史和子智能体上下文落盘，可继续同一个 child session。
- **执行可恢复**：宿主进程退出后，原来的在途协程、进程和外部副作用继续执行或被安全接管。

四个样本普遍能做到前者；没有足够证据支持“任意在途子任务都能跨宿主崩溃透明复活”。Kimi 会持久化 background task 状态，但其文档也明确会在 session close 时停止后台任务。OpenCode 当前后台 job registry 是进程内状态。Pi 官方子智能体示例甚至显式使用 no-session。

成熟度概览：

- **综合范式最完整**：Codex。强项是 thread 一等化、根界面汇聚审批、控制原语和 App Server 事件协议。
- **前后台任务体验最直接**：Kimi Code CLI。强项是 foreground/background 双模式、自动结果投递、可恢复 child context 和 agents dock。
- **权限表达最细**：OpenCode。强项是 allow/ask/deny、参数/路径 pattern、task 和 question 独立权限；后台能力仍处在实验期。
- **最小可扩展示范**：Pi。强项是实现简单、上下文隔离清晰、流式聚合容易理解；不适合作为 OURO 的 durable runtime 目标。

## 3. 产品拆解

### 3.1 OpenAI Codex

#### 执行与编排

Codex 将子智能体称为 agent thread。官方文档描述的编排动作包含 spawn、路由 follow-up、等待结果、关闭线程；多 agent 工作流通常并行启动，再等待全部结果并由主线程合并。App、CLI 和 IDE 都会展示 child thread，CLI 可用 /agent 切换，IDE 的 background-agent panel 可查看状态、停止或打开单个线程。

从设计上看，它采用的是“异步原语 + fork-join 习惯用法”，而不是把同步/异步做成两套执行器。

#### 会话、控制和恢复

Codex App Server 提供 thread/start、thread/resume、thread/fork、thread/read、thread/list，以及 turn/steer 和 turn/interrupt。thread/list 可按 parentThreadId 或 ancestorThreadId 查询，sourceKinds 也明确区分 subAgent 等来源；thread.sessionId 表示会话树根。

这套设计把三个层次分得很清楚：

- thread：持久历史和 agent identity；
- turn：一次可 steer、可 interrupt 的执行；
- item：消息、工具调用、审批和增量输出。

需谨慎解读的是，thread/resume 证明的是历史可继续，不等于宿主进程退出后在途 child turn 会透明复活。

#### 前端感知

App Server 使用 thread/status/changed、turn 生命周期、item/started、item/completed 和各种 delta 事件驱动客户端。状态可表达 active 以及 waitingOnApproval。用户既可以只看根线程聚合，也可以打开 child thread 深入检查。

这是 OURO 最值得借鉴的 UI 原则：**根树聚合 + 子会话可下钻，不把全部 child transcript 塞回主上下文**。

#### HITL 与权限

Codex 明确允许不活跃 child thread 的审批请求出现在主界面，审批层标注来源，并允许先打开对应线程再决定。无法弹出新审批的 non-interactive flow 会让动作失败，并把错误交回父工作流，避免无期限挂起。

子智能体默认继承父会话当前 sandbox 和 permission mode，包含运行期间改变的权限选择；自定义 agent 可显式改为 read-only 等更窄配置。这个默认对本地产品很合理，但 OURO 应再加一道“父能力上限”，保证 child 配置不能扩大父权限。

主要来源：

- [Codex Subagents 官方文档](https://developers.openai.com/codex/multi-agent)
- [Codex App Server 官方文档](https://developers.openai.com/codex/app-server)

### 3.2 OpenCode

#### 执行与编排

OpenCode 的 Task 工具默认前台执行。当前 dev 分支已经包含 background 参数、立即返回、自动完成通知、前台任务 promotion 为后台、task_id 继续旧子会话等机制，但必须开启 OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS。因此本报告将其分类为“前台稳定、后台实验”。

前台 abort 会同时取消 child session 和 background job。后台完成后，系统向父会话注入 synthetic task result，模型被提示不要轮询。

#### 会话与恢复

child 是普通 Session，持久结构包含 parentID；Task 元数据也包含 parentSessionId 和 child sessionId。task_id 可复用 child session，继续其上下文。

但 active background job 当前通过 InstanceState 保存。这意味着：

- child history 是 durable 的；
- 活跃 job 的进程状态不是 durable state machine；
- 重启后可以继续同一 child session，但不能把原协程视为仍在运行。

#### 前端感知

OpenCode 的 Session、Message、Part 更新和父子 Session 结构足以构建 child tree；TUI 也有父/子/兄弟会话导航。后台完成通过父会话 synthetic result 触发后续处理。

这种设计比“独立进程 stdout 拼接”好，但把结果伪装成对话文本会模糊 provenance。OURO 已有 host/plugin message 语义，不应把子智能体结果伪装成 user。

#### HITL 与权限

OpenCode 将 task 和 question 都纳入统一权限键。permission.task 能按子智能体类型做 allow/ask/deny；具体工具也可按命令、文件路径、URL 等 pattern 配置。

当前子会话权限推导会携带父会话的 deny 和 external_directory 规则，然后由 child agent 自身配置决定能力；task 和 todowrite 默认在 child 中禁用，除非 Agent 明确开放。这个思路比“无脑复制父权限”安全，但最好进一步形式化为不可突破的 delegated capability cap。

主要来源：

- [Task 工具当前源码](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/task.ts)

### 3.3 Pi coding agent

#### 先明确产品边界

Pi 当前官方仓库中的 subagent 是一个 extension example，不是核心 runtime 的一等内建协议。因此它更适合用来研究“最小扩展实现”，不适合用来证明完整的会话恢复或权限模型。

#### 执行、取消和持久化

示例每次调用 spawn 一个独立 pi 子进程，以 JSON 模式收集事件：

- single：单 child；
- parallel：最多 8 个任务、并发上限 4；
- chain：上一步输出传给下一步。

parallel 虽内部并发，但整个 subagent tool execute 会等待所有结果，从父循环看仍是阻塞式。AbortSignal 对 child 发送 SIGTERM，5 秒后必要时 SIGKILL。

关键是 child 参数包含 no-session，因此官方示例不保存 child session，也没有 resume/reconnect。Pi 主产品本身有 session persistence，扩展也可 appendEntry 保存状态，但该示例没有把这些能力组合成 durable subagent。

#### 前端、HITL 与权限

示例解析 message_end 和 tool_result_end，通过 onUpdate 返回 intermediate detail，并自定义 tool render 展示每个 agent 的文本、工具调用、usage、模型和状态。这说明“子进程 + JSON event stream”足以快速做 UI，但缺少一等父子会话树。

project-local agent 是仓库控制的配置，示例会在父 UI 中先询问是否信任。child 用 JSON/print 模式运行时 hasUI 为 false，不能依赖 ctx.ui 在 child 内发起审批或提问。

Agent 定义可指定 tools 列表，但 Pi extension 本身按官方安全说明拥有完整系统权限并可执行任意代码。因此 tools 列表是模型动作面，不是 OS 级安全边界。

主要来源：

- [Pi Subagent 官方示例源码](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/examples/extensions/subagent/index.ts)
- [Pi Extensions 官方文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md)
- [Pi Sessions 官方文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sessions.md)

### 3.4 Kimi Code CLI

#### 执行与结果联动

Kimi 的 Agent 工具把 foreground/background 作为显式参数：

- foreground：父 Agent 等待 child 完成；
- background：立即返回 task id，完成时自动把结果送回主 Agent；
- resume：继续指定 child agent instance；
- AgentSwarm：批量启动并等待全部完成，返回聚合结果。

它在用户体验上做得很完整：background 不要求模型轮询，foreground 多 Agent 会分组展示，AgentSwarm 有 live panel。

#### 会话与恢复

主 Agent 和每个 child 都有独立 agents/<id>/wire.jsonl，用于 replay 和 session recovery；background task 另有 tasks/<id>.json 和 output.log，保存状态、pid、exit code 和输出。session 可关闭终端后再 resume，现有 child 也可继续同一上下文。

同时，Kimi changelog 明确说明 session close 会请求后台任务停止，并在宽限期后强制停止。因此其“持久化”应理解为历史、状态和恢复线索持久化，而不是任意后台进程永久脱离宿主。

#### 前端感知

Kimi TUI 展示每个 child 的 running、waiting、completed、failed 和 elapsed；Web 的 agents dock 与 wire replay 能在刷新后重建视图。近期修复项还专门涉及 agents dock 去重、session reload 后保留 background child 输出、权限模式切换同步等，说明它把前端一致性当成核心产品问题。

#### HITL 与权限

Kimi 文档写明 child 不直接与用户对话，只把结论交给主 Agent；AskUserQuestion 则是 Host 介导的交互工具。危险工具继续受审批策略控制，运行中的 child 也会观察权限模式变化。

当前文档存在一个值得记录的不一致：

- Agents 指南称每次 dispatch 会请求审批，除非命中 allow rule 或 YOLO；
- Built-in Tools 表将 Agent 标为默认 auto-allow，并称 AgentSwarm 在普通模式下需审批。

这更说明 OURO 不应把“调度默认是否审批”藏在隐式产品规则里，而应把 spawn 权限和 child tool 权限分别建模。

Kimi 会把主 Agent 的 always-allow 规则传播给 child。这样减少重复弹窗，但授权范围偏大。OURO 更适合将“本 child session”“整个 subtree”“root session”做成用户可见的不同批准 scope。

- [Kimi Built-in Tools 文档](https://moonshotai.github.io/kimi-code/en/reference/tools.html)

## 4. 可复用的设计范式与反模式

### P1. 底层 Spawn 与 Join 分离，模型表面保持单工具

application 底层原语应是：

    start_child(task, agent_profile, policy) -> AgentHandle
    wait(handles, timeout) -> partial_or_complete_results

模型侧只暴露一个 `SpawnAgent(execution_mode=sync|async)`：sync 在原 ToolCall 上建立 durable join，async 立即
返回 handle 并自动交付结果。这样不会把底层协调原语泄漏成额外模型工具。

收益：

- 同一套状态机覆盖同步、异步、并行和 swarm；
- application/Host 仍可先启动多个 child，再一次 wait；
- Host wait 可超时、可返回部分完成结果；
- Host 和模型都能独立控制 child。

### P2. 子智能体是会话，委派是边

Session 负责历史、模型上下文和 Run；DelegationRecord 负责“谁因为什么任务启动了谁”。分开后才能同时表达：

- fork：复制历史、探索另一分支；
- spawn：执行独立任务、只返回结论；
- resume child：同一 child Session 新开 Run；
- 多次委派：一个 child Session 可被同一父任务继续调用；
- 未来 task tree：DelegationRecord 可引用 goal/task，但不等同于 task。

### P3. History durability 不等于 in-flight durability

启动前先写 durable record；崩溃恢复时根据 child Run 对账，而不是尝试恢复 Python coroutine。

在途工具遵循 OURO 已有规则：

- queued/running Run 转 recoverable；
- running tool call 转 unknown_outcome；
- 未知副作用不自动重放；
- 用户选择 retry/resume 时创建新 Run，并保留 provenance。

### P4. 根 Host 汇聚 HITL

每个 child 自己持久化 ApprovalRecord 或 ToolInputRequest；root Host 负责展示和路由回答。请求必须显示：

- agent 名称和可读昵称；
- 父任务描述；
- session/run/tool call；
- workspace 和权限影响；
- child 当前是 sync 还是 async。

后台 child 遇到 HITL 时应进入 waiting 状态并发通知，不能静默挂死；headless 模式必须按明确策略 deny、fail 或 unattended resolution。

### P5. 权限是能力上限与审批策略的组合

推荐把两层分开：

    hard capability cap
        ∩ parent delegated cap
        ∩ agent profile cap
        ∩ workspace/resource constraints
        → candidate capability
        → auto / approval / deny policy

父 Agent 只能下放自己已有的能力；child profile 只能继续缩小。deny 优先于 allow，“自动批准”只绕过 ask，不能绕过 capability deny。

### P6. 结果必须有 provenance，不能伪装成用户消息

OpenCode/Kimi 的 synthetic result 很实用，但把结果作为 synthetic User message 注入会混淆主体。

OURO 已经区分 user、host 和 plugin 来源，建议使用专用 AgentResult：

- sync：作为原 SpawnAgent 工具调用的 ToolResult，恢复同一父 Run；
- async：先发 durable result-ready 事件，再以 host synthetic message 在安全边界进入父上下文；
- 永远包含 delegation_id、child_session_id、child_run_id 和 delivery_id；
- exact-once 标记避免进程重启后重复投递。

### P7. Parked parent 不应占用执行 permit

如果父 Run 在 sync wait 时仍占一个 RuntimeSupervisor worker，而 child 也要从同一 worker pool 获取 slot，则 max_concurrency=1 会死锁，较小并发也会出现线程池饥饿。

因此需要区分：

- active execution：模型请求、工具执行，占 permit；
- parked wait：等待 child、审批、用户输入，不占执行 permit，但 Run 仍是 durable active。

这是 OURO 实现中最容易被忽略、也最关键的调度不变量。

### P8. Interrupt、Close 和 Lifecycle Binding 分开

- interrupt：停止当前 child Run，Session 可继续；
- close：不再接收 follow-up，释放活动资源，历史仍可读；
- archive/delete：持久化层生命周期；
- bound child：父任务中断时级联取消；
- detached child：父任务结束后仍可继续，仅显式选择时允许。

默认建议 bound，尤其是共享工作区中的写任务，避免产生孤儿修改。

### 反模式

以下做法不建议进入 OURO：

1. 在父 Agent 工具处理器里递归调用完整 RuntimeService。
2. 把 forked_from 同时用于分支和委派，导致 lineage 语义不清。
3. 将 child 完成消息伪装成 user 输入。
4. 将 child 全量 transcript 回灌父上下文。
5. 让后台 child 在无 UI 环境中无限等待审批。
6. 父 Run wait child 时继续占满全局并发 slot。
7. 在首版提前引入 child、subtree、root 的“always allow”传播体系。
8. 崩溃后自动重放状态不明的 child 工具调用。

### 5.1 已具备的地基

当前实现已经非常接近可扩展目标：

- [ouro/core/state.py](../ouro/core/state.py) 的 SessionRecord 已有 root_session_id、parent_session_id；RunRecord 已有 parent_run_id。
- Run 已有 queued、running、waiting_user、waiting_approval、paused、recoverable 等 durable 状态。
- [ouro/application/supervisor.py](../ouro/application/supervisor.py) 已有全局并发、submit/wait/abort、订阅与启动恢复。
- [ouro/application/supervisor_models.py](../ouro/application/supervisor_models.py) 和 [ouro/application/runtime_activity.py](../ouro/application/runtime_activity.py) 已能把 Run、phase、tool batch 和 tool call 投影为前端活动状态。
- SessionStore 已有 LocalSessionStore 与 SQLiteSessionStore 两个同契约后端；Delegation 不能只支持文件布局。
- [ouro/core/approvals.py](../ouro/core/approvals.py) 的 ApprovalRecord 已绑定 session/run/tool_call，并记录 user 或 host_policy provenance。
- [ouro/core/interactions.py](../ouro/core/interactions.py) 已把 interactive/unattended 和 user/host_policy resolution 分开。
- [dev/specs/sessions-persistence.md](../dev/specs/sessions-persistence.md) 已规定崩溃后 Run 进入 recoverable、在途工具进入 unknown_outcome，不自动猜测结果。
- [dev/specs/future-platform.md](../dev/specs/future-platform.md) 已明确禁止用递归 RuntimeService 或裸 prompt 拼接代替任务模型。

### 5.2 需要补齐的部分

| 缺口 | 当前表现 | 建议 |
|---|---|---|
| 委派关系 | parent_session_id 主要由 fork 使用，forked_from 字段表达历史分支 | 新增 DelegationRecord；fork relation 与 spawn relation 分离 |
| Session 分类 | 无 primary/subagent 分类 | 增加 session_kind 或 relation_kind |
| 父 Run 等 child | 无 waiting_child 和 subagent_join phase | 在现有 ToolBatchCall 保存 durable wait request；Session 仍可投影为 running |
| 并发 permit | Supervisor worker 与整个 Run 生命周期绑定 | parked wait 释放 permit，恢复执行时重新竞争 |
| 根树订阅 | ActivitySnapshot 是单 session | 增加 root subtree subscription 和 AgentTreeSnapshot |
| 子结果交付 | 无 exact-once delegation result channel | 增加 DelegationResult + delivery state，复用现有 queued input |
| HITL 汇聚 | 请求绑定 child session，但无 root inbox/source DTO | 增加 root projection 和来源标签，不改变 child canonical record |
| Definition 管理 | 无 builtin/custom AgentDefinition 配置目录 | 内置不可编辑 general，用户配置 custom；两者归一化到同一运行类型 |
| 派遣参数联动 | 模型工具没有可冻结的 Agent 选项来源 | 每 Run 冻结 AgentCatalogSnapshot，自动生成 SpawnAgent.agent_id schema |
| 权限上限 | 有 session approval mode 和 tool policy，但无 delegated cap | 冻结 AgentDefinition 与显式 tool/workspace/model 等约束，执行前先求交 |
| 生命周期 | 只有单 Run abort | 增加 child interrupt、Host close、bound/detached 和 cascade policy |
| 预算 | 已有 RunBudgetPolicy，Supervisor 只有全局 max_concurrency | child 复用 RunBudgetPolicy，只增加 root max_children/max_depth/usage quota |

## 6. OURO 目标数据模型

### 6.1 AgentDefinition

AgentDefinition 是可配置模板，不是运行实例：

| 字段 | 含义 |
|---|---|
| agent_id | 稳定 identity；创建后不随 name 修改 |
| name、description | Host 展示与供模型选择的有界说明 |
| system_prompt | 位于 OURO base instructions 之后的 child 专用指令 |
| model_policy | 固定模型或继承策略 |
| tool_selection | all 或 selected ToolRegistry public names；selected 可为空 |
| sandbox_profile | read-only、workspace-write 等 |
| can_spawn | 是否可继续派生 child |
| default_budget | 复用 RunBudgetPolicy 的 model round、token、elapsed time 限额 |

首版只要求一个 code-owned `agent_id=general`：不可编辑、不可删除、不可被 user/plugin 覆盖，默认 all tools、
can_spawn=false。用户可创建/编辑/删除 custom definition，也可复制 general 为新的 custom id。

builtin/custom 只在管理 DTO 的 editable 上不同；运行时使用同一个 AgentDefinition、contract hash、目录快照、权限求交、
Session/Run、HITL 和恢复管道。AgentService 不按来源分支。

user definitions 保存到 `config/config.json` 的 `agents.revision + agents.definitions`，复用现有原子配置更新。name 不是
identity；修改/删除只影响 next Run，active Run 和旧 Delegation 继续使用冻结 contract。

all 只表示当前 Run ExtensionCatalog 的候选工具，仍需与 parent cap、workspace、depth、revocation、approval/deny 和
ToolPolicy 求交。selected 保存 ToolRegistry public names；当前未知 name 在保存时拒绝，后续缺失则保留配置、标
unavailable，不静默降级。Run snapshot 将 name 解析为包含 canonical identity/owner 和 execution contract hash 的
EffectiveToolRef，恢复时不能用同名不同 contract 工具猜测替换。

### 6.2 DelegationRecord

建议字段：

| 分组 | 字段 |
|---|---|
| identity | delegation_id、root_session_id |
| parent | parent_session_id、parent_run_id、parent_tool_call_id |
| child | child_session_id、current_child_run_id、agent_id、nickname |
| task | description、initial_message_id、prompt_digest、显式 resource refs、task_id 可选 |
| execution | sync/async、bound/detached、depth、spawn_state、control_state |
| policy | frozen AgentDefinition、EffectiveToolRefs、显式 delegated constraints、approval_mode、interaction_mode、RunBudgetPolicy |
| result | result_message_id、result_digest、delivery_id、delivery_status |
| time/error | created_at、started_at、ended_at、error |

Delegation 不镜像 child 执行状态，只保存关系自身状态：

    requested
      → child_created
      → submitted | failed

    control_state = open | closed

child Run 是 queued/running/waiting/terminal 的唯一执行状态权威；DelegationRecord 只保存关系创建阶段、冻结契约和结果
投递状态。Host 状态从 child Run 投影，不在 relation 上同步第二套状态机。

### 6.3 Session/Run 最小改动

SessionRecord：

- 增加 session_kind = primary | subagent；
- root_session_id 继续表示树根；
- parent_session_id 表示直接父会话；
- forked_from_* 只表示分支复制；
- delegation_id 可存在 metadata 或显式字段，但不能靠标题反推。

RunRecord：

- 增加 waiting_child 到 RunStatus，并把 AgentWaitRequest/Resolution 保存到现有 ToolBatchCall；
- 增加 subagent_join RunPhase；
- parent Run 保持 active，但 SessionStatus 可继续映射为 running，避免扩大顶层粗粒度状态；
- active_tool_batch 中的 AgentWait/Agent 调用应有 waiting_child 状态。
- parent Run 持久化 AgentCatalogSnapshot，保证重启后继续使用原 agent_id schema 和 definition contract。

## 7. 控制面与执行语义

### 7.1 Application API

配置管理由细粒度 AgentDefinitionService 提供：

    agent_definitions.list/get/create/update/delete/copy_builtin
    agent_definitions.tool_options/compatibility

运行控制由 AgentService 提供，不新增大一统 facade：

    agents.spawn(parent_run, request) -> AgentHandle
    agents.wait(parent_run, handles, timeout) -> AgentWaitResult
    agents.send(handle, message, delivery=follow_up|steer)
    agents.interrupt(handle, reason)
    agents.close(handle)
    agents.list(root_session_id)
    agents.read(handle, include_history=false)

模型首版工具收敛为 SpawnAgent（可显示为“派遣子智能体”）、ListAgents、SendAgentMessage、InterruptAgent。
read/close 保留为 Host application API，模型结果查询并入 ListAgents。

每个 parent Run 在取得 ExtensionCatalogLease 后冻结 AgentCatalogSnapshot。SpawnAgent.agent_id enum/oneOf、选项的
name/description 和 handler 解析都来自这个同一快照；system_prompt/完整 tools 不进入工具描述。配置 CRUD 从 next_run
生效，active Run 不热切 schema。

底层 spawn 始终尽快返回 durable handle。SpawnAgent(sync) 在 application 层调用 spawn 后，直接在原
ToolBatchCall 建立 wait request，不先向父模型提交 handle ToolResult；async 才立即返回 handle。这使 Host API 与
模型工具共享同一底层语义，且不复制 batch/turn/tool identity。

Agent 控制工具只产生类型化 intent；AgentService 通过窄 RunScheduler port 调用现有 RuntimeSupervisor。LocalApplication
负责装配 RuntimeService、Supervisor、AgentDefinitionService 和 AgentService。标准 Agent-capable Host 必须经过
Supervisor，裸 RuntimeService 不注册 Agent 工具或在缺少装配时 fail closed，不新增第二个 scheduler 或 reverse
host.call。

### 7.2 提交事务与幂等

安全顺序：

1. 从 parent Run AgentCatalogSnapshot 按 agent_id 解析冻结 definition/EffectiveToolRefs；
2. 以 parent_tool_call_id + logical_slot 生成稳定 delegation id；
3. 写 requested DelegationRecord；
4. 创建 child Session，写 root/parent/session_kind；
5. 更新 DelegationRecord.child_session_id；
6. 创建 child queued Run；
7. 以专用 DelegatedTaskInput 和 delegation_id 交给 Supervisor，初始任务写为带委派 provenance 的 user message；
8. 发 agent_spawned；后续执行状态继续使用 child Run 事件。

每一步可重复执行且能检测已存在记录。启动恢复扫描“不完整边”：

- 有 relation、无 child session：标 failed 或安全重建；
- 有 child session、无 Run：保持 queued/recoverable，等待用户或策略继续；
- child Run terminal、result 未交付：重建 AgentResult 并 exact-once 投递；
- child Run active 但无 live job：沿用 OURO recovery，转 recoverable。

### 7.3 Sync 与 Async 结果

sync：

- 父 Agent 调用 Spawn/Agent；
- child 启动；
- 父 tool call 进入 waiting_child；
- 父执行 permit 释放；
- child terminal 后，结果提交为父 tool result；
- 父 Run 恢复竞争 permit 并继续。

async：

- spawn 返回 AgentHandle/TaskId；
- 父 Agent 可继续或结束本轮；
- child terminal 立即更新 UI；
- AgentResult 进入专用 pending-result queue；
- 到父模型的安全边界，以 host synthetic message 注入；
- delivery_id 确保只进入一次上下文。

child completion 不得冒充新 user turn。模型侧投递策略不再作为参数暴露：

- async 固定 next_boundary：父 active 时进入下一安全模型边界，父 idle 时启动 host-origin Run；
- sync 固定 resume_waiter：恢复原 SpawnAgent ToolCall；
- Host 直接派遣可使用 notify_only，只更新 Host 投影。

### 7.4 中断、恢复和级联

- interrupt child：停止当前 child Run；Delegation relation 与 child Session 保留，可 resume。
- resume child：同一 child Session 创建新的 Run，记录 resumed_from_run_id；不修改旧 Run。
- interrupt parent：默认取消 bound children；detached children继续。
- parent 失败：已完成 child 结果保留；未完成 bound child 取消或转 recoverable。
- root archive：默认连同 descendant sessions 归档；delete 需二次确认并明确级联范围。
- close child：只关闭控制句柄/活动资源，不删除历史。

## 8. 前端事件与活动树

### 8.1 不复制 child 事件，只增加关系事件

child 继续产生现有 run/model/tool/interaction 事件。只新增无法从 child Run 无歧义表达的少量关系/交付事件：

- agent_spawned
- agent_result_ready
- agent_result_delivered
- agent_closed

每个前端 DTO 增加可推导的 scope：

    root_session_id
    parent_session_id
    delegation_id
    agent_id
    agent_name
    nickname
    depth

不要把 scope 重复写入每条 canonical child event；可由 Session/Delegation join 后投影。高吞吐 delta 仍保留 per-session sequence，root aggregator 使用自己的 projection revision，避免假设多 Session sequence 可直接全序比较。

### 8.2 AgentTreeSnapshot

建议 Host 获得一个 bounded snapshot：

| 字段 | 含义 |
|---|---|
| root_session_id、revision | 树身份和投影版本 |
| nodes | primary/child session 的当前 activity |
| edges | delegation relation |
| active_count、waiting_count | 汇总 |
| pending_interactions | 根 inbox 的审批/问题摘要 |
| usage | 每 child 和整棵树的 token/time/cost |

每个 node 至少展示：

- agent name/nickname、任务摘要；
- queued/running/waiting approval/waiting user/completed/failed/aborted/recoverable；
- elapsed、当前 phase、当前 tool；
- sync/async、bound/detached；
- Stop、Open、Steer/Follow-up 控件。

根 UI 默认展示摘要，展开后查看 child transcript 和工具事件。不要把 reasoning 或大段日志自动复制到根会话。

## 9. HITL 目标机制

### 9.1 Interaction inbox projection

现有 ApprovalRecord 和 ToolInputRequest 保持 child-local canonical。新增可重建的 root interaction inbox projection，
不建立新的 Store、Broker 或状态机：

    child request
      → durable waiting state
      → root interaction inbox
      → Host shows source and impact
      → response routed to exact child run/tool call
      → child continues

父 Agent 是否等待取决于执行模式：

- sync：父 Run 已在 waiting_child；
- async：父 Run 不被阻塞，只有 child waiting；
- 多个 child 同时请求：根 inbox 排队或并列展示，不允许 modal 丢失来源。

当前循环交互 Host 已完成 sync 路径：收到 `waiting_child` 后先订阅 AgentTree，再读取 inbox 并按精确 child
identity 路由 approval/input；决议提交后继续等待 canonical parent 状态变化，不轮询或把 stdin 错当成新的根消息。
interaction projection 仅携带有界工具参数预览，完整调用仍归 child Run 所有。

### 9.2 审批与提问分开

OURO 当前已经有 approval_mode 与 interaction_mode，建议继续保持两条正交轴：

- approval_mode：工具动作 auto / approval / deny；
- interaction_mode：interactive / unattended。

Kimi 对 YOLO 和 Auto 的区分值得借鉴：自动批准工具不等于禁止 Agent 提问。OURO 可进一步定义：

- interactive：允许 root UI 提问；
- unattended：调用 tool 的 UnattendedResolution，或按 AgentDefinition 的 fail/skip/default 策略；
- headless-approval：无 Host 时 ask 统一变 deny/fail，绝不无限等待。

### 9.3 审批继承边界

首版复用现有逐 ToolCall ApprovalRecord 和 child Session approval_mode，不新增 child_session/subtree/root_session
记忆型授权。批准 spawn 不批准 child 的危险工具；一次 child 批准不传播到 sibling、root 或未来 descendant。只有该
能力成为全产品权限系统的独立需求后，才单独设计持久化、撤销、匹配和传播语义。

## 10. 工具权限目标机制

### 10.1 Spawn 自身也是权限

需要独立控制：

- 是否允许创建 child；
- 可创建哪些 agent_id；
- 最大 depth；
- 最大同时 child 数；
- 可否 async/detached；
- 可否向 child 下放写工具；
- 可否向 child 下放网络、MCP、shell。

这相当于 OpenCode 的 permission.task，但应叠加资源预算和 lifecycle 限制。

### 10.2 推荐的继承规则

1. 平台/管理员 hard deny 永远保留。
2. 父 session hard deny 永远保留。
3. 父 Run 只能从自身 capability 中选择下放子集。
4. AgentDefinition 的 all/selected EffectiveToolRefs 与其他约束再收窄；all 不是权限授权。
5. child session 的临时批准只能作用于候选能力，不能扩权。
6. 工具声明为 tool-controlled 的强制策略继续不可绕过。
7. parent 权限在 child 运行期间收紧时，新的调用立即按新上限重算；已批准但未执行的调用重新校验。

### 10.3 工作区与并行写入

Codex 官方也提醒并行写任务会产生冲突。建议：

- builtin general 和 custom 都受同一 workspace policy；
- 首版 writer concurrency=1，同一文件写入需冲突检测；
- 后续提供 per-child git worktree；
- 并行 writer 不允许自动合并到父工作区；
- child 结果返回 changed files、diff reference 和验证结果，由父 Agent 归并。

## 11. 推荐 MVP 与演进路线

### M1：一等 child Session，先做 sync

目标：

- builtin general + custom AgentDefinition CRUD；
- name/description/system_prompt/all-or-selected tools；
- Run-frozen AgentCatalogSnapshot 与 SpawnAgent.agent_id 自动联动；
- DelegationRecord；

- child Session/Run 复用现有持久化；

- AgentTreeSnapshot 与 CLI 最小展示；
- max_depth 默认 1，root max_children 默认 4；
- bound lifecycle；
- child approval/question 进入 root inbox。

暂不做：

- detached；
- nested child；
- swarm；
- 自动 worktree；

### M2：async 与可靠投递

## 12. 必须覆盖的测试

1. max_concurrency=1 时 sync parent 等 child 不死锁。
2. spawn 写 relation 后、创建 Session 前崩溃，启动恢复可对账。
3. child tool running 时进程崩溃，tool 进入 unknown_outcome，绝不自动重放。
4. sync child 请求审批，根 UI 显示正确来源，批准后父 Run 继续。
5. async child 请求问题，父 Run 可继续，child 独立 waiting。
6. 多 child 同时审批/提问，不串答、不丢失。
7. 父 hard deny 不能被 child AgentDefinition 或 auto mode 放宽。
8. 权限在 child 运行中收紧，未执行调用重新校验。
9. async result 在崩溃前后只投递一次。
10. interrupt parent 正确级联 bound child，首版 detached 请求明确拒绝。
11. resume child 创建新 Run，旧 Run 状态和 provenance 不被覆盖。
12. root tree 刷新/重连后与 canonical Session/Run/Delegation 一致。
13. 两个 writer 修改同一文件时触发冲突策略。
14. 无 UI/headless 场景遇到新审批时确定性失败或拒绝，不悬挂。
15. builtin general 始终存在且 update/delete/覆盖失败，copy 产生新 custom agent_id。
16. builtin/custom 以同一参数化测试验证 spawn、permission、HITL、恢复和结果交付。
17. name rename 不改变 agent_id，删除 custom 不破坏 active Run 或旧 Delegation resume。
18. all/selected/selected-empty 正确解析，all 不突破 parent hard deny/ToolPolicy/depth。
19. selected tool 后续不可用时配置保留且新 Run 不再暴露该 definition，不静默降级。
20. AgentDefinition CRUD 自动改变 next Run SpawnAgent schema，active Run schema/handler 保持同一 snapshot。
21. custom system_prompt 不替换 OURO base instructions，也不泄漏到派遣工具描述、事件或根树。

## 13. 建议立即冻结的架构决策

在进入编码前，建议先通过以下 ADR：

1. **子智能体实例等于 Session，执行等于 Run。**
2. **Delegation 与 Fork 是两种独立 relation。**
3. **底层 spawn 永远非阻塞；模型侧 SpawnAgent(sync) 在原 ToolCall 上做 durable join。**
4. **waiting_child 是 durable 状态，parked wait 不占执行 permit。**
5. **root Host 统一展示 HITL，child 保存 canonical request。**
6. **权限按显式 capability intersection，首版审批逐 ToolCall 且不向 sibling/root/descendant 传播。**
7. **async result 使用 host provenance 和 exact-once delivery，不伪装 user。**
8. **MVP 只承诺 durable history/relation，不承诺崩溃后透明复活执行。**
9. **builtin general 与 custom definition 只在 editable 上不同，运行时使用同一管道。**
10. **agent_id 是 identity；每个 Run 冻结 AgentCatalogSnapshot，派遣 schema 与 handler 从同一快照生成。**
11. **tool_selection=all 只表示候选工具，不表示授权。**

这些决策一旦稳定，OURO 可以最大限度复用现有 runtime，而不会把子智能体做成一块难以恢复、难以展示、难以治理
权限的特殊执行路径。
