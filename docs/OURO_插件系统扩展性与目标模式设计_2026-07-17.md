# OURO 插件系统扩展性与目标架构设计

状态：目标设计（2026-07-17；B1-B8 已实现）

本文定义 OURO 作为强扩展个人智能体时，插件系统应采用的整体结构，并以 `/goal` 说明深层插件如何复用该结构。
当前实现问题见[插件系统架构审查](OURO_插件系统扩展性架构与Pi对照_2026-07-17.md)，规范性约束见
[插件系统目标规格](../dev/specs/plugin-system.md)。

## 1. 设计目标

OURO 插件不是外部脚本集合，而是系统级扩展模块。目标是让用户能够用插件改变 Agent 的工具、上下文、运行策略、
跨 Run 行为和长期资源，同时不破坏 OURO 对 Session、Run、工具审批、持久化和 Host 的统一控制。

设计必须同时满足：

- 插件能够深度参与真实 Agent 生命周期；
- 插件贡献可以组合、诊断、撤销和原子替换；
- 一个 Run 从开始到结束使用一致的扩展目录；
- 插件更新失败不影响正在服务的旧版本；
- CLI、TUI、Desktop 和其他 Host 共享同一 application 语义；
- 个人用户可以理解和控制插件，而不承担企业插件平台的复杂度。

## 2. 产品决策

### 2.1 插件只有两类

- `builtin`：随 OURO 装配的内置插件，属于产品实现，不能被用户插件覆盖、更新或卸载；
- `user`：用户安装到当前 `OURO_HOME` 的系统插件，默认 disabled，显式授权和启用。

不存在项目插件、workspace 插件、managed 插件或 scope overlay。同一个 `OURO_HOME` 中，每个 user plugin id 只有
一个 selected digest、配置和期望启用状态。

workspace 仍是 Run 和工具调用的重要执行上下文，但不决定插件发现、安装或激活。Skills 与提示词可以继续从
workspace 发现，因为它们是按上下文使用的资源，不是长期运行的系统模块。

### 2.2 安全采用信任模型，而非沙箱模型

用户插件是在用户明确安装和启用后运行的可信扩展代码：

- in-process 拥有 OURO 进程权限；
- worker 拥有当前 OS 用户权限，但与 OURO 进程、依赖和协议隔离；
- permission 约束 OURO 提供的 Host service，也是授权界面的能力声明；
- ToolExecutor、凭据、路径、安装校验和 contribution ownership 仍是必须保持的核心边界。

不引入 OS sandbox、publisher trust root、managed policy 和多租户权限系统。

### 2.3 开发期直接修正契约

当前没有需要保护的公开插件生态。发现 Manifest、SDK、worker protocol 或 state 模型错误时，直接修改权威契约并
严格拒绝旧格式，不增加 deprecated 字段、双写、迁移分支或兼容 adapter。

不可变候选安装、原子切换和失败回退仍然保留，因为它们保证一次当前操作的事务正确性，不属于历史兼容负担。

## 3. 系统模型

插件系统分为五个概念：

```text
Plugin Package
  静态 manifest、资源和可选 runtime
        |
        v
Installed User Plugin
  来源事实、digest、可选候选版本
        |
        v
Plugin Activation
  selected digest、desired state、active configuration revision、授权
        |
        v
Plugin Generation
  当前进程中的实例、资源和贡献 owner
        |
        v
Extension Catalog
  一个 Run 使用的不可变、完整扩展目录
```

Package、Install、Activation、Generation 和 Catalog 不得合并成一个可变 `Plugin` 对象。它们的变化原因不同：

- 包内容由插件作者改变；
- 安装事实由 installer 改变；
- 激活意图与 configuration revision reference 由用户改变；
- generation 由 runtime 生命周期改变；
- catalog 由 active generation 集合改变。

## 4. 不可变 Extension Catalog

`ExtensionCatalog` 是运行时一致性的核心，而不是若干全局 registry 的临时快照。它包含当前可用的：

- Tools；
- Commands；
- Observational Hooks 与 Context providers；
- Turn policies；
- Compaction strategies；
- Continuation policies；
- Tool policies；
- Skills；
- MCP 投影；
- 每个 contribution 的 owner、contract hash 和 generation gate。

`background_services` 不作为 Run 可调用目录保存在 Catalog 中，而是当前 plugin activation 的单例资源。旧、新
Catalog 可以并存，但 Host 严格按“旧代停止、新代启动”串行转交同一 plugin id 的后台服务，避免定时任务、
listener 或轮询器重复产生副作用。

### 4.1 Catalog 发布

```text
解析受影响 generation closure
  -> 按拓扑构建候选 generation set
  -> prepare contributions 和无自主副作用的候选资源
  -> 验证必需 contribution、依赖契约与健康状态
  -> 由当前 catalog + 候选 generation set 构建新 catalog
  -> expected-state compare-and-commit
  -> 打开新 generation gate 并原子替换 current catalog pointer
  -> 按逆拓扑停止旧后台服务，再按拓扑启动新后台服务
  -> 新 Run 获取新 catalog
  -> 旧 Run 保持旧 catalog
  -> 旧 generation set 引用归零后停止
```

插件代码、I/O 和资源启动不能发生在 catalog pointer 临界区中；临界区只替换已完整构建的 Catalog pointer。
候选阶段不启动声明式 Background Service；通过 Host data API 的写入进入 generation-local staging，发布成功后才
提交，失败候选整体丢弃。`python-inprocess` 是 full trust，直接绕过 Host API 的外部副作用不属于该事务保证。

### 4.2 Run 绑定

每个 Run 在开始时持有一个 catalog lease。模型工具目录、Hook、策略和 compaction 都从该 catalog 解析，不能在
Run 中途回读 current catalog。

Run 不必租用与自己无关的全局 mutation lock。启用或更新一个插件不会阻止已有 Run，也不会要求它们切换实现。

### 4.3 撤权

Catalog 不可变不等于撤权必须等待旧 Run。每个 user generation 持有一个可撤销 gate；每次进入插件 Tool、Command、
Hook、Policy 或 continuation 前检查 gate。revoke/disable 可以先关闭 gate，使后续调用失败，再按正常引用释放停止资源。

这只保证 OURO 不再调用插件，不宣称能阻止已经受信代码直接执行任意 OS 行为。

## 5. Contribution 元架构

插件作者只能使用 OURO 明确提供的 contribution 类型。为了让 OURO 内部新增类型不再散落修改多个中心化分支，
Host 维护一个小型 `ContributionTypeAdapter` 集合。每个 adapter 负责：

- Manifest declaration 校验；
- SDK/worker descriptor 适配；
- identity、冲突与 optional 规则；
- contract hash；
- 合并到 `ExtensionCatalog`；
- owner 撤销和诊断投影。

它不是公开的动态插件接口，也不是通用 middleware。真实语义仍由具体类型定义。例如 Tool Policy 使用最严格值，
Continuation 冲突时暂停，观察 Hook 失败隔离；它们不能被抽象成相同的“优先级回调”。

首批 contribution 保持：

- `tools`；
- `commands`；
- `hooks`；
- `context_providers`；
- `turn_policies`；
- `compaction_strategies`；
- `skills`；
- `mcp_servers`；
- `background_services`；
- `continuation_policies`；
- `tool_policies`。

新增 Agent、provider、resource、UI 或 message contribution 必须由至少一个真实 user plugin 需求驱动。

Adapter 同时标明 contribution 是 snapshot-bound 还是 activation-singleton。Tool、Hook、Context Provider、
Turn Policy、Command、Skill 和 MCP tool projection 属于前者；Background Service 属于后者，不能伪装成
Catalog callback。

该边界现已落地为 `ouro/plugins/contribution_types.py` 中的不可变 Host 清单。每个类型记录组合 SDK、worker、
prepare/optional、contract、resource 与 projection facet；共享 projection 只代表相同 Catalog 目标，不合并类型
语义。Skill/MCP resource facet 仅为实际准备成功的资源产出 contract，Background Service projection 为显式 no-op。
清单没有用户注册入口，也不提供万能事件分发。

## 6. Runtime 设计

### 6.1 Declarative

用于 Skills、MCP 描述和未来明确支持的静态资源。没有 Python entrypoint。

插件启用时，其所有 MCP server 随 generation 启动；Manifest 不提供无调用入口的 `auto_start=false`。必需 MCP 失败
使 activation 失败，可选 MCP 失败使 generation degraded。

### 6.2 Python in-process

用于最深扩展和最低调用开销。要求：

- user 对 exact digest 授予 code trust；
- entrypoint 使用 plugin-owned 顶层 namespace；
- Manifest namespace `calendar` 的 canonical 顶层名是 `calendar_plugin`（已经以 `_plugin` 结尾时不重复添加）；
- Host 检查 canonical module 冲突，但把实际 generation 加载到 `_ouro_plugin_<generation_id>` 私有 module tree；
- bundled dependency 位于 owned package 并使用相对 import，代际关闭删除完整私有 module tree；
- `prepare` 不发布全局贡献、不启动长期资源；
- `start/stop` 管理 owner 资源且 stop 幂等；候选期 supervised task 等待 generation 发布，Host data 写入被隔离暂存；
- 自主长期任务必须声明为 Background Service；普通 supervised task 不能绕过 service gate；
- 不向 OURO 主解释器安装第三方依赖。

需要独立依赖环境、多语言或崩溃隔离时，插件应使用 worker，而不是继续复杂化 Python import 清理。

### 6.3 Worker

worker 是语言无关的进程和协议边界，不是安全沙箱。基础协议提供 initialize、prepare、lifecycle、contribution
calls、cancel、diagnostic 和 shutdown。

Host 必须保证：

- timeout 和 task cancellation 都发送 cancel；
- worker 退出后撤销可调用 contribution，并投影 failed；
- stdout 只承载有大小上限的协议消息；
- stderr 限流、脱敏；
- shutdown 关闭进程树。

当前阶段只提供显式 restart，不建设自动重启、熔断和每插件环境管理。反向 Host RPC 按真实能力逐项增加，不能
先定义万能 `host.call`。

## 7. 授权与配置

### 7.1 最小授权模型

- Builtin plugin 不需要用户 code trust 或 capability authorization；
- User plugin 安装后默认 disabled；
- executable digest 首次启用前需要 code trust；
- contribution 或 Host-service permission 发生变化时需要 capability authorization；
- user tool 不能仅凭 Manifest 获得自动执行权；
- credential 只能通过 Manifest 声明 slot 和本地 reference 解析。

Capability 与 permission 可以在 UI/CLI 中一次确认，但状态模型继续分离代码执行信任和 Host 能力授权，避免二者
变化时无法判断应使哪项授权失效。

### 7.2 Permission 语义

Permission id 来自 OURO 的封闭核心注册表。每项 permission 必须有真实 Host service 或明确的执行披露语义；未知
id 严格拒绝，不允许插件用自定义字符串制造虚假权限。

当前核心 permission 包括 credential slot、MCP process/network 披露、Session input 和 background continuation。
只有在提供对应 service 时，才增加 filesystem、resource 或 model permission。

### 7.3 配置

配置值与 credential binding reference 规范化后保存为不可变 revision；秘密值不进入 revision。每个 installed
digest 可以保存多个 revision，active activation 只引用其中一个。配置命令先创建候选 revision，再以它构建
generation set；只有 Catalog 发布成功才切换 active revision reference。失败不改变 current catalog 或旧 revision。

没有配置 schema 的插件使用规范化空 revision；存在 required 字段但尚未满足时才进入 `needs_configuration`。

durable contract 引用 revision fingerprint；被 active generation 或 durable Run 引用的 revision 不得 GC。这样同一
digest 的配置更新也能与选版使用相同的候选发布语义，而不是依靠覆盖后补偿。

插件数据按 plugin id 跨版本保留。候选 data view 可读取共享数据，但写入/删除只修改隔离 staging；仅发布成功后
提交，候选失败不改变旧代仍在使用的数据。
当前不提供通用数据迁移协议或向后兼容承诺；需要改变数据格式时，插件必须要求显式 disable 后处理，或由用户
清空重建。出现多个真实插件需要事务迁移后再设计公共协议。

## 8. 依赖与状态协调

Plugin dependency 只使用 `plugin_id + SemVer range`，不包含没有实现语义的 optional feature。

一个 activation reconciler 根据 persistent desired state 和 observed generation state 工作：

1. 解析 selected digest 的依赖图；
2. 拒绝 cycle、缺失版本和范围冲突；
3. 先确保全部依赖 active；
4. 依赖失败时把依赖者标记为 blocked，不启动其 runtime；
5. 依赖恢复后重新协调；
6. 关闭时按逆拓扑顺序 drain。

依赖 package digest、configuration 或 contract 改变时，reconciler 计算所有受影响的 active dependant，并按拓扑
构建候选 generation set。只有整个集合和候选 Catalog 都成功才一次发布；依赖者不得带着旧 dependency lock 留在
新 Catalog。依赖被显式 disabled 时不自动改写其 desired state，依赖者保持 blocked 并给出诊断。

状态至少区分 `disabled`、`needs_configuration`、`needs_code_trust`、`needs_authorization`、`ready`、`starting`、
`active`、`degraded`、`blocked`、`stopping` 和 `failed`。状态必须来自同一 reconciler，不能由一次命令返回值和
另一套查询逻辑分别推导。

## 9. Skills 与 MCP

### 9.1 Plugin Skills

Plugin Skill 进入现有 Skill Catalog，来源为 `plugin`，并携带 plugin id、package digest 和 generation owner。
Skill 的名称冲突、禁用、metadata 校验和按需读取复用同一套逻辑，不再用 Hook 注入第二份技能目录。

运行时把基础 user/workspace Skill 与插件 Skill 一起冻结到每个 Run 的 `ExtensionCatalogLease`；每轮模型请求从该
lease 生成提示词。冲突使候选 Catalog 失败，每个插件声明只允许一个同名 `SKILL.md`，Catalog 固定其不可变包路径。

用户级和 workspace 级 Skill 来源保持不变；这不意味着 workspace 可以安装插件。

### 9.2 Plugin MCP

Plugin MCP 复用 `MCPManager` 和 ToolExecutor，但其配置与连接由 plugin generation owner 持有。启用插件即连接，
禁用或 generation retire 即关闭。发现的工具冻结在该 catalog 中；server 后续工具变化在下一 generation 生效。
只有 connected server 产生资源 contract；required 启动失败中止候选，optional 失败产生 degraded，且不会伪造
空 contract。

## 10. 会话控制与 `/goal`

插件不能直接取得 `RuntimeService`、`SessionStore` 或 session lock。需要改变后续执行时，通过类型化控制面表达意图：

- Command 返回 `SessionInput`；
- Continuation policy 对终态 `RunOutcome` 返回 `continue/complete/pause/fail/ignore`；
- Application 负责来源、幂等队列、Run lock、冲突和持久化。

`/goal` 插件映射如下：

| 用户动作 | 插件职责 | OURO 职责 |
|---|---|---|
| 创建目标 | 保存插件私有目标状态，返回初始输入请求 | 写入 synthetic input 并创建 Run |
| 每轮判断 | 根据目标状态和 `RunOutcome` 返回 continuation | 处理冲突、幂等入队和 checkpoint |
| 修改/引导 | 更新插件状态，返回 steer/follow-up 请求 | 按当前 Session 并发规则提交 |
| 暂停/恢复 | 改变插件目标状态 | 决定何时创建下一 Run |
| 取消 | 不自行复活失败或 abort Run | Host 取消当前 Run 并释放资源 |

该场景证明插件可以扩展跨 Run 行为，但不要求 OURO 建立通用 workflow engine。

## 11. Durable recovery

Run 持久化它使用的 catalog contract，至少包括：

- plugin id；
- package digest；
- 有效配置指纹；
- dependency lock；
- Plugin API/worker protocol；
- contribution contract hashes。

进程重启后，只要能够从相同 package、配置和依赖重建相同 `execution_contract_hash`，即可创建新的进程内
generation 并恢复 Run。随机 `generation_id` 只用于当前进程 owner 和诊断，不是跨进程恢复条件。

恢复优先复用当前等价 generation；current selection 已更新时，可从仍安装的旧 digest、immutable configuration
revision 和依赖锁构建非当前 generation。该 owner 不改变 persistent activation，不接管 Background Service 单例，
只由对应 durable Catalog lease 保留并在释放后回收。

如果 contract 不一致或 package 缺失，恢复显式失败；绝不能仅按同名 Tool 或 contribution 替代。

## 12. 更新、回滚与失败

Update 只安装候选 digest，不原地覆盖 current package。用户选择候选并完成必要授权后，runtime 构建受影响的
generation set；只有新 catalog 发布成功才提交 active selection。失败时 current catalog、依赖者和 selected digest
均不变。

Rollback 选择本地仍存在的 digest，再走同一 activation 流程。它保证操作失败不破坏当前版本，但不承诺兼容任意
历史 OURO schema 或任意插件私有数据格式。

故障规则：

- 必需 contribution、实例 start 或必需 MCP 失败：候选 activation 失败；
- 可选 contribution 失败：generation degraded，诊断可见；
- worker 退出：generation failed，调用入口撤销；
- observer Hook 失败：隔离该 Hook，不破坏 Run；
- optional Context Provider 失败：省略该项；required provider 失败：阻断本轮；
- Turn Policy 失败：暂停 Run，不能把候选回复静默视为完成；
- Tool Policy 失败：拒绝工具；
- Continuation 冲突或失败：暂停自动续跑；
- 旧 generation stop 失败：记录错误并继续回收其他 owner 资源。

## 13. 非目标

- 项目/workspace 插件；
- OS sandbox、企业权限中心和多租户隔离；
- Marketplace、签名和 publisher policy；
- 自动第三方依赖安装；
- 万能 Host RPC、事件总线或 middleware；
- 插件动态定义新 extension point；
- Run 中途动态覆盖 builtin 或改变 active tool contract；
- 对开发期旧 Manifest、state、SDK 或 worker protocol 保留兼容层。

## 14. 验收重点

- 候选 generation 启动失败时旧 catalog 始终可用；
- 长 Run 不阻止无关插件启停，新旧 Run 可以持有不同 catalog；
- builtin identity 不能被 user plugin 覆盖；
- 没有任何 workspace plugin discovery 或 activation 路径；
- 依赖失败时依赖者不会启动，查询状态与命令结果一致；
- worker cancel、退出和 shutdown 无悬挂 request/process；
- Plugin Skill 使用统一 Skill Catalog；
- 插件 MCP 随 generation 启停，不存在无入口的 dormant 声明；
- 相同 execution contract 可以跨进程重建，不同 contract 稳定拒绝恢复；
- 新 contribution 类型通过同一 adapter 边界接入 catalog、contract 和 owner lifecycle。
