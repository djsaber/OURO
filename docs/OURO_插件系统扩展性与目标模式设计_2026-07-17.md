# OURO 插件系统扩展性与目标模式设计

状态：已实现（2026-07-17）

本文把 `/goal` 作为跨多个 Run 持续工作的详细验收场景；它不是插件架构的唯一目标。通用扩展架构、Pi 对照
和新增扩展点的判定规则见
[OURO 插件系统扩展性架构与 Pi 对照](OURO_插件系统扩展性架构与Pi对照_2026-07-17.md)。
本文说明 OURO 插件目前能够扩展到什么程度，以及 `/goal` 一类模式应如何实现。
通用包、授权、generation 和 worker 契约仍以
[插件系统规格](../dev/specs/plugin-system.md)为准。

## 1. 结论

OURO 的插件扩展分为两个平面：

- **能力贡献面**：插件向 Agent 提供工具、命令、上下文、压缩策略、Skills、MCP、Hook 和后台资源；
- **会话控制面**：应用层决定何时创建 Run、如何排队输入、如何持久化来源、何时续跑，以及冲突或失败时
  如何停下。

能力贡献面已经较完整。此前的主要缺口是：插件虽然能观察 Run，却不能通过稳定公共契约请求下一轮 Run；
交互 slash command 也没有直接映射插件命令；工具 handler 无法取得 Host workspace/cancel 上下文，
`before_tool_call` 也没有安全、可组合的阻断结果。现在这些缺口分别由 `continuation_policies`、类型化
`SessionInput`、Host 命令路由、`ToolExecutionContext` 与限制性 `tool_policies` 补齐。

插件仍不能直接取得 `RuntimeService`、`SessionStore` 或 session lock。这不是扩展性不足，而是为了保证插件
不能绕过 canonical 消息、单 Session Run 锁、审批、恢复和 generation lease。

## 2. 当前可扩展范围

| 扩展点 | 能做什么 | 不能做什么 |
|---|---|---|
| Tool | 增加模型可调用能力，经过 schema、权限、审批和恢复；可选接收 workspace/cancel 上下文 | 绕过 `ToolExecutor` 或自行批准 |
| Tool policy | 把 `auto` 提升为审批或拒绝调用，实现 plan mode、危险命令和保护路径 | 放宽 Host 权限、批准调用或改写参数 |
| Command | 暴露 `<plugin_id>:<name>` Host-neutral 命令；经授权可返回会话输入请求 | 直接操作 CLI/TUI 或写 SessionStore |
| Context provider | 在上下文构建时追加带 owner 的上下文 | 修改 canonical 历史 |
| Compaction strategy | 替换摘要策略并记录 contract | 改写消息事实或覆盖其他 owner |
| Hook | `after_context_build`、`before_tool_call`、`after_tool_call`、`on_event`、`after_run` | 把观察型 Hook 当成任意状态 mutation API |
| Continuation policy | 在终态 Agent Run 后返回 `continue/complete/pause/fail/ignore` | 自行启动 Run、伪造用户消息或静默解决冲突 |
| Skills / MCP | 贡献指令资源和经 OURO 工具边界投影的远端能力 | 绕过工具权限与 generation 冻结 |
| Background service | 管理插件自有连接、监听器和 task | 获得隐式 Session 写权限 |

Python in-process 插件拥有同进程代码权限；worker 提供进程和协议隔离，但没有 OS sandbox。Host-service
permission 对公共 OURO API 强制生效，同时也是对 full-trust 代码的审计声明。

## 3. 为什么不使用普通 `after_run` Hook 续跑

普通 Hook 适合观察或局部富化，不适合决定新的 Run，原因包括：

1. 多个 Hook 同时返回“继续”时缺少唯一控制权；
2. Hook 重试可能重复创建消息或 Run；
3. 插件升级后，恢复必须知道原 Run 使用的精确 policy generation；
4. 续跑必须在释放旧 Run lock 后、释放 extension generation lease 前完成决策；
5. 插件输入不能伪装成 `role=user`。

因此 `after_run` 保持 fail-open 的观察型 Hook；会改变后续执行的决定使用单独的
`ContinuationPolicyContribution`，由 application service 解释。

## 4. 续跑协议

插件策略接收只读 `RunOutcome`：session/run identity、终态、origin、最终文本、错误和 usage。返回：

- `ignore`：本策略不请求控制；
- `continue`：请求加入一个 `follow_up` 或 `steer` 合成输入，必须提供非空 prompt；
- `complete`：目标已完成，不再自动运行；
- `pause`：保留插件目标状态，但不自动继续；
- `fail`：插件目标判定失败，不自动继续。

每个 Agent Run 启动前会持久化 `RunContinuationCheckpoint`：

- `decision_id` 与稳定 `queue_id`；
- policy 的 plugin id、local id、version、digest、generation 和 contract hash；
- 最终 action、controller、reason、state revision 和 resolved time。

终态后的执行顺序为：

```text
Run 达到终态
  -> 释放该 Run 的 Session run lock
  -> 用冻结的 generation 调用 continuation policy
  -> application 聚合并校验决策
  -> 以稳定 queue_id 幂等写入持久队列
  -> 持久化 checkpoint 结果和审计事件
  -> 调用观察型 after_run Hook
  -> 释放 generation lease
  -> 由标准队列路径创建下一 Run
```

聚合规则刻意保守：没有非 `ignore` 决策即结束；一个决策按其 action 执行；多个决策、策略异常、超时或
冻结 generation 不可用时自动暂停，不按 priority 静默选择。priority 只保证调用和诊断顺序。

若用户输入或更新后的 Run 已经抢先占用会话，旧 Run 的自动 continuation 会标记为 superseded，不再在用户
输入之后追加过期脚手架。下一 Run 会取得自己的新 checkpoint，再重新评估目标。

## 5. 输入、来源和权限

`CommandOutput.session_inputs` 与 `ContinuationDecision(prompt=...)` 都只是请求；只有 application runtime
可以提交它们。使用这两种能力的插件必须同时声明并获得：

- `sessions.write`：请求写入会话；
- `background.run`：请求由 Host 继续执行。

插件输入持久化为 `role=system_synthetic`，并包含 plugin、contribution、generation、caused-by Run 和
continuation decision 等 metadata。由用户键入的输入仍为 `role=user`。后续 Run 的 `origin=plugin`，自动续跑
还记录 `parent_run_id` 和 `initiator_id`。

这使上下文可以继续工作，同时保留“谁产生了这条指令”的事实，不让插件冒充用户。

## 6. Slash command 与并发 Host

交互 Host 的解析顺序为：

1. builtin 命令优先；
2. `/<plugin_id>:<name>` 精确匹配；
3. `/<name>` 只在该 local name 唯一时作为短别名；
4. 多个插件同名时返回稳定的 canonical choices，不按加载顺序选择。

插件命令启动的会话输入在 Interactive Host 中由受控后台任务执行。终端继续读取命令和普通输入；新的
`follow_up`/`steer` 仍进入同一个 RuntimeService 和持久队列。退出时 Host 先协作式中止该 Session，再等待任务
结束，避免关闭插件 owner 时仍有 generation lease。

其他 Host（Desktop、HTTP、测试宿主）可并发调用 `RuntimeService.run` 或 `submit_plugin_input`，获得相同的
单 Session 序列化语义，不需要复刻目标状态机。

## 7. `/goal` 插件映射

一个目标模式插件只需要实现自身目标状态和判断逻辑，不需要接管 OURO runtime：

| 用户动作 | 插件实现 |
|---|---|
| `/goal <objective>` | command 持久化 session-keyed 目标状态，并返回初始 `SessionInput` |
| 每轮检查 | continuation policy 读取目标状态和 `RunOutcome`，返回 continue 或 complete |
| 修改目标 | command 原子更新插件私有状态，可附带 steer/follow-up 输入 |
| 插入引导/排队消息 | command 返回指定 mode 的 `SessionInput`，或用户直接输入 `/steer`、`/follow` |
| 暂停 | command 把目标标为 paused；当前 Run 可完成，但 policy 不再续跑 |
| 恢复 | command 把目标标为 active，并返回恢复脚手架输入 |
| 取消当前执行 | Host `/abort`；Run 终态不会自动续跑 |

插件应按 `session_id` 保存目标记录，并用自身锁或单写者策略保护 command 与 policy 的并发更新；状态至少包含
目标 id、objective、active/paused/completed 状态、revision 和最后评估的 run id。OURO 不为一个插件特例引入
通用 workflow engine。

## 8. 明确边界

- continuation 只附着 `kind=agent` 的 Run，不附着 compaction Run；
- 非 completed 终态默认解析为 pause，不在 abort/failure 后自行复活；
- 自动续跑仍受 run budget、上下文预算、工具审批、AskUser、权限和 abort 约束；
- worker 支持 `continuation.call`、`tool_policy.call` 和 command `session_inputs`，但仍没有反向任意 Host-service RPC；
- plugin data 提供原子文件替换，不提供跨进程 CAS；需要高并发共享状态的插件应使用自己的单写者/锁，未来
  只有在多个真实插件需要同一能力时才增加通用 session-scoped KV/CAS API。

## 9. 验收证据

集成测试覆盖：真实 in-process 插件的两轮自动续跑、合成消息归因、command 输入、交互运行中继续接收命令、
typed `after_run`、多 policy 冲突暂停和重复 settlement 只入队一次。通用扩展测试还覆盖工具 workspace/cancel
上下文、真实插件阻止 builtin Bash、策略失败关闭，以及审批修改参数后的最终策略复核。文件与 SQLite
SessionStore 继续共享同一 `SessionRepository` 事务契约。
