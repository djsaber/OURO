# OURO 会话与 TUI 性能审计

日期：2026-09-05。基线：`a8b61b0`。环境：Windows 11 26200、CPython 3.14.6、项目锁定依赖。

## 结论

当前实现确实存在会影响实时交互的阻塞，主要来自异步编排遗漏的同步存储访问、Resize 的整段历史渲染，
以及对活动快照反复深度序列化。已在原有边界内优化，无需更换数据库、事件总线或 TUI 框架。

最终三轮离线对照中，两种后端的 TUI 主循环 Store 调用都降为零，loop lag p99 的三轮中位数明显下降。
然而最大延迟仍超过现行规格的 32 ms 目标，自动垃圾回收仍产生明显尖峰。本次完成的是已证实瓶颈的改良，
不能据此宣布 Windows/POSIX 真实终端的性能验收通过，也不能保证所有规模的会话都无卡顿。

## 全链路审查与改动

| 环节 | 审查结果与处理 |
|---|---|
| 输入、Session 创建、调度 | Supervisor 在 async submit 中仍同步创建/读取 Session、检查 Run、查询事件边界。完整查询/写入交给现有 `run_blocking`；线程返回后再次检查关闭及 Session 任务所有权，再原子登记任务，避免并发提交互相覆盖。 |
| 恢复与运行准备 | 单 Session/根树恢复、待结算 continuation、模型绑定、扩展快照的持久记录读取存在遗漏。现在数据访问在线程完成，进程内扩展 lease、队列、任务登记仍由事件循环持有。 |
| 上下文与压缩 | 普通 context preparation 已有线程边界；手动与自动压缩共用的内部路径仍有同步读取、投影、摘要 lineage digest 和写入。补齐线程边界，append/activate 在同一 worker mutation 内完成。压缩保留区间改为扫描索引，消除反复 `list.insert(0, ...)` 的平方级引用移动。 |
| Provider 流与工具执行 | 保留现有 8 ms / 16 KiB delta 合并、语义边界 flush、异步 provider 和工具/回调隔离。没有扩大窗口、降低动画频率或削减检查点。 |
| 事件持久化与发布 | 继续逐 Session 保证 durable-before-live。修复取消窗口：线程写入与主循环发布由一个受保护任务完成，owner 被多次取消时仍等待该任务，再释放顺序锁。不会出现磁盘已写而实时通知被取消跳过的情况。 |
| 活动投影 | 原比较将前后两个完整模型 dump 后再比较，sequence 更新时间也会遍历全部工具结果。改为直接比较语义字段，复用 reducer 共享的未变对象；忽略 sequence、时间和流参数尾部的原有语义不变，字段列表从模型生成。 |
| 子 Agent 生命周期 | Spawn 校验/预留/child 准备、follow-up、等待、关闭与恢复中的完整 Store 操作在线程完成。调度和通知保持原 async 编排；提交记录与结果结算共用 delegation 生命周期锁，保留 revision CAS。 |
| Session 及树订阅 | 原订阅构造和树刷新会在调用方线程执行多次 Store 查询。初始化改为 async，先接入有界 live 队列，再读取回放；按 sequence 合并去重。树快照在线程投影，初始化取消/失败会解除订阅。TUI 切换根后，迟到的旧树订阅被关闭。 |
| TUI 历史和渲染 | 原大历史 load 虽然分块在线程渲染，冷布局或 Resize 仍会进入整段同步重绘。整段重绘现在复用已有主题刷新 worker，对宽度、主题和当前 entries 再校验后一次替换可见 buffer。Resize 连续发生时保留旧画面，提交最新结果。 |
| 后续输入与终态 | 补齐排队输入及批量输入、取消未消费输入、已落地 Host 输入重读、恢复终态等路径的 Store 边界。保留事件持久化顺序、RunResult 去重和现有每帧最多 64 条事件的 consumer。 |
| Run 锁与即时回答 | 审批/提问可以在原 owner 释放锁前到达 Host，立即回答原本可能收到 `run is already active`。Run ownership 现在拥有异步 acquire/release 及本地释放信号，合法挂起响应等待同一 owner 交接；外部未知 owner 仍由文件锁拒绝。取消 acquisition 会收回线程已取得的锁。 |

这些改动没有增加常驻缓存、第二套状态事实源、全局单 I/O 队列、进程池或依赖包。
线程迁移以完整 query/mutation 为单位；持有文件 mutation lock 或 SQLite transaction 的操作不会跨线程拆分。

## 测量方法与结果

使用同一份[离线脚本](../dev/benchmarks/session_pipeline.py)分别运行原始 checkout 与修改后的 checkout，
每种后端和模式各三轮，运行期间未并行执行测试。只使用临时合成数据，无网络模型。
每个会话有 120 条历史消息、两轮各 40 个文本 delta，以及中间一次只读工具执行。
TUI 为 Textual headless 120×40；Key 统计是注入事件到 Composer 文本改变，spinner 统计是实际回调间隔。
分位数列取三轮分位数的中位数，最大值列取三轮最差值，单位 ms。

| TUI 指标 | 文件后端：原始 → 修改后 | SQLite：原始 → 修改后 |
|---|---:|---:|
| 主循环 Store 调用次数／轮，包含公共方法嵌套调用 | 341 → 0 | 173 → 0 |
| loop lag p99 | 55.030 → 19.390 | 60.674 → 15.318 |
| loop lag 最大值 | 205.820 → 210.005 | 232.379 → 185.591 |
| Key → Composer p95 | 27.319 → 14.339 | 28.793 → 9.402 |
| Key → Composer 最大值 | 71.327 → 221.166 | 210.800 → 134.440 |
| spinner 回调间隔最大值，标称 120 ms | 251.803 → 314.051 | 251.090 → 220.509 |
| history 整段同步渲染入口最大耗时 | 107.028 → 0.069 | 204.075 → 0.126 |

同步渲染入口耗时的下降表示重活已退出该同步调用，并不表示全部 Markdown 计算在 0.1 ms 内完成。
各指标的收益并不相同；最大 loop lag 仍然很高，不能只以 p99 的进步判断全部尖峰已消除。
最终 TUI 六次运行的 loop lag p99 为 15.277–22.962 ms，并非每次都满足 16 ms 目标。

不带 TUI 的同一会话负载，主循环 Store 调用从文件后端 102 次、SQLite 53 次降为零。
修改后 SQLite 三轮最大 loop lag 为 15.282–15.506 ms；文件后端为 15.769–17.697 ms。

活动比较分项使用四个工具各 5,000 条合成结构化结果，数据不变只改变 sequence。
每轮 30 次比较的 p50，三轮中位数从 47.467 ms 降至 0.002 ms。
这是“重复比较共享大结果”的分项收益，不是整体会话吞吐量加速倍数。

原始 JSONL、测量口径和重跑命令保留在 [benchmarks](../dev/benchmarks/README.md)。
小样本、Windows 调度精度、GC 时机和后台桌面负载都会影响最大值，不据此设定机器无关的 CI 时间阈值。

## 尚未解决和未扩大实施的部分

1. **GC / GIL 尖峰仍存在。** 修改后 TUI 测量中，GC 最长样本达到约 191 ms，多个较长 loop callback 同时记录到 GC。
   线程能移走同步 I/O，不能消除 CPython 的全局解释器锁和垃圾回收停顿。没有通过关闭 GC、调高阈值或更改动画
   节奏让数字变好。还需要在目标 Python 版本和真实长会话中定位对象分配与存活图，才能决定进一步减小对象量的边界。
2. **全历史成本仍随历史量增长。** Store runtime/session snapshot、TUI 已保存历史和 ContextSnapshot 的完整表示，
   并未改为按页首屏；万条消息的首屏、内存上限不在本次样本的证明范围。消息分页必须连同 tool/compaction 边界、
   live 尾部和历史跳转一起设计，不能只给 UI 加一个截断。
3. **写放大与子树扩展性仍需专门测量。** 文件 Catalog 更新、完整 Run/tool/context JSON 编码及树快照的多项 join
   仍可能随历史或 child 数量增长。现有存储是 canonical，未新增 checkpoint sidecar、摘要 DTO 或缓存失效协议。
   当前数据没有证明应更换存储布局；SQLite 的连接常驻试验也未显示可靠收益，因此没有加入连接池。
4. **真实终端和网络未验收。** 本次覆盖 Windows headless TUI 的 dispatch、按键和动画回调，不包含 Windows Terminal
   或 POSIX 终端最终呈现、真实 Provider、网络磁盘、多进程竞争及所有插件组合。现行性能规格的完整验收仍保持待完成。

## 兼容性

外部 Python Host 调用需要更新：

```python
subscription = await supervisor.subscribe(session_id, after_sequence=sequence)
tree = await agents.subscribe_agent_tree(root_session_id)
```

返回后可立即读取 `initial_activity` / `initial_snapshot` 并消费异步迭代器。
`close()` 仍为同步的解除观察操作，不会取消被观察的 Run。CLI/TUI 的协议和调用已同步更新。
存储 schema、已有 Session 文件和数据库均无需迁移。

## 验证

新增和扩展的回归覆盖：两种 Store 的主循环线程归属；会话提交冲突；回放与 live 重叠去重；回放期间溢出、失败、
重复取消和 shutdown；子 Agent 生命周期及提交 CAS 竞争；手动压缩、排队输入取消；事件写入期间取消但仍按序发布；
活动语义字段；连续 Resize 的可见 buffer 保留及最新宽度提交；TUI 迟到树订阅清理；原 Run 尚持锁时立即审批/回答，
以及 acquisition 期间重复取消后的锁回收。

完整检查已执行：

| 检查 | 结果 |
|---|---|
| `uv sync --frozen --all-groups` | 通过，未修改锁文件 |
| 全量 `pytest --cov=ouro --cov-report=term-missing` | 2125 passed，2 skipped，4 failed；总覆盖率 83.29%，超过 80% 门槛 |
| 最后补充的订阅顺序及 Supervisor 回归 | 49 passed；包括回放后过滤旧活动快照的两种后端测试 |
| `ruff check ouro tests` 及 benchmark 脚本 | 通过 |
| `ruff format --check`：本次涉及的 27 个 Python 文件 | 通过 |

| `mypy ouro` | 通过，266 个源文件 |

剩余四项全量失败均已在原始 `a8b61b0` checkout 独立复现：

- `test_active_session_model_switch_applies_to_the_next_model_request`：实际下一轮使用新模型，但返回的 Run.model 仍是旧模型。
- `test_provider_update_json_exposes_safe_template_merge_report`：断言 preset revision 为 1，实际为 2。
- `test_instruction_loader_uses_workspace_as_boundary_without_git_repository`：加载了测试预期之外的上级指令文件。
- `test_provider_submenu_updates_from_latest_preset_in_place`：同样是 preset revision 1 / 2 的预期不一致。

这些既有失败未作为性能优化一起修改。全仓库质量门禁因此仍非全绿；不能把覆盖率达标写成全部测试通过。
本次暴露的即时 HITL 锁交接问题已经修复，原有连续审批、插件回答和子会话切换测试在最终全量运行中均通过。
