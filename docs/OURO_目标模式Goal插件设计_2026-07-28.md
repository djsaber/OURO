## 1. 结论先行

OURO 的 Goal Mode 不应是一套新的 Agent Loop，也不应是 Plan Mode、Todo List 或工作流引擎的变体。

它的最小本质是：

> 在不改变单个 Run 内部执行语义的前提下，用一个 Session 级、可持久化、可仲裁的控制器，持续保存用户定义的结果状态；每个 Run 只推进一个有界工作片段，Run 结束后由 Host 依据插件的类型化决策，安全地创建下一次带来源的合成输入，直到目标被显式完成、阻塞、暂停或取消。

首版设计作出以下决定：

1. Goal 是“最终必须成为什么”，不是“下一步做什么”。
2. 一个 Session 同时最多有一个当前 Goal。
3. Goal 与 Plan 共同 claim `ouro.session.primary_behavior`，二者互斥，不做静默抑制。
4. Goal 复用现有 Runtime、Run、Tool、Approval、Queued Input、Continuation 和 Session Controller；不增加第二套主循环。
5. 模型自然结束一次回答只表示本 Run 结束，不表示 Goal 完成。
6. Goal 完成或阻塞必须通过显式 Tool 声明，并附带可审计报告；Runtime 不假装能证明语义正确性。
7. 用户拥有创建、暂停、恢复、替换、取消和预算权限；模型只能声明 `complete` 或 `blocked`；Runtime 只能因错误或资源边界暂停/阻塞。
8. Goal 不提高工具权限，不绕过审批，不改变已有 permission mode。
9. 首版只支持可选 token budget，且只在 Run 边界结算；不加入 wall-clock scheduler、目标队列、子目标树、DAG 或多 Goal 并行。
10. 实现插件前，先补齐三个最小通用底层契约：Continuation 的控制权 transition、release payload 到 deactivate 的对称传递，以及 controller activation 可见 Session kind。不能在 Goal 插件中用私有旁路绕过。

## 3. 主流实现的核心设计

### 3.1 Codex CLI：Goal 是持久状态加空闲续跑

Codex 把 Goal 实现为独立扩展，而不是把逻辑塞进一个超长 system prompt：

- thread 级持久状态保存 `goal_id`、objective、status、token budget、token/time usage；
- `get_goal`、`create_goal`、`update_goal` 构成模型控制面；
- 只有用户明确要求时才能创建 Goal，模型不能从普通任务自行推断；
- 模型只能把 Goal 更新为 `complete` 或 `blocked`，pause、预算限制等由用户或系统掌握；
- thread idle 时，Runtime 检查当前 Goal 身份与状态，再注入 continuation steering item；
- 所有 accounting 和状态更新绑定精确 `goal_id`，避免旧 Turn 修改已替换 Goal；
- token budget 到达后不会把“停止”误写成“完成”；
- continuation prompt 要求从当前 worktree 和外部事实重新取证，逐项审计目标，不能把已经做出的部分重新定义为成功。

Codex 还暴露了一个值得 OURO 主动规避的交互问题：Plan Mode 会抑制 Goal continuation；如果产品层没有清楚呈现，用户会看到“Goal 仍 active，但不再运行”。OURO 已经有通用 Session claim 仲裁，因此不需要复制这种隐式组合语义。

核心来源：

- [Goal extension lifecycle](https://github.com/openai/codex/blob/8e271dc02b23d42827875019924be0f5005642b0/codex-rs/ext/goal/src/extension.rs)
- [Goal runtime 与 idle continuation](https://github.com/openai/codex/blob/8e271dc02b23d42827875019924be0f5005642b0/codex-rs/ext/goal/src/runtime.rs)
- [模型 Goal tools 约束](https://github.com/openai/codex/blob/8e271dc02b23d42827875019924be0f5005642b0/codex-rs/ext/goal/src/spec.rs)

- [持久 Goal 状态与 accounting](https://github.com/openai/codex/blob/8e271dc02b23d42827875019924be0f5005642b0/codex-rs/state/src/runtime/goals.rs)

### 3.2 Kimi Code：Goal 是跨 Turn 的结果契约

Kimi Code 的文档直接区分了普通 prompt 和 Goal：普通 prompt 表达下一步，Goal 表达最终必须成立的结果。其 Harness 具有以下特征：

- `/goal <objective>` 保存目标，并把目标作为下一次输入启动 Goal；
- 每个 Turn 后检查 active、complete、blocked、paused；
- `/goal status|pause|resume|cancel|replace` 形成完整用户生命周期；
- objective 推荐同时写清 finish line 和证明它的 evidence；
- continuation 作为 `system_trigger/goal_continuation` 的新 Turn 入队，而不是在同一个模型 Turn 里无限循环；
- Goal 状态带精确 `goalId`，过时 Goal tool call 会被拒绝；
- active Goal 在 journal replay 后转为 paused，避免进程恢复后意外自治；
- runtime/provider/model error 导致 paused，预算耗尽导致 blocked；
- token、turn、wall-clock 都可作为预算，硬预算还能阻止后续 Tool；
- Goal 不改变 permission mode；手动权限下仍可能等待审批；
- 子 Agent 不继承主 Agent Goal。

Kimi 还实现了 upcoming goal queue。它证明队列有产品价值，但队列已经开始承担 backlog 与调度语义，不是 Goal Harness 成立所必需的部分，因此不进入 OURO 首版。

### 3.3 OpenCode：普通 Loop 与 Todo 还不是 Goal

在固定的 OpenCode `dev` 提交中，没有发现与 Codex/Kimi 同等级的独立 Goal 状态机和跨用户消息的 Goal continuation：

- Session prompt loop 会在模型产生 Tool Call 时继续，在模型自然 finish 后退出；
- Todo 被持久化到 Session，并通过事件投影给 UI；
- Todo 描述进度，但不拥有 Session 续跑权，也不定义谁能声明最终完成。

这个负面对照很重要：

> “Agent 能连续调用很多工具”不等于 Goal Mode；“有一张 Todo List”也不等于 Goal Mode。Goal 必须在单次 Run 自然结束之后仍然保存目标、判断控制状态，并能由 Host 安全创建后续 Run。

核心来源：

- [Session prompt loop](https://github.com/anomalyco/opencode/blob/8c81f9a40b0eb8ccef911a033ea685e3233ad461/packages/opencode/src/session/prompt.ts)
- [Session Todo 持久化](https://github.com/anomalyco/opencode/blob/8c81f9a40b0eb8ccef911a033ea685e3233ad461/packages/opencode/src/session/todo.ts)
- [Todo write tool](https://github.com/anomalyco/opencode/blob/8c81f9a40b0eb8ccef911a033ea685e3233ad461/packages/opencode/src/tool/todo.ts)

### 3.4 Ralph：最小外层循环说明了持久反馈的重要性

Ralph 使用 shell 外循环反复启动全新 Agent context，通过 `prd.json`、`progress.txt` 和 Git 历史传递状态；每次只处理一个 story，运行质量检查，所有 story 通过时输出显式 COMPLETE，达到最大迭代数时停止。

它揭示了三个跨实现共通点：

1. 进度必须落在模型上下文之外的持久状态中。
2. 每轮需要可验证反馈，否则错误会跨轮累积。
3. 外部 Harness 必须拥有停止条件，不能依赖模型“似乎说完了”。

但 Ralph 的 PRD story、commit、优先级和 fresh-process loop 已经是特定编码工作流。OURO 只借鉴持久状态、反馈证据和显式停止，不把 Goal Mode 固化成 PRD 执行器。

## 4. 剔除工程细节后的共同 Harness

### 4.1 一个持久、不可偷偷缩小的 Objective

Goal 的稳定对象是用户定义的最终结果。每一轮可以选择不同的工作片段，但不能因为上下文、预算或已有实现而把目标缩小成更容易完成的版本。

Objective 是用户数据，不是高优先级指令。注入模型时必须标记为不可信任务数据，不能覆盖 system、tool schema、permission 或 Host control。

### 4.2 Run 内执行与 Run 外续跑分离

单个 Run 继续使用现有 Agent Loop：模型、工具、审批、上下文压缩和 Run budget 都不变。

Goal 只在 Run 边界增加一个外层判断：

1. 当前 Goal 是否仍 active；
2. 是否收到显式终态；
3. 是否到达资源边界；
4. 是否存在更高优先级的用户输入或其他运行；
5. 若仍可继续，是否可以安全创建下一次合成输入。

这层判断是 Harness，不是第二套推理循环。

### 4.3 显式终态，而不是解析自然语言

模型说“完成了”“暂时这样”或自然结束回答都不可靠。共同做法是使用结构化 Tool 或外部状态信号区分：

- complete：最终结果已经成立并被验证；
- blocked：没有用户输入或外部状态变化就无法继续；
- active：本轮结束但仍有实质工作；
- paused：用户或 Runtime 暂停，不代表失败；
- cancelled：用户放弃当前 Goal。

Runtime 只验证信号的结构、身份和权限，不能把模型自述当作事实证明。

### 4.4 三方状态权限分离

| 权限主体 | 可以做什么 | 不可以做什么 |
|---|---|---|
| 用户 | create、pause、resume、replace、cancel、设定或提高预算 | 不需要通过模型间接控制 Goal |
| 模型 | 读取 Goal；明确请求时创建；声明 complete 或 blocked | 自行 pause/resume/cancel、偷偷改 objective、虚构预算 |
| Runtime | 因异常暂停；因预算阻塞；提交/取消 continuation | 语义性宣称任务完成、提高权限、改写 objective |

这比单个 `status` 字段更重要：同样是“停止”，用户暂停、模型阻塞、预算耗尽和执行错误的含义完全不同。

### 4.5 身份、revision 与旧工作隔离

每个 Goal 必须有稳定 `goal_id` 和单调 revision。Run、context、Tool 和 continuation 都必须绑定创建它们时看到的 Goal/activation 身份。

旧 Run 的 Tool Call、恢复事件或 continuation 不得修改替换后的新 Goal。这个约束不能依赖 objective 文本相同与否。

### 4.6 资源边界是治理，不是成功条件

预算耗尽只说明不能继续消耗资源，不说明目标已完成。模型也不能因为“快没 token 了”而调用 complete。

预算必须由用户明确提供；没有预算时不凭经验虚构一个。预算计量复用 Host 的 canonical usage，不在插件里自行估算 tokenizer。

### 4.7 当前事实与证据优先

跨 Run 的对话记录只能帮助定位，当前 worktree、测试结果、外部系统状态和生成制品才是判断完成的权威证据。

Completion audit 至少要求：

1. 从 objective 和被引用的规范中重新枚举要求；
2. 对每项要求检查当前状态；
3. 执行用户要求或项目要求的验证；
4. 确认没有未完成的必要工作；
5. 通过 Tool 提交简短证据报告。

### 4.8 User input 和安全控制始终优先

Goal continuation 是最低优先级的自动输入。新用户输入、已有 queued input、活动 Run、审批、取消和 Session Controller release 都优先于自动续跑。

Goal 不能借由“自治”获得额外文件、网络、命令或审批权限。

## 5. Goal、Plan、Todo、Workflow 的边界

| 机制 | 核心问题 | 是否跨 Run 自动续跑 | 是否拥有完成语义 | 是否拥有 Session 控制权 |
|---|---|---:|---:|---:|
| Prompt | 下一次要做什么 | 否 | 否 | 否 |
| Plan | 应该如何做 | 否 | 只完成计划制品 | 是，限制行为 |
| Todo | 当前进度如何表示 | 否 | 通常只是模型投影 | 否 |
| Goal | 最终必须成为什么 | 是 | 是，显式终态 | 是，驱动续跑 |
| Workflow | 哪些节点按什么依赖执行 | 是 | 每个节点及整体终态 | 是，并负责调度图 |

因此首版明确不做：

- Goal queue；
- 子目标树或目标自动拆分；
- DAG、依赖、重试图和节点调度；
- 多 Goal 并行；
- 自动 commit、PRD story 或特定测试命令；
- 用 Todo 完成率推断 Goal 完成；
- 用 LLM 判别器再调用一次 LLM 来裁决完成；
- 给 Host 添加 `if goal_mode` 特例。

这些能力只有在独立需求出现时才应进入 Workflow、Scheduler 或专门插件，而不是堆进 Goal Mode。

## 6. OURO 中的架构定位

Goal Mode 作为 builtin plugin 发布，但必须只依赖公共 Plugin SDK 和通用 Application 协议。builtin 代表默认信任与随发行版交付，不代表可以访问 Runtime 私有实现。

建议稳定身份：

- plugin id：`dev.ouro.goal_mode`
- Session Controller local id：`mode`
- claim：`ouro.session.primary_behavior`，`exclusive`
- Command：`goal`
- Context Provider：`goal-scaffold`
- Continuation Policy：`goal-continuation`
- Tools：`get-goal`、`create-goal`、`update-goal`

### 6.1 贡献映射

| 目标语义 | OURO 贡献点 | 说明 |
|---|---|---|
| 用户控制面 | Command | `/goal ...` 始终可见 |
| 模型控制面 | Tool | Get/Create 始终可见；Update 绑定 active controller |
| 长期行为所有权 | Session Controller | Host 持久化 activation 并仲裁冲突 |
| 每轮目标约束 | Context Provider | `active_when=mode`，以 `message` persistence 注入 |
| 跨 Run 续跑 | Continuation Policy | `active_when=mode`，只返回类型化决策 |
| 权限限制 | 现有 Host Tool/Approval | Goal 不新增 Tool Policy，不改变 permission |
| 单 Run 内循环 | 现有 InnerAgentLoop | 不修改 |

Goal 不需要 Turn Policy。一次正常 Run 就是一个有界工作片段；如果用 Turn Policy 强迫同一 Run 一直继续，会重新制造上下文膨胀、Run budget 失效和无法清晰恢复的问题。

Goal 也不需要 Tool Policy。它没有理由收紧或放宽一般工具；所有工具继续遵循 Session 原有 permission、approval 和 interaction mode。

### 6.2 数据所有权

| 数据 | Owner |
|---|---|
| active activation、claim、activation revision | Host SessionStore |
| Run、RunOutcome、continuation checkpoint、queued input、provenance | Host Runtime/Application |
| objective、Goal status、Goal revision、usage、终态报告 | Goal plugin 私有 data |
| worktree、测试结果、外部系统事实 | 对应真实系统，不复制成 Goal 真相 |

插件不能直接写 SessionStore，Host 也不解释 objective、completion report 或 blocked reason 的业务含义。

## 7. Goal 状态模型

首版每个 Session 只保存一条 current Goal record：

| 字段 | 必要性 |
|---|---|
| `goal_id` | 隔离旧 Run、旧 Tool 与替换后的新 Goal |
| `objective` | 用户定义的完整最终状态，不可被模型改写 |
| `status` | `active | paused | blocked | complete` |
| `actor` | 最近状态变化来自 `user | model | runtime` |
| `revision` | 每次语义变化单调增加，用于 CAS 与恢复 |
| `activation_id` | active 时绑定 Host controller activation |
| `token_budget` | 可选；只在用户明确指定时存在 |
| `tokens_used` | 由 RunOutcome canonical usage 累积 |
| `runs_used` | 进度可见性与 blocked audit 辅助信息 |
| `last_accounted_run_id` | continuation 重放时保证 usage 幂等 |
| `reason_code` | 稳定的暂停/阻塞/完成原因 |
| `report` | complete/blocked 的简短证据或原因报告 |
| 时间戳 | create/update/status change 的可观测性 |

不在首版加入单独 `completion_criteria` 结构、requirements array 或 evidence graph。用户应直接在 objective 中写清 finish line 和证据；模型在完成审计时从 objective 与引用规范中派生检查项。提前结构化这些内容会把 Goal 推向需求管理系统。

`cancel` 删除 current Goal；`replace` 创建新 `goal_id` 并替换当前记录；`complete` 保留当前记录供 status 与最终 usage 查询，直到用户开始新 Goal 或取消。

### 7.1 状态转换

| 当前状态 | 事件 | 新状态 | Actor |
|---|---|---|---|
| 无 / complete | 用户 `/goal <objective>` | active | user |
| 无 / complete | 模型在明确请求下 CreateGoal | active | model |
| active | 模型 UpdateGoal complete | complete | model |
| active | 模型 UpdateGoal blocked | blocked | model |
| active | 用户 pause | paused | user |
| active | Run abort、provider/runtime error | paused | runtime |
| active | token budget 到达 | blocked | runtime |
| paused / blocked | 用户 resume | active | user |
| 任意 current | 用户 replace | 新 Goal active | user |
| 任意 current | 用户 cancel | 无 | user |

以下转换非法：

- 模型 pause、resume、cancel 或 replace；
- Runtime complete；
- 未完成 Goal 上再次 create；
- blocked/paused Goal 自动恢复；
- 旧 `goal_id` 或旧 activation 的 Tool/continuation 更新新 Goal。

## 8. 用户与模型接口

### 8.1 `/goal` Command

首版控制面：

| 命令 | 语义 |
|---|---|
| `/goal <objective>` | 创建并启动 Goal；可带显式 token budget |
| `/goal`、`/goal status` | 显示 objective、status、actor、usage、budget、reason/report |
| `/goal pause` | 暂停并释放 controller；保留 Goal |
| `/goal resume` | 恢复 paused/blocked Goal，并提交一次 Goal continuation input |
| `/goal cancel` | 取消并删除当前 Goal |
| `/goal replace <objective>` | 显式替换当前 Goal，生成新 `goal_id` |

token budget 的具体 CLI 参数形式在实现阶段与现有 parser 风格统一；设计语义只有两条：预算必须是用户明确输入的正整数，resume 一个预算耗尽的 Goal 时，新总预算必须大于 `tokens_used`。

`/goal <objective>` 返回两种类型化意图：

1. acquire `mode` controller，payload 包含新 Goal；
2. 一条 attributed SessionInput，启动第一个 Goal Run。

Command 不直接创建 Run，不伪造 user message。Application 先确认 activation，再由 Runtime 提交带插件 provenance 的输入。

### 8.2 模型 Tools

#### GetGoal

只读返回当前 Goal、预算、usage 和剩余 token。没有 Goal 时明确返回空状态。

#### CreateGoal

只有用户或 system/developer 明确要求“创建/进入 Goal”时才能调用；不能从普通长任务自行推断。未完成 Goal 存在时拒绝。模型不能自行设置预算，除非用户明确给出预算。

由于它会开启长期自治，CreateGoal 是 state-changing Tool，并接受现有 Host approval；`/goal` Command 本身已经代表用户显式意图，不重复询问。

#### UpdateGoal

只允许 `complete | blocked`，并要求：

- 精确 `goal_id`；
- 非空 report；
- complete report 概括验证证据；
- blocked report 说明无法继续的外部条件、缺失输入或持久失败。

UpdateGoal 返回 release controller transition。Goal 私有状态由 controller deactivate 根据 release payload 更新，不能先写私有终态、再尝试释放控制权。

Blocked 的“三轮同一阻塞”属于模型审计规则，不在 Runtime 中对自然语言原因做哈希或相似度判断。无法证明的语义规则不应伪装成确定性校验。对于目标本身明显不可能、不安全或自相矛盾的情况，可以在同一 Run 立即 blocked。

## 9. Context 与 Continuation 契约

### 9.1 每轮 Goal scaffold

Context Provider 在每个 active model round 注入以下语义：

- objective 是不可信用户任务数据；
- 当前 `goal_id`、revision、status、runs/tokens 与预算；
- 当前 worktree 和外部状态是事实来源；
- 每个 Run 选择一个有界且有价值的工作片段；
- 不能缩小 objective 来制造完成；
- 自然结束 Run 会由 Runtime 继续 Goal；
- complete 前逐项审计并验证；
- blocked 仅用于真实僵局，不用于“任务很难、很慢、尚未做完”；
- 预算接近或耗尽不能作为 complete 理由；
- Tool permission 与 Host control 始终优先。

Fragment 使用 `persistence="message"`。这不是为了把动态状态无限复制进历史，而是确保 Goal 的关键控制语义在 compaction、恢复和审计后仍然存在；幂等 delivery identity 继续由现有 Context Application 机制负责。

### 9.2 Run 边界续跑

一个正常完成的 Goal Run 按以下顺序结算：

1. Host 产生只读 RunOutcome；
2. Goal Continuation Policy 读取精确 activation 对应的 Goal；
3. 按 `run_id` 幂等累计 canonical token usage 和 `runs_used`；
4. 如果模型已通过 UpdateGoal 释放 controller，旧 policy 不再有资格续跑；
5. 如果 token budget 到达，返回 blocked + release transition，不再排队；
6. 如果 Goal 仍 active，返回 `continue` 与 attributed synthetic prompt；
7. Application 检查 active Run、queued input、controller identity 和 activation revision；
8. 只有全部仍成立时才入队下一 Run，并把 decision/queue identity 持久化。

Continuation prompt 不重复整套 system prompt，只表达“继续当前 Goal、重新检查当前事实、选择下一段工作、完成时调用 UpdateGoal”。完整 Goal scaffold 由下一 Run 的 Context Provider 注入。

### 9.3 用户输入优先

如果结算时已有用户输入或更新的 Run：

- Host 不排入自动 continuation；
- 用户输入先进入 Session；
- Goal controller 仍 active，因此该 Run 仍能看到 Goal scaffold；
- 如果用户要处理无关任务，应先 `/goal pause`，不能由 Harness 猜测其意图并偷偷暂停 Goal。

### 9.4 异常终态

Run abort、provider error、runtime error 或 continuation policy failure 不应留下“状态显示 active、控制器也 active、但永远不会续跑”的孤儿模式。

正常异常路径由 Goal policy 返回 paused + release transition。owner policy 不可用或失败时，Host 对该 policy 绑定的精确 activation fail-closed release，并记录“owner 私有清理未确认”的诊断；不影响其他 controller。

等待 Tool approval、ToolInputRequest 或 child agent 不是终态。Run 仍处于 waiting，Goal 保持 active，不创建额外 Run。

## 10. Token budget

首版只实现可选 token budget：

- 只在用户明确提供时创建；
- 计量完全复用 RunOutcome 中的 Host canonical usage；
- 每个 Run 只结算一次，`last_accounted_run_id` 防止 recovery 重放重复扣减；
- 在 Run 边界检查，因此允许最多一个 Run 的自然 overshoot；
- budget 到达后状态为 blocked，actor 为 runtime，reason 为 `token_budget_exhausted`；
- resume 时用户必须提高总预算；
- provider 无法给出 canonical usage 时，预算 Goal 必须 visible pause，不能把缺失 usage 当作 0。

首版不做硬 wall-clock deadline 和 Run 中途 Tool veto。它们需要实时 usage/deadline scheduler、在途取消与 grace turn 语义；没有真实需求前引入，会把一个简单的跨 Run governor 变成第二套资源调度系统。

`runs_used` 可以记录并显示，但首版不提供 turn budget。它服务可观测性与审计，不成为另一种隐式终止条件。

---

## 11. 与 Plan Mode 的组合

Goal controller 与现有 Plan controller 都声明：

- domain：`ouro.session.primary_behavior`
- access：`exclusive`

因此：

- Plan active 时启动 Goal，Host 返回标准 `SessionControlConflictError`；
- Goal active 时进入 Plan，同样明确冲突；
- 不按插件 priority、加载顺序或“最近一次命令”自动覆盖；
- 用户先退出/暂停当前模式，再进入另一模式；
- `/control status` 能观察统一 activation；
- `/control release` 仍是 owner 不可用时的通用逃生口。

推荐流程是先用 Plan 产出并确认计划、退出 Plan，再以最终目标启动 Goal。Goal 可以把计划文件作为 objective 引用，但不拥有或解析 Plan 文件格式。

这比“Plan 开启时静默不续 Goal”更符合 OURO 的显式契约与错误可见性原则。

## 12. 现有框架已经提供的能力

Goal 不应重复实现以下机制：

- Session 一次只有一个 active Run；
- `follow_up` / `steer` queued input；
- plugin synthetic input provenance；
- continuation decision/queue 的 durable identity 与恢复；
- 用户 queued input 优先于自动 continuation；
- controller activation、claim、revision 和 generation contract；
- `active_when` contribution 绑定；
- controller release 自动取消其 queued continuation 和 pending interaction；
- Context Fragment `message` persistence；
- PluginDataStore 隔离；
- permission、approval、unattended resolution；
- `/control status/release` 通用管理面；
- extension catalog generation 与恢复契约。

如果 Goal plugin 重新写队列、锁、Run loop、permission 或 Session persistence，说明实现层次已经错误。

## 13. 实现前必须补齐的通用框架契约

> 实施状态（2026-07-28）：Phase A 已按本节契约落地。Plugin API 已升级为 `1.2.0`，worker protocol
> 已升级为 `1.2`；本节继续保留问题背景与设计理由。Phase B 的 Goal builtin plugin 尚未实现。

Phase A 实施前的代码已经接近支持 Goal，但有三个不能在插件里绕过的底层缺口。

### 13.1 ContinuationDecision 必须能携带 Session control transitions

Phase A 实施前，Command 和 Tool 可以返回 `acquire | release | replace`，Continuation 只能返回 `ignore | continue | complete | pause | fail`。结果是：

- token budget 到达时 policy 可以说 pause，却不能原子释放 Goal controller；
- Run abort/error 当前被 Host 直接标为 continuation pause，owner policy 没有机会更新 Goal 并释放控制权；
- policy failure 后可能留下 active controller 孤儿；
- 插件若先写私有终态、再另行 release，会产生两阶段不一致。

通用改良：

1. ContinuationDecision 增加与 Command/Tool 相同的 `session_control_transitions` 字段；插件只返回 local intent，Registry/Application 再绑定 plugin、generation 与 execution-contract attribution；
2. policy 对所有 terminal RunOutcome 都可评估；非 completed Run 不允许 `continue`，但允许 pause/fail + release；
3. Application 校验 transition 只能操作同 plugin、且必须绑定 Run checkpoint 中的精确 activation；
4. settlement 以 durable staged transaction 提交 transition、queue 和 checkpoint，恢复时幂等重放；
5. bound policy unavailable/timeout/exception 时，Host 只 fail-closed release 其精确 activation，并记录诊断；
6. 多个非 ignore policy 仍按现有规则冲突并暂停，不能选择性猜测赢家。

这是通用的“后 Run 决策可以结束自己拥有的 Session 控制权”能力，不是 Goal 特例。未来任何长期 controller 都会需要它。

### 13.2 release payload 必须传给 controller deactivate

`SessionControlTransition` 和 `SessionControllerCall` 都已有 payload，但 Phase A 实施前的 release 路径只把 reason 传给 deactivate，丢弃 payload。Goal completion 需要把以下 owner 数据与 release 一起提交：

- `goal_id` 与 expected Goal revision；
- terminal status；
- actor 与 reason code；
- completion/block report。

通用改良：Application 将 release transition payload 原样、类型安全地传给 owner deactivate；worker protocol 与 in-process SDK 行为一致。Host 不解释 payload，只负责 attribution、revision、claim 和 transition 生命周期。

reason 继续用于稳定的 Host/诊断原因；结构化 owner 状态不能塞进自由文本 reason。

### 13.3 Controller activation 必须可见 Session kind

首版 Goal 只允许 primary Session。subagent Session 的生命周期、预算与完成权属于父 Agent delegation；允许子 Agent 再开启独立 Goal，会形成两层长期控制器和不清晰的父子完成关系。

Phase A 实施前，`SessionControllerCall` 只有 session id 与 workspace，owner 不能通过公共 SDK 判断 primary/subagent。通用改良是在 activation/deactivation call 中加入 Host 已知的 `session_kind`：

- Goal controller 在 activate 时拒绝 subagent Session；
- Host 只提供事实，不解释各 controller 的业务限制；
- 不根据 session id 格式、父目录或私有 SessionStore 猜测 kind；
- 字段进入 in-process SDK、worker protocol 与 execution contract。

这里只补充现有 Session 事实，不引入新的 scope DSL、继承模型或 Goal 特例。

### 13.4 不增加 Goal 专用 Core API

不接受以下替代方案：

- Runtime 内新增 `goal_manager`；
- Host 根据 plugin id 特判 Goal；
- Continuation callback 直接调用 Runtime 创建 Run；
- Plugin 直接写 SessionStore 或 queued input；
- 用后台 task 轮询 Session 是否 idle；
- 只在 Goal plugin 中捕获异常并留下 active controller；
- 用 reason 字符串编码 JSON 终态。

这些做法会绕开已经建立的 Application ownership、provenance、recovery 和 claim 仲裁。

## 14. 持久化、恢复与幂等

### 14.1 持久化不变量

1. Host active Goal controller 与 plugin active Goal record 必须由同一次 transition 生命周期建立/释放。
2. 每个 active Goal record 只绑定一个 activation id。
3. 每个 continuation 同时绑定 run id、goal id、Goal revision、controller id、activation id 和 plugin execution contract。
4. usage 按 run id 最多结算一次。
5. release 后，旧 queued continuation 自动取消。
6. replace 后，旧 Goal 的 Tool/continuation 无法命中新 `goal_id`。

### 14.2 进程恢复

OURO 不在进程启动时扫描所有 Session 并无条件启动后台 Goal。恢复以已有 durable state 为准：

- active Run 按 Runtime recovery 处理；
- 已持久化 queued continuation 继续由 queued input 恢复；
- terminal Run 的未结算 checkpoint 重新 settlement；
- controller activation 只在 execution contract 可恢复时继续有效；
- owner contract 不可用时 fail-closed release，并显式诊断；
- active Goal 没有 queued input 时不会仅因 Host boot 自动创建新 Run；它保持可见的 active/idle，下一条用户输入会在 Goal context 下执行。若恢复流程已因错误把 Goal 置为 paused，才由用户显式 resume；

这同时避免“重启机器后突然自治”和“明明已有 durable continuation 却丢失”两个极端。首版不为此增加全局 Goal scheduler。

### 14.3 Compaction

Goal objective 和关键审计规则通过 `message` Context Fragment 持久化；Goal canonical state 仍在插件 data 中。Compaction summary 不是 Goal 真相，不能覆盖 objective、goal id、budget 或 status。

---

## 15. 权限与安全不变量

1. Goal 不修改 Session permission mode。
2. Goal 不自动批准 Tool，不降低 Tool Policy，不绕过 approval。
3. `/goal` 不等于“允许执行任何命令”；无人值守能力仍由现有 permission/interaction 配置决定。
4. CreateGoal 的模型路径是 state-changing，并接受 Host approval；用户 `/goal` 路径不重复审批。
5. objective、report、外部文件内容都按不可信数据处理。
6. 安全策略、内容过滤、资源限制可以暂停/阻塞 Goal，但不能被 Goal continuation 覆盖。
7. Goal 只适用于 primary Session；subagent 不创建或继承 Session Goal。
8. Goal plugin 需要 `sessions.write` 与 `background.run`，不因 Goal 本身申请 shell、network 或 filesystem 权限。

## 16. 可观测性

用户至少能从 `/goal status` 与通用事件看到：

- goal id 与完整 objective；
- active/paused/blocked/complete；
- 最近 actor 与 reason；
- runs/tokens used；
- token budget 与 remaining；
- 当前是否存在 active controller；
- 最近 completion/block report；
- 自动 continuation 是否 queued、被用户输入取代、因冲突暂停或因 owner failure 释放。

重要错误不能只写 debug log：Plan/Goal claim conflict、usage unavailable、stale Goal tool、continuation conflict、owner unavailable、forced release 和 budget exhausted 都必须进入用户可见诊断或事件。

首版不建设独立 Goal Dashboard。CLI/TUI 可以先投影已有 Command output、Session control 和 Run continuation event。

## 17. 验收不变量与测试范围

### 17.1 框架级

- release payload 在 in-process 与 worker 路径都到达 deactivate；
- Continuation transition 具有 plugin/generation/execution-contract attribution；
- 非 terminal Run 不能 settlement；
- 非 completed terminal Run 可以 pause + release，但不能 continue；
- stale activation/revision 拒绝，不影响新 controller；
- controller release 与 queued continuation cancellation 一致；
- settlement crash/replay 不重复 queue、不重复 usage；
- bound policy timeout/unavailable 时精确 fail-closed release；
- 多 policy 冲突不自动挑选；
- user queued input 继续优先。

### 17.2 Goal plugin

- `/goal` 创建 controller、Goal record 和首个 attributed input；
- 未完成 Goal 上 create 被拒绝；
- pause/resume/cancel/replace 状态表完整；
- Plan 与 Goal 的 claim 冲突可见且无部分激活；
- 模型自然 finish 后 Goal 自动产生下一 Run；
- UpdateGoal complete/blocked 释放 controller，且不再续跑；
- report 为空、goal id 过时或状态非法时拒绝；
- replace 后旧 Tool 与旧 continuation 不影响新 Goal；
- abort/provider/runtime error 变为 paused 并释放 controller；
- waiting approval 不创建额外 Run；
- token usage 精确累计，recovery 不重复；
- budget 到达变为 runtime-blocked，不伪装 complete；
- usage 缺失时 visible pause；
- release 后 queued continuation 被取消；
- compaction 后 objective、audit 规则与 identity 仍可恢复；
- Goal 不改变 permission mode 或工具可见性；
- subagent 不获得 Goal controller。

### 17.3 端到端验收场景

至少覆盖：

1. 多 Run 修复一组失败测试，验证后 complete；
2. 连续三次遇到同一真实外部阻塞后 blocked；
3. 用户在 continuation 入队前发送 steering input；
4. Goal 运行中进入 Plan，被 claim conflict 拒绝；
5. 进程在 usage 结算后、queue 提交前崩溃并恢复；
6. Goal replace 与旧 Run 并发完成；
7. token budget 在一个 Run 后 overshoot 并停止；
8. 手动 approval 下 Goal 等待用户，不产生并发 Run。

## 19. 最终设计原则

Goal Mode 的价值不在于让模型“更努力”，而在于把长任务最容易失真的几件事交给 Harness：

- 目标不能丢；
- 目标不能偷偷变小；
- 一轮结束不等于任务完成；
- 完成必须显式并留下证据；
- 资源耗尽不等于成功；
- 用户与安全控制始终优先；
- 旧工作不能污染新目标；
- 恢复、冲突和失败必须可见；
- 插件只能表达意图，Application 才能改变 Session 和调度 Run。

在 OURO 现有架构中，正确实现 Goal Mode 的关键不是增加更多抽象，而是补齐 Continuation 与 Session Controller 之间缺失的通用 transition 边界，然后用一个小而完整的 builtin plugin 组合既有能力。
