# R3：Run 资源清理与绑定解释减负验收

日期：2026-09-13。改前为 `5c2b4bb`；改后为 `2b1316f`。
最终契约见[核心运行时规格](../../../specs/OURO_核心运行时规格_2026-09-02.md)。
生产修改仅涉及 `ouro/application/runtime.py`，没有引入 TUI/CLI/Textual 依赖，也未修改任何 TUI 生产代码。

## 必要改进与最终范围

原实现的终态和 detach 各自列出七张资源表，Runtime 关闭则只清除其中两张；关闭但仍被引用的 Runtime
会继续持有工具协调器、Agent Catalog 等五类 Run 引用。现在由一个私有清单列出全部 Run 资源，终态、
未取得结果的异常退出、detach 与 Runtime 关闭共用移除入口；直接读取资源的热路径保持原样。
不新增资源管理服务、持久状态或第二套 Run 状态机，不再要求为了统一形式把七张表聚合为一个对象。
同一生命周期要求统一释放职责，并不必然要求相同存放形态：直接索引服务运行读取，一份资源清单服务完整收尾。
静态差异复核确认 16 个资源读取、实时权限更新及模型轮次绑定方法的 AST 与基线一致（忽略行号），
包括工具/策略/Observer registry 选择、协调器惰性创建、控制身份读取、Session 控制快照与每轮请求绑定。

同时修正了同一边界上的两项问题：

- Catalog 恢复先登记租约、后验证控制快照，失败后该入口会留下租约，再次进入可能因命中缓存而跳过验证。
  现在验证成功后才登记，失败关闭取得的租约。公开运行路径原有外层清理仍保留，因此不将这个问题夸大为
  所有失败运行都会永久泄漏或绕过校验。
- 委派工具范围在引用与约束验证前登记，失败时可能留下半更新绑定；预备 Run 路径还重复解释相同 metadata。
  现在在绑定/恢复入口全部验证成功后一起登记，删除调用者重复解释，不缓存跨轮或跨恢复阶段的检查结果。

Runtime 关闭还会汇总租约回调错误并继续关闭其余资源，避免第一项失败中断整次收尾。
结构收益是减少同步维护的清理位置、完整释放引用与减少重复解释，不以删除字段或引入新对象数量为目标。

| 保留边界 | 最终行为 |
|---|---|
| Run 状态 | queued/running/三种 waiting 状态保留绑定；终态、异常退出和关闭释放 |
| 排队输入 | queue_id 独立持有租约；临时 Run 转入队列时仅转交租约，移除其他引用 |
| Observer | fork 的独立租约直到观察工作结束才释放，旧代次不随 Run 终态提前卸载 |
| 锁与 abort signal | 继续由 RunExecutionOwnership 管理 |
| 控制、权限与工具契约 | 每轮请求与执行前按原有边界重检，实时权限更新仍生效 |
| 存储与性能机制 | metadata/schema、IO 线程边界、并发、背压、流式窗口及 TUI 消费预算不变 |
| 框架与 TUI | Runtime 资源生命周期不由界面驱动，TUI 使用既有 Application 接口 |

## 环境与可重复方法

同一 Windows 11 机器、Python 3.14.6 和锁定依赖；基线经 `git archive 5c2b4bb` 解压至忽略目录
`.pytest_cache/r3-baseline`。使用同一版[资源脚本](../../run_resources.py)和
[管线脚本](../../session_pipeline.py)，三组交替顺序为 before/after、after/before、before/after；
性能测量不与 pytest 或其他本轮基准并发。系统桌面负载未锁定，不把本机短样本当作跨机器保证。

- 资源脚本每组 100/1,000 个 Run，分别终结、等待/恢复、转交队列及全部等待后关闭；真实 Runtime、协调器和
  Catalog lease，仅 Catalog 查找替换为内存返回。计时与 tracemalloc 分开，RunRecord 在计时前创建。
- 关闭后 Runtime 仍存在，用弱引用计数协调器；traced current 也包括探针弱引用列表和空字典容量，不全是泄漏。
- files/SQLite 各组一次预热后记录十个独立 Session 的 run_prepared 与事件收尾；创建 Session、reserve 和
  解码 spy 均不计入运行耗时。另核对约束解码次数、终态、消息 role/content 摘要和租约归零。
- 管线场景保持 120 条历史、两轮完整流式输出、一次约 32 KiB 工具结果；常规每轮 40 delta，慢存储注入 5 ms，
  长流改为每轮 400 delta。后两项均测 files/SQLite TUI；常规还测无界面 Runtime。
- 这些是离线、headless 证据，不是网络 Provider、真实插件规模或 Windows/POSIX 终端 paint 验收。

## 最终性能结果

关闭时仍存活的协调器由 **100/1,000 个降为 0/0**；全部场景的 lease 收尾均为 0。
两版正常终结、等待/恢复、队列转移的协调器收尾均为 0，修复的是 Runtime 关闭后仍持有等待 Run 引用的问题。
close_waiting 的 traced current 中位数为 311,040 → 32,768 B（100 Run）、
3,067,688 → 271,592 B（1,000 Run）；后者峰值为 3,449,336 → 3,490,432 B。
完整清理需要临时收集 Run 身份，运行峰值未宣称下降；关闭后约 91% 的 traced current 降幅才是本项的直接收益。

## 行为与质量门槛

改前定向回归 391 passed（165.76 s）。针对已确认问题的新测试在旧实现上有 6 failed / 7 passed：
关闭引用残留两项、控制恢复失败与重试两项、部分委派绑定一项、重复解码一项。
收窄后的最终方案新增测试文件 16 passed（6.02 s），包括两个租约关闭回调失败场景和一个隔离进程解耦场景。
隔离进程禁止导入 ouro.tui/textual，files 与 SQLite 均能完成 Run、排空事件并关闭 Runtime。

测试覆盖等待绑定保留、终态重复释放、Observer 独立租约、队列转移、恢复失败重试、绑定及恢复取消、
委派约束与实时权限更新。既有全量集成范围还包括热更新、跨重启审批/用户恢复、每轮请求绑定、CLI 和 TUI。
聚合试点的定向回归结果不冒充最终方案验收；试点的全量运行在撤回结构修改时中止，最终方案重新跑完整门槛。

最终全量复跑 **2,785 passed / 4 skipped**（2,002.81 s），覆盖率 **84.53%**，达到 80% 门槛。
锁定依赖同步、Ruff 检查及格式检查（488 文件）、mypy（293 源文件）、compileall、源码包与 wheel 构建、
`git diff --check` 和文档本地链接检查均通过。

全量测试后格式检查发现 `test_builtin_goal.py` 的重命名调用所在行混用了行尾格式；Ruff 仅统一该行行尾，
未改变代码语义，随后重新执行静态检查、格式检查、编译与构建，不因这一格式调整重复运行整套测试。

首次最终方案的全量运行得到 2,784 passed / 1 failed / 4 skipped（2,001.12 s，覆盖率 84.49%）。
唯一失败是 `test_approval_panel_denies_selected_tool`：只等待 projection 的审批状态清除，就立即断言面板已隐藏，
未覆盖之后的异步交互刷新。基线普通重跑五次通过；在原有 UI 刷新 await 处受控延迟 1 s 后，
原始测试在基线和最终 Runtime 上均复现相同失败，说明该等待条件不能代表界面已完成更新。

仅修正该测试：发键前等待面板显示并聚焦，拒绝后同时等待模型状态清除和面板隐藏；保留“不执行被拒绝工具”
及面板隐藏断言，保留 5 s 超时，不增加固定 sleep，不修改 Runtime/TUI 生产同步策略。
修正后的测试在两版 Runtime 上均通过同样的受控延迟验证，相关六项审批交互回归全部通过（23.13 s）。
随后重新执行完整质量门槛，不把首次失败隐去或把定向复测冒充全量通过。
