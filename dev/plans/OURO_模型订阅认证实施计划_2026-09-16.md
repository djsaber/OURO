# 模型订阅认证实施计划

> 文档类型：未来规划
> 规划基线：2026-09-16
> 状态：通用凭据核心、驱动契约、配置/模板、Application/CLI 及现有协议请求认证已实现；Runtime 共享认证装配和默认/压缩路由重绑定已实现；通用 TUI 认证管理已实现；生产驱动验证与 Responses 仍待实施。

目标是交付多厂商认证边界与首个 OpenAI 订阅组合。设计取舍见[目标设计](../../docs/OURO_模型订阅认证扩展设计_2026-09-16.md)，权威契约及验收编号见[模型订阅认证规格](../specs/OURO_模型订阅认证规格_2026-09-16.md)。本计划只安排实施工作，不重复维护状态机、schema 或安全规则。

## 前置与实施原则

- 阅读现行开发架构、编码准则及 Provider 配置/类型/模板规格；以代码校准差异。
- 保持静态 API Key 行为，使用现有配置 mutation、HTTP/SSE、retry、Session 和账本能力。
- 每阶段形成可独立验证的提交；领域/协议变化先于 Host 接线，不顺手重构无关模块。
- 不添加多层重复校验、额外授权审批、动态插件框架、历史迁移或第二套运行状态。
- 首期生产存储只交付受限文件 store，系统钥匙串不作为完成条件。

## 验证与范围控制

开发过程中按阶段运行相关契约/集成测试，完成实现后运行规划索引规定的全局门槛：

```bash
uv run --frozen pytest --cov=ouro --cov-report=term-missing
uv run --frozen ruff check ouro tests
uv run --frozen ruff format --check ouro tests
uv run --frozen mypy ouro
uv run --frozen python -m compileall -q ouro
git diff --check
```

测试应证明状态与边界行为，不复制实现分支。真实凭据不进入 fixture 或普通 CI。若实现表明契约不成立，先修正规格和取舍，再继续下一阶段；不靠增加多层兜底掩盖问题。
