# OURO 性能优化计划

> 文档类型：持续治理计划
> 规划与进度基线：2026-09-02
> 已实现约束见[性能热路径规格](../specs/OURO_性能热路径规格_2026-09-02.md)；测量与根因证据见
> [全生命周期性能调研](../../docs/调研_OURO全生命周期性能_2026-08-30.md)。

## 目标

性能治理只处理经可重复测量确认的用户可见瓶颈，同时保持 canonical 顺序、持久化原子性、恢复、取消、
插件 generation、Host 观察和 UI 交互语义。不得以丢事件、放宽 durability、扩大无界缓存或隐藏错误换取吞吐。

本计划同时记录当前进度：已实施项说明落地机制和验证入口；未实施项说明现状、启动条件和验收标准。

## 前置条件

- 现行 Runtime、Session、Plugin、Provider、Tool 和 TUI 规格保持稳定；性能改动不得绕过其业务边界。
- 所有基线与验收使用同一单调时钟，并记录操作系统、终端、存储后端、模型事件脚本和数据规模。
- 性能探针默认关闭，不记录用户正文、凭据、reasoning、完整工具参数或结果内容。
- 只有超过一帧预算且能够定位责任层的同步段进入修复范围；增长阶推断不能替代现实测量。

## 里程碑 A：运行热路径基础治理

状态：**主体已实施；整 Run 事件留存仍是明确的条件性剩余项。**

- [x] Provider 首个语义事件即时发布，后续普通 text/reasoning delta 使用固定 8 ms 窗口、16 KiB 上限和有界 FIFO
  合并。实现位于 `ouro/core/adapter.py`，边界、异常、取消和背压由 `tests/core/test_adapter_stream.py` 覆盖。
- [x] Compaction `_next_chunk()` 使用可加字符度量和固定包络估算，候选 frame/message 只序列化一次，选块复杂度保持
  线性。实现位于 `ouro/application/compaction.py`，回归位于 `tests/application/test_compaction.py`。
- [x] Runtime Event Observer 在已知无匹配注册时跳过 observation 构造、脱敏和 `freeze_json`；每个 Observer 使用独立
  有界 mailbox，慢 Observer 不阻塞其他消费者。实现位于 `ouro/application/events.py`、`ouro/core/observers.py` 和
  `ouro/application/observers.py`。
- [x] TUI 输入草稿使用 300 ms 尾沿防抖，保存在线程中执行；关闭 Host 时等待最新 revision，失败后允许后续 revision
  重试。实现位于 `ouro/tui/app.py` 和 `ouro/tui/input_drafts.py`。
- [x] 同一工具批次的结果按 `source_index` 构造，并通过一次 `append_messages` 有序提交；资源引用先校验，成功提交后才
  发布完成 observation。实现位于 `ouro/application/tool_calls.py`，批量与幂等恢复由
  `tests/application/test_tool_call_batches.py` 覆盖。
- [x] Store、文件锁、SQLite 写事务、上下文物化和运行边界通过 `run_blocking()` 以完整 query/mutation 为单位离开
  asyncio/UI loop；caller cancellation 会等待已取得所有权的 worker settle。实现位于 `ouro/core/callbacks.py`、
  `ouro/core/inner_loop.py` 及 Application 各运行服务。
- [x] `AbortSignal.is_aborted()` 只读取进程内状态；激活时执行一次 worker-side durable read，跨进程 abort 由 50 ms
  后台 poller 桥接，Run 结束时取消并等待 poller。实现位于 `ouro/application/run_ownership.py`。
- [x] TUI spinner、计时器和定宽状态更新使用 paint-only 刷新；工具行批量 mount/remove，复杂 Markdown 和 immutable
  transcript 在 worker 渲染。实现位于 `ouro/tui/widgets.py` 和 `ouro/tui/conversation_history.py`。
- [x] TUI pending Runtime event buffer 上限为 1,000，每个 compositor frame 最多应用 64 条；lagged 后按 durable
  cursor 重载。终态 `RunResult.events` 按 projection/pending sequence high-water 去重后复用同一 consumer，不旁路帧预算。
  实现位于 `ouro/tui/app.py`。
- [x] Session catalog 使用有界 projection，不为目录读取完整 Runtime history；文件和 SQLite Store 均提供 message/event
  cursor。实现位于 `ouro/sessions/local_index.py`、`ouro/sessions/local_files.py` 和 `ouro/sessions/sqlite.py`。
- [x] 子智能体等待通过 completion event 和 Supervisor continuation 恢复，不在占用运行 worker 时轮询 child；取消与
  queued child 清理已有自动化覆盖。实现位于 `ouro/application/agents.py` 和 `ouro/application/supervisor.py`。
- [ ] **待证据触发：限制整 Run 事件留存。** 当前 `ouro/core/results.py` 的 `RunResult.events` 仍是完整列表，Runtime 的
  `emitted` 也会累积整个 Run。TUI 已限制应用速率，但没有限制 Runtime 内存。只有超长 Run 的 O(E) 内存或终态扫描成为
  现实瓶颈时，才增加显式 `capture_events` Host 契约：CLI JSON/print 保留完整事件，已有可靠 subscription 的 Host 可只取
  terminal summary 与 event cursor；不得静默改变现有 CLI 输出。

验收：上述已实施项的顺序、恢复、取消、线程所有权和 TUI 消费上限测试持续通过；未触发的事件捕获策略不得提前引入
第二套事件事实源。

### 场景矩阵

| 场景 | 当前覆盖 | 剩余验收 |
|---|---|---|
| 首段文本、reasoning 和工具名称到达 | 自动化功能/顺序测试 | 真实 terminal 首次 paint 延迟 |
| 持续长文本与 1,000 行以上代码块 | headless Markdown 与流式测试 | 帧间隔、loop stall 和峰值内存分布 |
| 工具开始、工具输出提交和模型续接 | headless 工具边界探针与功能测试 | 工具落盘、Application 投影和 UI 呈现的分段时间 |
| AskUser、审批、Plan 退出和 AFK 自动解决 | 功能与状态转换测试 | 交互期间 Key latency、spinner cadence 和资源收尾 |
| root 与两个并发 child Session 切换 | 子智能体与 TUI 功能测试 | 并发真实终端响应性和 mailbox 峰值 |
| 用户滚离底部后持续接收事件 | 滚动锚点自动化测试 | 长流期间视口稳定性复测 |
| 打开 500、2,000、10,000 条消息的 Session | Store cursor 测试 | 读取、投影、挂载、首屏和峰值内存；分页完成前预期不达标 |
| 慢插件 Observer、慢 MCP 和大工具结果同时存在 | 各组件隔离测试 | 组合场景的队列、追赶和终态一致性 |

### 指标与预算

- 首个可见语义事件：Provider 事件时间到 Textual 首次 paint 的差值。
- 持续流：帧间隔 p50/p95/p99、最大 UI loop stall、mailbox 峰值和持久化追赶次数。
- 工具边界：工具终态落盘、Application 投影和 UI 呈现时间分别记录。
- 长历史：读取、投影、挂载、首屏和峰值内存分别记录，不把总时间归因于单一层。
- 取消：请求到进程/worker 资源收尾、审计落盘和最终 `aborted` 的各阶段时间。
- 受控目标：1 ms ticker 的 event-loop lag p99 不超过 16 ms、最大值不超过 32 ms；Key 注入到 Composer 状态变化的
  p95 不超过 50 ms；标称 120 ms 的动画不得连续错过两个周期。

验收：同一场景至少重复 20 次；没有持续增长的事件队列、Markdown task、线程、进程或 Session lease；视口不被增量
夺回；工具终态、Run 终态与 UI 状态一致；Windows 与 POSIX 结果均达到预算。

## 里程碑 D：Compaction 与 Context 规模化

状态：**部分实施；剩余优化只在 canonical history 成本重新成为请求准备主因时启动。**

- [x] 摘要选块保持 frame 原子性和线性复杂度，不在累计前缀上重复 token estimate。
- [x] active compaction lineage、source digest、branch 复制、失败重试和恢复保持 canonical message 不删除；相关行为由
  `tests/application/test_compaction.py`、`tests/core/test_compaction.py` 和 Session 测试覆盖。
- [x] Context Provider 每轮重新求值以保持请求级新鲜度；Context message 持久化、资源物化、ContextView 构造和 Store
  操作在完整 worker 边界执行。实现位于 `ouro/application/compaction.py`。
- [ ] **待证据触发：摘要边界查询。** 当前 Runtime 启动和 Context 准备仍可能加载完整 canonical history，active
  compaction 也会重新验证 covered prefix。只有分层测量证明该成本主导时，才增加可验证的摘要边界查询，使请求准备成本
  与实际未压缩窗口相关。
- [ ] **待证据触发：immutable digest 与 token estimate 复用。** cache key 必须覆盖 message content、模型路由、
  compaction lineage、工具定义和影响模型可见内容的参数；任何失效条件缺失都视为不可实施。
- [ ] **待证据触发：ContextSnapshot 大对象去重。** 只有完整快照序列化或 prepared/completed 重写在现实 Session 中稳定
  主导 GIL/存储成本时，才把 ContextView 预算、Provider 请求快照和审计记录拆为共享不可变数据与小型状态记录。
- [ ] **未实施：缓存负向测试。** 若上述任一缓存落地，必须覆盖动态 Context Provider、Skill generation、resource
  projection、模型切换、branch、手动/自动 compaction、失败重试和恢复的命中与失效。

验收：请求准备成本与实际未压缩窗口相关；摘要覆盖、原子 turn、资源和动态上下文语义不变；缓存命中与失效均有负向
测试。未达到触发门槛时，以保持现行简单实现为完成决策，不为“可能更快”增加缓存。

## 里程碑 E：资源投影

状态：**请求级正确性和 loop 隔离已实施；重复投影缓存未实施。**

- [x] 文本/图片资源只在构造真实模型请求时物化；canonical Message 只保存 resource ref，不保存 request-local base64。
- [x] 每次投影重新执行 Session 可达性、digest 完整性、media type、消息角色、Endpoint vision capability、附件数量和
  字节上限校验。实现位于 `ouro/application/resources.py`。
- [x] 资源读取、hash/完整性校验、UTF-8 解码、base64 和 Message 投影随 Context projection 在 worker 中执行，不占用
  asyncio/UI loop。
- [ ] **未实施：重复附件基准。** 对多轮复用文本、大图片和并发请求分别测量读取、校验、编码时间与峰值内存，确认其在
  请求准备中占主导后才允许加缓存。
- [ ] **待证据触发：digest 绑定只读缓存。** cache key 至少包含 resource id、digest、media type、vision capability、
  message role 和投影参数；缓存不能替代任何可达性、完整性或 capability 校验。
- [ ] **随缓存实施：生命周期与并发。** 设置总字节上限和淘汰策略；删除最后引用后可回收；并发请求只共享 immutable
  bytes/结果，不共享可变 buffer；日志和诊断不得复制资源内容。

验收：无缓存时保持现行请求级正确性；启用缓存后输出与未缓存路径完全一致，命中、失效、淘汰、并发和最后引用回收均
有自动化测试，峰值内存受配置字节上限约束。

## 里程碑 F：条件性扩展治理

状态：**未实施；以下项目没有高于真实终端验收和长历史分页的优先级。**

- [ ] **待规模证据触发：文件 catalog 表示。** 当前文件后端更新一个 Session 仍会重写单体 catalog JSON；1 万 Session
  的现有测量约为 9.17 MB、单次刷新约 238 ms。先降低刷新频率；若现实目录持续超预算，再改为分片或 SQLite 投影，
  不伪装成“原地更新单个 JSON 条目”。
- [ ] **待锁等待证据触发：FileMutationLock deadline。** 当前 live holder 等待没有显式上界。增加 deadline 时必须提供
  holder/operation 诊断并保持原子事务；进程崩溃后的 OS 锁释放不是该项依据。
- [ ] **低风险候选：SQLite compaction 索引。** `compactions` 尚无 `(session_id, row_id)` 索引；只有 compaction 数量或
  查询计划显示现实收益时加入，并同时覆盖迁移与两后端契约。
- [ ] **待 Agent 规模证据触发：增量 usage/activity 聚合。** 当前 Agent tree 与 root budget 会按 delegation 和 run history
  扫描；首版深度限制下通常可控，只有大量并行 child 和长 run history 稳定主导时才维护增量聚合。
- [ ] **待唤醒成本证据触发：MCP 状态同步降频。** 配置 MCP 时 TUI 周期同步状态；只有空闲唤醒或 I/O 争用可测时才改为
  事件驱动或空闲降频。

验收：每个项目有独立现实基线、单点假设和停止规则；不得借低优先级扩展项重写 Session、TUI 或 Runtime 架构。

## 测试策略

- 热路径单元与契约测试覆盖 Provider stream、compaction、Observer、Runtime、Session control、tool batch、abort、
  Supervisor、TUI event consumer、conversation history 和输入草稿。
- 文件与 SQLite 后端使用相同 SessionStore contract；分页、catalog、恢复和 migration 必须保持等价语义。
- 每个性能改动同时提供责任层基线、失败/取消/恢复回归、资源释放证明和同场景复测。
- 真实终端验收与 headless 测试分开报告；headless wall time 不能声明 terminal paint SLA 已满足。
- 完成改动后运行 TUI、Application、Session、Plugin、Provider、Tool 与架构测试，并通过全量 lint、类型和覆盖率门槛。

## 风险与控制

- 线程切换破坏事务：只迁移完整 query/mutation 闭包，不把闭包内 Store 调用逐个切换线程。
- 流式合并改变语义：只合并普通 text/reasoning delta，结构事件、工具边界、错误、完成和取消立即 flush。
- UI 为追求帧率丢事实：只合并可派生 projection；canonical event 保持持久化和可重放。
- 分页造成历史/live 缺口：窗口 snapshot 与 event high-water 在同一 Application 边界定义，并以竞态测试证明。
- 缓存返回过期上下文：没有完整 key、失效规则、字节上限和负向测试时不实施缓存。
- 单点 benchmark 诱导过度设计：至少报告重复样本和尾延迟，达到响应性预算后停止。

## 明确不做

- 不把所有同步函数机械改成 async。
- 不在没有阻塞证据时增加线程池、进程池、队列层、renderer 或多级缓存。
- 不使用全局单 I/O worker；它会制造跨 Session head-of-line blocking。
- 不把 durability 写入延后到用户已经看到成功之后。
- 不丢弃 Provider 语义事件、工具审计事件或 Session 恢复事实。
- 不用更长 debounce 或更低动画频率掩盖 O(n²) 文本处理或 loop starvation。
- 不读取 Textual/Rich 私有状态实现脆弱优化。
- 不因 benchmark 单点变快而扩大常驻内存、文件描述符或后台任务数量。

## 退出条件

- 里程碑 A 的现行热路径契约持续通过自动化测试，且没有已知 loop-thread durable I/O 回归。
- 里程碑 B 在 Windows 与 POSIX 真实终端完成全部场景并满足 Key、spinner 和 event-loop lag 预算。
- 里程碑 C 使 10,000 条消息 Session 的首屏工作量受页大小约束，同时保持历史/live/compaction 正确。
- 里程碑 D、E、F 中的条件性项目只有达到各自证据门槛才实施；未触发项目保持显式未实施状态。
- 所有已实施优化不降低 canonical 顺序、持久化原子性、恢复、取消、Observer、插件 generation 或 Host 交互语义。
