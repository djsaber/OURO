# OURO 设计减负重构计划

> 日期：2026-09-13\
> 状态：R1、R2、R3 已完成；其余项目待实施。\
> 审查基线：`a57b14a`；实际实施以启动时记录的提交和工作区差异为准。\
> 范围：仅推进已确认有必要的设计减负，保持现有功能、性能、持久化语义与有效扩展契约。

依据：[设计减负审查与重构建议](../../docs/OURO_设计减负审查与重构建议_2026-09-13.md)、
[中文编码准则](../../docs/OURO_编码准则_ZH_2026-09-02.md)。

本计划沿用审查中的 R1–R8 编号，方便追踪证据，但不把审查建议或既有规格当作必须实现的设计。
实施前重新检查实际调用者、状态归属和失败边界；若事实已变化或简化收益不成立，缩小或撤销对应项。
每步必须指出实际删除的重复读取、解释、可写状态或编排职责，不能仅靠移动代码、增加包装层或减少行数宣告完成。

## 1. 推进顺序与范围

默认按下表顺序逐项推进，每项独立提交、独立验收。阶段是组织顺序，不要求一次合并整阶段。
R1 与 R2、R3 与 R5 没有必须捆绑交付的关系；有明确局部收益的项目无需等待后续整理。

| 阶段 | 工作项 | 前置与衔接 | 完成时应能证明 |
|---|---|---|---|
| 0 | 建立实施基线 | 所有代码改动之前 | 行为、性能和现存失败可对照 |
| A | R1：Session/Harness 读取复用（已完成） | 阶段 0 | 契约与验收结果见下方 R1 引用 |
| A | R2：worker 返回值一次解码（已完成） | 阶段 0 | 契约与验收结果见下方 R2 引用 |
| B | R3：Run 资源清理与绑定解释（已完成） | 阶段 0；保持 R1 的边界 | 契约与验收结果见下方 R3 引用 |
| B | R5：插件命令编排归 Application | 阶段 0 | CLI/TUI 不再复制接受与执行协议 |
| C | R4：插件贡献装配压平 | 建议在 R2、R3 后，减少交叉修改 | 试点确实减少转发和反向依赖，再推广 |
| C | R6：TUI 工作流组合 | 本计划先验收 R5，再调整 Host 结构 | 工作流依赖显式，交互语义保持一致 |
| D | R7：TUI 事件转换减负 | 建议在 R5、R6 后；通道删除另设条件 | 去掉无意义往返转换，通知和恢复无缺口 |
| D | R8：工具回调绑定时适配 | 可提前独立实施；避免与 R2 改同一适配层 | 调用热路径不再反复检查相同签名 |
| 收尾 | 全局回归与文档收敛 | 本轮决定实施的项目分别验收 | 无未说明的回归或遗留双路径 |

本轮不引入新的通用管线、注册框架、命令总线、调度器或业务事件源；不迁移存储格式，不以新缓存解决重复读取。
不同时推进长历史分页、渲染算法重写、权限体系改造、全面冻结模型或全局 metadata 类型化。
这些工作若有独立需求，使用各自证据和计划，不借减负扩大范围。

## 2. 全程保留的不变量

| 边界 | 必须保持的行为 |
|---|---|
| 会话与持久化 | 文件后端决定记录的恢复能力、SQLite 事务、提交回执、CAS、操作身份、历史代次、分支/撤销/转移及当前数据可读写；Session 与 Harness 在一致性边界内匹配 |
| 执行与取消 | Run 所有权、挂起/恢复、工具批次顺序、重复执行防护；取消后已取得所有权的同步工作必须有明确收尾，不能把未知结果误报为未执行 |
| 插件与控制 | 外部输入校验、执行时权限重检、只读和 owner 隔离、SDK/core 边界；插件热更新代次、执行契约与租约、Observer 独立生命周期 |
| 状态含义 | Session、Run、ToolBatch 各自的状态职责；请求当时的控制绑定和当前设置不混用；撤销业务状态不撤销已发生的 usage 或外部副作用 |
| Host 与观察 | 输入接受语义、FIFO 与不可分批次、durable-before-live、事件顺序/去重、断线追赶、子会话通知、过期结果丢弃 |
| 性能与交互 | 完整同步 IO 操作离开事件循环；有界缓冲、背压、增量渲染、首段输出、键盘响应、焦点/草稿/滚动位置和关闭后的资源释放 |

删除检查前，先判断它是否面对同一个未变输入、同一时点和同一信任边界。
外部解码、锁内提交检查、跨 `await` 后状态确认和实际执行前权限重检不能笼统合并。
当前模型存在可变对象及 `model_copy` 路径，不能以“已经建模”为由直接删除提交边界校验。
编码准则中的历史兼容清理也不构成破坏当前有效 API 或用户数据的理由。

### R5：插件命令的完整用例由 Application 承担

- [ ] 以完整 query/mutation 为单位通过现有 `run_blocking` 离开事件循环；保持取得线程所有权后的收尾语义，不在 Host 零散添加 `to_thread`。
- [ ] CLI、TUI 依次改为调用同一用例，保留各自显示、等待和输入体验；删除两端创建会话、判断回执、区分接受路径和派发输入的重复业务分支。

Host 不承担接受协议，也不为统一形式强迫所有运行走同一种调度入口。不新增命令总线或第二套调度/回执系统。

## 6. 阶段 C / D：在明确边界内整理结构

### R4：压平插件固定贡献类型的内部适配拓扑

主要落点：`ouro/plugins/contribution_types.py`、`ouro/plugins/contributions.py`、`ouro/plugins/adapters.py`；
检查 `ouro/application/runtime.py` 的基础 registry 读取。

- [ ] 从一种贡献类型开始，追踪准备、SDK/worker 调用、投影、契约和资源关闭；列出纯转发类及局部循环 import。
- [ ] 试点用明确参数的普通函数和必要的静态清单替代纯转发适配层，装配留在上层；下层不再反向导入总清单。不预建通用注册器、元类或代码生成。
- [ ] 检查 `ContributionCoordinator` 的 registry 真正调用者：Runtime 仍使用 `tools.revision` 和基础 catalog。先明确基础 registry 的所有者和访问方式，再删除中间层，不能当死字段移除。
- [ ] 试点通过后逐类推广，覆盖现有全部 13 种贡献类型；MCP 与 tools 共享的准备结果只投影一次，不依赖适配器对象身份猜测去重。
- [ ] 删除被替代的转发和反向依赖，验证热更新、冲突、契约、配置变化、租约和关闭流程。

验收：准备/投影的调用跳转、反向依赖或需要同步维护的位置实际减少，同时所有既有贡献能力仍可用。
保持 catalog 原子发布、代次租约、单例后台服务和依赖拓扑；不同含义的身份/hash 不合并。
若试点只是把复杂度搬进更大的分支函数，停止推广，修正或撤销试点，不为统一形式增加另一层抽象。

回归入口：`tests/plugins/test_plugin_system.py`、`test_execution_contracts.py`、SDK/worker 对应测试；
`tests/application/test_plugin_extensibility.py`、`tests/architecture`。
性能证据：相同插件集合的装载/热更新、catalog 构建及资源释放成本。

- [ ] 验证独立/嵌套入口的返回、Esc/取消、焦点、选中项、草稿、主题、实时刷新和错误提示；保持 Textual worker 的分组、互斥与清理语义。

### R7：去掉 TUI 事件往返转换，有条件收敛观察路径

主要落点：`ouro/application/event_models.py`、`ouro/tui/app.py`、`ouro/tui/state.py`。
本项拆成两个可分别决定是否交付的小步。

- [ ] **R7a：去掉往返转换。** 核对 reducer 实际读取字段，使其消费合适的现有只读 Host 事件表示，删除仅为 reducer 将 `RuntimeEventView` 重建为 `EventRecord` 的转换；保留必要脱敏和投影，不合并所有事件模型。
- [ ] 验证重放、实时事件、终态结果三种来源得到同样状态和内容；保持单一 reducer、序号/历史代次校验、去重、有限消费和 lagged 后恢复。
- [ ] **R7b：先证明通道覆盖。** 用现有 replay/agent-tree 能力验证新会话首次运行、受控父会话与可见子会话不同、并发子任务、会话切换、终态、断线重连；明确会话身份可用到 snapshot/cursor 再到订阅的交接顺序。
- [ ] 仅当上述覆盖及无丢失/重复已有证据时，删除被完整替代的 fallback 分支和订阅状态；否则保留有独立用途的路径，记录具体缺口，R7a 可独立完成。

验收：消除 DTO 往返构造，所有用户可见通知和最终状态等价；落盘先于实时发布，旧订阅被关闭，过期异步结果不能覆盖新会话。
不能仅因观察入口有两个就删除 fallback，它目前参与首次运行及父子会话通知。
不能为统一入口每个 delta 重读整个历史/Activity，也不能增大无界队列或绕过每帧消费预算。
R7b 未满足条件时标记“未实施，保留”，不能勾选为已完成。

回归入口：`tests/tui/test_state.py`、`test_async_observation.py`、`test_live_session_attachment.py`、
`test_subagent_navigation.py`、`test_history_commands.py`、`test_run_summaries.py`；
`tests/application/test_session_event_following.py`、`test_agent_multi_host.py`。
性能证据：长流、慢消费者、会话切换和并发子会话下的事件分配、缓冲峰值、追赶次数及首段/按键延迟。

### R8：在工具绑定阶段完成回调签名适配

- [ ] 列出现有合法 handler/resume 签名及调用方式：单参数、context/signal、`**kwargs`、同步、异步和返回 awaitable 的 callable。
- [ ] 在工具绑定或插件代次创建时完成签名适配，已知内部闭包直接调用；新绑定随热更新重新建立，不增加全局签名缓存。

## 7. 性能对照与功能等价验证

优先复用[现有基准说明](../benchmarks/README.md)和脚本。在同一机器、解释器、依赖、数据和负载下，
使用同一版测量脚本顺序比较改前/改后；不得与 pytest 或其他基准并发运行。至少保留每项的直接前置版本，
最终再与阶段 0 对照，防止多个小改动累积退化。

```powershell
uv run --frozen python -m dev.benchmarks.session_pipeline --repeat 3
uv run --frozen python -m dev.benchmarks.session_pipeline --mode tui --store-delay-ms 5 --repeat 3
uv run --frozen python -m dev.benchmarks.harness_lifecycle --label before --repeat 3
```

改后使用相同命令和场景，Harness 的 `--label` 改为对应阶段的 `after` 标识。
原始 JSONL 和环境摘要保存在 `dev/benchmarks/results/<本次实施日期>/`，文件名包含工作项和 before/after。
不是每项都重跑所有性能场景：R1 重点 Harness/Session，R2/R8 重点解码/绑定计数及调用成本，
R3/R4 重点生命周期和插件规模，R5–R7 重点 Session/TUI；最终按受影响范围作整体对照。

- files 与 SQLite 均须覆盖涉及存储的改动；Harness 基准保留现有 100/10,000 条消息、固定撤销后缀、不同 owner 数据规模及无变化/只读场景。
- 功能结果核对包含消息/事件内容与顺序、状态提交、回执、恢复和错误语义；时间戳、随机 ID 等仅做必要规范化，不抹去业务差异。
- 延迟记录 p50/p95/p99、最大值及样本数，同时查看首段输出、Key latency、loop lag 和关键操作耗时；低样本不作高分位保证。
- 成本记录可获得的 IO 调用/字节、同步、版本、构造/反射次数，以及任务、租约、订阅、缓冲和内存的峰值/收尾趋势。
- Store 方法计数包含嵌套调用，不代表物理磁盘操作；进程 IO 也不等同于介质 IO。SQLite 同步探针不可用时明确标记，不能报告为零。
- 3 次重复只用于初筛；异常或波动通过更多交替运行定位。可重复的功能或性能退化阻止验收，不能用平均数掩盖尾延迟，也不设跨机器固定耗时断言。
- headless 基准不能证明终端 paint。R6/R7 及其他实际影响交互的改动须在 Windows 和一个受支持 POSIX 终端复核相关场景；缺失环境时保留待验收状态。

对照期间保持流式窗口、合并上限、并发、背压、超时、同步策略及 TUI 消费预算不变。
当前源码流式窗口为 8 ms，上限为 16 × 1,024 **字符**；TUI 缓冲上限 1,000、每帧最多消费 64 条。
不得靠少呈现内容、延迟首段输出、降低刷新频率或持久化保障换取漂亮数字。
