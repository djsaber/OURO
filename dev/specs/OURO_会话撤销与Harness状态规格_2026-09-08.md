## 2. 状态与身份契约

### HS-01：状态归属

Harness 是会话内可撤销业务状态，包含已提交控制关系及 owner-scoped JSON 值。
原生组件与插件使用同一状态和持久化端口。插件 owner 由框架根据安装身份绑定；原生 owner 由组合根保留，
不得接受插件冒用原生 owner 或读写其他 owner 的请求。

框架校验 owner、JSON、schema 版本和控制引用完整性；业务 payload 的解释与校验属于该 owner。
状态不得以进程内实例、插件私有文件或缓存作为 canonical 来源，不得从事件正文猜测重建。

实际 usage、已发生调用结果、审批/输入 resolution 和 Run/Delegation 审计不随 Harness 撤销。
执行绑定、pending request、锁、任务、Generation 句柄及缓存不得嵌入可恢复业务状态以复活旧执行许可。
影响业务的预算值可恢复，实际消耗由原生账本按业务身份投影。

### HS-02：不可变版本

Harness 版本保存完整控制关系与 owner 状态集合；每次实际业务状态变更创建不可变版本。
无业务变化不得因读取、回调次数或 updated_at 刷新创建新版本。消息引用版本，不复制该状态集合。

版本身份必须在 Session 内唯一且不复用。撤销只改变当前版本引用，不修改旧快照内容，不将旧版本当作新写入。
每个版本明确属于一个 Session；引用其他 Session 的版本必须失败。初始空状态也是有效版本。

当前状态只有一个 canonical 版本引用。既有 controls/extension 读取端口必须从它取得同一状态，不能保留
可独立写入的第二份 controls 或 extensions 真相；需要的兼容投影只读且可重建。

### HS-03：历史代次与前置条件

Session 保存单调递增的 history_epoch。canonical 撤销成功时递增一次，普通状态提交和待消费输入取消不递增。
同一撤销操作的恢复重试不得重复递增。

产生会话效果的操作绑定开始时的 history_epoch 和基准 Harness 版本。提交时还必须验证操作未失效及本次
使用的消息头、队列状态和控制关系前置条件；其他审计事件或 usage 追加不构成 Harness 冲突。
同内容快照、回到同一版本、相同消息数量均不能绕过代次检查。

state_schema_version、Harness 版本、history_epoch、业务 revision 和 execution contract 是不同概念，
不得共用一个计数器或靠 Generation 是否存活代替操作有效性。

## 3. 消息与状态的逻辑边界

### AN-01：消息前锚点

每条本次格式下的新 canonical MessageRecord 必须带有有效 before_harness_version。
该版本表达从该消息节点开始撤回时应恢复的业务状态，不得由时间戳或相邻 Run 的最终状态推导。

| 消息来源 | 锚点与生效边界 |
|---|---|
| 直接用户输入 | canonical 接受该输入之前；拒绝输入不产生消息或状态变化 |
| 已排队输入 | 实际消费之前；排队接受时间不是执行状态边界 |
| 模型输出/上下文片段 | 应用层确定的消息逻辑位置；只读准备不会直接改变 Harness |
| 工具结果 | 对应工具操作的状态变化提交之前；变化与结果共同提交 |
| 批量消息 | 应用层按消息顺序关联状态变化，保留每个节点对应的有效版本 |

无消息的模式/状态命令独立提交版本，随后消息引用其结果版本。
一次用户输入引起的后续状态变化位于该输入之后，撤销该输入必须一并消除这些后续变化。

### AN-02：物理提交与逻辑顺序

一次事务包含多条消息时，应用层必须给出有序的消息及状态变化边界。状态变化在其对应消息处生效，
该消息记录变化前版本，后续消息记录变化后版本；必要中间版本与最终状态一起持久化。
不能让所有消息共享错误的操作前状态，也不能因为同批写入而拒绝任意节点撤销。

并发工具结果按应用层确定的结算顺序关联状态，不按工具线程结束时刻排序。
对不能安全并行写入的工具复用现有 exclusive 规则；竞争冲突不得静默覆盖。
框架的有序提交数据是有限的类型化记录，不接受插件提供任意事务脚本。

## 4. 插件调用规范

### PI-01：实例上下文与调用上下文

PluginContext 只持有实例级资源、配置、日志、凭证和插件私有文件能力，不持有长期有效的 canonical 状态写入器。
会话调用通过显式调用上下文获得 owner-scoped 状态视图。生命周期 prepare/start/stop 不隐式获得会话写权限。

调用范围必须封装 Session、owner、基准版本、history_epoch、执行归属、取消/超时和读写能力。
插件不需要传递版本或手工提交；底层存储与事务对象不得暴露给插件。
调用关闭后持有的状态视图必须失效，包含取消后仍运行的同步线程或继承上下文的后台任务。

### PI-02：读写视图

读取返回不可变值或防御性副本，修改返回对象不得隐式保存。可写调用只能暂存当前 owner 完整值的替换或删除，
并能够读到本操作内此前已接受的暂存修改。嵌套 Controller 使用父操作的暂存视图，不创建独立提交。
只读范围写入、跨 Session/owner 写入、关闭后写入必须明确失败。

视图通过 `controls()` 只读提供当前 owner 的已激活控制关系；返回值必须隔离修改，关闭后读取失败。
owner 状态不应重复持久化这一控制投影。

同一模型准备阶段的 Context/Policy 与 active_when 选择必须基于一致的状态快照；不能整 Run 固定旧状态，
也不能每个回调重新读取不同当前版本。工具结算或显式状态命令生效后的下一阶段取得新快照。

### PI-03：贡献类型职责

| 类型 | 可直接暂存 Harness 变更 | 生效规则 |
|---|---|---|
| Observer | 否 | 非阻塞观察已提交事实，不能驱动必要业务结算 |
| Context、Prompt/Tool/Turn Policy、Compaction | 否 | 返回现有类型化输出，应用层按各自契约处理 |
| read_only Tool | 否 | 遵守现有 effect 声明 |
| 状态变更 Tool、Command、Controller | 是 | 输出通过校验并被应用层接受后提交 |
| Continuation | 是，作为决策提案 | 状态与被接受的续跑决策共同结算 |
| Background Service | 不持有常驻写权限 | 复用已有调度能力建立新的有归属会话操作 |

贡献的特定输出类型继续保留，不将所有回调替换为万能结果字典。
策略聚合失败、冲突或提案未被采用时，不提交其状态；不能因为 handler 已经返回就逐个保存。
业务错误结果与回调异常不同：若业务结果是有效的暂停/失败决定，其明确状态变化可随决定结算；异常没有此含义。

### PI-04：in-process 与 worker 等价

worker 调用携带所需的 owner 状态快照，结果携带与 SDK 同语义的暂存变化；owner、Session、代次及权限以
Host 建立的调用范围为准，不信任 worker 自报归属。沿用现有协议大小限制与类型校验，不增加逐字段存储 RPC。

两种运行形态必须在只读限制、schema 错误、取消、超时、挂起、迟到结果和重复结算上具有相同可见结果。
本次 SDK 与 worker 协议必须显式推进版本，并纳入既有执行契约；旧接口不得无提示改变 save 的生效语义。
升级以新契约和明确迁移/拒绝为准，不保留运行时双写或直接保存 fallback。

## 5. 提交、失败与恢复

### CM-01：单一提交决定

应用层是逻辑操作的提交拥有者。一次操作相关的 Harness、控制关系、canonical 消息或挂起/队列意图，
以及用于恢复去重的结算结果，必须共享一个 durable 提交决定。
消息追加、直接状态保存、控制器 active 更新不得各自成功后由插件补偿。

操作身份优先复用已有 tool call、交互、队列或 continuation 结算身份，并区分挂起与恢复阶段；相同 tool call
跨阶段不能误去重。需要独立身份的状态命令由应用层分配。只读回调不新增持久化操作记录。
同一操作的重复提交返回已保存结果，不重复追加消息、队列、事件或版本。

### CM-02：短提交与失效

调用前获取快照，调用内计算提案，调用后校验并提交；不得跨插件调用、网络访问或人工等待持有持久化事务锁。
取消信号尽力停止计算，提交检查独立保证失效操作不能改变当前会话。

| 失败位置 | 必须呈现的语义 |
|---|---|
| 回调异常、非法结果、超时或提交决定前取消 | 丢弃未提交提案，不改变 canonical Harness |
| 基准状态/消息头/队列发生竞争 | 明确冲突，不覆盖、不悄悄改选目标 |
| 旧 history_epoch 或关闭的调用 | 拒绝当前会话效果；真实执行结果可归入原运行审计 |
| durable 决定已经形成，后续写入或响应失败 | 恢复该决定并按操作身份查询结果，不能报告“确定未生效” |
| canonical 提交成功、Catalog/界面刷新失败 | 保留成功，诊断并重新加载投影 |

自动重新计算只适用于无外部副作用的纯决策，并受原调用期限约束。
已执行的工具、文件/网络操作不能因为状态冲突或响应丢失自动重跑。

### CM-03：挂起与控制转换

ToolInputRequest、审批或子调用等待是显式阶段边界：状态变化、等待记录及恢复身份共同提交，随后关闭调用范围。
恢复调用使用新范围和当前版本，验证原交互仍有效。撤销后原 resolution 不可用于授权新执行。

控制器的已提交业务关系和 owner 数据必须一致。activating/deactivating 等执行准备过程归于操作恢复信息，
不能作为半完成的可撤销业务状态发布。claim 在准备时检查、在提交时再次校验；controller 失败不留下孤立
active 关系或 owner 状态。replace 内所有相关回调与状态变化作为一次逻辑转换结算。

replace 在同一草稿内先 deactivate 所选旧关系，再 activate 新关系；新回调读取已接受的前序草稿。
Continuation 保存的 settlement plan 必须包含已准备完成的状态提案与控制转换结果。恢复不再次调用策略或
Controller；基准状态失效时暂停该旧决定，不能覆盖新状态。没有可证明状态基准的旧计划只能暂停。

### CM-04：两种后端

SQLite 必须通过单一本地事务提交本次相关 canonical 数据。
文件后端必须收敛现有 history-cut 意图为覆盖本次操作的可恢复提交机制，不叠加一个互不协调的插件提交日志。

文件提交顺序：验证前置条件；写入并持久化所需不可变快照；持久化完整提交决定；可重入地应用消息/状态/
交互/队列更新与必要事件；确认完成。提交决定形成前的孤立快照不成为当前状态。
完整决定包含重做所需的确定数据，恢复不得重新调用插件、模型或工具。

所有 canonical 读取和写入入口必须在目标 Session 锁内完成未完成决定后再返回；不能有仅消息查询或状态
查询绕过此边界。决定形成后的故障恢复到决定所指的新状态，不以“回退一半文件”补偿。
目录/catalog 查询仍按现有只读投影契约工作，不为了本次恢复扫描所有会话。

提交事件沿用现有日志和稳定提交身份去重，处理“事件已经 append、完成标记尚未写入”的故障窗口。
日志序号不回退；事件发布在 canonical 决定生效之后。既有审计日志不承担 Harness 的推算恢复。

## 6. 撤销接口与应用行为

### UN-01：框架撤销

框架接受精确 before_message_id 和调用方看到的历史前置条件，返回实际首条撤回消息、最后保留消息、数量、
当前 Harness 版本和 history_epoch。具体类型名可以沿用现有 MessageTruncation/SessionService 契约演进。

在当前消息 m 之前撤销，必须满足：

1. 保留的 canonical 历史严格等于原历史中 m 之前的前缀，m 本身被移除。
2. 当前 Harness 等于 m.before_harness_version 所指完整状态。
3. 本次 history_epoch 只递增一次，并撤销受影响旧操作/恢复/投递的有效性。
4. 消息头、数量、压缩可达性、上下文缓存与当前活动投影对应新历史。
5. Run、事件、实际 usage、资源与子会话执行事实保留。

对 user/system/assistant/tool_result 节点使用相同语义。不以 role、scaffold、turn_id 或工具帧作为框架拒绝条件。
目标不存在、已撤回、锚点不可用、快照损坏或前置条件冲突时，必须在形成提交决定之前失败。
已知同一操作的重试按结果去重，不能将“目标已不存在”一律解释为成功。

### UN-02：执行所有权

canonical 撤销必须取得既有 Session 执行所有权。活跃执行尚未完成取消结算时，应用入口返回明确忙碌状态，
由用户先中断；不得强行释放其他 owner 的锁。无活跃 owner 的遗留运行通过已有恢复/终止入口结算。

history_epoch 是所有会话效果入口的持久化校验，包括插件、工具结果、恢复任务、continuation 和父会话交付。
不能只给 /undo 或某个插件加检查。Generation 的共享生命周期不得因一个会话撤销而关闭。

### UN-03：任意切口与 /continue

历史裁剪与 Provider 协议完整性必须分离。允许精确保留工具请求而撤回其结果；不能把切口向前移动。
构造 Provider 上下文时排除被切开的不完整交换并产生诊断，不修改已保留 canonical 前缀，不伪造工具成功结果，
不从旧 Run checkpoint 补交被撤回消息。

撤销后的 /continue 只能基于当前前缀和 Harness 开始新 Run，不恢复旧 epoch 的原 Run，也不再次追加保留输入。
没有保留的有效输入时明确拒绝。普通、未撤销的崩溃恢复继续使用原 Run 和原执行契约。
Provider continuation artifact、旧上下文快照与旧工具恢复许可均须经过历史有效性判断。

### UN-04：应用选择与完整输入

应用入口支持 message_id 或 queue_id 定位直接用户输入；默认 /undo 优先最后一条待消费直接用户输入，
否则选当前历史最后一条直接用户消息。来源依据 canonical provenance，不仅检查 role=user 或 scaffold=false。
其他角色和插件/Host 代发的用户角色消息不能通过用户撤销入口获得直接用户身份。

返回完整编辑输入，包括内容块、资源引用和技能激活内容；Host 的纯文本输入框能力不是底层拒绝理由。
CLI/TUI 必须保留这些内容的现有表示，不能静默丢附件或技能。重新提交走正常输入链，产生新消息身份。

## 7. 排队输入与跨会话交付

### QU-01：精确消费与取消

queue_id 从接受到消费保持稳定；消费后的消息必须能由该身份查询。
消费决定必须把队列移出待消费集合、消息追加、锚点和必要运行归属共同提交，消除 append/ack 中间态。
不得让同一输入同时表现为“已取消”和“已消费”，恢复不得重新消费已有消息。

取消仍待消费的直接用户输入只移除该项并返回完整输入，不改变 Harness、历史或其他排队输入。
仅属于该输入的待调度工作和资源租约按既有所有权机制释放，不停止其他输入正在进行的执行。
取消与消费在同一 Session mutation 边界竞争；若消费获胜，则按该 queue_id 的消息身份进入 canonical 撤销。
此时若执行忙碌，返回目标已消费且需要中断的结果，不能把取消成功返回给 Host。

### QU-02：历史撤销后的队列

已消费输入不随快照恢复重新排队。仍待消费的其他直接用户输入保留原身份、内容和相对顺序；撤销本身不触发 drain。
用户下一次明确提交/继续触发正常调度时，消费前重新校验当前历史下的策略、控制和执行契约；旧检查许可不能沿用。

旧 epoch 产生的插件自动输入、续跑和 child delivery 不再具有投递许可，按现有队列/交付记录标记取消或失效。
与这些来源无关的待处理 Host 工作保留接受事实，消费时重新取得有效执行范围；不能借撤销隐式修改任务配置。
现有输入批次作为完整单位接受/消费，不破坏 batch 身份。已消费后撤销某消息后缀不会复活或重新消费该批次。

### QU-03：父子会话

父会话撤销不回滚 child Session、Run、usage 或资源。对旧 parent epoch 的结果交付必须在父提交边界拒绝。
框架按现有 bound lifecycle 请求停止相关子工作；独立 child 工作仍按其原归属运行。
父会话的撤销决定不依赖跨会话原子事务，也不以 child 记录存在为 blanket 拒绝条件。

## 8. 内置插件规范

### BI-01：统一机制

Todo、Plan、Goal 必须使用同一 owner 状态适配与提交机制。不得在撤销入口出现按插件 id 分支、反向调用业务
undo 钩子、清空整个 extension state，或异常时恢复整个插件私有目录。

Todo：列表修改与对应工具结果共同提交；失败或撤销恢复到准确旧列表。
Plan：模式由原生 controls 持有，owner 状态保存计划路径；两者共同提交。审批内容、digest、选项和恢复身份
由原生交互请求持有，不在 owner 状态保存 pending ID、独立 revision 或重复执行输出。恢复业务条件不能复用旧审批授权。
计划文件内容不回滚，文件与业务数据可能不同，以明确的状态数据决定当前行为。
Goal：稳定目标身份、内容、业务状态、报告和预算属于 Harness；Run/activation 绑定由原生运行快照提供。
Context 不得保存运行绑定；Continuation 的业务变更随结算提交。

### BI-02：usage 与预算

原生 usage 是唯一消耗事实，按稳定目标身份及既有 usage entry 身份关联，重试不能重复计费。
同一目标恢复后计入其已发生的全部关联消耗，包含被撤回消息对应的真实执行；新目标使用新身份。
tokens_used、remaining 等展示和预算裁决从账本与当前业务预算派生，不作为可回退的累计事实重复保存。
控制器的可选 `usage_scope` 是 owner 内业务身份；运行准备固定控制及用量归属，账本保留请求当时的绑定，
不使用完成时的当前 Harness 重新归属。相同 owner/scope 每个 usage entry 只累计一次。
SDK `run_controls()` 与 `usage_tokens()` 是 owner 绑定的只读调用视图；没有原生账本时 usage 为 `None`，
不得解释为零。worker 使用同一快照语义。无归属信息的旧账本 entry 不推断归属，已知迁移另行处理。
运行绑定来自执行调用实际持有的 Run 请求快照；命令和事件观察不通过 run_id 反查并推断请求归属。
旧数据迁移不得把无法精确归属的 usage 重复计入多个目标，需保存可验证基线或明确拒绝不确定转换。

## 9. 观察、索引与 Host

### OB-01：提交后同步

应用发布包含提交身份、当前代次和历史变化边界的事实通知，复用现有有序事件/订阅管线。
订阅者成功或 lag 恢复时读取同一提交边界的消息、状态、活动和队列快照，不混用旧缓存。
事件 sequence 单调；旧 epoch 的流式内容不能改变当前消息或将终态投影回 running/context preparation。

撤销后的已知旧消息事件不能再次要求读取已删除消息；通过事件归属与代次过滤处理，不能笼统吞掉 PersistenceError。
当前有效历史的缺失记录仍必须报告真实数据错误。

### OB-02：界面与缓存

TUI 在撤销成功后重载标准会话投影并恢复输入草稿；失败保留原草稿和投影并显示原因。
恢复后新提交、新流式响应和另一个 Host 的观察必须使用同一 canonical 历史。
重启进入中断/撤销后的会话必须呈现已结算的活动状态，不能卡在旧“准备上下文”。

消息查询索引必须识别截断后同长度或更长的重写，覆盖跨 store reader 情形；不得仅按文件大小或固定短尾判断有效。
压缩和上下文引用必须按保留消息可达性处理，不清空所有仍有效压缩，也不保留覆盖被撤回消息的摘要。

## 10. 数据与接口迁移

### MG-01：明确基线

持久化模型、layout、SQLite schema、SDK 与 worker 协议按各自现有版本规则升级；不得靠默认字段吞掉旧格式。
迁移必须可重入、在一致状态下读取源数据，全部必要数据成功后才推进完成标记，不破坏原始审计。

已有会话以可验证的当前 Harness 建立迁移基线。基线之前的消息没有可证明的历史状态时，显式标记锚点不可用；
不得为它们填入空状态或当前状态。此后新消息具有准确锚点，可以撤销回基线，但不能越过不可恢复边界。
有活跃执行所有权的旧会话不能一边运行一边迁移，必须先按既有所有权机制静止。

旧 plugin state、Run 绑定和 usage 的转换必须针对已知 schema 编写明确迁移。迁移结束后移除旧直接写路径，
不长期保留旧私有文件/旧 controls 与新 Harness 的双读双写。

### MG-02：恢复与插件可用性

恢复已保存 Harness 版本是原生存储操作，不调用插件 activate/deactivate、工具或业务初始化来重放效果。
框架结构有效但 owner 插件暂时缺失时可以恢复原始状态；相关执行明确报告契约不可用，不静默丢弃状态或更换版本。
正常加载仍使用现有 Catalog 和执行契约；Generation 资源按当前进程重新建立，不从快照恢复句柄。

不支持的 owner schema 保留为可诊断数据，业务读取/执行明确失败。若需要 schema 迁移，以明确迁移生成新版本并
一致更新引用，不原地修改不可变历史快照，不把迁移回调塞进 undo 热路径。

### MG-03：已有会话生命周期

导出/导入、回收站和 File/SQLite 转换必须保留当前状态、保留消息锚点所需快照、代次与必要去重事实。
会话分支复用既有 copy/reset/reject：按该策略一致转换复制的状态版本和当前状态，并重映射 Session/版本引用。
reset 的 owner 状态不得通过分支内 undo 复活；reject 不得因新格式被绕过。无需新增分支 UI 或策略类型。

## 11. 性能与结构约束

### PF-01：成本边界

设 H 为一份 Harness 的序列化大小，R 为被撤回后缀长度，D 为受影响压缩/队列/交付元数据。
本次状态快照写入成本允许为 O(H)，只在状态变化时发生；每条消息增加常量大小版本引用。
撤销按目标定位、O(H + R + D) 相关工作实现，不能复制保留消息正文或全量重放事件来恢复状态。
文件后端保留尾部定位和原地裁剪；SQLite 使用索引定位与范围操作。

每个逻辑阶段有界读取一次状态并分发 owner 视图，避免每个插件分别加载全部 owner 或每次字段访问一次 RPC。
同步 query/commit 以完整操作离开事件循环，不能通过降低 fsync、丢事件或无界缓存换性能。

### PF-02：最小结构

保留不可变 Catalog、Generation gate/lease、现有贡献类型、observer mailbox、执行监督和存储端口。
新增共享机制限于 Harness 版本/锚点、调用范围/暂存变化与原生提交边界；不得复制另一套会话状态机、
插件安装体系或通用事务 DSL。删除被这些机制取代的直接写、重复锁和恢复特例。
