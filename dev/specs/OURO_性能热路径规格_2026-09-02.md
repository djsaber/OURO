# 运行热路径性能规格

> 文档类型：现行规格，含明确标注的目标增量
> 代码基线：2026-09-02

## 目标与原则

运行热路径按业务语义边界分配工作，而不是按传输碎片、UI 按键或可重复派生投影分配工作。异步事件循环只做
编排和轻量投影；可能等待文件锁、`fsync`、SQLite writer 或执行大对象物化的同步工作必须离开事件循环。性能改进
不能改变 canonical 顺序、原子提交、恢复、取消、插件 generation 隔离或 Host 观察语义。

Runtime loop 所有权、投影门禁和 TUI dispatch 条款属于现行契约；文末“真实终端响应性验收”属于目标增量。

## 流式事件

`RuntimeAdapter` 为每个 Provider stream 维护一个 reader 和一个固定容量 FIFO。reader 独占 Provider async
iterator，消费者独占 FIFO；FIFO 满是唯一无损背压点。

普通 `text_delta` 和 `reasoning_delta` 的 Provider chunk 边界不构成稳定业务语义：

- 每种普通 delta 在一个连续语义段中的首个分片不得等待未来分片；
- 后续分片以最近一次同类发射时间为锚点，在最多 8 ms 的固定窗口内合并；窗口不得因新分片到达而续期；
- 分片到达时窗口已经截止则立即发射，因此慢流不逐片承担额外等待；
- 每批最多 16 KiB，超出部分保持顺序留给下一批；
- continuation、tool、retry、done、error、usage/completion、delta 类型切换和 abort 都会立即结束当前合并边界；
- Provider 异常在先前事件后按序交付；取消或消费者关闭必须关闭 reader 和 Provider iterator。

该合并只降低事件频率，不改变拼接后的 text/reasoning 内容。

## 压缩容量规划

摘要选块必须保持 frame 原子性，并使用与 `estimate_text_tokens` 相同的精确保守估算。一次 `_next_chunk` 中：

- summarization prompt 和已有摘要包络只度量一次；
- 每个候选 frame 的模型可见文本最多序列化一次；
- 累计字符度量必须可加，选块工作量对已检查 frame/message 数为线性复杂度；
- 已有摘要已占满输入容量、单 frame 超预算时继续抛出原有 `ContextOverflowError`。

不得通过放宽 token 预算或拆开工具交换获得更低计算成本。

## Runtime Event Observer

canonical Event 持久化和 Host event sink 投递总是执行。Plugin Observer 是独立可选消费者：

- Registry 可用 event name、runtime event type 和 active controller 集合判断是否存在 enabled 匹配项；
- 已知不存在匹配项时，不构造脱敏/冻结的 `RuntimeEventObservation`，不获取额外 Catalog lease，也不进入 dispatcher；
- 当前 Catalog 或 Run snapshot 不可确定时，必须保守走完整观察路径；
- 存在匹配项时继续在事件发布时保留对应不可变 Registry/Catalog 视图。

## TUI 输入草稿

内存 `TuiInputDrafts` 始终包含最新修订。磁盘保存采用 300 ms 尾沿防抖：持续编辑只延后保存，静默后保存
最新完整快照。保存期间出现新修订时必须再次保存最新值。Host 关闭必须等待最终修订完成原子保存；保存失败沿用
现有 warning 语义，不能阻塞编辑或 Runtime。

## 工具结果消息

同一 `ToolCallBatchRecord` 的完成结果按 `source_index` 构造消息，并作为一个有序 `append_messages` 批次提交。
所有资源引用必须在任何新消息提交前验证。提交成功后才发布 `ToolCallFinishedObservation` 并推进批次状态。

幂等恢复时，已有 `(tool_result, tool_call_id)` 消息直接复用，只把缺失消息放入新批次；sequence 和
`result_message_id` 必须保持确定性。单结果接口与批接口共享同一构造和校验规则。

## Runtime 阻塞边界

同步 Store port 保持同步接口；application/core 的异步编排通过一个受所有权保护的 worker 调用边界执行它们：

- 一个 transaction/mutation 闭包从取得锁、读取、状态转换、写入到释放锁必须完整留在同一个 worker；不得把闭包内
  的 Store 调用逐个切换线程；
- model round begin/commit、上下文投影和快照保存、usage、工具批检查点、Run complete/fail/pause，以及 Run 启动所需
  的 durable mutation 不得在事件循环线程执行；
- 不使用全局单线程 executor。不同 Session 可以由默认 worker pool 并行，顺序与排他性仍由 Session/SQLite 的既有锁
  和事务定义；“同一 worker”只约束一次完整操作；
- caller cancellation 不能遗弃仍持锁或正在修改 durable state 的线程。worker 必须先 settle，随后再向 caller 传播
  cancellation；
- canonical event 仍在 durable boundary 成功后由事件循环按序发布。

Windows 的文件/目录原子发布共享同一个有界 transient sharing-race 重试；重试发生在 worker 上，不得冻结 TUI。

## 取消观察

Provider 和工具执行中的 `AbortSignal.is_aborted()` 是高频同步检查，只能读取进程内状态：

- 本进程 abort 在 durable transition 成功后立即发布到本地 signal；
- signal 激活时先执行一次 worker-side durable read，关闭 `run_started` 与 signal 建立之间的竞态；后续 Run mutation
  必须从 latest Run 派生，不能用旧快照覆盖 `abort_requested`；
- 跨进程 abort 由后台 poller 最多每 50 ms 读取一次 durable Run，再桥接到本地 signal；
- durable poll 和 settlement 检查在 worker 上运行，signal 检查不得读 Store；
- Run 结束必须取消并等待 poller，不能留下后台任务或未观察异常。

## TUI 流式消费与结构边界

- Host 的 Runtime/Agent tree 订阅建立是异步操作：Store 查询与历史事件投影在 worker 中完成，订阅队列、任务与
  Supervisor 内存状态始终由事件循环拥有。先登记有界 live 队列，再读取 durable replay，合并时按 sequence 去重；
  初始化期间溢出继续发布 lagged，失败或取消必须撤销订阅。不得在线程中运行持有 asyncio 队列的整个 Supervisor。
- Supervisor 的提交、交互恢复和 enqueue 前查询离开事件循环；最后一次 await 后必须重新检查关闭状态和 Session
  调度所有权，再一次性登记 job。Agent tree 的持久化查询同样在 worker 执行，订阅集合的变更留在 loop。
- 历史区宽度变化与主题变化共享同一个后台全量渲染 worker；完整 render request、宽度和 revision 校验通过后才
  原子替换 strip buffer。只改变高度的 Resize 不重绘历史，已有有效 buffer 在新结果完成前保持可见。

- spinner、计时器和其他定宽内容动画只触发 paint；只有几何尺寸实际变化时才触发布局；
- 同一工具批的新行使用一次批量 mount，终态使用一次批量 history append 和一次批量 remove；复杂 Markdown/批量
  immutable transcript 渲染在 worker 上完成；
- Runtime event buffer 每个 compositor frame 最多应用 64 条；积压前缀处理完后在下一原生帧继续，buffer 上限和
  lagged 后 durable reload 语义保持不变；
- `batch_update()` 只用于合并可合并的刷新，不能被当作消除 `AwaitMount`、`AwaitRemove` 或结构布局成本的替代品。

## 目标增量：真实终端响应性验收

本节定义真实终端中的诊断、响应预算和停止规则，不扩大前述现行语义。

### 范围与实施门禁

工具进入、完成、下一轮和 Run 终态是第三里程碑的唯一交互范围。用户键入与状态动画同时停顿表示 event loop 没有
得到运行机会；键入单独延迟还可能表示 App pump 被长 handler 或 await 链占有。

Store、文件锁或 SQLite I/O 不得在 event loop 上直接执行。除此之外，候选改动必须依次满足以下条件：

1. 在重复的真实复现场景中与超预算 Key、spinner 或 event-loop lag 同相位；
2. 当前支持配置和现实 payload 下稳定超预算，而不是只在合成极端规模下变慢；
3. 已排除移动一个调用边界、消除一次重复工作或复用现行 consumer 等更小修复；
4. 实际减少工作量，不新增未经必要性证明的事实源、缓存、后台服务或异步提交状态机。

未通过门禁的增长阶或重构设想不是当前目标契约。若动态证据要求扩大数据布局、Host DTO 或 renderer 边界，必须先更新
本规格和对应计划，再开始编码。

### 最小诊断与响应性预算

- 诊断只记录 event-loop lag、`RuntimeEventsReady` handler wall time、最长 loop 同步段、结构提交、controller await，
  以及同相位 worker operation 的阶段、时长和字节数。
- 诊断不得记录 prompt、reasoning、工具参数或结果内容；关闭时不得复制 payload、执行第二次序列化或保留常驻遥测
  pipeline。
- 受控基准目标为：1 ms ticker 的 event-loop lag p99 不超过 16 ms、最大值不超过 32 ms；Key 注入到 Composer 状态
  变化的 p95 不超过 50 ms；标称 120 ms 的状态动画不得连续错过两个周期。
- thread id 与 loop thread 不同只是所有权证据，不是响应性证据；总 wall time 也不能替代最长不可让出片段的归因。

### 工具边界 loop 同步段

- `shared_budget_reason` 不得在 event loop 直接执行同步 port；使用现有 `run_blocking()` 执行完整 query。
- 工具/Run 边界可达的 abort/boundary finalization、continuation/terminal settlement、delegation query 和 Session
  control mutation，一旦执行 Store、文件锁或 SQLite 访问，必须以完整 query/mutation 为单位在同一 worker settle。
- 迁移范围只由工具边界可达性决定，不以“全仓库同步调用数量归零”为目标；冷路径不因此自动异步化。
- caller cancellation、Session lock、SQLite transaction 和“durable 后发布 event”顺序保持现有语义。
- Session control 的同步 prepare/commit/rollback 持久化相位在 worker 中执行；插件 controller coroutine 仍在原 async
  边界执行，不把整个 Runtime 或插件执行迁入线程。

### 投影成本验证

- `project_runtime_event`、activity reduction/change detection、redaction 和 `freeze_json` 必须可被分项测量，不得只以整个
  Supervisor handler wall time 归因。
- 现实 payload 下单段稳定超过 8 ms，或与超预算样本持续同相位，才允许实施投影短路。优先消除重复 dump/compare，
  或在已知无匹配 Observer 时跳过 freeze。
- 活动 TUI Session 已有 event subscription；“无订阅者不构造 event view”不能作为当前 TUI 卡顿的默认修复。
- 改变 `RuntimeActivitySnapshot` 字段、裁剪 Host payload 或增加摘要 DTO 不属于默认范围，必须先完成 Host 兼容审查并
  更新本规格。

### TUI dispatch 验证

- live subscription 与 `RunResult.events` 复用同一个按 sequence 去重、每帧最多 64 条的 consumer；terminal result
  不得旁路上限，也不得重新应用已经消费的事件前缀。
- 一个 applied prefix 最多登记一次 Session controls refresh。Store 查询在线程中执行，但 App 的
  `RuntimeEventsReady` handler 不等待该查询；结果提交前验证当前 Session，过时结果不更新页面。
- 现有 batch mount、immutable history append 和 batch remove 顺序保持不变。单调时钟 deadline 只有在诊断证明
  多事件累计而非单个不可让出单元主导时才允许加入现有 64 条上限。
- pump 外 prepare/commit、render generation 协议和第二个 renderer 不属于默认目标；只有上述局部修复后 App pump
  仍然主导超预算样本，才允许先更新设计与规格再评审。

上述 dispatch 约束由同一 pending event buffer 实现：terminal result 按 projection/pending sequence high-water 去重，
然后复用每帧最多 64 条的 consumer。Session controls 使用 dirty flag 和单一 refresh task 合并请求；提交查询结果前
必须再次校验当前 Session，不能建立第二份 controls 状态。

### 证据触发范围与停止规则

- Context completion sidecar 只在完整 ContextSnapshot 序列化被现实 Session 证明为主导 GIL stall 后另行设计；
- Run/tool checkpoint 拆分只在现实工具结果的重复编码被证明主导后另行设计；
- reasoning 后台化只针对展开 reasoning 且确实超预算的路径，默认折叠路径不得增加额外工作；
- files catalog 的大规模写放大属于独立扩展性目标，不因当前 TUI 卡顿进入第三里程碑；
- 达到响应性预算后立即停止，其余候选改动继续保持未实现状态。

### 兼容与验收

- 不降低 Event、Message、Run 或 Context 耐久性，不改变 canonical event 顺序、Observer、Host subscription、跨进程
  abort、工具结果 source order、interrupted reconciliation 或 TUI assistant→tool 顺序。
- 不通过扩大 delta 窗口、降低动画频率、减少 checkpoint 或隐藏状态满足预算。
- 必须新增：诊断隐私/关闭开销测试、目标 Store port 线程所有权测试、投影分项门禁测试、`RunResult.events` budget/
  dedup 测试、controls refresh 合并/过时结果测试，以及工具进入/完成/终态的 loop-lag、Key 和 spinner 基准。
- 验收退出时，未通过门禁的数据布局、DTO 和 renderer 改造不得出现在实现中；任何通过门禁的范围扩展必须
  先更新本规格，并具备其新增恢复状态所需的崩溃和兼容测试。

### 相关验收证据

2026-09-05 的[会话与 TUI 审计](../../docs/OURO_会话与TUI性能审计_2026-09-05.md)补充了 Supervisor、Agent 生命周期、
手动/自动压缩、队列取消、异步订阅初始化与 Resize 的遗漏边界。活动比较直接复用已有字段，未增加 DTO 或缓存。
事件写入取消须持有 per-Session 顺序锁直到 worker 写入和 live publication 都结束；Spawn submission 的持久化
更新复用 delegation 生命周期锁，防止线程化后与快速结果结算竞争。无 schema 迁移。
HITL 请求的实时呈现可以先于原 Run 完成释放锁。Run ownership 必须提供进程内锁释放信号，使已持久化挂起的
审批/回答等待同一个本地 owner 交接；不轮询、不延迟呈现，也不等待未知的外部 owner。文件锁仍为最终排他边界，
取消 acquisition 时必须收回线程已获得但尚未交给调用方的锁。
